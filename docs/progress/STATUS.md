# 현재 상태

> **덮어쓰는 문서다.** 과거 기록을 쌓지 않는다. 이력은 git이 갖고 있다.
> 작업을 시작할 때 읽고, 마칠 때 갱신한다.

## 한 줄 요약

**Phase 4 진행 중.** 적 4종과 무기 3종에 이어 방 배치 생성 규칙(4-A)을 마쳤다. 다음은 4-B 방 잇기와 오가기.

## 지금 하는 일

**Phase 4 진행 중.** 순서는 아래와 같다.

```
[x] 1-A. 아이템 효과 시스템
[x] 1-B. 가방 그리드와 배치
[x] 1-C. 인접 시너지
[x] 1-D. 나머지 시너지 3종 (같은 행 · 같은 열 · 모서리)
[x] 1-E. 아이템 15종 채우기
[x] 2-A. 돌진 적 + FSM 재검토
[x] 2-B. 원거리 적
[x] 2-C. 분열 적
[x] 3.   무기 3종 (활 / 검 / 창)
[x] 4-A. 방 배치 생성 규칙   (순수 로직 + EditMode 테스트)
[ ] 4-B. 방 잇기와 오가기     (방 프리팹, 문, 카메라)
[ ] 4-C. 웨이브와 보상        (방 클리어, 아이템 획득, 가방 여는 시점)
[ ] 5.   보스
[ ] 6.   난이도 튜닝
```

1번을 맨 앞에 둔 것은 GDD 가 가방 배치를 이 게임의 차별화 지점으로 꼽았기
때문이다. 아이템이 없으면 평범한 탑다운 슈터다.
6번은 앞이 다 있어야 곡선을 볼 수 있으므로 반드시 마지막이다.

**아이템 20종이 데이터만으로 되는지 점검했고, 답은 15종까지였다.**
나머지 다섯은 고유 행동이 필요하다. 12종으로 줄이지 않고 다양성을
시너지에 맡기기로 했다. 근거는 [아이템 효과 설계](../decisions/item-effect-design.md)에 있다.

**인접 하나로는 부족했고, 넷으로도 아직 뻔하다.** 전수 조사로 확인했다.
좋은 배치는 전부 '검을 귀퉁이에 두고 나머지를 둘레에 붙인다' 는 한 모양이다.
조건끼리 부딪힌다는 예상은 아이템이 넷일 때 성립하지 않았다.
원인은 값이 아니라 **가방에 동시에 든 아이템의 수**다.
근거는 [시너지 판단](../decisions/synergy-needs-more-items.md)에 있다.

**그래서 1-E 를 새로 넣었고, 15종이면 빌드가 갈린다.** 기준을 값 표보다 먼저 정했다.
'목표를 바꿀 때 옮겨야 하는 아이템이 절반 이상인가' 로 셌고, 5·7·9개 모두 넘었다.
**하지만 선택은 한쪽으로 기운다.** 게임에 놓아 보니 연사 최선이 체력 2만 지고
나머지를 전부 이겼다. 수치 조정은 전투의 맥락이 생긴 뒤 난이도 튜닝에서 한다.
근거는 [15종 판단](../decisions/item-roster-judgment.md)에 있다.

**적 AI 를 공통 부모와 `switch` 로 정리했다.** 상태 패턴은 적 넷 규모에서 이르다고 판단했다.
골격을 그려 줄을 세어 고른 것이며 근거는 [FSM 구조](../decisions/enemy-fsm-structure.md)에 있다.
`MeleeEnemy` 는 120줄에서 38줄이 됐고, 거리 판정은 `Logic` 으로 빼서 테스트 7개가 붙었다.

**원거리 적은 편을 레이어로 가르고, 투사체 풀을 씬에 뒀다.** 적 투사체를 넣는 데 `Projectile` 과
`Health` 는 한 줄도 바뀌지 않았다. 같은 레이어로 플레이어와 적의 물리 충돌을 끊어, 돌진에 밀리는 것과
적을 밀고 다니는 것이 함께 사라졌다. 풀은 적이 가지면 적이 죽을 때 함께 버려져 씬에 올렸다.
후퇴는 상태가 아니라 `switch` 밖의 규칙으로 두어 상태 폭발을 피했다. 근거는
[편 가르기](../decisions/enemy-projectile-layers.md), [충돌](../decisions/player-enemy-collision-off.md),
[풀](../decisions/projectile-pool-in-scene.md), [후퇴](../decisions/retreat-is-not-a-state.md)에 있다.

**분열 적은 `MeleeEnemy` 에 갈라지는 부품 하나를 붙인 것이고, 상태 머신은 한 줄도 바뀌지 않았다.**
판 도중에 태어나는 적은 만든 쪽이 `SetTarget` 으로 대상을 넣고,
`EnemyBase.Spawned` 로 태어났다고 알린다. 카운터는 0 판정을 `LateUpdate` 로 미룬다. 죽는 순간 판정하면
카운터가 늘 첫째 구독자라 갈라진 적이 태어나기 전에 클리어가 뜬다. 적끼리의 겹침은 태어날 때 둘레에 퍼뜨리고
쫓아올 때만 부드럽게 비켜 가게 해 풀었고, 공격 중에 몸 절반쯤 겹치는 것은 알려진 한계로 뒀다.
근거는 [판 도중에 태어나는 적](../decisions/enemy-runtime-spawn.md)과 [겹침](../decisions/enemy-overlap-soft-separation.md)에 있다.

**무기는 활, 검, 창이고 '한 번 공격하기' 만 자식이 갖는다.** GDD 의 근접 / 원거리 / 광역을 바꿨다.
공통 부모 `Weapon` 이 `Attack` 하나를 약속하고 `PlayerAttack` 은 입력, 간격, 대시, 스탯을 맡는다. 무기의 공격력과 공격 속도는
스탯 기본값 0 위에 출처가 무기인 `Flat` 으로 얹혀, 무기를 바꾸면 퍼센트 아이템이 함께 강해진다. **창은 코드 0줄로 들어갔다**(스크립트 해시 49개 비교).
근접 판정은 공격 순간 겹침 쿼리 한 번이고 **플레이어 무기와 적의 근접 공격이 `AreaHit` 을 함께 쓴다.** 그러면서 `EnemyBase` 에서
대상에게 직접 피해를 주던 코드와 `Start` 가 빠졌다. 근거는 [무기 구조](../decisions/weapon-structure.md)와 [근접 판정](../decisions/melee-hit-query.md)에 있다.

**방 배치는 격자 위 한 줄 걷기이고, BFS 검증과 재생성을 넣지 않았다.** 가지형(아이작)을 먼저 설계했다가
방이 화면 두세 장이라 되짚어 걷는 비용이 크고 가지 끝에 둘 특수 방도 없어 접었다. 한 칸씩 이어 붙이는 배치는
만들 때부터 모두 이어져 있어 도달성 검증이 늘 통과하고, 방 8개는 일곱 걸음에서 끝나 자기 길에 갇히지도 않는다.
**모든 걷기를 전수 조사해 확인했다**(끝까지 걸은 경우 2,172 가지, 막힌 갈래 0). 걸은 순서가 곧 진행 순서라
거리 계산도 필요 없고, 문은 순번이 하나 차이인 두 방 사이에만 둬 기록이 좌표 목록 하나로 끝난다.
**BFS 는 방 안 장애물 배치로 옮겨 4-B 후보로 뒀다.** 거기서는 길이 실제로 막힐 수 있다.
EditMode 테스트는 28개가 늘어 111개다. 근거는 [한 줄 걷기](../decisions/room-layout-linear-walk.md)에 있다.

**`Logic/` 을 주제별 폴더로 나눴다.** 파일이 15개가 되어 `Stats`, `Bag`, `Rooms`, `Common` 으로 나누고
네임스페이스와 테스트 폴더도 따라 바꿨다. 직렬화된 데이터에는 네임스페이스가 저장되지 않아 에셋과 프리팹은 그대로였다.
근거는 [Logic 폴더](../decisions/logic-folders-by-topic.md)에 있다.

**적 셋은 명세를 따로 둔다.** 셋이 각자 다른 기술 문제를 끌고 온다.
돌진은 늘어나는 상태, 원거리는 적의 투사체와 편 가르기, 분열은 런타임 생성과
적 수 세기다. 한데 섞으면 문제가 생겼을 때 어디서 생겼는지 가르기 어렵다.

**15종을 추가하는 데 게임 로직 코드는 바뀌지 않았다.** `ItemData` 의 크기 제한과
디버그 가방 UI 만 바뀌었다. 아이템 모양은 긴 막대까지만 넓혔고, 직사각형이 아닌 모양은
기능 후보 풀에 올렸다.

**선택이 존재하는 데까지만 만든다.** 밸런싱을 정교하게 다듬지 않는다.
신입 포트폴리오에서 재미의 깊이는 평가 항목이 아니지만,
**기획서가 주장하는 것이 게임에 없으면 그것은 다른 문제다.**

## Phase 3 에서 한 일

**Phase 3 는 끝났다.** 세 항목을 순서대로 마쳤다.

```
[x] 1. 오브젝트 풀링 (+ 프로파일러 전후 측정)
[x] 2. ScriptableObject 데이터 분리
[x] 3. 스탯 · 모디파이어 시스템 (+ EditMode 테스트 22개)
```

원래 4번이던 '적 종류 확장하면서 FSM 재검토' 는 Phase 4 콘텐츠 확장과
같은 작업이라 그쪽으로 넘겼다. 미리 나누지 않고 적이 실제로 늘 때 판단한다.

2번이 3번의 바닥을 깔았다. 적과 투사체 수치가 데이터 에셋으로 나왔고,
컴포넌트는 `Awake` 에서 그 값을 자기 필드로 복사한다.
**그 필드가 곧 버프를 곱할 자리다.** 근거는 [데이터 소유](../decisions/data-ownership.md)에 있다.

2번에서 미뤄뒀던 플레이어 수치는 3번에서 `PlayerStats` 로 모였다.
ScriptableObject 로 빼지는 않았다. 하나뿐인 것을 데이터로 빼는 것은
확장성 증명이 되지 않기 때문이다.

**3번에서 `JM2D.Logic` 어셈블리를 처음 썼고 asmdef 4분할이 증명됐다.**
`Stat`, `StatModifier`, `ModifierType` 이 `System` 과 `System.Collections.Generic`
만 참조하므로 테스트 22개가 씬도 플레이도 없이 1초 안에 끝난다.
근거는 [스탯 설계](../decisions/stat-modifier-design.md)에 있다.

ROADMAP 의 "이벤트 기반 UI 갱신"과 "FSM 으로 정리"는 Phase 2에서 이미 됐다.
UI 는 전부 이벤트로 돌고, 적은 처음부터 상태 머신으로 만들었다.

**각 기능은 착수 전 `docs/specs/`에 명세를 만든다.**

### 정리해야 할 것

- **면접 문답 100문항 = 직접 쓴 답 20, 모범 답안 43, 빈 문항 37.**
  이 프로젝트의 목표가 '면접에서 방어 가능한 게임' 이므로 **가장 밀린 항목이다.**
  최근 일곱 기능(방 배치, 무기 3종, 분열 적, 원거리 적, 돌진 적, 아이템 15종, 시너지 4종)에는 Claude 가 쓴 모범 답안이 들어 있다.
  대화에만 있던 수치와 사연이 사라지기 전에 채운 것이다.
  **모범 답안은 준비된 답이 아니다.** 읽고 덮은 뒤 '내 말로' 칸을 채워야 그 문항이 준비된 것이다.
  빈 문항 37개는 결정 문서 열넷에 근거가 남아 있어 문서를 읽고 채울 수 있다.
- **제출 전에 `docs/interview/` 를 공개할지 정한다.** 지금은 백업 때문에 git 에 둔다.
  **답을 다 채웠으면** 힌트 문구만 정리하고 공개한다. 결정 문서와 짝을 이루어
  강점이 된다. **못 채웠으면** `.gitignore` 로 옮긴다. 비어 있는 문답은
  시작만 하고 만 것처럼 보인다.
  힌트에 '이렇게 답하면 무너진다' 같은 코칭 문구가 있어 그대로는 공개하기 어색하다.
- **가방 시너지 문답 Q1 의 마지막 문단이 틀린 말이 됐다.** '모서리가 인접과
  정면으로 부딪힌다' 는 아이템이 넷일 때 성립하지 않았다. 답변 내용이라 직접 고친다.
- **`BagGrid` 테스트는 대부분 5×5 정사각형에서 돈다.** `Width` 와 `Height` 를
  함께 쓰는 곳이 뒤바뀌어도 드러나지 않는다. 모서리에서 한 번 겪었고
  6×4 테스트로 막았지만 그 메서드 하나뿐이다. 시너지 문답 Q2 의 꼬리질문과 이어진다.
- 폰트 에셋의 `Clear Dynamic Data on Build` 가 꺼져 있다. Phase 6 빌드 전에 켠다.
- 성능 측정을 에디터에서 했다. `EditorLoop` 이 85%를 차지한다.
  Phase 6 빌드 때 개발 빌드로 다시 잰다.
- **총알이 풀 오브젝트 밑에 모이는 비용을 잰 적이 없다.** 하이어라키 규칙은 움직이는 것을 루트에 두는데,
  풀링은 Hierarchy 가 총알로 뒤덮이지 않게 부모를 지정해 규칙의 예외가 된다.
  **Phase 6 개발 빌드 측정 때 부모가 있을 때와 없을 때를 함께 잰다.**
  적의 추적 중 분리가 물리 스텝마다 주변 적을 찾는 비용도 같은 측정에서 본다.
- **적을 풀링하면 `Health.InitializeMaxHealth` 호출이 깨진다.** `EnemyBase.Awake`
  에서 부르고 있어 재사용될 때 다시 돌지 않는다. 투사체에서 `_damage` 를 `Launch` 로
  옮긴 것과 같은 문제다. **적을 대량으로 만드는 방과 웨이브 작업에서 함께 본다.**
  **같은 뿌리의 문제가 둘 더 있다.** `EnemyCounter` 는 적의 `health.OnDied` 를 해제하지 않는데(적이 파괴되면 목록째 치워진다),
  풀링하면 `Health` 가 살아남아 두 번 구독되고 한 적이 두 번 빠진다. 원거리 적을 런타임에 만들려면 투사체 풀을 넣어 주는 입구가 필요하다.
- **적끼리 공격 중에 몸 절반쯤 겹친다.** 분열 적의 작은 적 셋이 그렇다. 적이 많아지면 심해진다.
  **방과 웨이브 작업에서 공격 자리 나눠 주기(DOOM 2016 의 공격 토큰 같은 것)를 본다.** 동시에 공격하는 적 수를 조절하는
  난이도 기능과 이어진다. 근거는 [겹침](../decisions/enemy-overlap-soft-separation.md)에 있다.
- **무기를 얻는 방법이 없다.** 숫자 키 1, 2, 3 으로 바꾸는 확인용 입력뿐이고 `Keyboard.current` 로 바로 읽어 게임패드로는 못 바꾼다.
  방 보상으로 줄지 시작 전에 고를지 **절차적 방 배치에서 가방 여는 시점과 함께 정한다.** 메타 해금은 Phase 5 세이브다.
- **근접 판정은 공격하는 순간 한 번이다.** Phase 5 에서 공격 애니메이션이 붙으면 애니메이션 이벤트로 칼이 지나가는 프레임에 맞춘다.
  한 번에 맞히는 수가 16 으로 묶여 있어 웨이브에서 적이 몰리면 다시 본다.
- **방을 크게 만들면 카메라가 플레이어를 따라가야 한다.** 지금은 고정이다.
  맵 구조 결정의 파급효과이며 **4-B 에서 방 프리팹과 함께 본다.**
  4-B 에서 정할 것이 셋 더 있다. 방 프리팹 수와 크기, 판마다 시드를 어디서 얻을지,
  그리고 **넓은 방이 비어 보이면 방 안 장애물과 BFS 길 확인을 명세에 넣을지**다.
- **가방의 스탯 표시가 디버그용이다.** 배치를 바꿀 때마다 값이 보여야 판단할 수
  있어서 급히 붙였다. Phase 5 에서 정리하거나 제대로 만든다.
- **수치 스케일이 작아 퍼센트 증가가 묻힌다.** 공격력 1에 +10% 는 반올림해도 1이다.
  기본 수치를 키워야 풀리므로 **Phase 4 밸런싱에서 다룬다.**
  **같은 뿌리에서 가방의 선택이 한쪽으로 기운다.** 망치의 '같은 행 하나당 공격력 +1' 이
  한 배치에서 +6 을 내, 연사 최선이 체력 2만 지고 나머지를 전부 이긴다.
  [15종 판단](../decisions/item-roster-judgment.md)에 예가 있다. 난이도 튜닝에서 함께 본다.

## 열려 있는 질문

결론이 나면 여기서 지우고 `확정된 것` 또는 `docs/decisions/`로 옮긴다.

- **가방을 언제 열 수 있게 할 것인가**
  지금은 `Tab` 으로 언제든 연다. **임시 결정이다.**
  방 사이에만 열게 하면 배치가 더 무거운 선택이 되어 게임이 달라진다.
  전투 중에 못 바꾸는 것이 규칙이 되기 때문이다.
  **지금은 판단할 근거가 없다.** 방이 하나뿐이고 웨이브도 없어서 '방 사이'
  라는 개념 자체가 없다. **4-C 에서 방 클리어가 생길 때 정한다.**
- **한 판에 아이템을 몇 개 얻는가, 그리고 가방 크기**
  시너지 판단의 원인이 가방에 동시에 든 아이템의 수였으므로 둘은 짝으로 정한다.
  가방을 키우면 공간이 넉넉해져 판단과 반대 방향이 된다.
  **아이템 수는 정했다. 한 판은 방 8개를 한 줄로 지나고 시작 1 + 전투 6 + 보스 1 이라 6개다.**
  가방은 5×5 를 유지하고, 넉넉한지는 난이도 튜닝에서 본다. 근거는 [방 배치 생성 규칙](../specs/room-layout.md)에 있다.
- **URP 도입 여부**: Phase 5에서 2D 라이트가 필요하면 그때 판단.
  스프라이트 기반이라 나중 전환 비용이 낮아 지금 결정하지 않았다.
