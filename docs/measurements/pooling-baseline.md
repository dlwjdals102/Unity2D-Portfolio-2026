# 오브젝트 풀링: 적용 전 측정

풀링을 적용한 뒤 **같은 조건으로 다시 재서** 이 문서에 결과를 덧붙인다.

## 측정 조건

조건이 하나라도 다르면 비교가 성립하지 않는다.

| 항목 | 값 |
|---|---|
| 씬 | `PerfTest_Projectiles` |
| 스포너 | `ProjectileStressSpawner`, `Per Second` **600** |
| 투사체 수명 | **1초** |
| 측정 환경 | **에디터 플레이 모드** (개발 빌드 아님) |
| 선택 프레임 | 2382 / 3073 (안정 구간) |
| Deep Profile | 끔 |

## 결과

| 항목 | 값 |
|---|---|
| CPU 총 | 6.64ms |
| `EditorLoop` | 4.08ms (61.4%) |
| **`PlayerLoop`** | **2.29ms (34.5%)** |
| └ `FixedUpdate.Physics2DFixedUpdate` | 1.28ms |
| └ `Update.ScriptRunBehaviourUpdate` | 0.26ms |
| **GC Alloc (프레임당)** | **0.7 KB** |
| Object Count | 7.78k |

**에디터 부하가 포함된 수치다.** `EditorLoop` 4.08ms 는 게임과 무관하다.
절대값이 아니라 `PlayerLoop` 의 전후 비교로 판단한다.

## 여기까지 온 과정

**가설을 두 번 수정했다. 이 과정 자체가 결과보다 중요할 수 있다.**

### 1차 가설: GC Alloc 이 줄 것이다

측정하니 **176 B 로 고정**이었다. 초당 200개를 쏟아부어도 변하지 않았다.

`Instantiate` 가 만드는 GameObject 와 컴포넌트는 **C# 관리 힙이 아니라 엔진 내부(네이티브) 메모리**에 잡힌다.
`GC Alloc` 은 관리 힙만 세므로 여기 잡히지 않는다.

### 2차 가설: 프레임 스파이크가 줄 것이다

스파이크 프레임(22.04ms)을 열어 보니 **18.73ms 가 `EditorLoop`** 이었다.
게임 코드는 3.05ms 뿐이었다. **에디터가 튄 것이지 게임이 튄 것이 아니었다.**

동시에 게임 비용의 절반 이상이 `Physics2DFixedUpdate` 라는 것도 드러났다.
투사체가 전부 Rigidbody2D 와 콜라이더를 갖고 있기 때문이다.

### 문제: 이대로는 풀링 효과를 잴 수 없다

풀링이 없애는 것은 **생성과 파괴 비용**이다.
그런데 지배적인 것은 **물리 연산**이고, 풀링을 해도 **동시 활성 수는 그대로**라
물리 비용은 줄지 않는다. 전후를 재도 거의 같은 숫자가 나온다.

### 3차 설계: 변수를 분리한다

**동시 활성 수를 고정하고 생성·파괴 빈도만 늘렸다.**

| | 이전 | 이후 |
|---|---|---|
| 설정 | 200개/초 × 수명 3초 | 600개/초 × 수명 1초 |
| 동시 활성 | 600 | **600 (같음)** |
| 초당 생성·파괴 | 200 | **600 (3배)** |

`Object Count` 가 7.65k 에서 7.78k 로 거의 같아 **동시 활성 수 고정을 확인**했다.
`EditorLoop` 도 4.18ms 에서 4.08ms 로 같아 **에디터 부하가 변수가 아님**을 확인했다.

### 그 결과 생성·파괴 비용이 드러났다

| 항목 | 200/초 | 600/초 | 변화 |
|---|---|---|---|
| `PlayerLoop` | 1.70ms | 2.29ms | +35% |
| `Physics2DFixedUpdate` | 0.98ms | 1.28ms | +31% |
| `ScriptRunBehaviourUpdate` | 0.12ms | 0.26ms | **+117%** |
| GC Alloc | 176 B | 0.7 KB | **약 4배** |

`ScriptRunBehaviourUpdate` 는 스포너의 `Update` 가 도는 곳이다. `Instantiate` 호출이 3배가 된 결과다.

`Physics2DFixedUpdate` 가 오른 것은 **물리 엔진에 바디를 등록하고 해제하는 비용** 때문이다.
동시 활성 수가 같아도 등록·해제 횟수는 3배가 된다. 이 역시 풀링이 줄일 수 있는 부분이다.

## 예상

`PlayerLoop` 2.29ms 중 **0.3~0.5ms 개선**을 예상한다. 극적이지 않다.

물리 연산이 여전히 지배적이고 그 부분은 풀링과 무관하기 때문이다.
Phase 4에서 적이 웨이브로 쏟아지면 생성·파괴 대상이 늘어 효과가 커질 것이다.

**예상을 미리 적어 둔다.** 결과가 예상과 다르면 그 차이가 다시 배울 거리가 된다.

## 한계

- **에디터에서 측정했다.** `EditorLoop` 부하가 섞여 절대값을 신뢰할 수 없다.
  개발 빌드로 재면 더 정확하지만, 전후 비교에는 지장이 없어 미뤘다.
- 투사체 하나만 측정했다. 적과 이펙트까지 풀링 대상이 되면 결과가 달라진다.
- 프레임 하나를 골라 읽었다. 여러 프레임의 평균을 내면 더 정확하다.
