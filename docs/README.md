# 문서 지도

문서는 **변경 빈도**로 나눈다. 자주 바뀌는 것과 안 바뀌는 것을 섞지 않는다.

| 계층 | 위치 | 변경 빈도 | 성격 |
|---|---|---|---|
| 규칙 | `CLAUDE.md` · `.claude/rules/` | 거의 없음 | 작업 방식. 어디에 둘지는 CLAUDE.md 첫 표를 본다 |
| 기획 | `docs/design/` | 마일스톤마다 | 무엇을 만드는가 |
| 명세 | `docs/specs/` | **수시** | 기능이 어떻게 동작하는가 |
| 진행 | `docs/progress/` | **매 작업** | 지금 어디까지 왔는가 |
| 결정 | `docs/decisions/` | 추가만 | 왜 그렇게 만들었는가 |
| 문답 | `docs/interview/` | 기능마다 | 면접에서 어떻게 설명할 것인가 |
| 측정 | `docs/measurements/` | 최적화마다 | 무엇이 얼마나 좋아졌는가 |

---

## 변경에 강하게 만드는 5가지 규칙

### 1. 손으로 관리하는 목차를 만들지 않는다

**폴더의 파일 목록이 곧 인덱스다.**
목차 파일을 두면 기능 하나 추가할 때 명세와 목차 두 곳을 고쳐야 하고,
그 둘은 반드시 어긋난다. 이 문서에도 기능 목록을 적지 않는다.

### 2. 기능 1개 = 파일 1개

`docs/specs/` 안에서 기능은 항상 독립 파일이다.

- 추가 → 파일 생성. **다른 파일을 건드리지 않는다.**
- 변경 → 그 파일만 수정.
- 폐기 → **삭제하지 않고** `status: dropped`로 바꾼다. 왜 접었는지가 남는다.

### 3. 파일명에 번호를 붙이지 않는다

`F01-`, `F02-` 같은 접두사는 삭제와 재정렬에 약하다.
`object-pooling.md`처럼 **내용으로 이름 짓는다.** 순서가 필요하면 frontmatter를 쓴다.

### 4. 링크는 한 방향으로만

상위 문서가 하위를 가리키는 것만 허용한다. 양방향 링크는 한쪽을 지우는 순간 깨진다.
명세끼리 서로 참조하지 않는다. 관계는 frontmatter의 `related`에만 적는다.

### 5. 상태는 frontmatter에, 이력은 git에

문서 안에 "2026-08-28 수정함" 같은 변경 이력을 쓰지 않는다. git이 이미 갖고 있다.
문서에는 **지금의 사실**만 적는다.

## 각 폴더 사용법

### `docs/design/` — 기획
- [GDD.md](design/GDD.md): 코어 루프와 스코프. **A4 1장 유지.**
- [feature-pool.md](design/feature-pool.md): 기능 **후보** 풀. 아직 만들기로 정한 게 아니다.

### `docs/specs/` — 기능 명세
**실제로 만들기로 확정한 기능만** 파일을 만든다. 후보 단계면 `feature-pool.md`에 둔다.
착수 직전에 `_TEMPLATE.md`를 복사해서 시작한다.

### `docs/progress/` — 진행 상황
- [STATUS.md](progress/STATUS.md): **지금 상태.** 덮어쓰는 문서. 과거를 남기지 않는다.
- [ROADMAP.md](progress/ROADMAP.md): 14주 계획. 큰 단위 체크리스트.

**명세를 `done`으로 닫을 때 ROADMAP 의 해당 항목도 함께 본다.**
STATUS 만 갱신하고 ROADMAP 을 잊으면 다 해놓고 안 한 것처럼 남는다.
실제로 Phase 2 가 전부 끝난 뒤에도 체크가 비어 있었다.

**절반만 된 항목을 통째로 체크하지 않는다.** 범위를 괄호로 적는다.
'투사체·이펙트 풀링' 에서 이펙트가 아직 없다면 그렇게 쓴다.
통째로 체크하면 나중에 안 한 것을 했다고 믿게 된다.

### `docs/interview/` — 면접 문답

**답변은 사용자가 직접 쓴다.** Claude가 써준 답을 외우면 꼬리질문에서 무너진다.
Claude는 답을 검토하고 보완만 한다.

설계 판단에 대한 질문은 여기 답을 쓰지 않는다. `docs/decisions/` 에 이미 있으므로
링크만 건다. 같은 내용을 두 곳에 두지 않는다.

파일은 출처를 따라간다. 명세에서 나온 질문은 그 명세와 같은 이름으로,
결정에서 나온 질문은 주제 이름으로 만든다.

**기능 하나를 닫을 때 그 문답도 함께 채운다.** 몰아서 쓰려고 미루면 안 하게 된다.
질문이 45개까지 쌓이고 답이 7개인 상태를 한 번 만들어 봤다.
**만든 직후가 가장 잘 쓸 수 있는 때다.** 왜 그렇게 했는지가 아직 머릿속에 있다.

### `docs/decisions/` — 설계 결정
**추가 전용.** 한번 쓴 결정 파일의 **판단과 근거는 고쳐 쓰지 않는다.**

단, **오타, 깨진 링크, 잘못된 인용을 바로잡는 것은 허용한다.**
그러지 않으면 문서가 틀린 채로 남아 거짓말을 하게 된다.
이 규칙이 막으려는 것은 판단을 나중에 유리하게 고쳐 쓰는 일이다.
판단이 바뀌었으면 새 파일을 쓰고 옛 파일에 `superseded_by`를 적는다.
**틀린 결정도 지우지 않는다.** "왜 바꿨는지"가 면접에서 가장 좋은 이야깃거리다.
