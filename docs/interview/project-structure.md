## Q2. 어셈블리를 나누면 무엇이 달라지나요? `Assembly-CSharp` 하나로 두면 안 되나요?

**내 답변**

asmdef 가 없으면 모든 스크립트가 Assembly-CSharp 하나로 묶입니다.
파일 하나만 고쳐도 전부 다시 컴파일됩니다.
다만 이 프로젝트는 스크립트가 스무 개 남짓이라 그게 주된 이유는 아닙니다.

진짜 이유는 경계입니다. 어셈블리가 하나면 아무 코드나 아무 코드를 참조할 수
있습니다. Logic 이 MonoBehaviour 를 끌어다 써도 컴파일이 됩니다.
규칙을 문서에 적어둬도 어기는 순간 아무 일도 안 일어납니다.

나누면 컴파일러가 막습니다. 참조 목록에 없으면 컴파일 에러입니다.
테스트 어셈블리에서는 Runtime 을 일부러 뺐습니다. 참조를 열어두면
MonoBehaviour 를 테스트하려 들게 되고, 그러면 씬을 띄워야 해서 느려집니다.

실제로 스탯 테스트 24개가 씬도 플레이도 없이 1초 안에 끝납니다.
Stat 이 System 만 참조하기 때문인데, 그게 유지된 건 참조를 열 수 없게
막아뒀기 때문입니다.

대가도 있었습니다. internal 이 어셈블리 경계를 못 넘어서,
테스트할 타입을 public 으로 바꿔야 했습니다.

**보완**

**첫 문단(Assembly-CSharp 로 묶여 전체 재컴파일)은 직접 썼다.**
'로드' 를 '다시 컴파일' 로 고쳤다.

나머지는 설명을 듣고 정리한 것이다. **경계 이야기가 이 답변의 핵심이고,
컴파일 시간은 오히려 약한 근거다.** 이 프로젝트 규모에서는 체감이 없어서
그것만 말하면 '그게 체감되나요' 에 막힌다.

**핵심 비유: 팻말과 잠금.** 규칙을 문서에 적는 것과 컴파일러가 막는 것은 다르다.

꼬리질문 대비:
- "컴파일 시간이 체감되나요" → 이 규모에서는 아니다. 그래서 그걸 이유로 대지 않는다
- "Logic 이 UnityEngine 은 쓸 수 있지 않나요" → 맞다. 막힌 건 Runtime 참조다.
  UnityEngine 을 안 쓰는 것은 규칙이지 컴파일러가 막는 게 아니다
- "internal 문제는 어떻게 해결했나요" → 테스트 대상을 public 으로 열었다.
  결정 문서에 파급효과로 적어뒀다
