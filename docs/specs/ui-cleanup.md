# UI 정리

## 왜 필요한가

**포트폴리오에 필요해서다.** Phase 6 에서 영상을 찍는데 화면에 **디버그로 붙인 것이 남아 있다.**
가방의 글 한 덩어리가 '급히 붙였다' 고 주석에 적혀 있고, 휠을 굴리면 아이템이 손에 들어온다.

**체력 바 둘이 서로 다른 방식으로 줄어든다.** 플레이어는 스프라이트와 `fillAmount`,
보스는 스프라이트 없이 앵커다. 보스 바는 조각 셋을 코드가 만들어 **씬에서 모양을 볼 수 없다.**
`boss.md` 계단 6이 '두 바가 다른 방식인 것은 폴리싱에서 맞춘다' 고 적어 두었다.

**4-D 가 남긴 구멍 하나를 여기서 닫는다.** 손에 아이템을 든 채 다음 보상을 고르면 든 것이 사라진다.
`room-rewards.md` 는 '놓지 않아도 잃지 않는다' 고 적었는데 `ItemInventory.PutInHand` 는
'이미 들고 있으면 덮어쓴다' 고 적혀 있다. **명세가 '다음 보상을 받는 순간' 을 다루지 않았다.**

## 동작 정의

- 가방을 열면 **손에 든 것과 스탯 넷이 보인다.** 지금과 같은 자리, 같은 글이다.
  달라지는 것은 그것이 **정식 표시라는 점**이다. 디버그라는 말이 코드에서 사라진다.
- **휠을 굴려도 아무 일도 일어나지 않는다.** 아이템이 손에 들어오는 길은 방 보상 하나다.
- 가방에 아이템을 놓거나 빼도 **콘솔에 아무것도 찍히지 않는다.**
- 보스 바와 플레이어 바가 **같은 방식으로 줄어든다.** 둘 다 스프라이트의 `fillAmount` 다.
- 보스 바가 **씬에 보인다.** 플레이하지 않고도 자리와 크기를 인스펙터에서 고칠 수 있다.
- 보스 바의 **2페이즈 경계선은 여전히 보스 데이터를 따른다.** `PhaseChangeAt` 을 바꾸면 선도 움직인다.
- 판이 시작될 때 보스 바는 **숨어 있고**, 보스가 태어날 때 켜지고 죽을 때 꺼진다. 지금과 같다.
- **손에 아이템을 든 채 방을 깨면 보상 창이 그 사실을 알린다.** 제목 아래에 든 것의 이름과
  사라진다는 말이 한 줄 붙는다. 손이 비어 있으면 그 줄이 없다.
- 보상을 고르면 **든 것은 사라지고 새 것이 손에 들어온다.** 지금 동작과 같고, 그것이 규칙이 된다.
- **Esc 로 보상을 넘길 수 있다.** 넘기면 손에 든 것이 그대로 남는다.
  넘어가기 자체의 규칙은 [보상과 가방](room-rewards.md)에 적었다. 이 기능은 안내 문구만 맡는다.
- **가방을 열면 격자가 화면 가운데에 있다.** 칸 수나 칸 크기를 바꿔도 가운데가 유지된다.
- 스탯 글은 **격자의 오른쪽 위에 붙어 보인다.**
- **가방이나 보상 창이 열려 있는 동안 클릭해도 공격이 나가지 않는다.**
  칸을 누른 클릭과 카드를 누른 클릭이 무기를 휘두르지 않는다. 창이 닫히면 다시 나간다.

## 경계 — 이 기능이 하지 않는 것

- **새 레이아웃을 만들지 않는다.** ROADMAP 이 그렇게 적었다. 자리를 옮기거나 패널을 새로 짜지 않는다.
- **UI 스프라이트를 입히지 않는다.** 보스 바에 필요한 흰 네모 하나만 쓴다.
  CC0 UI 에셋 적용은 별개 작업이고 지금 범위가 아니다.
- **보상 창이 씬 오브젝트의 앵커를 코드로 정하는 것은 손대지 않는다.** 아래 '남기는 흠' 에 적었다.
- **'손이 차 있으면 가방을 먼저 열게 하는' 안을 쓰지 않는다.** 보상을 미뤘다는 상태를 들고 있어야 해서
  이 작업보다 비싸다. 고른 안은 '알리고 덮어쓰기' 다.
- **보상 창의 에디터 메뉴는 지우지 않는다.** 방을 깨지 않고 창을 띄워 보는 수단이고,
  `#if UNITY_EDITOR` 로 감싸 빌드에서 사라지게만 한다.
- **해상도가 바뀔 때 UI 가 틀어지는지 보지 않는다.** Phase 6 의 실행 빌드 항목에 묶여 있다.
- **체력 바에 애니메이션을 넣지 않는다.** 줄어드는 것이 한 프레임에 끝나도 그대로 둔다.
- **아이템 아이콘 15종을 만들지 않는다.** 지금처럼 색이 다른 네모다.

## 설계

### 자리를 누가 정하는가

이 작업의 기준이다. 축이 둘이다.

```
오브젝트를 코드가 만들었다        -> 자리도 코드가 정한다
자리가 계산에서 나온다            -> 씬에 있어도 그 값만 코드가 쓴다
둘 다 아니다 (보기값, 개수 고정)  -> 씬과 인스펙터가 정한다
```

둘째 줄은 `unity-csharp.md` 에 이미 있었고(앵커와 피벗을 사람이 건드리면 오류 없이 위치만 틀린다),
**첫째 줄을 이번에 규칙으로 더했다.** 마지막 문장이 보스 바에서 겪은 것이다.
**계산값 하나 때문에 오브젝트 전체를 코드로 만들지 않는다.**

지금 코드가 자리를 정하는 곳은 일곱이고, 그중 여섯은 첫째나 둘째 조건에 맞는다.

| 어디 | 왜 코드인가 | 판정 |
|---|---|---|
| `BagView` 칸과 아이템 | 개수가 런타임에 정해지고 자리가 칸 좌표 계산이다 | 맞다 |
| `BagView` 이름 라벨 | 코드가 만든 것이다 | 맞다 |
| `RewardPanel` 카드 | 후보 수가 데이터에서 온다 | 맞다 |
| `BossHealthBar` 채움 | 체력 비율이다 | 맞다 |
| `BossHealthBar` 경계선 | 보스의 `PhaseChangeAt` 에서 온다 | 맞다 |
| `SpawnScale`, `RangeView` | 자라는 비율, 공격 범위 크기다 | 맞다 |
| **`BossHealthBar` 조각 셋과 바 자신의 자리** | **조각 수가 늘 셋이고 자리는 보기값이다** | **어긋났다** |

### 보스 바를 씬으로 옮긴다

```
지금                                  옮긴 뒤
조각 셋을 코드가 만든다               씬에 셋이 있다. 플레이어 바와 같은 모양이다
바 자리를 _size, _topOffset 으로      RectTransform 이 정한다
채움을 anchorMax.x 로                 Image.fillAmount 로
색 넷이 인스펙터 값                   기본 색은 Image, 2페이즈 색만 인스펙터 값
경계선 자리를 코드가 계산              그대로 코드가 계산한다
```

**마지막 줄을 옮기지 않는 것이 이 설계의 핵이다.** 경계선은 보스 데이터에서 나오는 값이라
씬에 두면 보스의 페이즈 기준을 바꿀 때 조용히 어긋난다. 옮기는 것은 보기값이고 남기는 것은 계산값이다.

채움을 `fillAmount` 로 바꿀 수 있는 이유는 **스프라이트가 생기기 때문**이다.
앵커로 줄인 것은 스프라이트 없이 돌게 하려던 것이었다. 흰 네모 하나를 쓰면 그 제약이 사라지고
플레이어 바와 방식이 같아진다.

**함정 하나.** 지금 `Awake` 가 조각을 만든 뒤 `SetActive(false)` 로 숨긴다.
씬에서 처음부터 꺼 두면 **`Awake` 가 돌지 않아** 참조가 비는 것처럼 보이는 길이 생긴다.
오브젝트는 씬에서 켜 둔 채로 두고 `Awake` 가 끄는 지금 흐름을 유지한다.
그래야 에디터에서 모양이 보이는데, 그게 이 변경의 목적이다.

### 디버그 표시는 셋을 가른다

| 무엇 | 어떻게 | 왜 |
|---|---|---|
| `StatText` | **남긴다.** 정식 표시로 올린다 | 지금 스탯을 보는 것은 로그라이트에서 플레이어가 필요한 정보다. 가방을 열었을 때만 보여 전투 화면을 어지럽히지 않는다 |
| 휠 팔레트 | **지운다** | 아이템을 손에 넣는 정식 경로(방 보상)가 생겼다. 플레이 중 휠 입력을 먹고 있다 |
| `Debug.Log` 셋 | **지운다** | 릴리스 경로에 로그를 남기지 않는다 |

`StatText` 를 정식 표시로 올리면 `_stats` 가 필수 참조가 되므로 **`_stats == null` 가드 셋이 사라진다.**
디버그 전제(스탯을 꽂지 않아도 돌게)가 없어지기 때문이다.

`Data/*.cs` 의 `Debug.LogWarning` 일곱은 `OnValidate` 경고라 **남긴다.** 성격이 반대다.

### 손에 든 것은 알리고 덮어쓴다

창은 지금 `Show(후보)` 와 `OnPicked(고른 것)` 만 안다. 그 모양을 지킨다.
**`RewardGiver` 가 손에 든 것을 함께 넘기고, 창은 받은 것을 글로 적기만 한다.**
창이 `ItemInventory` 를 참조하게 하는 안을 버렸다. 창이 가방을 알게 되면 둘이 묶인다.

버린 안이 둘 더 있다. '보상 창에 사라진다고만 적기' 는 언제 사라지는지 알려 주지 않고,
'손이 차 있으면 가방을 먼저 열기' 는 **보상을 미뤘다는 상태**를 들고 있어야 한다.
방을 깬 직후에 가방을 열고, 닫힐 때 보상 창을 띄우고, 그 사이에 다음 방에 들어가면 어떻게 되는지까지
정해야 한다. UI 정리보다 큰 작업이다.

### 창이 열린 동안 공격 입력을 막는다

클릭으로 칸을 누르는데 같은 클릭이 무기를 휘둘렀다. 보상 창의 카드도 같았다.

**막는 자리를 `PlayerInputReader` 에 두었다.** `FireHeld` 를 읽는 곳이 공격만이 아니기 때문이다.
`PlayerAttack` 이 몸이 바라보는 쪽을 정할 때도 그 값을 본다. 입력에서 막으면 읽는 곳이 전부 조용해진다.

**거는 쪽은 창 자신이다.** 처음에는 창을 띄우는 `RewardGiver` 가 걸었는데,
**확인용 메뉴로 띄운 창은 그 경로를 지나지 않아 막히지 않았다.** 창이 스스로 걸고 풀게 하자
가방과 같은 모양이 되고, '풀고 나서 가방을 연다' 는 호출 순서를 맞추던 자리도 사라졌다.

버린 안이 둘이다. `EventSystem.IsPointerOverGameObject()` 는 `BagPanel` 에 Image 가 없어
**격자 밖 빈 자리를 막지 못하고**, raycastTarget 설정에 동작이 걸린다.
Input System 의 액션 맵 전환은 현업 표준이지만 **지금 막을 입력이 공격 하나**이고,
가방의 Tab 과 보상 창의 숫자 키가 이미 `Keyboard.current` 를 바로 읽어 맵 바깥에 있다. 절반만 덮는다.

**참거짓 하나를 두 창이 나눠 쓴다.** 둘이 동시에 열리지 않아 성립한다.
세 번째가 생기면 몇 겹인지 세야 한다. 지금 세지 않고 주석에 적어 두었다.

### 격자를 화면 가운데에 맞춘다

격자가 오른쪽 아래로 치우쳐 있었다. **씬에는 `CellRoot` 가 가운데로 맞춰져 있는데
코드가 앵커와 피벗을 왼쪽 위로 덮어쓰고 있었다.** 그래서 격자의 왼쪽 위 모서리가
`BagPanel`(100 곱하기 100)의 왼쪽 위에 놓이고, 거기서 320 곱하기 320 이 오른쪽 아래로 펼쳐졌다.
중심이 화면 가운데에서 110, 110 만큼 밀려 있었다.

**피벗은 옮길 수 없다.** 칸 좌표를 만드는 계산과 마우스로 칸을 찾는 계산이 둘 다
'피벗이 왼쪽 위' 를 전제한다. 그래서 **앵커를 부모의 가운데로 두고 격자 절반만큼 되밀었다.**
되미는 값이 격자 크기에서 나오는 계산값이라 코드가 정한다.

`Awake` 에서 코드로 정한다. 새 규칙으로 보면 씬이 정해야 하는 쪽이다.
**지금 고치지 않는다.** 보기에 문제가 없고, 옮기는 일이 순수 손작업이며
**그 자리에서 같은 버그를 두 번 겪었다**(카드와 글자, 그리고 패널 자신이 100 × 100 이던 것).
위험이 이득보다 크다. `_title` 의 `400f`, `60f` 와 `Margin = 12f` 도 함께 남는다.

**체력 바를 플레이어 쪽에 맞춘 이유.** 반대 방향(플레이어를 앵커 방식으로)도 가능했다.
그쪽을 버린 것은 **에디터에서 모양을 볼 수 있는 쪽이 플레이어 방식**이기 때문이다.
코드가 UI 를 만들면 자리를 고칠 때마다 플레이해야 한다.

**스탯 글을 격자에 묶으려다 되돌렸다.** 격자 크기가 코드에서 나오니 글도 따라가게 하려고
`CellRoot` 의 자식으로 옮기고 오른쪽 변에 앵커를 붙였는데, **`CellRoot` 에 `RectMask2D` 가 있어
격자 밖으로 나간 글이 잘려 보이지 않았다.** 부모를 옮기기 전에 거기 무엇이 붙어 있는지 보지 않았다.

**더 근본적으로는 일어나지 않기로 한 변경에 대비한 것이다.** 가방 5 곱하기 5 는 확정값이고
근거 문서까지 있다. 지금은 `BagPanel` 의 자식으로 되돌리고 **숫자로 두었다**(`Pos (180, 160)`).
180 과 160 은 격자 절반(160)에서 나온 값이라, 가방 크기를 바꾸는 날 함께 본다.
**규칙은 '계산값은 코드가 정한다' 이지 '혹시 바뀔 수 있으니 전부 따라가게 만들라' 가 아니다.**

**`CellRoot` 는 씬에서 보이는 모양과 플레이 중 모양이 다르다.** 씬에는 100 곱하기 100 이고
플레이 중에는 320 곱하기 320 이다. 코드가 `Awake` 에서 덮기 때문이다.
보스 바에서 지적한 '씬에서 모양이 안 보인다' 와 같은 성질의 값이고, 격자는 칸 수가
데이터에서 오므로 코드가 쥐는 쪽을 유지했다. 미리보기만 맞추고 싶으면 씬에 같은 값을 적어 두면 된다.

**확인용 메뉴로 띄운 창에서 카드를 고르면 아이템이 실제로 손에 들어오고 가방이 열린다.**
`OnPicked` 가 그대로 도는 경로다. 확인만 하려면 Esc 로 닫는다.

**플레이어 체력 바의 `Raycast Target` 도 껐다.** 보스 바를 씬으로 옮기며 코드가 하던 일
(`image.raycastTarget = false`)이 사라진 것을 보고 함께 맞춘 것이다. 증상은 없었다.
화면 왼쪽 위 300 곱하기 30 자리의 클릭을 먹고 있었다.
