# 영상 전 점검

## 왜 필요한가

**포트폴리오 때문이다.** 면접관이 보는 첫 관문은 플레이 영상이고, 코드 규칙은 영상에 보이지 않는다.
빌드와 영상에 들어가기 전에 **플레이어가 보는 것만** 한 번 보기로 했다.

## 범위를 어떻게 정했나

한 판을 처음부터 끝까지 돌며 적은 것 여섯과, 문서에 '나중에' 로 미뤄 둔 것 스물셋을 합쳐 가렸다.
가른 기준은 둘이다. **영상에 보이는가, 빌드에 없으면 안 되는가.**

| 가름 | 항목 |
|---|---|
| 넣는다 | 보스 방 카메라(버그), Esc 메뉴와 조작 안내, 진행 표시와 판 결과, 씬 전환, 패널 구조 통일 |
| 설계를 되돌려야 해서 못 한다 | 특수 방, 재화와 상점, 둘째 던전, 적 변종, 2D 라이트 |
| 포트폴리오라서 없어도 된다 | 미니맵, 아이템 HUD, 조준 표시, 대시 쿨다운, 넉백, 적 공격 예고, 게임패드, 업적, 로딩 화면 |
| 쌓아 둔다 | 피해 숫자, 적 사망 연출, 피격 소리 구분, 아이템 아이콘, 문 스프라이트, 볼륨 조절 |

**전부 고치려 들면 Phase 6 이 다시 Phase 5 가 된다.** 넷으로 끊은 것이 이 명세의 범위다.

## 동작 정의

### A. 보스 방 카메라가 방 밖을 비추지 않는다

- 보스 전투가 시작돼 시야가 넓어져도 **옆방이 보이지 않는다**
- 화면 비율이 넓어도 그렇다
- 보스가 방 어디에 있어도 화면에 들어온다
- 보스를 잡으면 평소 시야로 돌아온다

### B. Esc 메뉴와 조작 안내

- 던전과 마을에서 Esc 를 누르면 창이 뜨고 시간이 멈춘다
- 계속하기, 타이틀로 가기, 게임 종료를 고를 수 있다
- 그 창에 조작이 적혀 있다
- 마을에 처음 들어서면 무엇을 하면 되는지 한 줄이 보인다

### C. 진행 표시와 판 결과

- 던전에서 **지금 몇 번째 방인지** 화면에 보인다
- 판이 끝나면 기록과 **이번 판으로 열린 것**이 글로 보인다
- 마을에서 기록(보스 처치 횟수, 도달한 방)을 볼 수 있다

### D. 씬이 바뀔 때 어두워지고 밝아진다

- 타이틀, 마을, 던전 사이를 넘을 때 툭 끊기지 않는다

### E. 창 넷의 구조가 한 모양이다

**영상에 보이지 않는 항목이다.** 일관성 때문에 넣었고 그렇다고 적는다.

- 창을 다루는 컴포넌트는 모두 `Canvas` 에 붙는다
- 켜고 끄는 패널은 그 자식이고, 씬에서 꺼진 채로 저장된다
- 패널 오브젝트 이름은 `~Window` 로 끝나 클래스 이름과 겹치지 않는다

## 경계 — 이 기능이 하지 않는다

- **미니맵을 만들지 않는다.** 방이 한 줄이라 지도가 직선이고, 진행 표시가 같은 정보를 더 싸게 준다
- **퀘스트를 만들지 않는다.** GDD 5번이 스토리와 대사를 뺐다. 판이 끝난 뒤의 '다음' 은 해금이 맡는다
- **해상도와 볼륨 옵션 창을 만들지 않는다.** 메뉴는 계속하기, 타이틀, 종료 셋이다
- **키 리바인딩과 게임패드를 넣지 않는다**
- 위 표의 '쌓아 둔다' 는 손대지 않는다. STATUS 의 미해결 목록으로 간다

## 메모

**A 의 원인은 주석이 거꾸로 읽은 것이다.** `Room.BeginCombat` 이 보스 시야를 `Size.y / 2f` 로
정하는데, 세로를 방 높이에 맞추면 가로는 화면 비율만큼 늘어난다. 주석은 '16 대 9 는 1.78 이라
가로가 남는다' 고 적어 두었고, 그 남는 것이 곧 방 밖이다. 방은 `RoomSpace.ToWorld` 가
`cell.X * roomWidth` 로 놓아 딱 붙어 있어 넘친 자리가 옆방이다. `Confiner2D` 는 카메라 뷰가
경계보다 크면 가둘 수 없어 가운데에 둔다. **새는 조건은 '화면 비율 > 방 비율 1.667' 하나다.**

**평소 시야(5)는 비율 2.0 까지 버틴다.** 울트라와이드 빌드에서는 평소에도 샌다.
빌드 확인 항목에 올렸다. 또 비율이 2.2 를 넘으면 **보스 때 시야가 평소보다 좁아진다**(가로에 맞춘
값이 5 보다 작아져서다). 연출이 거꾸로 되는 것이고, 평소 시야까지 같은 계산으로 깎으면 풀리지만
그건 범위를 넓히는 일이라 하지 않았다. 16 대 9 를 기준 비율로 둔다.

**`Lens.Aspect` 를 쓸 수 있는지는 패키지 소스에서 확인했다.** `CinemachineCamera` 가
`PullStateFromVirtualCamera(worldUp, ref Lens)` 로 `Lens` 를 넘기고 그 안에서
`m_AspectFromCamera = camera.aspect` 가 채워진다. **켜진 카메라라면 실제 출력 비율이 들어 있다.**
보스 방 카메라는 플레이어가 그 방에 있어 켜진 상태다.

**'클리어 뒤에 뭘 할지 모르겠다' 를 퀘스트 부재로 보지 않았다.** 보스를 잡으면 `RunRecorder` 가
기록을 올려 무기가 열리는데, 열렸다는 것을 아무도 알려주지 않는다. 퀘스트 시스템 없이
저장된 값 넷을 읽어 글로 보이는 것으로 고리가 닫힌다. 그것이 C 다.

### A 를 하며 알게 된 것

**시야 하나를 고치는 일이 아니었다.** 겹쳐 있던 세 가지를 차례로 걷어야 했고,
셋 다 Cinemachine 이 어떻게 동작하는지 소스를 읽어야 보였다.

```
1. 시야가 방보다 넓었다          세로에 맞추면 가로가 화면 비율만큼 넘친다
2. Confiner 가 옛 크기로 가뒀다   크기를 바꿔도 구워 둔 폴리곤을 다시 계산하지 않는다
3. 가두는 자리의 넓이가 0 이 됐다  방에 딱 맞추면 Confiner 가 다른 해법으로 갈아탄다
```

**둘째와 셋째는 첫째를 고친 뒤에야 드러났다.** 먼저 고친 것이 다음 것을 드러내는 순서였고,
세 번 모두 '값을 바꿔 볼까' 가 아니라 패키지 소스에서 근거를 찾아 고쳤다.

**카메라가 끌리던 것은 판단이 둘이라 다툰 것이다.** `PositionComposer` 는 플레이어 쪽으로
(댐핑 1초), Confiner 는 가운데로(댐핑 0.5초) 당겼다. 보스 전투 동안 따라갈 대상을
**방 자신의 `transform`**(곧 방 가운데)으로 바꿔 두 힘의 방향을 맞췄다.
오브젝트를 새로 만들지 않아도 된 것은 `LevelBuilder` 가 방을 방 가운데에 놓기 때문이다.
**적 끼임에서 잡은 원인 다섯 중 마지막과 같은 모양이다**(판단이 둘이면 경계에서 다툰다).

**남는 한계 셋이다.**

```
가. FitSize 가 비율을 줌 시작 때 한 번 읽는다
    줌이 도는 0.5초 사이에 창 크기를 바꾸면 목표값이 낡는다
나. InvalidateLensCache 가 0.5초에 서른 번쯤 할당한다
    보스 등장은 영상의 가장 화려한 자리다. Phase 6 개발 빌드 측정에 넣는다
다. 화면 비율이 2.2 를 넘으면 보스 시야가 평소보다 좁아진다
    연출이 거꾸로 된다. 울트라와이드 빌드 확인 항목이다
```

**빌드 전에 확인할 것을 하나 찾았다.** `LevelBuilder` 의 `_useFixedSeed` 가 커밋된 씬에서
켜져 있었다(시드 50). 그대로 빌드하면 **누가 몇 번을 돌려도 같은 배치가 나와** 절차적 생성을
영상에서 증명할 수 없다. 껐다. 성격이 `#if UNITY_EDITOR` 와 같아서 STATUS 의 빌드 확인
항목에 올린다. `_debugRoomCount` 도 같은 자리다. 0 으로 두면 코드가 기본값 8 을 쓴다.

**바닥 타일맵이 쓸데없이 넓은 범위를 들고 있었다.** `30 × 16` 이던 것이 Compress 로
`20 × 12` 가 됐다. 타일 수는 240 그대로다. `Room.Size` 는 `Walls` 만 읽으므로 동작에는
영향이 없고, 방 크기를 줄인 Phase 5 의 뒷정리가 늦게 따라온 것이다.

### B 를 하며 알게 된 것

**Esc 는 이미 임자가 있었다.** 보상 창이 '고르지 않고 넘어가기' 로 쓰고 있어, 메뉴가 같은 키를
받으려면 **누가 자기 차례인지 가리는 장치**가 필요했다. 창이 열렸는지는 `PlayerInputReader` 가
`SetFireBlocked` 로 이미 알고 있어, 창 둘을 참조하지 않고 그 값 하나로 끝냈다.

**거기에 프레임 가드를 더했다.** 창이 열려 있는지만 보면 **창이 닫히는 그 한 프레임**에 틈이 생긴다.
창이 먼저 돌아 닫으면 뒤에 도는 메뉴가 '창이 없다' 고 보기 때문이다. `Update` 가 도는 순서는
보장되지 않으므로 둘 다 필요하다.

```
IsWindowOpen            창이 떠 있는 동안을 막는다
IsEscapeUsedThisFrame   창이 Esc 로 닫히는 그 프레임을 막는다
```

프레임 번호로 적는 이유는 **치우는 코드가 0줄**이기 때문이다. 참거짓이면 되돌릴 자리를 정해야 하고
한 군데서 잊으면 Esc 가 영영 막힌다. 시간으로 막으면 그 사이에 누른 다음 Esc 까지 삼킨다.
타격음이 같은 기법을 쓰는데, 거기는 적는 쪽과 읽는 쪽이 같아 필드를 자기가 갖는다.

**이 버그는 드러나기 전에 막은 것이다.** 확인했을 때 정상이었던 것은 `PauseMenu` 가 먼저 돌았기
때문이고, **E 에서 `RewardPanel` 컴포넌트를 `Canvas` 로 옮기면 순서가 바뀔 수 있다.**

**시간이 멈춘 동안 이동 입력을 0 으로 읽게 했다.** 메뉴를 열고 방향키를 누르면 걷지는 않는데
몸만 뒤집혔다. `PlayerAttack` 이 쏘지 않을 때 `MoveInput.x` 로 보는 쪽을 정하기 때문이다.
막는 조건을 '창이 열렸다' 가 아니라 **'시간이 멈췄다'** 로 둔 것은, 가방은 시간을 멈추지 않아
열어 둔 채 걸어 다니는 것이 설계이기 때문이다. 보상 창도 함께 고쳐졌다.

**마을에는 화면용 Canvas 가 없었다.** 넷이 있었지만 전부 무기대와 입구의 머리 위 안내(World Space)다.
새로 만들면서 Scaler 를 던전과 맞췄다(`Scale With Screen Size`, `1920 × 1080`, `match 0`).
기본값인 `Constant Pixel Size` 로 두면 **해상도를 올릴 때 메뉴만 작아진다.** 빌드 확인 항목과 같은 뿌리다.

**안내판은 무기대의 `Prompt` 를 복제해 만들었다.** `Prompt` 가 '켜고 끄기 위한 빈 겹' 이고
그 아래에 World Canvas 와 글이 있어, 복제해 꺼내고 켜 두면 늘 보이는 안내판이 된다.

**남는 한계 둘이다.**

```
가. 조작이 적힌 자리가 둘이다 (메뉴의 조작표, 마을 안내판)
    키를 바꾸면 두 곳을 고쳐야 한다. 지금 겹치는 줄은 E 하나다
나. SetFireBlocked 가 참거짓 하나라 창이 동시에 둘 열리면 깨진다
    지금은 셋 중 하나만 열리도록 서로 막고 있다. 넷째가 생기면 겹침을 세야 한다
```

### C 를 하며 알게 된 것

**순서 문제가 또 나왔는데 이번에는 가드로 풀지 않았다.** `ResultPanel` 이 죽음과 클리어를
직접 듣고 `RunRecorder` 도 같은 것을 들어, 저장보다 먼저 글을 쓰면 기록이 한 판 뒤처진다.
B 의 Esc 는 '둘 중 하나만 반응해야' 하는 문제라 가드가 맞았지만, 이쪽은 **순서 자체가 필요한 일**이라
저장하는 쪽이 끝낸 뒤 알리게 했다. 같은 증상에도 처방이 다르다.

**그 덤으로 `ResultPanel` 의 의존이 줄었다.** `Health`, `RoomCombat`, `RoomType`, `RoomLayout` 을
놓고 `RunRecorder` 하나만 본다. **'보스 방인지 묻는 분기' 가 두 곳에 있던 것도 한 곳이 됐다.**

**'지금 열려 있다' 와 '이번에 열렸다' 는 다른 질문이다.** 해금 목록을 저장하지 않기로 한 선택의
대가가 여기서 드러났다. 지금 열렸는지는 기록 하나로 계산되지만, 새로 열렸는지는 **전과 후를
견줘야** 안다. `NewlyUnlockedCount(before, after)` 가 그래서 인자를 둘 받는다.
`!IsUnlocked(i, before)` 를 빼면 두 번째 클리어에서도 열렸다고 알린다. 테스트 5개를 붙여 18개가 됐다.

**진행 표시가 뜻을 갖는 것은 배치가 한 줄 걷기이기 때문이다.** 걸은 순서가 곧 진행 순서라
순번 하나로 '몇 번째인가' 를 말할 수 있다. 가지형이었으면 이 숫자에 뜻이 없어 미니맵이 필요했다.
**미니맵을 범위에서 뺀 근거가 이 한 줄과 같다.**

**숫자만으로는 읽히지 않는다.** `1 / 8` 로 띄우니 무슨 수인지 알 수 없어 `방` 을 붙였고,
기록판도 숫자 둘만으로는 뜻이 없어 `현재 기록` 을 붙였다. **두 번 같은 지적을 받았다.**
수치를 화면에 띄울 때는 그것이 무엇인지 한 마디가 함께 있어야 한다.

**첫 판에 보일 글을 미리 손봤다.** 저장이 없으면 `최고 0번째 방` 이 된다. 처음 켠 사람이
보는 글이라 '아직 없습니다' 로 갈랐다.

**남는 한계 셋이다.**

```
가. 기록을 적는 자리가 둘이다 (결과 창, 기록판). 표현을 바꾸면 둘을 고쳐야 한다
나. RecordSign 은 Start 에서 한 번만 읽는다. 마을에서 기록이 바뀌지 않는다는 전제다
다. '새 무기가 열렸습니다' 가 어느 무기인지 말하지 않는다
    WeaponData.DisplayName 이 있어 이름을 쓸 수 있지만, ResultPanel 이 PlayerAttack 을
    참조해야 한다. 마을에 가면 어두움이 풀린 자리로 알 수 있어 넣지 않았다
```

### D 를 하며 알게 된 것

**가림막 두 장이 이어달리기를 한다.** 오브젝트가 씬을 넘지 않는 결정 때문에 하나를 들고
다니지 못한다. 나가는 씬의 것이 어두워지고 들어오는 씬의 것이 밝아지는데,
**이어지는 지점에서 둘 다 알파 1** 이라 끊긴 것이 보이지 않는다.
그래서 가림막은 **알파 1(검정)로 저장해 둔다.** 0 으로 저장하면 씬이 열리는 첫 프레임에
밝은 화면이 한 번 번쩍한다.

**`unscaledDeltaTime` 이 아니면 영원히 멈춘다.** 전환이 시작될 때 `timeScale` 을 0 으로
만들어 플레이어와 적을 세우기 때문이다. 결과 창과 Esc 메뉴도 0 으로 두고 있어,
거기서 눌리는 버튼이 전부 이 길을 지난다.

**`StopAllCoroutines` 가 자기 자신을 멈추는 것을 겪었다.** 들어온 직후 바로 나갈 때
두 페이드가 겹치는 것을 미리 막으려고 `Fade` 의 첫 줄에 넣었는데, `Start` 가
`StartCoroutine(Fade(...))` 로 부르면 **그 코루틴도 이 오브젝트의 것**이라 자기를 멈췄다.
화면이 조금 밝아지다 멈추는 증상으로 나타났다.

```
요청받지 않은 예방이 실제 버그를 만들었다.
막으려던 것은 0.3초 깜빡임이고, 만든 것은 넘어가지 않는 화면이었다.
```

그 줄을 빼고 **겹침은 한계로 적었다.** 멈추고 싶으면 `Start` 가 만든 코루틴의 핸들을 들고
`StopCoroutine(handle)` 로 그것만 멈추면 되지만, 값에 비해 장치가 미묘하다.

**`_isLoading` 은 남겼다.** 결과 창에 버튼이 둘 보이므로 0.3초 사이에 두 번 누르는 것이
실제로 가능하다. 이쪽은 일어나지 않을 일이 아니다.

### E 를 하며 알게 된 것

**통일할 방향을 두 번 잘못 봤다.** 둘 다 '어느 쪽이 다수인가' 를 파일에서 세지 않고 정한 것이다.

```
가. 가림막이 Root 에 붙어 있었다
    '빈 겹' 이라 여겨 지우라고 했고, 지우니 가림막이 사라졌다.
    CellRoot 에 RectMask2D 가 있는 것을 보지 않고 부모를 옮기자고 한 것과 같은 실수다.
나. 패널을 끄는 쪽이 코드였다
    BagView 와 RewardPanel 이 Awake 에서 끄고, ResultPanel 만 씬에서 꺼진 채 저장돼 있었다.
    둘 대 하나인데 소수 쪽으로 통일하려 했다. ResultPanel 에 한 줄을 넣어 되돌렸다.
```

**코드가 끄는 쪽이 나은 이유**는 씬에서 켜 두고 모양을 보며 작업할 수 있고, **켠 채로 저장해
게임이 창과 함께 시작하는 실수가 사라지기** 때문이다.

**`timeScale` 의 주인이 둘인 버그를 찾았다.** 보상 창이 뜬 채로 돌아다닐 수 있었다.
`HitFeedback` 이 멈춤이 끝나면 **조건 없이 1 로 되돌리는데**, 마지막 적을 때린 히트스톱(0.01초)이
보상 창이 뜬 바로 다음 프레임에 풀어 버린 것이다. **E 가 만든 것이 아니라 Phase 5 에서
히트스톱이 들어올 때 생긴 것**이고, 그때 '창이 뜬 동안 움직여 보기' 를 확인하지 않았다.

**한 자리를 고쳐 세 증상이 함께 나았다.** 보상 창, Esc 메뉴(0.08초), 결과 창이 같은 뿌리였다.
`HitFeedback` 이 `IsWindowOpen` 을 보게 했고, 창 셋이 모두 `SetFireBlocked` 를 쓰므로
참조 하나로 셋이 덮였다. **원인을 코드로 증명해 로그를 붙이지 않았다.**

**프레임 가드가 예고한 대로 일했다.** `RewardPanel` 컴포넌트를 `Canvas` 로 옮겨 `Update` 순서가
바뀌었는데 Esc 충돌이 드러나지 않았다. B 에서 미리 막아 둔 것이다.

**마을의 하이어라키를 Gameplay 와 같은 모양으로 묶었다.** 루트가 열다섯에서 여덟이 됐다.

**남는 한계 둘이다.**

```
가. timeScale 을 만지는 곳이 넷이다 (히트스톱, 보상 창, 메뉴와 결과 창, 씬 로더)
    요청을 세는 중재자가 없어, 새로 멈추는 쪽이 생기면 같은 버그가 다시 난다
나. '창이 열렸다' 와 '시간이 멈췄다' 가 같은 말이 아니다
    가방이 반례다. 전투가 끝난 뒤에만 열려 지금은 어긋나지 않는다
```
