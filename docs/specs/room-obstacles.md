# 방 안 장애물과 흐름장 길찾기 (4-E)

## 왜 필요한가

**방이 넓고 비어 있다.** 4-C 에서 웨이브가 방을 채운 뒤에도 그랬고, 관찰 항목으로 미리 적어 둔 기준에 걸렸다.
싸움이 '넓은 빈 곳에서 뒤로 빼며 쏘기' 한 가지로 풀린다. 지형이 있어야 자리를 두고 겨루는 장면이 생긴다.

**장애물만 넣으면 적 AI 가 망가진다.** 적은 플레이어 쪽으로 곧장 움직여(`DirectionToTarget`) 기둥 뒤의 플레이어를 쫓다 기둥에 붙은 채 멈춘다.
그래서 장애물과 길찾기는 한 몸이다. 4-B 계단 5 에서 이미 따져 둔 결론이다.

포트폴리오에서는 **BFS 가 두 곳에서 일하는 것**이 이 기능의 값이다.

```
1. 문에서 문까지, 문에서 출현 지점까지 길이 막히지 않았는지 확인한다
   4-A 가 '한 줄 걷기라 도달성 검증이 늘 통과한다' 고 남긴 약점을 여기서 메운다. 여기서는 실제로 실패할 수 있다.
2. 플레이어에서 시작해 칸마다 거리를 적어 두고, 적은 거리가 줄어드는 쪽으로 걷는다 (흐름장)
   적 한 마리가 늘어도 길찾기 비용이 늘지 않는다. 브로그의 Dijkstra map 과 같은 모양이다.
```

## 정해진 것

명세를 쓰기 전에 합의했다. 근거는 4-E 를 마칠 때 결정 문서로 옮긴다.

- **장애물은 방 프리팹의 `Obstacles` Tilemap 에 판이 시작될 때 코드로 칠한다.** 칸이 곧 BFS 의 칸이고, 콜라이더는 벽처럼 Composite 가 합쳐 준다.
  벽 Tilemap 에 섞어 칠하지 않는다. 방 크기를 읽는 `cellBounds` 와 뒤섞인다.
- **격자와 BFS 는 `Logic/Rooms` 에 순수 계산으로 둔다.** 통행 가능 여부와 거리 맵을 다루고 Unity 를 모른다. EditMode 테스트가 이 기능의 증거물이다.
- **배치는 시드로 뽑되 문 앞, 출현 지점, 방 가장자리는 비운다.** 작은 덩어리 여럿을 놓는다. 수와 모양은 값 표로 따로 정한다.
- **BFS 로 길이 막혔는지 확인하고, 막혔으면 다시 배치한다.** 몇 번까지 다시 할지 정하고, 그래도 실패하면 장애물 없는 방으로 둔다.
- **흐름장은 플레이어가 다른 칸으로 옮길 때만 다시 계산한다.** 싸우는 방 하나만 계산한다.
- **흐름장은 추적할 때만 쓴다.** 돌진 적의 직선 돌진과 원거리 적의 후퇴는 그대로 둔다.
  돌아가며 돌진하면 '예고하고 곧게 달린다' 는 그 적의 성격이 사라진다. 벽에 부딪히는 것은 약점으로 남긴다.
- **장애물은 투사체를 막는다.** 벽과 같은 취급이라 엄폐가 생긴다. 이것이 전투를 바꾸는 가장 큰 변화다.
- **시작 방은 비운다.** 나머지 일곱 방에는 놓는다.

## 동작 정의

### 방

- 판이 시작되면 **방마다 장애물이 놓인다.** 시작 방은 비어 있다.
- 장애물은 **문 앞을 막지 않는다.** 문에서 문까지 걸어갈 수 있다.
- 장애물은 **적이 나오는 자리를 막지 않는다.** 나온 적은 플레이어에게 갈 수 있다.
- **고정 시드를 켜면 방마다 같은 배치**가 나온다.
- 장애물은 **벽처럼 막는다.** 플레이어와 적이 통과하지 못하고, 투사체가 닿으면 사라진다.

### 적

- 추적 중인 적은 **장애물을 돌아 플레이어에게 온다.** 기둥 뒤에 서 있어도 붙은 채 멈추지 않는다.
- 플레이어가 움직이면 적이 가는 길도 따라 바뀐다.
- 돌진 적은 전과 같이 **예고한 방향으로 곧게 달린다.** 장애물에 막히면 거기서 멈춘다.
- 원거리 적은 전과 같이 뒤로 물러나며 쏜다.
- 적이 장애물에 끼거나 떨리지 않는다.

### 판의 흐름

- 웨이브, 방 클리어, 보상, 가방이 4-C 와 4-D 대로 그대로 돈다.
- 게임 오버, 다시 시작, 타이틀로 가기가 전과 같다.

## 정할 것

**구조를 먼저 정하지 않는다.** 계단에서 대안을 견주고 정한 뒤 메모에 적는다.

### 1. 격자를 무엇으로 들고 있나

`bool[]` 한 줄로 펼칠지 `bool[,]` 로 둘지, 방 하나의 격자를 누가 만들고 누가 들고 있을지 정한다.
칸 좌표(0 ~ 31, 0 ~ 17)와 월드 좌표 사이의 변환도 정한다. `RoomSpace` 가 방 단위 변환을 이미 갖고 있다.

### 2. 거리 맵의 모양과 갱신

거리 맵을 `int[]` 로 둘지, 방향을 미리 구해 둘지 정한다. 닿을 수 없는 칸을 어떻게 표시할지도 정한다.
**적은 한 프레임에 여러 마리가 읽는다.** 읽는 쪽이 칸을 어떻게 묻는지(월드 좌표로? 칸으로?) 정한다.

### 3. 적이 흐름장을 어떻게 따르나

이웃 넷만 볼지 여덟을 볼지, 칸 가운데를 향해 갈지 방향만 쓸지 정한다.
**지금 `MoveTowardTarget` 은 비켜 가기(`SeparationPush`)를 섞고 있다.** 흐름장 방향과 어떻게 섞을지 함께 정한다.

### 4. 배치 규칙과 값

덩어리 수, 모양(1×1, 2×2, 1×3 등), 비워 둘 여백(문 앞 몇 칸, 출현 지점 둘레 몇 칸)을 정한다. **값 표를 먼저 합의한다.**

### 5. 막혔을 때

다시 배치하는 횟수, 그래도 실패하면 무엇을 할지 정한다. 4-A 가 재생성을 두지 않기로 한 것과 반대 방향이라 이유를 남긴다.

### 6. 장애물이 카메라와 출현 지점에 미치는 영향

출현 지점 위에 장애물이 놓이지 않게 하는 방법(지점을 피해 칠하기 vs 놓인 지점을 건너뛰기)을 정한다.
카메라 경계(`CameraBounds`)는 벽 범위를 읽으므로 영향이 없는지 확인한다.

## 경계: 이 기능이 하지 않는 것

- **가중치 있는 길찾기(A*, 다익스트라)** → 하지 않는다. 칸 비용이 모두 같아 BFS 로 충분하다.
- **적끼리 밀어내기 다시 만들기** → 2-C 의 비켜 가기를 그대로 쓴다.
- **모양이 다른 방 프리팹 여러 개** → 만들지 않는다. 장애물이 그 역할을 한다. GDD 의 '방 프리팹 8' 은 이 판단으로 닫는다.
- **부술 수 있는 장애물, 함정, 지형 효과** → 하지 않는다.
- **적이 길을 막고 서로 밀치는 상황의 정교한 처리** → 하지 않는다.
- **플레이어 길찾기(자동 이동)** → 없다. 플레이어는 직접 움직인다.
- **장애물 아트** → 도형 프로토타입 기본. 벽과 같은 타일을 쓴다.

## 메모

**계단 1 결과: `RoomGrid` 와 `FlowField` 를 만들었다(정할 것 1, 2).** 격자는 `bool[,]`, 거리표는 `int[,]` 이고 `BagGrid` 와 같은 모양이다.
갈 수 없는 칸은 -1 로, 계산 중에는 '아직 안 본 칸' 이라는 표시를 겸한다. 배열과 큐는 다시 쓰므로 **계산을 시작할 때 전부 지우는 줄이 알고리즘의 일부**다.
`IsPassable` 이 격자 밖을 거르므로 BFS 안에 경계 검사가 없다.

**계단 2 결과: `ObstaclePlacer` 가 자리를 정하고 BFS 로 길을 검사한다(정할 것 4, 5).** 실패하면 사본을 버리고 최대 열 번 다시 놓는다.
덩어리는 방 안쪽을 가로 3 세로 2 로 나눈 구역마다 하나씩 놓고, 구역 고르기는 4-D 의 `RandomPick.Distinct` 를 그대로 쓴다.
**200판 시뮬레이션으로 값을 정했다.** 구역만 나누면 가장 가까운 두 덩어리가 2칸까지 붙어, 덩어리 사이 최소 거리 4 와 구역 테두리 여백 1 을 더했다.
여백 1 은 '자리를 못 찾는 덩어리' 를 7/987 에서 0 으로 줄였다. **길 검증은 200판에서 한 번도 실패하지 않았다.** 값을 조이면 일하는 안전망이다.

**계단 3 결과: `RoomObstacles` 가 격자를 만들고 타일을 칠한다(정할 것 6).** 격자는 벽 타일맵을 훑어 만들고, 문 구멍은 '가장자리인데 타일이 없는 칸' 으로 찾는다.
문 폭도 벽 모양도 코드에 없다. 좌표를 옮기는 곳은 `ToTilemapCell` 과 `ToGridCell` 두 곳뿐이다.
`TilemapCollider2D` 의 `Used by Composite` 는 Unity 6 에서 `Composite Operation = Merge` 로 이름이 바뀌었다.

**계단 4 결과: `RoomFlowField` 가 플레이어의 칸이 바뀔 때만 표를 다시 쓴다.** 한 번에 한 방만 싸우므로 표도 하나다.
`FlowFieldGizmo` 로 씬 뷰에 그린다. **처음에 '기둥 뒤가 눈에 띄게 어둡다' 고 설명했는데 과장이었다.**
30칸 넓은 방에서 2×2 기둥 뒤는 옆 칸보다 두 걸음 멀 뿐이라 색으로는 안 보인다. 숫자로 봐야 확인된다. 등고선으로 그려 봤다가 헷갈려서 한 색 진하기로 되돌렸다.

**계단 5 결과: 적이 거리표를 따라 걷는다(정할 것 3).** `IPathField` 로 '다음에 갈 자리' 하나만 약속해, 적이 방과 격자와 BFS 를 모르게 했다.
적은 그 자리를 붙잡고 가고, 도착하거나 0.4 초가 지나면 다시 묻는다. 매 프레임 고르면 칸 경계에서 자기 칸이 뒤집혀 선택이 흔들린다.

**계단 5 에서 끼임 버그를 다섯 번 고쳤다. 원인이 전부 길찾기 밖이었다.**

| 증상 | 원인 | 고친 것 |
|---|---|---|
| 모서리에서 떨림 | 시야를 굵기 0 인 선으로 판정 | 시야 판정 제거 |
| 모서리에서 완전 정지 | 마찰 0.4 와 진입 각도 비율 0.398 | 마찰 0 물리 재질 |
| 대각선 정면 정지 | 네모 콜라이더 꼭짓점 정면 충돌 | 원형 콜라이더 |
| 기둥 뒤 맴돎 | 판단이 둘(직선 vs 우회)이라 경계에서 다툼 | 시야 판정 제거 |
| 기둥 뒤 제자리 꿈틀 | 4방향에서 좌우 동점 | 이웃 여덟 + 모서리 규칙 |

원인은 **끼임 로그(접촉 법선과 파고듦), 기즈모(격자와 타일 대조), 파이썬 시뮬레이션**으로 잡았다. 그 전에 낸 추측 넷은 전부 틀렸다.
'움직이지 않는다' 를 속도로 재면 떨고 있을 때 걸리지 않는다. 위치로 재야 한다.
넣었다가 뺀 것이 셋이다(시야 직선 돌진 두 번, 못 움직이면 직선을 끄는 안전망, 방향 부드럽게 돌리기). 안전망은 **버그를 가려서** 뺐다.
근거는 [조종에서 겪은 끼임](../decisions/enemy-steering-jams.md)에 있다.

**계단 6 결과: 관찰**

| 관찰 | 결과 |

| 직각으로 꺾이는 움직임 | 거슬렸다. 이웃을 여덟로 늘려 해결했다 |

중간 보고에서 187 이라고 했다가 파일에서 다시 세어 186 으로 고쳤다. 더하기만 이어 붙이지 말고 그때그때 세어야 한다.
