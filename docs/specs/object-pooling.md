# 오브젝트 풀링

## 왜 필요한가

투사체를 매번 `Instantiate` 로 만들고 `Destroy` 로 지우고 있다.
코딩 규칙이 금지하는 패턴이며, **Phase 3에서 바꾸기로 하고 의도적으로 둔 것**이다.

측정으로 비용을 확인했다. 자세한 조건과 과정은
[기준선 측정](../measurements/pooling-baseline.md)에 있다.

동시 활성 수를 고정하고 생성·파괴 빈도만 3배로 올렸을 때:

| 항목 | 200/초 | 600/초 |
|---|---|---|
| `PlayerLoop` | 1.70ms | 2.29ms |
| `Update.ScriptRunBehaviourUpdate` | 0.12ms | 0.26ms |
| GC Alloc | 176 B | 0.7 KB |

**생성·파괴가 실제로 비용이라는 것이 수치로 확인됐다.**

## 무엇을 만드는가

**재사용 가능한 풀을 직접 구현한다.**

Unity에 `UnityEngine.Pool.ObjectPool<T>` 가 이미 있지만 쓰지 않는다.
CLAUDE.md 1번이 오브젝트 풀링을 사용자 직접 작성 목록에 두었고,
7번이 그 목록을 외부 사용 금지 목록으로 규정한다.

**내장이 있다는 것을 알고도 직접 만드는 것이다.** 모르고 만드는 것과 다르다.

## 동작 정의

**꺼내기**
- 발사할 때 풀에서 하나 꺼낸다.
- 풀이 비어 있으면 새로 만든다. **미리 개수를 정해 두지 않는다.**
- 꺼낸 오브젝트는 활성화되어 화면에 보이고 물리에 참여한다.
- **꺼낼 때 상태가 초기화된다.** 이전에 쓰였을 때의 속도나 남은 시간이 남지 않는다.

**돌려주기**
- 무언가에 닿거나 수명이 다하면 **파괴하지 않고 풀로 돌아간다.**
- 돌아간 오브젝트는 비활성화되어 화면에서 사라지고 물리에서 빠진다.
- 같은 오브젝트가 **두 번 돌아가지 않는다.** 벽에 닿는 순간과 수명이 끝나는 순간이
  겹쳐도 한 번만 처리된다.

**수명 처리 변경**
- 지금은 `Destroy(gameObject, 수명)` 으로 예약한다. 풀링하면 파괴하지 않으므로
  이 방식을 쓸 수 없다. **타이머로 바꾼다.**

**풀의 수명**
- 풀은 발사하는 쪽이 소유한다. `PlayerAttack` 이 투사체 풀을 갖는다.
- 씬이 끝나면 풀도 함께 사라진다. 씬을 넘어 유지하지 않는다.

## 경계: 이 기능이 하지 않는 것

- **전역 풀 관리자** → 만들지 않는다. 발사하는 쪽이 자기 풀을 갖는다.
  적도 투사체를 쏘게 되어 풀이 둘로 늘고 **그것이 실제로 문제가 될 때** 다시 본다.
  지금 만들면 싱글톤이 하나 생기고, 코딩 규칙이 static 남용을 경계한다.
- **적과 이펙트 풀링** → Phase 4. 지금은 투사체 하나만 한다.
- **풀 크기 상한과 축소** → 넣지 않는다. 상한이 필요할 만큼 많이 만들지 않고,
  줄일 시점을 판단할 근거도 없다.
- **미리 채워 두기(prewarm)** → 넣지 않는다. 첫 발사 때 만들어지는 비용이
  문제가 되는지 아직 모른다.
- **Unity 내장 `ObjectPool<T>`** → 위에 적은 이유로 쓰지 않는다.

## 검증

**EditMode 테스트**: 해당 없음.

풀이 GameObject 를 다루므로 Unity 에 의존한다. `JM2D.Logic` 대상이 아니다.
순수 자료구조로 분리할 수는 있으나 그러면 정작 중요한 활성화·비활성화가
테스트 밖으로 나가 실익이 없다.

**플레이모드 체크리스트**

- [x] 발사와 충돌, 수명이 지금과 똑같이 동작한다
- [x] 오래 쏴도 Hierarchy 의 투사체 오브젝트 수가 일정 수준에서 멈춘다
- [x] 벽에 맞은 투사체가 다시 발사될 때 정상으로 날아간다
- [x] **되돌아온 투사체가 화면에 남아 있지 않다**

## 메모

**예상 개선폭은 `PlayerLoop` 2.29ms 중 0.3~0.5ms 다.** 극적이지 않다.
물리 연산이 여전히 지배적이고 그 부분은 풀링과 무관하다.

**예상이 빗나가면 그것도 기록한다.** 지금까지 가설을 두 번 틀렸고,
그 과정이 결과보다 나은 이야깃거리가 됐다.

**결과: 예상이 맞았다.** 3.05ms 에서 2.65ms, 0.40ms 개선으로 예상 범위 안이다.
다만 측정 방법을 한 번 더 고쳐야 했다. `FixedUpdate` 가 돈 프레임끼리
비교하지 않으면 물리 비용이 빠져 58% 개선처럼 보인다.
자세한 것은 [측정 기록](../measurements/pooling-baseline.md)에 있다.

투사체가 자기 풀로 돌아가려면 **자기를 소유한 풀을 알아야 한다.**
지금 `Projectile` 은 누가 쐈는지 모르는 상태로 설계했는데, 그 성질을
어디까지 유지할지는 구현하면서 정한다.
