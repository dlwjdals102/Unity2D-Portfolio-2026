# ScriptableObject 데이터 분리

## 왜 필요한가

**포트폴리오를 위해서다.** 지금 게임에는 적이 한 종류뿐이고 투사체도 하나뿐이라,
값을 프리팹에 박아 두어도 당장 불편하지 않다.

CLAUDE.md 3번의 포트폴리오 예외를 **여기서 처음 적용한다.**

> 데이터 주도 설계: 적이 1종뿐이어도 ScriptableObject로 분리한다.
> 확장성 증명이 목적이다. 단 Phase 3부터.

Phase 2에서 하드코딩으로 뚫어 둔 것을 이제 넓히는 단계다.
Phase 4에서 적이 4종, 무기가 3종으로 늘 때 **프리팹을 복제해 수치를 하나씩
고치는 방식은 무너진다.** 그 전에 바꾼다.

## 무엇을 데이터로 빼는가

**적과 투사체만 뺀다.**

| 대상 | 빼는 값 |
|---|---|
| `EnemyData` | 최대 체력, 이동속도, 감지범위, 포기범위, 공격범위, 공격이탈범위, 공격쿨다운, 공격력 |
| `ProjectileData` | 속도, 수명 |

**투사체 피해량은 데이터에 넣지 않는다.** 투사체는 '어떻게 날아가는가'만 알고,
'얼마나 아픈가'는 발사하는 쪽이 정한다. 같은 투사체를 적이 쏘거나 무기 여러 종이
이를 공유할 때 각자의 공격력이 실려야 하기 때문이다.

**플레이어는 빼지 않는다.** 플레이어 캐릭터는 하나뿐이라고 GDD가 못 박았다.
하나뿐인 것을 데이터로 빼는 것은 확장성 증명이 되지 않는다.
플레이어 수치는 다음 단계인 **스탯 · 모디파이어 시스템**이 다루게 되므로,
지금 옮기면 곧바로 다시 손대야 한다.

## 동작 정의

**데이터는 원본이고, 런타임 값은 사본이다**

- 컴포넌트는 시작할 때 데이터의 값을 **자기 필드로 복사한다.**
  이후 데이터 에셋을 다시 읽지 않는다.
- **플레이 중에 무슨 일이 일어나도 에셋 파일은 바뀌지 않는다.**
  적이 피해를 입어도, 죽어도, 나중에 버프가 붙어도 마찬가지다.
- 같은 데이터를 쓰는 적 둘은 서로 독립이다. 한쪽이 맞아도 다른 쪽은 멀쩡하다.

**프리팹과 데이터의 역할이 갈린다**

- 프리팹은 **생김새와 구성**을 갖는다. 콜라이더 크기, 스프라이트, 붙어 있는 컴포넌트.
- 데이터는 **수치**를 갖는다.
- 적 프리팹의 인스펙터에는 개별 수치가 남지 않고 데이터 참조 하나만 보인다.

**적 체력의 출처가 바뀐다**

- 최대 체력은 `Health` 컴포넌트가 아니라 `EnemyData`에서 온다.
- **컴포넌트 초기화 순서와 무관하게 같은 결과가 나온다.**
  `Health`가 먼저 깨어나든 `EnemyController`가 먼저 깨어나든 체력은 데이터 값이다.
- 플레이어의 `Health`는 지금처럼 인스펙터 값을 그대로 쓴다.

**투사체 피해량을 발사하는 쪽이 정한다**

- 투사체는 자기 피해량을 스스로 정하지 않는다. **발사할 때 넘겨받는다.**
- 지금 넘기는 값은 `PlayerAttack` 의 인스펙터 값이다.
  스탯 시스템이 들어오면 **그 자리에 계산된 공격력이 들어간다.**

## 경계: 이 기능이 하지 않는 것

- **플레이어 데이터** → 빼지 않는다. 위에 적은 이유로 다음 단계에서 다룬다.
- **아이템 · 무기 데이터** → Phase 4. 지금은 만들 아이템이 없다.
- **데이터 안에 로직 넣기** → 넣지 않는다. `EnemyData`에 `Attack()` 같은 메서드를
  두면 데이터와 행동이 섞인다. 지금은 값만 담는다.
  적 종류마다 행동이 갈리는 문제는 4번 항목에서 FSM 과 함께 본다.
- **데이터 검증 에디터 툴** → 만들지 않는다. 감지범위가 포기범위보다 크면
  적이 영원히 쫓아오지만, 데이터가 두어 개뿐이라 눈으로 확인된다.
  종류가 늘어 실제로 틀리기 시작하면 그때 만든다.
- **적 종류 추가** → 하지 않는다. 이번 단계는 **구조만 바꾸고 게임은 그대로 둔다.**
  데이터 에셋을 하나 더 만들어 보는 것은 검증용이며 게임에 배치하지 않는다.
- **어드레서블 · 로딩 시스템** → 하지 않는다. 참조로 충분하다.

## 어디에 두는가

`Assets/_Project/Scripts/Data/` 에 클래스를 두고,
에셋은 `Assets/_Project/ScriptableObjects/` 에 만든다.

**`JM2D.Logic` 이 아니라 `JM2D.Runtime` 이다.** ScriptableObject 는 UnityEngine 에
의존하므로 Logic 의 조건을 만족하지 않는다.
Logic 은 다음 단계인 스탯 계산에서 처음 쓰인다.

에셋 이름은 코딩 규칙대로 `타입_이름` 으로 짓는다. 예: `EnemyData_Slime`.

## 검증

**EditMode 테스트**: 해당 없음.

데이터 클래스는 값을 담기만 하고 계산하지 않는다. 테스트할 로직이 없다.
값을 읽어 쓰는 쪽은 MonoBehaviour 라 Logic 대상이 아니다.

**플레이모드 체크리스트**

- [x] 적의 체력, 속도, 감지, 공격이 데이터 분리 전과 똑같이 동작한다
- [x] 적이 여전히 세 발에 죽는다
- [x] 데이터 에셋의 이동속도를 바꾸고 플레이하면 적이 그 속도로 움직인다
- [x] 적 프리팹 인스펙터에 개별 수치가 남아 있지 않다
- [x] **적을 죽인 뒤 플레이를 멈추고 데이터 에셋을 열면 값이 그대로다**
- [x] 적 두 마리를 배치하고 하나만 때리면 나머지는 체력이 온전하다
- [x] 값이 다른 데이터 에셋을 하나 더 만들어 두 번째 적에게 물리면 서로 다르게 움직인다
- [x] 투사체 피해량을 2로 올리면 적이 두 발에 죽는다
- [x] 재시작 후에도 정상 동작한다

> 다섯 번째가 이번 단계의 핵심이다. 런타임에 데이터를 직접 고치면
> 에디터에서는 **에셋 파일이 실제로 바뀌고 플레이를 멈춰도 돌아오지 않는다.**
> 이 항목이 통과하지 못하면 원본과 사본이 분리되지 않은 것이다.
>
> 일곱 번째가 확장성 증명이다. 확인한 뒤 두 번째 적과 임시 에셋은 되돌린다.

## 메모

**가장 흔한 함정은 데이터를 런타임에 고치는 것이다.** ScriptableObject 는
씬에 놓인 오브젝트가 아니라 **디스크의 에셋 파일**이라, 값을 바꾸면 파일이 바뀐다.
빌드에서는 되돌아오지만 에디터에서는 남는다. 개발 중에만 나타나 원인을 찾기 어렵다.

이 성질을 알고 설계했다는 것 자체가 면접에서 할 이야기다.

**적 체력은 `Health` 에 있고 플레이어도 같은 컴포넌트를 쓴다.**
`Health` 가 `EnemyData` 를 직접 참조하면 플레이어까지 적 데이터를 갖게 된다.
`Health` 는 데이터를 모르는 채로 두고 **밖에서 최대 체력을 정해 주는 방식**이
자연스럽다. 초기화 순서 문제를 어떻게 피할지가 이번 구현의 갈림길이다.

**이번 단계는 게임을 바꾸지 않는다.** 플레이 화면은 전과 완전히 같아야 한다.
달라 보이면 값을 옮기다 틀린 것이다.

**결과: 게임은 바뀌지 않았다.** `EnemyController` 의 diff 가 20줄 추가에
14줄 삭제인데 `FixedUpdate` 와 `ChangeState` 는 한 줄도 안 바뀌었다.
필드 이름을 그대로 둔 것이 컸다. 이름까지 바꿨으면 로직 여섯 군데를
고쳐야 했고, 그러면 '값의 출처만 바꿨다'는 것이 diff 에서 안 보였을 것이다.

**투사체 수명이 1초로 남아 있던 것을 이 작업이 겸사겸사 고쳤다.**
풀링 측정 때 낮춘 값이 프리팹에 그대로 있었다.
문서에는 3초로 되돌렸다고 적혀 있었으므로, **문서와 파일이 어긋난 상태**였다.

**계단 3에서 나온 것이 가장 값지다.** 순서를 맞추려 하지 않고
순서가 상관없는 모양으로 만드는 방식은 Unity 초기화 문제 전반에 쓰인다.
