# 시너지 4종 완성

## 왜 필요한가

**인접 하나로는 배치를 고민하게 만들지 못했다.**

앞 명세의 완료 조건에서 판단한 결과다.

> 뭉치면 무조건 이득이라 최적해가 자명하다.
> 방향이 하나뿐이면 값을 어떻게 바꿔도 마찬가지다.

**GDD 가 요구한 넷이 이미 서로 충돌한다.** 새 개념을 발명할 필요가 없다.

| 시너지 | 유리한 배치 |
|---|---|
| 인접 | 뭉친다 |
| 같은 행 | 가로로 늘어놓는다 |
| 같은 열 | 세로로 늘어놓는다 |
| 모서리 | **네 귀퉁이로 흩는다** |

**모서리가 인접과 정면으로 부딪힌다.** 귀퉁이는 이웃이 적은 자리이기 때문이다.
같은 행과 같은 열도 서로 배타적이다.

그리고 **모서리는 자리가 넷뿐이라 다툼이 생긴다.** 인접은 뭉치기만 하면
다 같이 이득이라 다툴 일이 없었다.

## 어디까지 만드는가

**선택이 존재하는 데까지만 만든다.**

| | 하는가 |
|---|---|
| 4종을 만들어 배치에 따라 값이 갈리게 한다 | **한다** |
| 밸런싱을 정교하게 다듬는다 | 하지 않는다 |
| 최적 배치를 찾기 어렵게 만든다 | 하지 않는다 |

**어느 배치가 최적인지 계산해야 알 정도로 만들 이유가 없다.**
신입 포트폴리오에서 재미의 깊이는 평가 항목이 아니다.
다만 **기획서가 주장하는 것이 게임에 없으면 그것은 다른 문제**이므로,
'배치에 따라 성능이 달라진다' 가 참이 되는 데까지는 만든다.

## 무엇을 만드는가

| 어셈블리 | 무엇 |
|---|---|
| `JM2D.Logic` | 조건별로 세는 메서드 셋, 조건을 나타내는 열거형, **조건에 따라 세는 메서드를 고르는 `Count`** |
| `JM2D.Runtime` | 조건을 담는 구조체, 세어진 수를 곱해 스탯에 붙이는 조립 |
| `JM2D.Tests.EditMode` | 세 조건의 규칙, 조건과 메서드의 짝 |

**넷이 전부 `int` 를 돌려주므로 조립이 하나로 통일된다.**
조건에 따라 부르는 메서드만 갈리고, 곱해서 붙이는 부분은 같다.

**조건을 고르는 코드는 `BagGrid` 에 둔다.** 조건과 메서드의 짝을 뒤바꾸는
실수는 오류 없이 값만 틀린다. `SameRow` 에 `CountInSameColumn` 을 잇는 식이다.
`Runtime` 에 두면 플레이모드에서 사람이 매번 확인해야 하고, `Logic` 에 두면
테스트 하나로 잡힌다. 대가로 그리드가 시너지 조건이라는 말을 알게 된다.

## 동작 정의

### 세는 방법

**같은 행**
- 아이템이 걸친 **모든 행**을 본다. `2×2` 는 두 행에 걸친다.
- 그 행들에 있는 **다른 아이템**을 센다. 자기 자신은 세지 않는다.
- 같은 아이템이 두 행에 걸쳐 있어도 **한 번만 센다.**

**같은 열**
- 같은 행과 대칭이다. 걸친 모든 열을 보고 다른 아이템을 센다.

**모서리**
- 그리드의 네 귀퉁이 칸 중 **차지한 것의 수**를 센다.
- 5×5 에서 최대 크기가 `2×2` 이므로 **언제나 0 아니면 1** 이다.

### 조건을 데이터로 적는다

지금 `_adjacencyBonus` 는 인접 전용이다. **어느 조건인지 적을 자리가 필요하다.**

`ItemModifier` 에 조건 필드를 더하지 않는다. 일반 효과에는 조건이 없어
**절반이 늘 비어 있는 구조체**가 된다. 시너지 전용 구조체를 따로 둔다.

- 아이템은 시너지를 **여럿** 가질 수 있다. 배열이다.
- 조건이 다르면 같은 스탯에 여러 번 붙어도 된다.
  검이 '인접 1개당 +1' 과 '모서리에 있으면 +3' 을 함께 가질 수 있다.

### 계산은 지금과 같다

- 배치가 바뀌면 시너지를 **전부 지우고 다시 계산**한다.
- 붙는 값은 **`조건별 세어진 수 × 시너지 값`** 이다.
- 세어진 수가 0이면 아무것도 붙이지 않는다.

## 경계: 이 기능이 하지 않는 것

- **세트 시너지** (칼·부츠·갑옷이 모이면) → 하지 않는다.
  태그 체계가 필요하고, 계산기에 규칙을 더하는 방식으로 나중에 들어온다.
- **조건부 시너지** ('체력이 절반 이하일 때') → 하지 않는다.
  배치가 아니라 상태를 봐야 해서 재계산 시점이 달라진다.
- **음수 시너지** ('인접하면 약해진다') → 만들지 않는다. 값을 음수로 넣으면
  동작은 하지만 지금 필요하지 않다.
- **밸런싱** → 하지 않는다. 값이 배치에 따라 갈리는 것만 확인한다.
- **시너지 표시 UI** → 하지 않는다. 어느 시너지가 얼마나 붙었는지 화면에
  그리지 않는다. 가방의 스탯 표시로 결과만 본다.
- **아이템 15종 채우기** → 이번에도 넷에 시너지를 붙여 본다.

## 메모

**완료 조건 넷째가 이번에도 진짜 목적이다.** 앞 명세에서 '부족하다' 로 답했던
질문을 다시 던진다. **넷으로 충분한지, 아직도 답이 뻔한지**를 본다.

여전히 뻔하다면 원인을 갈라야 한다. 아이템이 넷뿐이라서인지,
25칸에 9칸만 쓰는 공간 여유 때문인지, 값이 작아서인지.
**아이템 15종을 채우는 것이 다음 후보**이며, 그것이 공간 압박도 함께 만든다.

**기존 에셋 넷의 시너지 값을 다시 넣어야 한다.** `_adjacencyBonus` 가
`ItemSynergy` 배열로 바뀌므로 기존 값이 유지되지 않는다.
**넷에 서로 다른 조건을 붙여야** 충돌을 확인할 수 있다.

**같은 행과 같은 열을 세는 코드가 거의 같아진다.** 행과 열만 뒤바뀐다.
하나로 합칠지 따로 둘지는 계단에서 정한다. 합치면 방향을 인자로 받아야 하고,
따로 두면 비슷한 코드가 둘이 된다.

**결과: 따로 두었다.** 합치면 칸에 접근할 때마다 축에 따라 인덱스 순서를
갈라야 하고, 같은 변수가 어떤 때는 x고 어떤 때는 y가 된다. 아끼는 것은
반복문 하나다. 격자 밖·빈 칸·자기 자신을 거르는 판단은 인접과 같아서
`AddNeighbor` 를 `AddOther` 로 이름을 바꿔 셋이 함께 쓴다.

**모서리를 세다가 x 와 y 를 뒤바꿔 적었는데 5×5 테스트를 전부 통과했다.**
두 줄이 서로의 칸을 보고 있어 합계가 같았고, 정사각형이라 오른쪽 아래는
순서가 뒤집혀도 같은 칸이었다. 가로세로가 다른 6×4 테스트를 더해 잡았다.

**`ItemSynergy` 는 `ItemModifier` 를 품는다.** 필드를 펼치는 안도 있었다.
시너지도 결국 조건이 붙은 효과라서 품는 쪽을 골랐고 필드가 넷에서 둘로 줄었다.
대가로 인스펙터에서 한 단계 더 펼쳐야 하고, 값이 한 단계 안으로 들어가
`[FormerlySerializedAs]` 로 옛 값을 옮길 수 없었다. 에셋 넷의 값은 다시 넣었다.

**조건 열거형은 에셋에 순서 번호로 저장된다.** 파일에 `Condition: 0` 으로 적힌다.
새 값은 끝에만 붙인다는 약속을 `SynergyCondition` 주석에 적었다.
`Count` 의 `default` 는 예외를 던진다. 지운 조건의 번호가 에셋에 남아 있으면
조용히 0이 되지 않고 그 자리에서 멈춘다.

**결과: 넷으로도 아직 뻔하다.** 완료 조건 넷째의 답이며, 근거는
[시너지 판단](../decisions/synergy-needs-more-items.md)에 있다.
전수 조사로 확인했다. 좋은 배치는 전부 '검을 귀퉁이에 두고 나머지를 붙인다' 는
한 모양이다. 원인은 값이 아니라 아이템 수와 공간이다.
**다음은 아이템 15종 채우기다.**
