# 이동 애니메이션과 무기 휘두르기

## 왜 필요한가

지금 캐릭터는 스프라이트 한 장으로 미끄러진다. **움직이는데 움직이는 그림이 없다.**
받은 팩에 `idle`, `run`, `attack` 프레임이 전부 들어 있어 쓰지 않을 이유가 없고,
Animator 를 다뤄 본 흔적이 포트폴리오에 남는다.

## 동작 정의

- 플레이어가 멈춰 있으면 **제자리 동작**이 돈다
- 플레이어가 움직이면 **걷는 동작**이 돈다
- 플레이어가 공격하면 **무기를 휘두르는 동작**이 한 번 돌고 원래 동작으로 돌아간다
- **적이 맞는 순간이 칼이 뻗은 순간이다.** 아직 휘두르지 않았는데 적이 죽지 않는다
- 공격 속도가 빨라지면 **휘두르는 동작도 그만큼 빨라진다.** 동작이 밀려 겹치지 않는다
- 적도 멈춤과 이동이 갈린다. 공격 동작이 따로 있는 적은 공격할 때 그것이 돈다
- 좌우 어느 쪽을 보든 동작이 이어진다. 방향이 바뀌는 순간 처음 프레임으로 튀지 않는다

## 경계 — 이 기능이 하지 않는다

- **피격과 죽음 동작.** 팩에 `hit`, `death` 가 있지만 넣지 않는다. 피격은 이미
  `HitReaction` 의 빨강 틴트가 알리고, 죽음은 적이 그 자리에서 사라지는 것으로 끝난다.
  동작을 넣으면 **죽는 중에는 맞지 않는다** 같은 상태가 생겨 전투 로직이 바뀐다.
- **상하 방향.** 아래 '좌우만 쓴다' 에 이유를 적었다.
- **무기마다 다른 휘두르기.** 활, 검, 창이 같은 동작을 쓴다. 무기별 프레임이 팩에 없다.
- **대시 동작.** 전용 프레임이 없다. 대시 중에는 걷는 동작이 그대로 돈다.
- **보스의 패턴별 동작.** 보스는 멈춤과 이동만 쓴다. 패턴 넷에 각각 동작을 붙이면
  예고와 발동과 회복의 3단을 Animator 로 다시 그리게 된다.

## 설계

### 좌우만 쓴다

**플레이어에게는 상하 프레임이 있고 적에게는 없다.**

```
char_idle_up / down / left / right      네 방향 전부, 각 6프레임
pinkbat_idle_left / right               좌우뿐
phantom_idle_left / right               좌우뿐
```

플레이어만 네 방향을 쓰면 **규칙이 둘이 된다.** 위로 걸을 때 플레이어는 뒤통수를 보이는데
쫓아오는 적은 옆을 보고 있다. 적에게 상하를 그려 넣는 것은 아트 작업이고 경계 밖이다.

5-B 에서 이미 `SpriteFacing` 이 `flipX` 로 좌우를 가르기로 정했다. 그 기준을 그대로 쓴다.
**적에게 `left` 와 `right` 두 벌이 따로 있지만 `right` 만 쓰고 뒤집는다.** 두 벌을 쓰면
Animator 상태가 두 배가 되고 `flipX` 와 역할이 겹친다.

### 상태는 속도로 가른다

**Animator 가 상태 머신을 알 필요가 없다.** 멈춤과 이동은 `Rigidbody2D.linearVelocity` 의
크기 하나로 갈린다. 플레이어와 적 여섯이 같은 규칙을 쓴다.

```
속도 크기가 임계값보다 크다   ->  걷는 동작
작다                        ->  제자리 동작
```

`EnemyBase.Phase` 는 `private enum` 이고 `Idle / Chase / Engaged` 셋인데, 이것을 Animator
파라미터로 내보내지 않는다. **`Idle` 과 `Chase` 의 차이는 '움직이는가' 이고 속도가 이미 그것을 말한다.**
상태를 내보내면 적을 추가할 때마다 Animator 와 상태 머신을 함께 고쳐야 한다.

`PlayerMotor` 에 `IsMoving` 이 이미 있지만 그것은 **입력** 기준이다. 벽에 밀려 못 가는 동안에도
참이라 제자리에서 걷는 그림이 돈다. 속도로 재면 그 경우가 저절로 걸러진다.

공격만 속도로 알 수 없다. **공격하는 쪽이 한 번 알린다.**

### 휘두르는 동작은 공격 간격에 맞춰 빨라진다

`PlayerAttack` 이 공격 간격을 스탯에서 가져온다.

```csharp
_fireCooldownLeft = 1f / _stats.AttackSpeed.Value;
```

활은 초당 6.67발이라 간격이 **0.15초**다. 6프레임짜리 휘두르기를 기본 속도로 돌리면
간격보다 길어져 **다음 공격이 앞 동작을 자른다.** 연사 아이템이 붙으면 더 짧아진다.

동작의 길이를 공격 간격에 맞춰 재생 속도를 정한다. 공격이 빨라지면 휘두르기도 빨라져
**둘이 어긋나는 구간이 생기지 않는다.** 수치를 하나 더 두지 않고 이미 있는 스탯에서 끌어온다.

버린 안이 둘이다. **고정 속도로 돌리고 잘리게 두는 안**은 연사를 올릴수록 첫 프레임만
깜빡이는 모양이 된다. **공격 간격의 하한을 동작 길이로 두는 안**은 연사 아이템의 효과를
애니메이션이 깎는 것이라 순서가 거꾸로다.

### 판정을 칼이 뻗는 프레임으로 옮긴다

근접 판정은 지금 **버튼을 누른 프레임**에 일어난다. 애니메이션을 붙이면 **아직 휘두르지
않았는데 적이 죽는다.** 프레임마다 알파 범위를 재서 칼이 언제 나가는지 확인했다.

```
char_attack_right  6프레임, 각 32x48

frame 0   폭 12   몸만 있다. idle 과 같은 폭이다
frame 1   폭 13   거의 몸만. 위로 7픽셀 올라간다 (치켜든다)
frame 2   폭 21   오른쪽으로 뻗었다        <- 여기서 칼이 나간다
frame 3   폭 21   뻗은 상태
frame 4   폭 21   뻗은 상태
frame 5   폭 12   거뒀다
```

**예비 동작이 둘이라 어긋남이 애니메이션 길이의 3분의 1이다.** 길이를 공격 간격에 맞추므로
활은 0.05초, 검은 0.17초쯤 된다. 활은 거의 안 보이지만 검은 보인다.

**애니메이션 이벤트가 `frame 2` 에서 공격을 부른다.** 입력에서 판정까지 간격의 3분의 1만큼
지연이 생기는데, 느린 무기일수록 길어지는 것이 오히려 맞는 방향이다. 묵직한 무기가 늦게 나간다.

**예비 동작 둘을 버리고 `frame 2` 부터 재생하는 안을 버렸다.** 지연도 불일치도 없앨 수 있지만
칼을 휘두르는 동작 자체가 사라진다. 근접 무기가 둘(검, 창)인 게임에서 휘두르는 그림이
읽히지 않으면 무기를 바꾼 티가 나지 않는다.

애니메이션 이벤트가 메서드 이름을 문자열로 가리키는 것은 사실이지만, `unity-csharp.md` 가
금지한 목록(`SendMessage`, `Invoke("이름")`, `Animator.Play("이름")`)에 없고 에디터에서
찍는 것이라 성격이 다르다.

### 공격 한 번에 쓸 값은 시작할 때 묶는다

판정이 뒤로 밀리면 **버튼을 누른 때와 공격이 나가는 때 사이에 값이 바뀔 수 있다.**

```
무기      휘두르는 중에 숫자 키로 바꾸면 든 적 없는 무기로 공격이 나간다
조준 방향  마우스를 돌리면 몸이 보는 쪽과 판정이 나가는 쪽이 갈린다
공격력    그 사이에 아이템을 먹는 경우는 전투 중이라 없지만 같은 성격이다
```

**공격을 시작할 때 무기와 방향과 피해량을 묶어 두고 이벤트가 그것을 쓴다.** 몸이 이미
그쪽으로 돌아간 상태로 휘두르므로 그림과 판정이 맞는다. 하데스나 소울류가 공격 시작에
방향을 고정하는 것과 같다. 휘두르는 중에 판정 방향이 홱 바뀌면 예측할 수 없다.

**쿨다운은 버튼을 누른 시점에 시작한다.** 이벤트 시점으로 옮기면 간격이 지연만큼 늘어나
연사 스탯이 그만큼 깎인다.

### 공격 동작은 중간에 끊기지 않게 한다

애니메이션이 중단되면 **이벤트가 불리지 않아 공격이 소실된다.** 쿨다운은 이미 돌아간 뒤다.

이것을 코드 안전망으로 막지 않는다. **Animator 에서 공격 상태가 끝까지 재생되도록 전환
조건을 거는 것이 원인 쪽 처리다.** 걷기와 멈춤으로 돌아가는 전환에 `Exit Time` 을 두면
공격 중에는 다른 상태로 가지 않는다.

### 공격 프레임만 크기가 다르다

```
char_idle_right    16x16   6프레임
char_run_right     16x16   6프레임
char_attack_right  32x48   6프레임     무기를 휘두르는 범위까지 담는다
적 전부            16x16
```

`idle` 에서 `attack` 으로 넘어가는 순간 **스프라이트의 크기가 바뀐다.** 피벗이 맞지 않으면
캐릭터가 그 프레임에 튄다. 두 스프라이트에서 캐릭터 몸이 프레임 안 어디에 있는지 재서
피벗을 맞춘다. **끼우기 전에 알파 범위를 측정한다.**

## 검증

**EditMode 테스트**: 해당 없음. Animator 와 스프라이트라 씬 없이는 확인되지 않는다.

**플레이모드 체크리스트**

- [ ] 가만히 있으면 제자리 동작이 돈다
- [ ] 움직이면 걷는 동작이 돈다
- [ ] 벽에 막혀 못 가는 동안에는 제자리 동작이다
- [ ] 좌우를 바꿔도 동작이 이어진다. 처음 프레임으로 튀지 않는다
- [ ] 공격하면 휘두르는 동작이 한 번 돌고 돌아온다
- [ ] **공격하는 순간 캐릭터가 위아래로 튀지 않는다** (프레임 크기가 바뀌는 자리)
- [ ] 연사 아이템을 먹어도 휘두르기가 밀리지 않는다
- [ ] **칼이 뻗은 순간에 적이 맞는다.** 휘두르기 시작에 죽지 않는다
- [ ] 휘두르는 중에 마우스를 돌려도 판정은 시작할 때 본 쪽으로 나간다
- [ ] 휘두르는 중에 숫자 키로 무기를 바꿔도 그 공격은 들고 있던 무기로 나간다
- [ ] 휘두르는 중에 움직여도 동작이 끊기지 않고 공격이 소실되지 않는다
- [ ] 연사를 최대로 올려도 공격이 빠지지 않는다
- [ ] 무기를 셋 다 바꿔 봐도 같은 동작이 돈다
- [ ] 적 여섯이 멈춤과 이동을 구분해 보여준다
- [ ] 돌진 적이 돌진할 때 멈춘 그림이 아니다
- [ ] 보스가 움직일 때 걷는 동작이다
- [ ] 콘솔에 예외가 없다

## 계단

```
1.  플레이어 idle 과 run         완료
2-A 플레이어 attack 동작          완료
2-B 판정을 frame 2 로            완료
3-A 공통 Controller 와 적 하나    완료
3-B 나머지 넷                    완료
4.  공격 동작이 따로 있는 적       Bomberplant 하나다. 나머지는 run_attack 으로 합쳐져 있다
5.  보스                        idle 과 run 만. 패턴별 동작은 경계 밖이다
```

1을 먼저 하는 이유는 **속도로 상태를 가르는 규칙이 여기서 정해지고 나머지가 그것을 쓰기 때문**이다.
임계값이 맞는지도 플레이어에서 먼저 본다.

2를 둘로 쪼갠 것은 **보이는 것과 맞는 것을 따로 확인하기 위해서다.** 2-A 에서 동작이
도는지만 보고, 2-B 에서 맞는 순간이 옮겨졌는지 본다. 한 번에 하면 공격이 안 나갈 때
동작 때문인지 판정 때문인지 가르기 어렵다.

3을 2보다 뒤에 둔 것은 적이 여섯이라 한 번에 여섯 군데를 고치게 되기 때문이다.
플레이어에서 모양이 굳은 뒤에 옮긴다.

## 메모

**역할 분담.** 상태를 읽어 Animator 에 넘기는 컴포넌트는 뷰 보일러플레이트라 Claude 가 써도 된다.
다만 `PlayerAttack` 과 `PlayerMotor` 를 건드리는 부분은 플레이어 컨트롤러라 직접 쓴다
(CLAUDE.md 1번). 공격이 일어났다고 알리는 자리가 거기다.

**적 여섯 중 공격 동작이 따로 있는 것은 Bomberplant 하나다.** Pinkbat 과 Spinner 는
`run_attack` 으로 합쳐져 있어 걷는 동작이 곧 공격 동작이다. 5-B 에서 그 구조에 맞춰
적을 배정해 두었다(`docs/specs/cc0-assets.md`).

**STATUS 에 적어 둔 계획이 그대로 간다.** '공격 애니메이션이 붙으면 애니메이션 이벤트로
칼이 지나가는 프레임에 맞춘다' 는 줄이 4-D 메모에 있고, 2-B 가 그것이다.

**계단 3을 3-A 와 3-B 로 쪼갰다.** 적이 다섯이라 한 번에 하면 틀렸을 때 어디가 문제인지 가려진다.
3-A 에서 `Pinkbat.controller` 하나로 구조를 굳히고, 3-B 에서 그것을 복제해 클립만 갈아 끼웠다.

**`Animator Override Controller` 를 검토했다가 버렸다.** 전환 구조를 공유해 한 번만 고치자는 것이었는데,
Override 는 **상태를 추가할 수 없어** 계단 4에서 Bomberplant 에 공격 상태를 붙일 때 막힌다.
전환이 둘뿐이고 한 번 만들면 고칠 일이 없어 공유할 이득도 작았다. 복제가 더 단순하다.

**Animator 를 건드리는 코드를 `CharacterAnimator` 한 파일로 모았다.** 처음에는 공격을 `PlayerAttack` 이
직접 넣었는데, 같은 Animator 를 두 파일이 건드리고 파라미터 해시가 흩어졌다.
Bomberplant 가 계단 4에서 `PlayAttack` 을 쓰므로 '적 대부분이 안 쓴다' 는 이유도 서지 않았다.

**애니메이션 이벤트 이름이 접근 제한자에 기대고 있었다.** `PlayerAttack` 쪽 핸들러 이름이
`OnAttackFrame` 으로 같아서 `private` 이라 안 불린다고 보고 넘어갔다. 에디터의 Duplicated Functions
목록에 `private` 메서드가 올라오는 것을 보고 `FirePendingAttack` 으로 바꿨다.
**Unity 는 접근 제한자와 무관하게 이름을 센다.**

**방을 줄인 것이 스폰 겹침을 깨웠다.** `_minSpawnDistance` 가 `6` 으로 남아 출현 지점이 한 번에
여럿 걸러졌고, 바닥 180칸 중 16칸에서 4마리 웨이브가 같은 자리에 겹쳤다. `5` 로 내려 풀었다.
애니메이션과 무관한 일인데 이 계단에서 드러났다. **방 크기에 묶인 상수를 찾은 두 번째 사례다**
(첫째는 `ObstaclePlacer` 의 구역 수).

**팩에 들어 있지만 쓰지 않는 것들.** `climbing`, `pushing`, `falling`, `shielded`,
그리고 `hit` 과 `death` 다. 이 게임에 그런 동작이 없다.
