# 포트폴리오 입구

## 왜 필요한가

**서류를 통과시키는 것은 영상과 README 와 이력서다.** 그런데 그 셋이 가리키는 곳이
흩어지면 읽는 사람이 길을 잃고, 같은 내용이 여러 곳에 적히면 고칠 때 한 곳만 고친다.
**입구마다 할 일을 먼저 가르는 것**이 이 작업이다.

## 동작 정의

### 세 겹으로 가른다

```
노션        이력서의 주 링크. 여기가 사람이 가장 많이 보는 곳이다
            영상, GIF, 기술 셋을 그림과 함께 놓고 설명한다
            긴 근거는 저장소로 링크한다

README      GitHub 에서 들어온다. 30초 판단용
            맨 위에 노션 링크를 둔다. 코드를 보러 온 사람이 읽는 문서다

docs/       더 파는 사람이 온다. 명세 32개, 결정 40개, 면접 문답은 비공개
            셋 중 사실의 출처는 여기 하나다
```

**이력서의 주 링크가 노션이므로 노션이 이력서보다 먼저 끝난다.**

### 어긋남을 막는 규칙 둘

- **`docs/` 를 노션에 복사하지 않는다.** 두 벌이 되면 한쪽만 고치는 날이 온다.
  노션은 읽히는 곳이고 `docs/` 는 근거다.
- **수치와 사실의 출처는 `docs/` 하나다.** 노션과 README 는 가리킨다.
  리소스 표를 한 곳에서만 관리하는 것과 같은 이유다 (CLAUDE.md 7번).
  같은 숫자가 네 곳에 적히면 넷이 다 달라진다.

### README 에 들어갈 것

- 한 줄 소개, **노션 링크**, 플레이 영상 링크, 실행 빌드 링크
- 조작 방법. 빌드를 받은 사람이 바로 움직일 수 있어야 한다
- 기술 세 항목. 각각 세 줄쯤이고 근거는 `docs/` 로 링크한다
- **코드 경계와 어셈블리 4분할.** 어디까지 본인 코드인지 밖에서 보여야 한다 (CLAUDE.md 7번)
- 사용 리소스 표. **맨 아래로 내린다**

### 어느 문서로 링크하는가

**지금 README 는 독자가 둘이다.** 면접관이 읽을 내용과 작업자에게 주는 운영 지시가
한 파일에 섞여 있다. 링크도 그렇다. 전수로 가렸다.

| 문서 | 판정 | 이유 |
|---|---|---|
| `design/GDD.md` | 남긴다 | 게임이 무엇인지가 여기 있다 |
| **`decisions/` 40개** | **새로 넣는다** | 가장 강한 자산인데 지금 링크가 없다 |
| **`specs/` 32개** | **새로 넣는다** | 같다 |
| `README.md` (문서 지도) | 뺀다 | '변경에 강하게 만드는 5가지 규칙', '폴더 사용법' 이다. 내부 운영 문서다 |
| `progress/STATUS.md` | 뺀다 | 아래 |
| `progress/ROADMAP.md` | **보류** | 지금은 미완 항목이 있어 '진행 중' 으로 보인다. Phase 6 이 닫히면 넣는다 |

**`STATUS.md` 를 빼는 이유.** '정리해야 할 것' 에 약점이 줄줄이 적혀 있다(페이드 겹침,
`RecordSign` 의 전제, 아무도 부르지 않는 `Restart`, 멈춘 적의 안전망).
정직한 기록이고 작업에 꼭 필요하므로 파일은 그대로 둔다. 다만 **면접관의 두 번째 클릭에
약점 목록이 오는 것**은 다른 이야기다. 서류 단계에서 공격 지점을 스스로 내주는 셈이다.
**반대 의견이 있을 수 있다.** 약점을 적어 둔 문서가 오히려 신뢰를 준다고 보는 쪽이다.
서류와 면접은 단계가 다르다고 보아 빼기로 했고, 면접에서는 이 문서가 무기가 된다.

### README 뼈대

```
제목과 한 줄 소개
가방 GIF 하나                  제목 바로 아래
링크 셋                        노션, 플레이 영상, 실행 빌드
프로젝트 정보                  엔진, 언어, 기간, 인원
기술 스택                      분류별 표. 스캔용
  그 아래 셋 각 한 줄           절을 따로 세우지 않는다. 설명은 노션으로
구조                           어셈블리 넷과 의존 방향. 한 문단
설계 기록                      링크 한 줄
조작                           접는다 (details)
사용 리소스                    접는다 (details). 맨 아래
```

**첫 화면에 보이는 것을 60줄 안쪽으로 둔다.** 전체는 100줄이고 접힌 둘이 40줄이다.

**가방 GIF 를 맨 위에 둔다.** 기준은 화려함이 아니라 **차별화**다. 보스 2페이즈 전환은
모든 액션게임에 있고 가방 격자 배치는 우리에게만 있다. 각 기능의 GIF 셋은 노션으로 보낸다.
**글만 있으면 링크를 누르지 않으므로** 맨 위 하나는 노션으로 미루지 않는다.

**'고민한 점' 은 노션에 둔다. README 에는 셋 각 한 줄이다.**
처음에는 README 에 무엇·어떻게·고민한 점 3단으로 넣었다가 뺐다(아래 계단 3 메모).
각 줄에는 **결과 하나씩만** 남긴다. '부모가 한 줄 바뀌었다', '계산이 한 번이다' 다.
설명이 아니라 **더 볼 이유**를 적는 자리다.

**조작과 사용 리소스는 `<details>` 로 접는다.** 지울 수 없는 것들이다. 조작은 빌드를 받은
사람에게 필요하고, 리소스 표는 한 곳에서만 관리하는 규칙이 있다 (CLAUDE.md 7번).
접으면 첫 화면에서 사라지고 필요한 사람만 펼친다.

**코드 스니펫을 넣지 않는다.**

### 기술 스택에 적을 것

저장소에서 확인한 것만 적는다. 없는 것(MVC, 네트워크, Addressables)은 적지 않는다.

```
게임플레이      상태 머신(FSM), 상속과 다형성, 인터페이스 기반 피격 판정,
                이벤트 기반 UI 갱신
최적화          투사체 오브젝트 풀링
데이터          ScriptableObject 데이터 주도, JSON 세이브 직렬화
알고리즘        절차적 방 배치, BFS 흐름장 길찾기, 격자 배치 유효성 검사
구조와 검증     어셈블리 분리, EditMode 유닛테스트
```

**기술 셋은 이 표 바로 아래에 세 줄로 붙인다.** 절을 따로 세우지 않는다.
두 자리가 모두 '무엇이 구현돼 있나' 이고 차이는 깊이뿐이어서 절이 둘이면 중복이 된다.

**오브젝트 풀링과 데이터 주도 설계가 여기 들어간다.** 셋으로 올리지 않아도 키워드로는
잡힌다. 현직자 조언이 가리킨 '메모리 관리, 최적화, 데이터 관리' 가 이 줄들이다.
프로파일링 수치가 나오면 그때 셋으로 올릴지 다시 본다.

**과해서 뺀 것 셋.** 면접관 눈으로 다시 보라는 요청에서 나왔다.

```
'툴' 분류          실물이 74줄 파일 하나다 (SaveFileMenu). 메뉴 5개뿐이고
                   커스텀 인스펙터도 EditorWindow 도 없다.
                   **기대를 올려놓고 실물이 작으면 그 항목만 깎이지 않는다.**
                   다른 항목까지 의심받는다
'Awake 캐싱'        기본기다. Update 에서 GetComponent 를 안 하는 것은
                   자랑거리가 아니라 안 하면 지적받는 것이다. 적으면 수준이 낮아 보인다
'GC Alloc 제거'     **'제거' 는 측정한 뒤에 쓰는 말이다.** 규칙으로 금지하고 코드에서
                   지켰지만 재지는 않았다. 프로파일링 뒤에 수치와 함께 넣는다
```

### 양을 세는 숫자는 README 에 적지 않는다

**기준은 하나다. 양을 세는 숫자는 빼고, 결과를 말하는 숫자는 남긴다.**

```
빼는 것    테스트 221개, 설계 결정 40건, 기능 명세 32건, 어셈블리 4분할,
           적 4종, 보스 1기
           '몇 개 했다' 는 양의 자랑이고, 링크를 누르거나 게임을 켜면 보이는 수다
           '적 4종' 은 넷이 같은 부모를 쓴다는 뜻이라 한 번 남겼다가 뺐다.
           '일반 적과 보스가 한 부모를 씁니다' 로 쓰면 숫자 없이 같은 말이 된다
남기는 것  '부모 클래스가 한 줄 바뀌었다'    적을수록 좋은 숫자. 결과다
           '길찾기 계산이 한 번이다'         같다
           '5x5 격자'                        게임 규칙이고 양이 아니다
           리소스 표의 '1점', '15점'         출처 기록이라 정확해야 한다. 접혀 있다
```

**숫자를 앞세우면 세는 방법을 설명해야 하는 자리가 된다.** 테스트가 그랬다. Runner 는 221 로
세고 메서드는 138개라서, 직접 세어 본 사람에게는 다르게 보인다. README 는 그 설명을 둘 자리가 아니다.

**셈법은 면접 문답 Q4 에 남겼다**(`interview/project-structure.md`).
노션과 면접에서는 숫자를 말할 수 있고, 면접관이 직접 셀 수도 있다.
**적지 않는 것과 답하지 못하는 것은 다르다.**

### 숫자를 말할 때는 세어서 말한다

README 에서는 양을 세는 숫자를 뺐지만(위), **노션과 면접에서 말할 숫자는 전부 파일에서 센 것이다.**
예측해 적지 않는다. 아래가 센 결과다.

```
조작              무기 교체 1 2 3 은 #if UNITY_EDITOR 라 조작표에서 뺀다
```

### 노션 뼈대

```
맨 위 요약 세 줄        무엇 / 스펙 / 강점. 10초 안에 판단되게
빠른 링크 표            영상, 빌드, GitHub
목차                    <table-of-contents /> 로 자동 생성
1  무엇을 만들었나       한 판의 흐름과 규모 표. 짧게. 그림이 말한다
2  기술 셋 셋            각각 문제 -> 과정 -> 해결 -> 결과
3  막혔던 것 하나        적 끼임 추적. 기술 셋에 없는 것이라 따로 둔다
4  수치                  프로파일링 전후. Phase 6 끝에 채운다
5  코드 경계와 구조      어셈블리 다이어그램. 짧게
6  저장소로 들어가는 문   링크 묶음
```

**Contact 는 빠른 링크 표에 둔다.** 맨 아래에 따로 절을 만들지 않는다. 맨 위가 10초 판단
자리이고 거기 연락처가 있으면 '연락할 수 있다' 가 바로 보인다. 두 곳에 두면 중복이다.

**문장 다듬기는 맨 마지막에 한 번에 한다.** 쓰는 중에 다듬으면 내용이 바뀔 때 또 다듬게 되고,
**같은 조사와 어미의 반복은 전체를 한 번에 봐야 잡힌다.**
다듬을 때 기준 하나를 더 본다. **게임 도메인에서는 외래어가 표준인 자리가 있다.**
'방을 비우면' 을 '방을 클리어하면' 으로 고쳐야 한다는 지적을 받았다. 번역투를 피하려다
게임 용어까지 우리말로 비튼 자리다. '스탯', '빌드', '시너지' 는 이미 외래어로 쓰고 있다.

**순서를 '문제 -> 과정 -> 해결 -> 결과' 로 고정한다.** 조사에서 가장 여러 곳에서 겹친
것이고, 게임잡의 면접관이 직접 '신입이 마주친 문제상황을 인식하고 해결해 나가는 과정이
궁금하다' 고 말했다. 같은 자료가 **'기능 나열 NO'** 를 함께 말한다.
그래서 기능 설명으로 시작하지 않고 **막힌 것**에서 시작한다.

**핵심 기능 셋만 깊게 쓴다. 단 '더 있다' 가 보여야 한다.**
셋만 쓰고 끝내면 '이것만 만들었나' 로 읽힌다. 규모 표와 기술 스택 목록이 그 역할을 한다.
세이브 직렬화, 오브젝트 풀링, 상태 머신처럼 단골 질문이 나오는 것은 **깊게 안 써도
있다는 것은 보여야 한다.**

**`<details>` 는 노션에서 작동하지 않는다.** HTML 태그가 리터럴 텍스트로 저장된다.
접으려면 `<toggle heading="...">` 을 쓴다. 쓰기 전에
`notion://docs/notion-flavored-markdown-spec` 을 읽는다. 도구가 요구하는 것이다.

### 짧게 쓰는 기준

**짧게 하는 것과 얇게 하는 것은 다르다.** 노션은 설명하는 자리라 얇게 쓰면 README 와 같은
것이 된다. **독자가 둘인 것이 문제의 핵심이다.** 서류 심사자는 제목과 첫 줄만 스캔하고,
면접 준비자는 읽는다. 그래서 **제목과 첫 줄만 읽어도 뜻이 통하게 쓰고, 깊은 것은 뒤로
미루거나 토글로 접는다.**

**깎는 순서를 정해 둔다.** '최대한 짧게' 를 규칙으로만 두면 깊이가 필요한 자리까지 깎인다.
영상 길이를 정할 때 '가방은 마지막에 깎는다' 로 같은 함정을 피했다.

```
먼저 깎을 것        곁가지 통찰, 중복, 부연 설명
                    소절 헤딩을 볼드 라벨로 (목차도 함께 짧아진다)
마지막까지 남길 것   문제 한 줄, 결과의 수치, 의도와 결과가 달랐던 자리
절대 깎지 않을 것    비교 표. 아래를 보라
```

### 글자 수가 아니라 밀도를 줄인다

**이 기준을 한 번 틀렸다가 고쳤다.** 처음에 '짧게' 를 글자 수 줄이기로 이해하고 비교 표를
문장으로 내렸다. 사용자가 **'논문 읽는 것 같다. 글이 많고 잘 들어오지 않는다'** 고 지적했다.

원인은 다섯이었고 **전부 밀도 문제**였다.

```
1  비교 표를 문장으로 내렸다      표는 눈이 훑지만 문장은 처음부터 읽어야 한다
2  문단이 3~4줄 덩어리였다        눈이 쉴 자리가 없다
3  볼드가 한 문단에 둘셋이었다     어느 것도 강조되지 않는다
4  그림이 하나도 없었다
5  모든 문단이 같은 무게였다       어디를 봐야 할지 알 수 없다
```

**5번이 '논문 같다' 의 정체다. 읽는 순서가 없었다.** 스캔하는 사람이 어디를 보고 어디를
건너뛸지 판단할 단서를 주지 않은 것이다.

그래서 이렇게 쓴다. **줄 수는 비슷하거나 늘어난다. 대신 읽힌다.**

```
비교        표로 둔다. 문장으로 내리지 않는다
결과        불릿으로 나눈다
문단        1~2줄로 끊는다
볼드        문단마다 하나
단락 경계    구분선(---)을 넣는다
구조        작은 아스키 그림으로. 글 세 줄을 대체한다
```

이력서와 자소서에도 같은 기준을 쓴다. **짧게 하는 것과 얇게 하는 것이 다른 것처럼,
짧게 하는 것과 빽빽하게 하는 것도 다르다.**

### 절 제목이 약속한 것을 본문이 지킨다

**이것도 한 번 틀렸다.** '가방 격자 배치와 시너지' 절을 쓰면서 본문을 **의존 방향 뒤집기
이야기로만** 채웠다. 시너지가 한 줄도 설명되지 않았고 배치 규칙도 없었다.
사용자가 **'중요한 것을 빼먹고 설명하는 기분'** 이라고 지적했다.

원인은 **'문제 -> 과정 -> 해결 -> 결과' 틀을 기술 문제 하나로만 채운 것**이다.
그 틀은 '막힌 것 하나' 를 요구하므로 가장 좋은 기술 이야기를 고르게 되고,
그러면 **기능 이야기가 사라진다.** 제목을 보고 온 독자가 다른 것을 읽고 나간다.

**결론도 그 기능의 결과여야 한다. 부수 효과가 아니라.**
고치기 전 결론은 '테스트가 가벼워진 것' 이었다. 그것은 의존 방향을 뒤집은 덤이다.
고친 뒤 결론은 **'뽑기 운이 아니라 배치가 빌드를 정한다'** 다. 기획서가 주장한 것을
게임이 실제로 하게 만든 것이 그 기능의 결과다.

그래서 각 절은 **이야기 둘**을 담는다.

```
기능/기획 판단    무엇을 만들었고 왜 그렇게 정했나
                  예: 인접 하나만 먼저 만들고 플레이해 보니 '다 붙이면 되는 게임' 이었다
기술 판단         만들면서 막힌 것과 그것을 푼 방법
                  예: Logic 이 Runtime 을 못 보는데 격자가 아이템 크기를 알아야 했다
```

**앞쪽이 먼저다.** 제목이 약속한 것이 그쪽이기 때문이다.

### 묻지 않은 것에 답하지 않는다

**이것도 한 번 틀렸다.** 사용자가 '두 안만 비교하고 하나를 고른 것으로 보여서 다양한 설계를
안 본 것처럼 읽힌다' 고 걱정했다. 나는 그 걱정을 **글에 적어 넣는 방식으로** 풀었다.

```
"그래서 남는 길이 둘이었습니다"        = 둘만 본 게 아니라 둘밖에 없었어요
"여기 적은 것은 정한 것 다섯 중 둘입니다"  = 이것만 한 게 아니라 더 했어요
```

사용자가 **'왜 이렇게 거슬리는지 모르겠다'** 고 했고, 원인은 이것이었다.
**읽는 사람이 하지 않은 질문에 답하면 스스로 약점을 지목하는 셈이다.**
변호는 공격을 전제한다. 글이 자기를 방어하기 시작하면 읽는 쪽이 먼저 알아챈다.

**걱정은 구조로 풀고 문장으로 풀지 않는다.** 저 걱정의 답은 두 가지였다.
전제를 밝히는 것(왜 그 둘만 남았는지)과 결정 문서로 링크하는 것이다.
**링크가 이미 '더 있다' 를 말하므로 말로 또 할 필요가 없었다.**

그리고 **숫자가 정보가 아닌 자리에 숫자를 넣지 않는다.** '둘', '다섯 중 둘' 은 정보가 아니다.
중요한 것은 왜 Logic 으로 옮길 수 없는지이고, 답은 ScriptableObject 의존이다.
README 에서 양을 세는 숫자를 뺀 것과 같은 기준인데, 노션에서 다시 들여왔다.

**내부 목표에 대한 보고를 공개 글로 옮기지 않는다.** 같은 뿌리의 다른 실수다.
보스 절의 결론을 이렇게 썼다가 지적을 받고 뺐다.

> 0줄로 끝낼 수도 있었습니다. 보스가 체력 변화를 들으려고 자기 필드를 잡았더니
> Unity 가 '같은 이름이 상속 관계에서 두 번 직렬화된다' 고 경고했습니다. (...)

`boss.md` 의 완료 조건이 **'EnemyBase 가 0줄이 목표이고, 아니면 왜인지 남긴다'** 였고
그 보고를 그대로 옮긴 것이다. **독자는 그 목표를 모르니 '왜 0줄에 집착하나' 가 된다.**
게다가 '한 줄' 도 적은데 '0줄도 가능했다' 를 덧붙이면 숫자 자랑이 두 겹이 된다.

**결정 문서와 명세는 내부 독자용이다.** 거기서 문장을 옮길 때는 그 문장이 기대는 전제가
공개 글에 있는지 본다. 없으면 다시 쓴다. 지금 결론은 '패턴을 더할 때 고치는 자리가
한 군데다' 이고, 그것은 전제 없이 읽힌다.

### 뿌리는 하나였다: 글의 주인이 독자인가 저자인가

**위의 실수 여섯을 개별 증상으로 고치다가, 사용자가 뿌리를 찾아 주었다.**

> 포트폴리오가 독자 입장에서 쓰여져야 하는데, 자꾸 저자 위주로 쓰여져서 그런 것 같아

맞다. '0줄 빼기', '변명 빼기', '단정 완화' 가 전부 같은 병의 증상이었다.

```
저자 시점    나는 0줄을 목표했는데 한 줄이 됐다. 이유는...
독자 시점    패턴을 더할 때 고치는 자리가 한 군데다
```

**기준은 '독자가 이 문장에서 무엇을 얻는가' 다.** 답이 '저자의 성실함' 뿐이면 뺀다.

**원인은 재료다.** 쓰는 재료가 결정 문서와 명세인데 그것들은 작업자용이다.
거기서 문장을 끌어오면 **저자 시점이 따라온다.**

**찾는 방법이 있다. 내부 참조가 저자 시점의 표식이다.** 여섯을 이렇게 찾아 고쳤다.

```
"기획서가 시너지 4종을 요구했는데"     -> "시너지는 네 종류인데"
"문서가 주장하는 것이 게임에 없었다"    -> "이 게임이 내세우는 것이 게임에 없었다"
"기획서 첫 줄이"                      -> "맨 위에 적은 한 줄이"
"기획서의 4종에 없는 개념"             -> (빼고 새 조건의 예를 들었다)
"선택이 존재하는 것까지만 보이면 된다"   -> "선택이 생기는 것까지만 만들었다"
"위의 다섯을 다시 짜야 하고"           -> "체력과 죽음과 길찾기를 다시 짜야 하고"
"가방 시너지가 '빌드가 갈린다' 고 본"   -> "여섯이면 조합을 고민할 만하고..."
```

**둘째가 가장 아까운 자리였다.** 이야기 자체는 좋은데 '기획서' 를 가리켜 독자가 소외됐다.
**독자는 그 한 줄을 이미 읽었다. 페이지 맨 위에 있다.** 거기를 가리키면 된다.

이력서와 자소서에도 같은 기준을 쓴다. **쓰기 전에 묻는다. 이 문장이 가리키는 것을
독자가 아는가.** 우리 문서, 우리 목표, 앞 문단의 개수 세기는 독자가 모른다.

**그러다 반대쪽으로 지나쳤다.** 문장을 전부 사실로 밀었더니 **판단이 사라졌다.**
'방 프리팹은 하나입니다', '다시 만드는 코드가 없습니다' 는 사실처럼 보이지만 내가 정한 것이다.
**판단을 사실로 쓰면 포트폴리오가 코드 설명서가 된다.** 누가 그렇게 정했는지가 사라진다.

사용자가 정리해 준 기준이 이것이다.

```
구성(순서)   독자. 결론과 제약을 먼저, 과정을 뒤에
시점(주체)   저자. 단 제약은 사실로, 선택은 '내가 했다' 로
```

가르는 법은 간단하다. **제약은 내가 마주친 것이고 선택은 내가 한 것이다.**

| | 어떻게 쓰나 | 예 |
|---|---|---|
| 제약과 조건 | 사실로 | 격자는 아이템을 볼 수 없습니다 |
| | | ScriptableObject 라 UnityEngine 에 의존합니다 |
| 내가 정한 것 | 저자 시점으로 | 방 프리팹은 하나로 두었습니다 |
| | | 다시 만드는 코드를 넣지 않았습니다 |

둘을 같은 말투로 쓰면 **어느 것이 내 판단인지 흐려진다.**

### 글의 형식 (확정)

**사용자가 정한 것이다. 노션, README, 이력서, 자소서에 모두 적용한다.**

```
시점    저자. 단 제약은 사실로, 선택은 '내가 했다' 로 (위 표)
구성    두괄식. 결론이 맨 앞에 온다
형식    개조식. 결론 아래의 근거는 불릿으로 나눈다
```

한 단락의 모양은 이렇다.

```
**결론 한 줄**          볼드. 산문 한 문장

- 근거 하나             짧게. 한 줄
- 근거 둘
- 근거 셋
```

**모든 것을 불릿으로 만들지는 않는다.** 산문과 불릿이 섞여야 리듬이 생긴다.

```
산문으로 둘 것    각 단락의 첫 줄(결론), 고른 안을 밝히는 문장
불릿으로 낼 것    근거, 제약 나열, 얻은 것
표로 둘 것        안 비교, 패턴 목록, 규모
```

**존댓말은 유지한다.** 명사형 종결('최적 배치가 자명')은 이력서의 형식이고,
읽는 문서에는 딱딱하다. 불릿 안에서도 '~습니다' 로 쓰되 **문장을 짧게** 끊는다.

### 기법 이름은 본문에 있어야 한다

결론을 앞세우며 **기법 이름을 빼먹었다.** 셋이 제목에만 있고 본문에서 사라졌다.

```
'상속'       3절에 없었다. "같은 부모 클래스를 씁니다" 로만 적혀 있었다
'상태 머신'   3절에 없었다. '상태' 는 있지만 기법 이름이 없었다
'흐름장'     4절에 없었다. 제목에만 있었다
```

**서류를 스캔하는 사람은 그 단어를 찾는다.** 제목에만 있으면 본문에서 확인되지 않는다.
조사에서 '기법 이름 중심으로 쓴다' 가 쿡앱스와 arena5045 둘에서 겹친 이유가 이것이다.
글을 고칠 때마다 **기법 이름이 살아 있는지 함께 본다.**

### 모르는 것은 그림으로 보인다

'가지가 뻗는 배치를 먼저 설계했다가 버렸습니다' 라고만 써서 **독자가 모양을 상상할 수
없었다.** 사용자가 '무엇인지 모르니까 답답하게 느껴졌다' 고 했다.

실제 배치 하나를 그려 넣어 풀었다. 격자 그림을 보면 갈림길이 없다는 것이 바로 보이고,
바로 뒤의 '가지 끝에 둘 것이 없다' 가 이해된다.

```
4 5 6
3 2 7
0 1 .
```

**이 예시는 작업 중에 이미 통한 것이다.** 방 배치를 설명할 때 같은 그림 하나로 걷기와 문과
방 놓기와 카메라까지 이어 쓰자 이해가 이어졌다. 글에서 설명이 막히면 **새 비유를 만들기
전에 작업 중에 통했던 그림이 있는지 본다.**

### 노션에 넣지 않을 것

들어가면 역효과인 것들이다.

```
명세 32개와 결정 40개의 전문        저장소에 있다. 링크로 보낸다
계단별 진행 기록                    과정을 그대로 옮기면 읽는 사람이 지친다

코드 전문                           스니펫 몇 줄까지다

커밋 수를 성과로 내세우는 것         수를 자랑하면 수를 센다

```

**실패한 시도는 한두 개만 깊게 쓴다.** 많이 늘어놓으면 성실함이 아니라 불안으로 읽힌다.

  둔다' 는 설명은 공개된 상태**다. 가려 둔 것의 존재를 알려주는 셈이다.

  README 에서 그 문서로 가는 링크를 빼는 것은 여기서 한다.

  원인은 조사 결과의 대상을 잘못 읽은 것이다. '의도와 장단점을 적는다' 가 세 출처에서 겹쳤는데,
  **그것을 둔 자리가 포트폴리오 문서였고 우리에게 그 자리는 노션이다.** 참고한 arena5045 조차
  README 에서는 요약만 하고 상세를 노션으로 보냈다. 사례가 사용자 안과 같았는데 내가 README 로 끌어왔다.

  금지한다. 세 줄이었고 전수로 찾아 고쳤다.
