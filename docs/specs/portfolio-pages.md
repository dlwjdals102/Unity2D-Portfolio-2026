# 포트폴리오 입구

## 왜 필요한가

**서류를 통과시키는 것은 영상과 README 와 이력서다.** 그런데 그 셋이 가리키는 곳이
흩어지면 읽는 사람이 길을 잃고, 같은 내용이 여러 곳에 적히면 고칠 때 한 곳만 고친다.
**입구마다 할 일을 먼저 가르는 것**이 이 작업이다.

## 확정 규칙 (2026-11-01)

**쓰기 전에 이 절만 본다.** 아래 `동작 정의` 는 각 규칙이 왜 생겼는지의 기록이고,
`메모` 는 조사한 표본이다. 쓰면서 그쪽을 뒤지지 않는다.

이 절은 2026-11-01 의 조사를 거쳐 확정했다. 표본과 출처는 `메모 / 계단 2` 에 있다.

**빌드를 영상보다 앞에 두는 이유.** 영어권 가이드가 `빌드를 직접 만져 보는 것이 영상보다
유용하다` 고 적는다. game feel 과 폴리싱은 영상으로 전달되지 않는다. 그리고 **크래프톤
지원서의 허용 파일 형식에 실행 파일도 압축 파일도 없다.** 빌드를 내려면 링크밖에 길이 없다.

**표 아래에 토글을 두는 이유.** 표는 키워드이지 설명이 아니다. `투사체 오브젝트 풀링` 이라고
적혀 있어도 어떻게 했는지 알 길이 없고 링크도 없다. **실물 표본들이 표만으로 끝낸 것은
프로젝트가 여럿이라 표도 여럿이기 때문**이고, 우리는 프로젝트 하나에 표 하나다.

토글 하나로 셋이 풀린다.

```
'더 있다' 가 키워드가 아니라 근거로 보인다
넥슨 NDC 의 '본인이 작업한 코드 위치와 간략한 설명' 을 만족한다
6절에 두려던 '어느 파일을 보면 되는지' 가 여기로 와서 자리가 맞는다
```

**토글 안이 길어지면 그것이 또 다른 절이 된다.** 항목당 한 줄로 묶고 긴 설명은 결정 문서로 보낸다.

**3절에 적 넷을 적는 이유.** 절 제목이 `적 공통 부모와 보스` 인데 본문이 보스에 쏠려,
상속한 적 넷이 각각 무엇을 하는지가 한 줄도 없었다. **절 제목이 약속한 것의 절반이 비어 있다.**
그리고 적 AI 상태 머신은 면접 단골인데 보스 것만 보였다.

### 뼈대는 최소선이지 울타리가 아니다

**쓰면서 필요한 것이 생기면 절을 더한다.** 더하기 전에 하나만 묻는다.

```
이것이 기존 절 어디에도 들어가지 않는가
  들어가면   그 절에 넣는다
  안 들어가면 새 절을 만든다
```

**조건을 하나만 둔다.** 여러 개를 걸면 쓰는 쪽이 갇힌다.

**빼지 않을 것은 넷이다.** 맨 위 요약과 링크, 기술 셋, 구조, 저장소.
조사에서 둘 이상 겹쳐 근거가 있는 것들이다. 나머지는 쓰면서 정한다.

**2026-11-01 에 사용자가 '여섯 절에 얽매이지 말라, 갇혀 있는 느낌이 든다' 고 했고 맞는 지적이다.**
조사에서 나온 것은 `핵심 셋만 깊게 쓴다` 였는데, 그것은 **깊이에 대한 말이지 절의 개수에 대한
말이 아니었다.** 내가 조사 결과를 뼈대로 옮기면서 구조까지 확정값으로 만들었다.
절 이름을 `확정 규칙` 으로 붙인 것도 닫힌 느낌을 키웠다.

괄호 안은 그 항목이 몇 개 출처에서 겹쳤는지다.

```

기법 이름 (넷)                        1절 기술 스택 표와 각 절 본문
강한 것을 앞으로 (넷)                  1절 끝의 다리가 그 역할
트러블슈팅 (합격 사례 셋)               기능 절 안에 둔다. 별도 절로 세우지 않는다
왜 이렇게 만들었나 (합격 사례 셋)        결정 문서 링크가 맡는다
알게 된 점 (셋)                       각 절 결론의 둘째 줄
시각 자료를 절 앞쪽에 (셋)              각 절의 첫 요소

```

**`한계` 를 빼지 않는다.** 2026-11-01 에 이것을 '독자가 묻지 않은 자기 평가' 라며 한 번
뺐다가 되돌렸다. 쿡앱스 합격자가 **합격 요인으로 `작업 의도, 장단점, 트러블 슈팅` 을 직접
꼽았고**, JaviLopez2 는 `수용 7명인데 5명으로만 테스트했다` 를 본문에 적는다.
**사실 진술과 자기 평가는 다르다.** 재서 아는 것은 적고, 느낌은 적지 않는다.

### 코드는 문서에 붙이지 않고 길을 낸다

세 자료가 같은 곳을 가리킨다.

```
실물 표본 다섯     포트폴리오 문서에 코드 블록 0개. 전부 GitHub 링크를 걸었다
넥슨 NDC2019      "본인이 작성한 코드를 읽을 수 있는 형태로 전달"
                  파일로 낼 경우 "본인이 작업한 코드 위치와 간략한 설명"
영어권            프로그래머인데 게임플레이 영상만 있는 것은 우려 사항
```

**문서에 코드를 붙이라는 것이 아니라 코드로 가는 길을 내라는 것이다.**
노션에 두는 코드는 **글로 설명하면 길어지는 것을 한눈에 보여줄 때만**이고, 그 밖에는
`어느 파일을 보면 되는지` 로 보낸다.

### 글의 형식과 문장

```
구성    두괄식. 결론이 맨 앞에 오고 근거가 뒤따른다
형식    개조식. 근거는 불릿으로 나눈다. 한 문단은 1~2줄
소절    헤딩 대신 볼드 라벨. 목차가 함께 짧아진다
문체    노션은 하십시오체, 명세와 결정 문서는 해라체. 한 문서 안에서 섞지 않는다
문장    무생물 주어 사동('A 가 B 를 하게 만든다'), 명사형 구문('~에 대한')을 쓰지 않는다
숫자    센 것은 쓰지 않고 잰 것만 쓴다
중복    같은 말을 두 번 하지 않는다. 뒤에 나올 말을 앞에서 미리 하지 않는다
용어    게임이 플레이어에게 보여주는 이름을 쓴다. 코드 주석의 말을 가져오지 않는다
기법    상속, 상태 머신, 흐름장, BFS, 인터페이스는 본문에 이름이 있어야 한다
표      셋 이상을 비교할 때만. 둘이면 문장, 한 열이면 불릿
```

**상세는 세 곳에 있고 셋 다 쓰면서 본다.**

```
쓰기 전 체크리스트 절              열 줄 + 절 단위 여섯
동작 정의의 '문장 규칙' 절          사동, 명사형, 문체를 표로
동작 정의의 '숫자는 센 것과 잰 것'   무엇이 센 것이고 무엇이 잰 것인지
.claude/rules/korean-style.md     조사 반복, em-dash, 따옴표
```

### 쓰는 순서

**쓰기 전에 한 번 본다.**

```
확정 규칙 절 전체            뼈대, 담을 것, 담지 않을 것, 글의 형식과 문장
빈 자리를 '자리' 로 만든다     회색 칸(callout). 체크박스는 글을 쓰면 사라진다
채울 수 있는 것은 먼저 채운다   빌드 링크가 그랬다
```

**절을 하나 쓸 때마다 넷을 돌린다. 이것만 외운다.**

```
1  check.py 를 돌린다     중복 / 사동·명사형 / 내부 참조 / 두 문장 불릿 / 숫자 / 볼드 줄 / 접속부사
2  두 문장 불릿을 본다      둘째가 새 정보인가. 부연이거나 바꿔 말하기면 뺀다
3  블록 질문 넷을 묻는다     아래. 도구가 통과해도 따로 묻는다
4  면접관 눈으로 읽는다     아래 다섯을 묻는다
```

**3번을 2026-11-02 에 더했다.** 그전에는 지적을 받은 절만 블록을 다시 봤고,
도구가 통과한 절은 문장만 다듬었다. 4절이 그렇게 남아 통독 네 판째에 지적을 받았다.
**도구는 반복을 보고 쓸모를 보지 않는다.**

```
[ ] 제목이 판정이면, 불릿이 그 대상을 먼저 밝히는가
[ ] 그림이 있으면, 읽는 법이 그림 안이나 바로 앞에 있는가
[ ] 이득을 말하는 줄이 기계를 설명한 뒤에 오는가
[ ] 절 안에서 주제가 바뀌는 자리에 다리가 있는가
```

**여섯 절을 다 쓴 뒤.**

```
4  전체에 check.py 를 all 로 돌린다   절 사이 중복과 0회인 항목이 여기서 걸린다
5  blocks.py 와 topics.py 를 돌린다   제목이 불릿을 요약하는지, 주제가 흩어졌는지
6  절 제목이 약속한 것을 항목으로 적고 본문에서 찾는다
7  leaveout.py 로 줄마다 빼 보고 남긴 이유를 적는다
8  뼈대 항목이 전부 있는지 짚는다      이것만 눈으로 한다
9  링크가 살아 있는지 본다            git ls-files 로 대조한다
10 사용자가 통독한다
```

**6번과 7번을 2026-11-02 에 더했다.** 통독 다섯 판 가운데 **마지막 판에서만 나온 것이
구멍 둘**이었고, 둘 다 앞의 검사 전부를 지나쳤다. 중복 검사는 '있는 것이 두 번 있는가' 를
보고, 6번은 **'있어야 할 것이 없는가'** 를 본다.

**2026-11-02 에 셋으로 줄였다.** 그전에는 확정 규칙, 체크리스트, 문장 규칙, 대조 목록이
넷으로 흩어져 **절마다 무엇을 볼지가 흐려졌다.** 실제로 4절에 체크리스트를 돌리지 않고 올렸고,
`0줄` 을 썼다가 지적을 받았고, 기계 검사를 따로따로 치다 통째로 빠뜨렸다.
사용자가 **'결정 구조가 너무 많아 오류가 나는 것이면 정리하자'** 고 했고 맞는 지적이다.
`CLAUDE.md` 가 말하는 대로 **규칙이 많아질수록 하나하나의 준수율이 떨어진다.**

**체크리스트와 면접관 눈은 성격이 다르다.** 앞은 **규칙을 지켰는지**를 보고,
뒤는 **읽는 사람에게 어떻게 보이는지**를 본다. 규칙을 다 지켜도 학생 티가 나거나
'그래서?' 가 나오는 자리가 남는다. 사용자가 `전문가나 면접관의 시선으로 점검한 뒤에 보여 달라,
내가 받는 것은 1차 검수를 거친 것이어야 한다` 고 해서 더한 단계다.

**면접관 눈으로 읽을 때 묻는 것 다섯.**

```
이 줄이 나를 뽑을 이유가 되는가
'그래서?' 가 나오는 자리가 있는가          맥락 없이 던져진 사실
학생 티가 나는 말이 있는가                 과목 이름 같은 분류, 교과서 말투
재지 않고 단정한 말이 있는가               '제거했다', '최적화했다'
질문하고 싶은 자리가 있는가                있으면 좋다. 단 답할 수 있어야 한다
```

**1번이 중요한 이유.** 빈 자리가 많으면 글을 아무리 고쳐도 부족해 보인다.
2026-11-01 에 글만으로 그 느낌을 없애려다 여섯 절을 두 번 다시 썼다.

**처음에는 '빈 자리를 다 채운 뒤에 글을 쓴다' 로 적었다가 그날 고쳤다.**
영상 편집은 사용자 몫이라 기다리면 글이 멈춘다. 그리고 **문제는 빈 자리가 있는 것이
아니라 그것이 글의 결핍으로 읽히는 것**이었다. 체크박스는 글을 쓰면 사라지지만
회색 칸은 자리로 남는다. 자리가 보이면 '아직 안 채운 곳' 으로 읽힌다.

## 동작 정의

**여기부터는 위 `확정 규칙` 이 왜 그렇게 정해졌는지의 기록이다.**
쓰면서 보는 곳이 아니다. 규칙을 바꾸려 할 때, 또는 왜 그렇게 정했는지 잊었을 때 본다.
스물넷이 시간순으로 쌓여 있어 쓰면서 보면 적용을 놓친다. 그래서 규칙을 앞으로 빼냈다.

**예외가 둘 있다.** `문장 규칙` 과 `숫자는 센 것과 잰 것으로 가른다` 는 근거가 아니라
규칙이고, 절을 다 쓴 뒤 한 번 더 볼 때 쓴다. 표가 길어 확정 규칙에는 요약만 두었다.

### 세 겹으로 가른다

```
노션        이력서의 주 링크. 여기가 사람이 가장 많이 보는 곳이다
            영상, GIF, 기술 셋을 그림과 함께 놓고 설명한다
            긴 근거는 저장소로 링크한다

README      GitHub 에서 들어온다. 짧게 훑고 더 볼지 정하는 자리
            맨 위에 노션 링크를 둔다. 코드를 보러 온 사람이 읽는 문서다

docs/       더 파는 사람이 온다. 명세 32개, 결정 40개, 면접 문답은 비공개
            셋 중 사실의 출처는 여기 하나다
```

**이력서의 주 링크가 노션이므로 노션이 이력서보다 먼저 끝난다.**

### 어긋남을 막는 규칙 둘

- **`docs/` 를 노션에 복사하지 않는다.** 두 벌이 되면 한쪽만 고치는 날이 온다.
  노션은 읽히는 곳이고 `docs/` 는 근거다.
- **수치와 사실의 출처는 `docs/` 하나다.** 노션과 README 는 가리킨다.
  리소스 표를 한 곳에서만 관리하는 것과 같은 이유다 (CLAUDE.md 7번).
  같은 숫자가 네 곳에 적히면 넷이 다 달라진다.

### README 에 들어갈 것

- 한 줄 소개, **노션 링크**, 플레이 영상 링크, 실행 빌드 링크
- 조작 방법. 빌드를 받은 사람이 바로 움직일 수 있어야 한다
- 기술 세 항목. 각각 세 줄쯤이고 근거는 `docs/` 로 링크한다
- **코드 경계와 어셈블리 4분할.** 어디까지 본인 코드인지 밖에서 보여야 한다 (CLAUDE.md 7번)
- 사용 리소스 표. **맨 아래로 내린다**

### 어느 문서로 링크하는가

**지금 README 는 독자가 둘이다.** 면접관이 읽을 내용과 작업자에게 주는 운영 지시가
한 파일에 섞여 있다. 링크도 그렇다. 전수로 가렸다.

| 문서 | 판정 | 이유 |
|---|---|---|
| `design/GDD.md` | 남긴다 | 게임이 무엇인지가 여기 있다 |
| **`decisions/` 40개** | **새로 넣는다** | 가장 강한 자산인데 지금 링크가 없다 |
| **`specs/` 32개** | **새로 넣는다** | 같다 |
| `README.md` (문서 지도) | 뺀다 | '변경에 강하게 만드는 5가지 규칙', '폴더 사용법' 이다. 내부 운영 문서다 |
| `progress/STATUS.md` | 뺀다 | 아래 |
| `progress/ROADMAP.md` | **보류** | 지금은 미완 항목이 있어 '진행 중' 으로 보인다. Phase 6 이 닫히면 넣는다 |

**`STATUS.md` 를 빼는 이유.** '정리해야 할 것' 에 약점이 줄줄이 적혀 있다(페이드 겹침,
`RecordSign` 의 전제, 아무도 부르지 않는 `Restart`, 멈춘 적의 안전망).
정직한 기록이고 작업에 꼭 필요하므로 파일은 그대로 둔다. 다만 **면접관의 두 번째 클릭에
약점 목록이 오는 것**은 다른 이야기다. 서류 단계에서 공격 지점을 스스로 내주는 셈이다.
**반대 의견이 있을 수 있다.** 약점을 적어 둔 문서가 오히려 신뢰를 준다고 보는 쪽이다.
서류와 면접은 단계가 다르다고 보아 빼기로 했고, 면접에서는 이 문서가 무기가 된다.

```
제목과 한 줄 소개

  그 아래 셋 각 한 줄           절을 따로 세우지 않는다. 설명은 노션으로
```

**첫 화면에 보이는 것을 60줄 안쪽으로 둔다.** 전체는 100줄이고 접힌 둘이 40줄이다.

**가방 GIF 를 맨 위에 둔다.** 기준은 화려함이 아니라 **차별화**다. 보스 2페이즈 전환은
모든 액션게임에 있고 가방 격자 배치는 우리에게만 있다. 각 기능의 GIF 셋은 노션으로 보낸다.
**글만 있으면 링크를 누르지 않으므로** 맨 위 하나는 노션으로 미루지 않는다.

**'고민한 점' 은 노션에 둔다. README 에는 셋 각 한 줄이다.**
처음에는 README 에 무엇·어떻게·고민한 점 3단으로 넣었다가 뺐다(아래 계단 3 메모).
각 줄에는 **결과 하나씩만** 남긴다. '부모가 한 줄 바뀌었다', '계산이 한 번이다' 다.
설명이 아니라 **더 볼 이유**를 적는 자리다.

**조작과 사용 리소스는 `<details>` 로 접는다.** 지울 수 없는 것들이다. 조작은 빌드를 받은
사람에게 필요하고, 리소스 표는 한 곳에서만 관리하는 규칙이 있다 (CLAUDE.md 7번).
접으면 첫 화면에서 사라지고 필요한 사람만 펼친다.

**코드 스니펫을 넣지 않는다.**

### 기술 스택에 적을 것

저장소에서 확인한 것만 적는다. 없는 것(MVC, 네트워크, Addressables)은 적지 않는다.

```
게임플레이      상태 머신(FSM), 상속과 다형성, 인터페이스 기반 피격 판정
입력과 UI       Input System 액션 맵, 이벤트 기반 UI 갱신
최적화          투사체 오브젝트 풀링
데이터          ScriptableObject 데이터 주도, 스탯과 모디파이어 중첩, JSON 세이브 직렬화
알고리즘        절차적 방 배치, BFS 흐름장 길찾기, 격자 배치 유효성 검사
구조와 검증     어셈블리 분리, EditMode 유닛테스트
```

**둘을 빠뜨렸다가 2026-11-01 에 더했다.** `스탯과 모디파이어 중첩` 과 `Input System 액션 맵` 이다.
둘 다 면접 단골이고 실물이 있는데(`Logic/Stats/` 넷, `Player/` 다섯) 표에 없었다.
**위의 '과해서 뺀 것 셋' 에도 없으므로 의도적으로 뺀 것이 아니라 빠뜨린 것이다.**
`이벤트 기반 UI 갱신` 을 게임플레이에서 `입력과 UI` 로 옮겨 한 줄에 넷이 몰리는 것을 풀었다.

**기술 셋은 이 표 바로 아래에 세 줄로 붙인다.** 절을 따로 세우지 않는다.
두 자리가 모두 '무엇이 구현돼 있나' 이고 차이는 깊이뿐이어서 절이 둘이면 중복이 된다.

**오브젝트 풀링과 데이터 주도 설계가 여기 들어간다.** 셋으로 올리지 않아도 키워드로는
잡힌다. 현직자 조언이 가리킨 '메모리 관리, 최적화, 데이터 관리' 가 이 줄들이다.
프로파일링 수치가 나오면 그때 셋으로 올릴지 다시 본다.

**과해서 뺀 것 셋.** 면접관 눈으로 다시 보라는 요청에서 나왔다.


### README 넷을 손본 결과 (2026-11-02)

**노션을 닫은 뒤에 미뤄 두었던 넷이다.** 노션이 확정돼야 무엇을 가리킬지 정해져서 미뤘다.

**하나. 링크 순서를 빌드 먼저로.** `노션 · 영상 · 빌드` 에서 `빌드 · 영상 · 노션` 으로 바꿨다.
영어권 가이드가 **빌드를 직접 만져 보는 것이 영상보다 유용하다**고 적고, 노션은 '더 읽을 것' 이다.

**둘. 어느 폴더를 보면 되는지.** 넥슨 NDC 의 `본인이 작업한 코드 위치와 간략한 설명` 이다.
노션 1절 토글은 **기술 스택 항목별**로 보내고, README 표는 **면접 단골별**로 보낸다.
자리가 겹치지 않는 이유는 README 가 저장소 안에 있어서다. 노션에 가지 않고 바로 누른다.

```
순수 로직과 그 테스트        Logic/ 과 Tests/EditMode/   주제 폴더가 짝을 이룬다
플레이어 입력과 이동, 대시     Scripts/Player/
적 상태 머신과 보스          Scripts/Enemy/
피격 판정과 체력            Scripts/Combat/
방 생성과 타일 칠하기        Scripts/Rooms/
데이터 에셋 클래스          Scripts/Data/
```

**셋. 코드 경계를 드러내는 한 줄.** 리소스 표가 접혀 있어 밖에서 보이지 않았다.
`구조` 절 첫 문단으로 올렸다. **노션 6절과 같은 문장을 쓰지 않았다.**
노션은 `어디까지가 제 코드인지 폴더로 가릅니다` 이고 README 는
`제가 쓴 코드는 Assets/_Project 안에만 있습니다` 다.

**넷. 기술 스택 표의 원본은 README 다.**

```
왜 README 인가   저장소가 사실이 있는 곳이다. 표의 항목은 코드에서 확인된다
                노션은 그 항목을 분류 표와 토글 열다섯으로 펼친 것이다
고치는 순서       README 를 고치면 노션 표와 토글, check.py 의 tech 리스트를 함께 본다
                노션의 설명 문장만 다듬는 것은 README 와 무관하다
대조             sync.py 가 두 곳의 항목을 맞춰 본다. 순서까지 본다
```

**표를 한 곳에만 두는 안은 버렸다.** README 에서 빼면 GitHub 를 먼저 여는 심사자가
키워드를 못 보고, 노션에서 빼면 주 포트폴리오가 약해진다. **문제는 두 벌인 것이 아니라
어긋나는 것**이라서 대조를 기계에 맡겼다.

**아이콘 팩 설명도 갈랐다.** 노션 6절이 **판단**(왜 뺐나)을 맡고 README 가 **운영**(어떻게
되살리나)을 맡는다. 양쪽에 같은 두 문장이 있던 것을 5어절 대조로 찾았다.

**첫 화면 62줄, 전체 99줄이다.** 접힌 둘(조작, 사용 리소스)이 37줄이다.

### 프로파일링은 다시 하지 않고, 이미 잰 것을 글로 꺼냈다 (2026-11-02)

**`프로파일링을 할지 정한다` 를 '하지 않는다' 로 닫았다.** 사용자가 안 해도 될 것 같다고
했고 맞다. 다만 **이유가 '할 가치가 없다' 가 아니라 '이미 했다' 다.**

`docs/measurements/pooling-baseline.md` 에 전후 비교가 다 들어 있다.

```
가설을 두 번 틀리고 세 번째에 맞췄다
변수를 갈랐다            동시에 살아 있는 수를 고정하고 생성 빈도만 세 배로
방법의 함정을 스스로 찾았다  FixedUpdate 가 돈 프레임끼리 비교해야 한다
예상을 먼저 적고 대조했다   0.3~0.5ms 예상, 0.40ms 실제
트레이드오프를 적었다      물리 -21%, 스크립트 +28%, Object Count +18%
```

**개발 빌드로 다시 재지 않는 이유.** 얻는 것이 '절대값을 믿을 수 있다' 하나인데
**포트폴리오에 쓰는 것은 절대값이 아니라 전후 변화율**이다. 그리고 전후 비교는
`EditorLoop` 이 18.73 과 18.79 로 같은 프레임끼리 골라 이미 성립한다.
한 웨이브 4마리 규모라 다시 재도 숫자가 커지지 않는다.

**반대 의견을 적어 둔다.** 면접관이 '개발 빌드로는 재 봤나' 를 물으면
'에디터로만 쟀고 전후 비교에는 지장이 없다고 봤습니다' 가 답이다. 약하지 않지만
강하지도 않다. 그 한 마디 때문에 빌드를 뽑을 가치는 없다고 보았다.

**진짜 문제는 그 기록이 포트폴리오에 0회였다는 것이다.** 노션과 README 양쪽에서
`측정`, `프로파일`, `GC` 가 한 번도 안 나왔고 `docs/measurements/` 링크도 없었다.
**기술 스택 표에 `최적화` 분류를 적어 두고 근거가 글에 없던 셈이다.**

```
넣은 자리 셋

기술 스택 표    최적화 분류에 '프로파일러 전후 비교' 를 더했다 (README 가 원본)
1절 토글       GC Alloc 이 프레임당 1.2KB 에서 0 으로 떨어졌다 + 측정 문서 링크
6절           '측정은 예상을 먼저 적고 결과와 대조합니다' 블록과 문서 표의 측정 행
```

**6절에 둔 이유.** 풀링 자체의 수치는 0.40ms 로 작지만 **측정을 설계한 과정**이 강하다.
6절은 '어떻게 일했나' 를 보여주는 절이라 자리가 맞는다.
확정 규칙의 `잰 방법과 한계(출처 둘에서 겹침)` 항목이 그제야 채워졌다.

**넷째 절로 올리지 않았다.** 조사 결과가 '핵심 셋만 깊게' 였고 풀링의 결과가 작다.
명세에 `프로파일링 수치가 나오면 그때 셋으로 올릴지 다시 본다` 고 적어 둔 것의 답이다.

**쓰면서 제 오류 둘을 찾았다.**

```
'세 틀은 각자의 _TEMPLATE.md 가 고정합니다'
  템플릿은 decisions 와 specs 둘에만 있다. 표에 측정 행을 더하니 더 틀려 보였다
  -> '설계 결정과 기능 명세는 각자의 _TEMPLATE.md 가 틀을 고정합니다'

'GC Alloc 이 줄 것이라 봤는데 고정이었고'
  측정 문서의 1차 가설은 '176B 로 고정' 인데, 같은 문서의 3차 표는
  '176B -> 0.7KB, 약 4배' 다. 두 진술이 어긋난다
  -> 재서 아는 교훈만 남겼다. 'Instantiate 가 네이티브 메모리를 쓰는 줄 몰라
     GC Alloc 으로 재려 했고'
```

**둘째는 측정 문서 쪽의 어긋남이라 아직 풀지 못했다.** 1차는 200/초에서, 3차는 600/초에서
쟀으니 조건이 달라 그럴 수 있다. 결정 문서는 추가 전용이라 제가 고치지 않고 남겨 둔다.
**면접에서 물으면 조건이 달랐다고 답할 수 있어야 한다.**

### 양을 세는 숫자는 README 에 적지 않는다

**기준은 하나다. 양을 세는 숫자는 빼고, 결과를 말하는 숫자는 남긴다.**

```
빼는 것    테스트 221개, 설계 결정 40건, 기능 명세 32건, 어셈블리 4분할,
           적 4종, 보스 1기
           '몇 개 했다' 는 양의 자랑이고, 링크를 누르거나 게임을 켜면 보이는 수다
           '적 4종' 은 넷이 같은 부모를 쓴다는 뜻이라 한 번 남겼다가 뺐다.
           '일반 적과 보스가 한 부모를 씁니다' 로 쓰면 숫자 없이 같은 말이 된다
남기는 것  '부모 클래스가 한 줄 바뀌었다'    적을수록 좋은 숫자. 결과다
           '길찾기 계산이 한 번이다'         같다
           '5x5 격자'                        게임 규칙이고 양이 아니다
           리소스 표의 '1점', '15점'         출처 기록이라 정확해야 한다. 접혀 있다
```

**숫자를 앞세우면 세는 방법을 설명해야 하는 자리가 된다.** 테스트가 그랬다. Runner 는 221 로
세고 메서드는 138개라서, 직접 세어 본 사람에게는 다르게 보인다. README 는 그 설명을 둘 자리가 아니다.

**셈법은 면접 문답 Q4 에 남겼다**(`interview/project-structure.md`).
면접에서는 물으면 답하고, 면접관이 직접 셀 수도 있다.
**적지 않는 것과 답하지 못하는 것은 다르다.**
노션도 적지 않는 쪽이다. 아래 '숫자는 센 것과 잰 것으로 가른다' 에서 범위를 넓혔다.

### 숫자를 말할 때는 세어서 말한다

공개 글에서는 양을 세는 숫자를 뺐지만(위), **면접에서 말할 숫자는 전부 파일에서 센 것이다.**
예측해 적지 않는다. 아래가 센 결과다.

```
테스트 221개      [Test] 138 더하기 [TestCase] 83
                  둘이 같은 메서드에 붙은 자리가 없고 다른 NUnit 속성도 없음을 확인했다
적 4종 더하기 보스 1기   SmallMeleeEnemy 는 분열로 나오는 것이라 종류에서 뺀다
아이템 15 / 무기 3 / 방 8
어셈블리          JM2D.Logic, JM2D.Runtime, JM2D.Editor, JM2D.Tests.EditMode
조작              무기 교체 1 2 3 은 #if UNITY_EDITOR 라 조작표에서 뺀다
```

### README 에서 걷을 것

줄 번호는 정비 전의 README 기준이다.

| 자리 | 지금 | 어떻게 |
|---|---|---|
| 24~25행 | `> 완성 후 채우는 항목. "무엇을 썼다"가 아니라...` | 뺀다. **작업자에게 주는 지시다** |
| 27~29행 | 비어 있는 `1. 2. 3.` | 계단 2에서 채운다 |
| 45~54행 | 아이콘 팩 라이선스 설명 네 문단 | 줄인다. 표의 라이선스 칸에서 각주 하나로 |
| 56~58행 | '스프라이트와 사운드는 Phase 5 에서 들여온다' | 뺀다. **끝난 일인데 미래형이다** |
| 60~61행 | '받는 즉시 위 표에 줄을 더한다...' | 뺀다. 이것도 작업자에게 주는 지시다 |

**운영 지시는 CLAUDE.md 의 일이고 README 의 일이 아니다.** 저장소 문서에 적어 두면
지켜질 것 같지만, 매 세션 실제로 읽히는 것은 CLAUDE.md 쪽이다. 리소스 표를 그때그때
채우는 규칙은 이미 CLAUDE.md 7번에 있다. **두 곳에 적힌 규칙은 한 곳이 낡는다.**

**표의 내용은 한 줄도 지우지 않는다.** 줄이는 것은 표 아래의 설명이다.

### 노션 뼈대를 정한 과정 (근거)

**확정된 뼈대는 맨 앞 `확정 규칙` 에 있다.** 아래는 그 뼈대가 어떻게 나왔는지와,
쓸 때 걸렸던 노션 문법이다.

```
맨 위 요약 세 줄        무엇 / 스펙 / 강점. 10초 안에 판단되게
빠른 링크 표            영상, 빌드, GitHub
목차                    <table-of-contents /> 로 자동 생성
1    무엇을 만들었나     한 판의 흐름과 규모 표. 짧게
2~4  기술 셋 셋          각각 문제 -> 과정 -> 해결 -> 결과
                        **막혔던 지점도 그 절 안에 둔다. 별도 절로 세우지 않는다**
5    구조                어셈블리 다이어그램
6    저장소              링크 묶음
(수치)                   프로파일링 뒤에 넣을지 다시 본다
```

**Contact 는 빠른 링크 표에 둔다.** 맨 아래에 따로 절을 만들지 않는다. 맨 위가 10초 판단
자리이고 거기 연락처가 있으면 '연락할 수 있다' 가 바로 보인다. 두 곳에 두면 중복이다.

**문장 다듬기는 맨 마지막에 한 번에 한다.** 쓰는 중에 다듬으면 내용이 바뀔 때 또 다듬게 되고,
**같은 조사와 어미의 반복은 전체를 한 번에 봐야 잡힌다.**
다듬을 때 기준 하나를 더 본다. **게임 도메인에서는 외래어가 표준인 자리가 있다.**
'방을 비우면' 을 '방을 클리어하면' 으로 고쳐야 한다는 지적을 받았다. 번역투를 피하려다
게임 용어까지 우리말로 비튼 자리다. '스탯', '빌드', '시너지' 는 이미 외래어로 쓰고 있다.

**순서를 '문제 -> 과정 -> 해결 -> 결과' 로 고정한다.** 조사에서 가장 여러 곳에서 겹친
것이고, 게임잡의 면접관이 직접 '신입이 마주친 문제상황을 인식하고 해결해 나가는 과정이
궁금하다' 고 말했다. 같은 자료가 **'기능 나열 NO'** 를 함께 말한다.
그래서 기능 설명으로 시작하지 않고 **막힌 것**에서 시작한다.

**핵심 기능 셋만 깊게 쓴다. 단 '더 있다' 가 보여야 한다.**
셋만 쓰고 끝내면 '이것만 만들었나' 로 읽힌다. 규모 표와 기술 스택 목록이 그 역할을 한다.
세이브 직렬화, 오브젝트 풀링, 상태 머신처럼 단골 질문이 나오는 것은 **깊게 안 써도
있다는 것은 보여야 한다.**

**`<details>` 는 노션에서 작동하지 않는다.** HTML 태그가 리터럴 텍스트로 저장된다.
접으려면 `<toggle heading="...">` 을 쓴다. 쓰기 전에
`notion://docs/notion-flavored-markdown-spec` 을 읽는다. 도구가 요구하는 것이다.

### 짧게 쓰는 기준

**짧게 하는 것과 얇게 하는 것은 다르다.** 노션은 설명하는 자리라 얇게 쓰면 README 와 같은
것이 된다. **독자가 둘인 것이 문제의 핵심이다.** 서류 심사자는 제목과 첫 줄만 스캔하고,
면접 준비자는 읽는다. 그래서 **제목과 첫 줄만 읽어도 뜻이 통하게 쓰고, 깊은 것은 뒤로
미루거나 토글로 접는다.**

**깎는 순서를 정해 둔다.** '최대한 짧게' 를 규칙으로만 두면 깊이가 필요한 자리까지 깎인다.
영상 길이를 정할 때 '가방은 마지막에 깎는다' 로 같은 함정을 피했다.

```
먼저 깎을 것        곁가지 통찰, 중복, 부연 설명
                    소절 헤딩을 볼드 라벨로 (목차도 함께 짧아진다)
마지막까지 남길 것   문제 한 줄, 결과의 수치, 의도와 결과가 달랐던 자리
절대 깎지 않을 것    비교 표. 아래를 보라
```

**상한은 볼드 결론 줄만 이어 읽어 절이 통하는가다.** 통하면 길이는 묻지 않는다.
깎는 순서만으로는 길이가 잡히지 않는다. **무엇을 먼저 버릴지는 정했는데 언제 멈출지가
없었다.** 과거 포트폴리오의 탈락 원인 후보에 분량이 있다.

**처음에 '한 절이 한 화면' 으로 적었다가 그날 고쳤다.** 다시 쓴 뒤 세어 보니 2절이 67줄,
4절이 70줄로 넘었는데, **볼드 줄만 이어 읽자 둘 다 이야기가 됐다.**

```
2절의 볼드 줄만 이어 읽기
  5x5 격자에 1칸에서 4칸을 차지하는 아이템을 놓습니다
  인접 시너지 하나만으로는 고를 것이 없었습니다
  그래서 나머지 셋을 만들었습니다. 넷이 서로 충돌하기 때문입니다
  격자는 아이템을 볼 수 없습니다
  IGridItem 인터페이스로 의존 방향을 뒤집었습니다
  뽑기 운이 아니라 배치가 빌드를 정합니다
```

**줄 수로 재면 깊이가 필요한 절까지 깎는다.** 서류 심사자가 스캔할 수 있게 하자는 것이
목적이었고, 그 목적은 볼드 줄로 재야 맞다. `짧게 쓰는 기준` 절의
'제목과 첫 줄만 읽어도 뜻이 통하게 쓴다' 와 같은 말이고, 이쪽은 측정된다.

**접는 것은 길이가 아니라 성격으로 고른다.**

```
접는다      버린 대안, 디버깅 과정
펼쳐 둔다    고른 것과 그 결과
순서        버린 대안을 먼저, 그 다음 디버깅 과정
```

2절은 버린 대안이 불릿 하나뿐이라 디버깅 과정(가로세로 버그)을 접었고, 4절은 버린 대안이
둘 있어 그쪽을 접었다. **4절의 이웃 넷과 여덟은 여덟을 고른 근거라서 펼쳐 두었다.**

### 글자 수가 아니라 밀도를 줄인다

**이 기준을 한 번 틀렸다가 고쳤다.** 처음에 '짧게' 를 글자 수 줄이기로 이해하고 비교 표를
문장으로 내렸다. 사용자가 **'논문 읽는 것 같다. 글이 많고 잘 들어오지 않는다'** 고 지적했다.

원인은 다섯이었고 **전부 밀도 문제**였다.

```
1  비교 표를 문장으로 내렸다      표는 눈이 훑지만 문장은 처음부터 읽어야 한다
2  문단이 3~4줄 덩어리였다        눈이 쉴 자리가 없다
3  볼드가 한 문단에 둘셋이었다     어느 것도 강조되지 않는다
4  그림이 하나도 없었다
5  모든 문단이 같은 무게였다       어디를 봐야 할지 알 수 없다
```

**5번이 '논문 같다' 의 정체다. 읽는 순서가 없었다.** 스캔하는 사람이 어디를 보고 어디를
건너뛸지 판단할 단서를 주지 않은 것이다.

그래서 이렇게 쓴다. **줄 수는 비슷하거나 늘어난다. 대신 읽힌다.**

```
비교        표로 둔다. 문장으로 내리지 않는다
결과        불릿으로 나눈다
문단        1~2줄로 끊는다
볼드        문단마다 하나
단락 경계    구분선(---)을 넣는다
구조        작은 아스키 그림으로. 글 세 줄을 대체한다
```

이력서와 자소서에도 같은 기준을 쓴다. **짧게 하는 것과 얇게 하는 것이 다른 것처럼,
짧게 하는 것과 빽빽하게 하는 것도 다르다.**

### 절 제목이 약속한 것을 본문이 지킨다

**이것도 한 번 틀렸다.** '가방 격자 배치와 시너지' 절을 쓰면서 본문을 **의존 방향 뒤집기
이야기로만** 채웠다. 시너지가 한 줄도 설명되지 않았고 배치 규칙도 없었다.
사용자가 **'중요한 것을 빼먹고 설명하는 기분'** 이라고 지적했다.

원인은 **'문제 -> 과정 -> 해결 -> 결과' 틀을 기술 문제 하나로만 채운 것**이다.
그 틀은 '막힌 것 하나' 를 요구하므로 가장 좋은 기술 이야기를 고르게 되고,
그러면 **기능 이야기가 사라진다.** 제목을 보고 온 독자가 다른 것을 읽고 나간다.

**결론도 그 기능의 결과여야 한다. 부수 효과가 아니라.**
고치기 전 결론은 '테스트가 가벼워진 것' 이었다. 그것은 의존 방향을 뒤집은 덤이다.
고친 뒤 결론은 **'뽑기 운이 아니라 배치가 빌드를 정한다'** 다. 기획서가 주장한 것을
게임이 실제로 하게 만든 것이 그 기능의 결과다.

그래서 각 절은 **이야기 둘**을 담는다.

```
기능/기획 판단    무엇을 만들었고 왜 그렇게 정했나
                  예: 인접 하나만 먼저 만들고 플레이해 보니 '다 붙이면 되는 게임' 이었다
기술 판단         만들면서 막힌 것과 그것을 푼 방법
                  예: Logic 이 Runtime 을 못 보는데 격자가 아이템 크기를 알아야 했다
```

**앞쪽이 먼저다.** 제목이 약속한 것이 그쪽이기 때문이다.

### 묻지 않은 것에 답하지 않는다

**이것도 한 번 틀렸다.** 사용자가 '두 안만 비교하고 하나를 고른 것으로 보여서 다양한 설계를
안 본 것처럼 읽힌다' 고 걱정했다. 나는 그 걱정을 **글에 적어 넣는 방식으로** 풀었다.

```
"그래서 남는 길이 둘이었습니다"        = 둘만 본 게 아니라 둘밖에 없었어요
"여기 적은 것은 정한 것 다섯 중 둘입니다"  = 이것만 한 게 아니라 더 했어요
```

사용자가 **'왜 이렇게 거슬리는지 모르겠다'** 고 했고, 원인은 이것이었다.
**읽는 사람이 하지 않은 질문에 답하면 스스로 약점을 지목하는 셈이다.**
변호는 공격을 전제한다. 글이 자기를 방어하기 시작하면 읽는 쪽이 먼저 알아챈다.

**걱정은 구조로 풀고 문장으로 풀지 않는다.** 저 걱정의 답은 두 가지였다.
전제를 밝히는 것(왜 그 둘만 남았는지)과 결정 문서로 링크하는 것이다.
**링크가 이미 '더 있다' 를 말하므로 말로 또 할 필요가 없었다.**

그리고 **숫자가 정보가 아닌 자리에 숫자를 넣지 않는다.** '둘', '다섯 중 둘' 은 정보가 아니다.
중요한 것은 왜 Logic 으로 옮길 수 없는지이고, 답은 ScriptableObject 의존이다.
README 에서 양을 세는 숫자를 뺀 것과 같은 기준인데, 노션에서 다시 들여왔다.

**내부 목표에 대한 보고를 공개 글로 옮기지 않는다.** 같은 뿌리의 다른 실수다.
보스 절의 결론을 이렇게 썼다가 지적을 받고 뺐다.

> 0줄로 끝낼 수도 있었습니다. 보스가 체력 변화를 들으려고 자기 필드를 잡았더니
> Unity 가 '같은 이름이 상속 관계에서 두 번 직렬화된다' 고 경고했습니다. (...)

`boss.md` 의 완료 조건이 **'EnemyBase 가 0줄이 목표이고, 아니면 왜인지 남긴다'** 였고
그 보고를 그대로 옮긴 것이다. **독자는 그 목표를 모르니 '왜 0줄에 집착하나' 가 된다.**
게다가 '한 줄' 도 적은데 '0줄도 가능했다' 를 덧붙이면 숫자 자랑이 두 겹이 된다.

**결정 문서와 명세는 내부 독자용이다.** 거기서 문장을 옮길 때는 그 문장이 기대는 전제가
공개 글에 있는지 본다. 없으면 다시 쓴다. 지금 결론은 '패턴을 더할 때 고치는 자리가
한 군데다' 이고, 그것은 전제 없이 읽힌다.

### 뿌리는 하나였다: 글의 주인이 독자인가 저자인가

**위의 실수 여섯을 개별 증상으로 고치다가, 사용자가 뿌리를 찾아 주었다.**

> 포트폴리오가 독자 입장에서 쓰여져야 하는데, 자꾸 저자 위주로 쓰여져서 그런 것 같아

맞다. '0줄 빼기', '변명 빼기', '단정 완화' 가 전부 같은 병의 증상이었다.

```
저자 시점    나는 0줄을 목표했는데 한 줄이 됐다. 이유는...
독자 시점    패턴을 더할 때 고치는 자리가 한 군데다
```

**기준은 '독자가 이 문장에서 무엇을 얻는가' 다.** 답이 '저자의 성실함' 뿐이면 뺀다.

**원인은 재료다.** 쓰는 재료가 결정 문서와 명세인데 그것들은 작업자용이다.
거기서 문장을 끌어오면 **저자 시점이 따라온다.**

**찾는 방법이 있다. 내부 참조가 저자 시점의 표식이다.** 여섯을 이렇게 찾아 고쳤다.

```
"기획서가 시너지 4종을 요구했는데"     -> "시너지는 네 종류인데"
"문서가 주장하는 것이 게임에 없었다"    -> "이 게임이 내세우는 것이 게임에 없었다"
"기획서 첫 줄이"                      -> "맨 위에 적은 한 줄이"
"기획서의 4종에 없는 개념"             -> (빼고 새 조건의 예를 들었다)
"선택이 존재하는 것까지만 보이면 된다"   -> "선택이 생기는 것까지만 만들었다"
"위의 다섯을 다시 짜야 하고"           -> "체력과 죽음과 길찾기를 다시 짜야 하고"
"가방 시너지가 '빌드가 갈린다' 고 본"   -> "여섯이면 조합을 고민할 만하고..."
```

**둘째가 가장 아까운 자리였다.** 이야기 자체는 좋은데 '기획서' 를 가리켜 독자가 소외됐다.
**독자는 그 한 줄을 이미 읽었다. 페이지 맨 위에 있다.** 거기를 가리키면 된다.

이력서와 자소서에도 같은 기준을 쓴다. **쓰기 전에 묻는다. 이 문장이 가리키는 것을
독자가 아는가.** 우리 문서, 우리 목표, 앞 문단의 개수 세기는 독자가 모른다.

**그러다 반대쪽으로 지나쳤다.** 문장을 전부 사실로 밀었더니 **판단이 사라졌다.**
'방 프리팹은 하나입니다', '다시 만드는 코드가 없습니다' 는 사실처럼 보이지만 내가 정한 것이다.
**판단을 사실로 쓰면 포트폴리오가 코드 설명서가 된다.** 누가 그렇게 정했는지가 사라진다.

사용자가 정리해 준 기준이 이것이다.

```
구성(순서)   독자. 결론과 제약을 먼저, 과정을 뒤에
시점(주체)   저자. 단 제약은 사실로, 선택은 '내가 했다' 로
```

가르는 법은 간단하다. **제약은 내가 마주친 것이고 선택은 내가 한 것이다.**

| | 어떻게 쓰나 | 예 |
|---|---|---|
| 제약과 조건 | 사실로 | 격자는 아이템을 볼 수 없습니다 |
| | | ScriptableObject 라 UnityEngine 에 의존합니다 |
| 내가 정한 것 | 저자 시점으로 | 방 프리팹은 하나로 두었습니다 |
| | | 다시 만드는 코드를 넣지 않았습니다 |

둘을 같은 말투로 쓰면 **어느 것이 내 판단인지 흐려진다.**

### 글의 형식 (확정)

**사용자가 정한 것이다. 노션, README, 이력서, 자소서에 모두 적용한다.**

```
시점    저자. 단 제약은 사실로, 선택은 '내가 했다' 로 (위 표)
구성    두괄식. 결론이 맨 앞에 온다
형식    개조식. 결론 아래의 근거는 불릿으로 나눈다
```

한 단락의 모양은 이렇다.

```
**결론 한 줄**          볼드. 산문 한 문장

- 근거 하나             짧게. 한 줄
- 근거 둘
- 근거 셋
```

**모든 것을 불릿으로 만들지는 않는다.** 산문과 불릿이 섞여야 리듬이 생긴다.

```
산문으로 둘 것    각 단락의 첫 줄(결론), 고른 안을 밝히는 문장
불릿으로 낼 것    근거, 제약 나열, 얻은 것
표로 둘 것        안 비교, 패턴 목록, 규모
```

**존댓말은 유지한다.** 명사형 종결('최적 배치가 자명')은 이력서의 형식이고,
읽는 문서에는 딱딱하다. 불릿 안에서도 '~습니다' 로 쓰되 **문장을 짧게** 끊는다.

### 성격이 다른 절로 넘어갈 때는 언질을 둔다

**'막혔던 것' 절을 넣고 나서 지적을 받았다.** 기술 셋(2~4절) 다음에 실패 이야기(5절)가
오는데 **언질이 없어 흐름이 끊긴다**는 것이다.

```
2~4절    만든 것
5절      겪은 것      <- 성격이 다른데 번호만 이어진다
6~7절    구조와 저장소
```

독자는 번호만 보고 '또 기능 설명이겠지' 하며 들어간다.

**연결점이 이미 있었는데 쓰지 않은 것이 원인이다.** 4절은 길찾기이고 5절은 조종인데,
결정 문서에 '버그가 전부 조종과 물리에서 나왔고 거리표는 한 번도 틀리지 않았다' 고
적혀 있었다. 그 한 줄이 두 절을 잇는다.

```
제목      '적이 장애물에 끼던 것' -> '가장 오래 막혔던 것'
          제목이 내용이 아니라 성격을 말하게 한다
첫 줄      '거리표는 길을 알려 줬지만, 적이 그 길을 걷는 것은 다른 문제였습니다'
          앞 절을 받아 다음 절로 넘긴다
```

**절을 새로 넣을 때는 그 절이 앞 절과 어떻게 이어지는지를 먼저 쓴다.**
이어지지 않으면 그 자리가 아니다.

놓은 다리는 셋이다. **같은 성격의 절 사이에는 놓지 않았다**(2절과 3절, 3절과 4절).

```
1 -> 2   '이 중 셋을 자세히 적었습니다. 자료 구조, 객체지향 설계, 알고리즘으로
          서로 다른 종류입니다'  왜 셋인지와 왜 그 셋인지가 함께 설명된다
4 -> 5   '거리표는 길을 알려 줬지만, 적이 그 길을 걷는 것은 다른 문제였습니다'
5 -> 6   '씬에서만 나는 버그는 로그와 기즈모로 잡고, 씬 없이 돌아가는 계산은
          테스트로 잡습니다. 그 둘을 어셈블리로 갈라 두었습니다'
```

### 실패 이야기는 '못 찾았다' 가 아니라 '어떻게 판단했나' 가 중심이다

**'막혔던 것' 절을 처음에 '추측을 넷 냈고 전부 틀렸습니다' 로 시작했다.**
사용자가 이렇게 지적했다.

> 사실 되게 단순한 문제였던 것 같은데, 우리가 너무 산으로 가서 오래 걸리지 않았어?
> 이런 건 오히려 마이너스가 될 것 같은데. 1+1을 잘못 봐서 오래 걸렸다고 하면
> 안 좋게 볼 수 있잖아

**맞는 우려다.** 원인 다섯 중 셋이 물리 설정(마찰 재질, 콜라이더 모양, 캐스트 굵기)이라
실패를 앞세우면 '기본을 몰라 오래 끌었다' 로 읽힌다.

**중심을 옮겨 풀었다.** '못 찾았다' 에서 **'덮지 않았다'** 로.

```
먼저 증상을 덮는 장치를 넣었다 (0.5초 못 움직이면 직선을 끈다)
증상이 사라졌지만 원인은 남아 있었다. 장치가 버그를 가린 것이다
떼었다. 원인은 다섯이었고 전부 물리 설정이었다
설정 셋만 고치면 되는 것을 코드 한 덩어리로 덮으려 했던 셈이다
```

**그 프레임으로 고쳐 쓴 뒤에도 사용자가 '약한 실패 이야기' 라고 판단했고, 나도 동의해 뺐다.**

**이유는 격이다.** 다른 절과 나란히 놓으면 종류가 다르다.

```
2절   의존 방향을 뒤집는 인터페이스를 설계했다     설계 능력
3절   상태 열둘을 셋으로 줄였다                  설계 능력
4절   전수 조사로 검증 코드를 없앴다              증명 능력
5절   물리 설정 셋을 몰라 헤맸다가 찾았다         ?
```

마찰 재질, 콜라이더 모양, 캐스트 굵기는 **2D 탑다운을 몇 번 만든 사람이면 처음부터
안 틀리는 것들**이다. 프레임을 바꿔도 그 사실은 남는다. 그리고 분량이 다른 절과 같았다.
**약한 이야기에 같은 자리를 주면 전체 평균이 내려간다.**

### 막혔던 지점은 기능 절 안에 둔다

**디버깅 능력은 보여야 한다.** 조사에서 게임잡 면접관이 직접 말했고 OKKY 가 역량 첫째로
꼽았다. **다만 답은 별도 절이 아니라 각 절 안이고, 원래 거기 있던 것을 내가 빼냈다.**

```
2절로 되살린 것   가방이 5x5 정사각형이라 가로세로를 뒤바꾼 버그가 테스트를 통과했다
                 6x4 테스트를 더해 드러냈다
4절로 되살린 것   적이 기둥 앞에서 꿈틀거렸다. 4방향이라 좌우 거리가 같았던 것인데,
                 넷으로 되돌려 재현하고 여덟으로 되돌려 사라지는 것까지 확인했다
```

**둘 다 설계 이야기 안에서 나오는 막힌 지점이라 격이 맞는다.**
'테스트가 못 잡은 버그' 와 '실험으로 확정한 것' 이라, 물리 설정을 몰랐던 것과 종류가 다르다.

**이것이 조사 결과를 구조로 옮기며 저지른 세 번째 같은 실수였다.**

```
고민한 점        포트폴리오 문서에 두라는 것을 README 로 가져왔다
직접 구현한 것    팀 프로젝트용 조언을 1인 프로젝트에 가져왔다
막혔던 것 하나    각 항목에 쓰라는 것을 별도 절로 만들었다
```

조사가 말한 것은 **'각 항목을 문제에서 결과로 쓰라'** 였고 별도 절을 만들라는 뜻이 아니었다.
**조사 결과를 구조로 옮길 때는 그 조언이 어느 단위를 겨냥한 것인지 본다.**

### 게임이 플레이어에게 보여주는 이름을 쓴다

**코드 주석의 용어를 공개 글로 가져왔다.** 시너지 네 종류 중 하나를 설명하며 '귀퉁이' 라고
썼는데, 사용자가 '되게 어색하다' 고 지적했다.

```
RewardPanel.cs:322   case SynergyCondition.Corner: return "모서리";   <- 화면에 뜨는 이름
BagGrid.cs:141       /// 그리드의 네 귀퉁이 칸 중...                  <- 코드 주석
```

**플레이어가 보는 이름은 '모서리' 다.** 설명에서 '귀퉁이' 를 쓰면 같은 것을 두 단어로
부르는 셈이고, 영상을 보거나 게임을 켠 사람에게는 어긋나 보인다.

**이것도 재료가 내부 문서인 데서 온 실수다**(위 '글의 주인' 항목과 같은 뿌리).
용어를 쓸 때는 **그 말이 화면에 뜨는 말인지** 본다. 코드와 주석의 용어는 내부용이다.

### 기법 이름은 본문에 있어야 한다

결론을 앞세우며 **기법 이름을 빼먹었다.** 셋이 제목에만 있고 본문에서 사라졌다.

```
'상속'       3절에 없었다. "같은 부모 클래스를 씁니다" 로만 적혀 있었다
'상태 머신'   3절에 없었다. '상태' 는 있지만 기법 이름이 없었다
'흐름장'     4절에 없었다. 제목에만 있었다
```

**서류를 스캔하는 사람은 그 단어를 찾는다.** 제목에만 있으면 본문에서 확인되지 않는다.
조사에서 '기법 이름 중심으로 쓴다' 가 쿡앱스와 arena5045 둘에서 겹친 이유가 이것이다.
글을 고칠 때마다 **기법 이름이 살아 있는지 함께 본다.**

### 모르는 것은 그림으로 보인다

'가지가 뻗는 배치를 먼저 설계했다가 버렸습니다' 라고만 써서 **독자가 모양을 상상할 수
없었다.** 사용자가 '무엇인지 모르니까 답답하게 느껴졌다' 고 했다.

실제 배치 하나를 그려 넣어 풀었다. 격자 그림을 보면 갈림길이 없다는 것이 바로 보이고,
바로 뒤의 '가지 끝에 둘 것이 없다' 가 이해된다.

```
4 5 6
3 2 7
0 1 .
```

**이 예시는 작업 중에 이미 통한 것이다.** 방 배치를 설명할 때 같은 그림 하나로 걷기와 문과
방 놓기와 카메라까지 이어 쓰자 이해가 이어졌다. 글에서 설명이 막히면 **새 비유를 만들기
전에 작업 중에 통했던 그림이 있는지 본다.**

### 문장 규칙 (2026-11-01)

근거는 `AI 한국어 문장 규칙.txt` 다. 사용자가 다시 쓰기 직전에 건넸다.
`korean-style.md` 와 겹치는 것은 적지 않고, **그 파일에 없는 것만** 아래에 둔다.

**이 규칙 하나가 통독 지적 둘의 원인이었다.** 무생물 주어 사동 구문이다.

```
"그 한 줄을 게임이 실제로 하게 만든 것이 이 기능의 결과입니다"
   -> '이게 무슨 소리야?'
"변수 이름도 뒤바뀐 뜻이 보이게 고쳤습니다"
   -> '굳이 필요없을거같아'
```

`korean-style.md` 에는 수동태 연쇄만 있어 걸리지 않았다. 사동은 주어가 사람이 아닌데
문장이 사람처럼 뭔가를 시키는 꼴이라, **읽는 쪽이 주어를 찾다 멈춘다.**

| 쓰지 않을 것 | 고치는 방향 |
|---|---|
| `A 가 B 를 하게 만든다`, `~를 가능하게 한다` | 조건절(`A 면 B 한다`)이나 사람 주어로 |
| `~에 대한`, `~에 있어서의` | 동사로 풀어 쓴다 |
| `~를 진행한다`, `~를 가지고 있다` | `한다`, `있다` |
| `가장 ~한 것 중 하나` | 통째로 뺀다 |
| `했었었다` | `했다` |
| 세미콜론, `그러나,` 처럼 문두 접속사 뒤의 쉼표 | 쓰지 않는다 |

**문체는 문서마다 하나로 고정한다.**

```
노션 포트폴리오    하십시오체    ~합니다, ~입니다
명세 / 결정 문서   해라체        ~한다, ~이다
```

**섞이는 자리가 실제로 있었다.** 지적받은 보스 절 네 문장이 **명세 문장의 어미만 바꿔
옮긴 것**이었다. 어미를 바꾸면 통과한 것처럼 보이지만 문장의 뼈대는 해라체로 남는다.
명세에서 재료를 가져올 때는 **문장을 다시 쓴다.** 어미만 갈지 않는다.

### 숫자는 센 것과 잰 것으로 가른다

README 뿐 아니라 **노션에도 센 숫자는 쓰지 않는다.** 범위를 넓힌 것이다.
사용자가 '핵심 지표를 쓰자' 고 했고, 가려 쓰기로 합의했다.

```
센 것   테스트 221개, 결정 40건, 아이템 15개, 적 4종
        링크를 누르거나 게임을 켜면 보이는 수다. 양의 자랑이 된다
잰 것   전수 조사 2,172갈래 중 막히는 경우 0가지
        부모 클래스가 한 줄 바뀌었다
        길찾기 계산이 한 번이다
        재지 않으면 알 수 없고, 무엇을 벌어 주었는지가 함께 적힌다
```

**없는 지표를 목표로 세우지 않는다.** 과거 포트폴리오의 탈락 원인 후보에 '성과 수치
없음' 이 있지만, 그 답은 프로파일링(Phase 6)을 끝내는 것이다. 수치가 생기면 그때 적는다.
**지금 없는 것을 메꾸려 하면 센 숫자를 지표처럼 꾸미게 된다.**

## 쓰기 전 체크리스트

**대조하는 자리가 셋이고, 성격이 달라 섞지 않았다.** 섞으면 열 줄이 서른 줄이 되고,
`CLAUDE.md` 가 말하는 대로 규칙이 많아질수록 하나하나의 준수율이 떨어진다.

### 스크립트

**저장소에 파일로 두지 않는다.** 포트폴리오 저장소에 글 검사 도구가 늘어날 이유가 없다.
필요할 때 아래를 임시 폴더에 그대로 만들어 쓴다.

````python
import sys
import re
from collections import Counter

sys.stdout.reconfigure(encoding='utf-8')

path = sys.argv[1]
n = int(sys.argv[2]) if len(sys.argv) > 2 else 4
# 세 번째 인자로 all 을 주면 '0회인 항목' 까지 본다. 전체 글일 때만 뜻이 있다.
whole = len(sys.argv) > 3 and sys.argv[3] == 'all'

with open(path, encoding='utf-8') as f:
    raw = f.read()

lines = raw.split('\n')
body = [(i, L) for i, L in enumerate(lines, 1) if not L.lstrip().startswith('#')]

problems = 0


def head(title):
    print('')
    print('=== ' + title + ' ===')


# 1. 중복
head('1. 중복 (' + str(n) + '어절)')
t = re.sub('```[^`]*```', ' ', raw)
t = re.sub('https?://[^ )]+', ' ', t)
t = re.sub('<[^>]+>', ' ', t)
t = re.sub('[^가-힣a-zA-Z0-9 ]', ' ', t)
w = t.split()
grams = Counter(tuple(w[i:i + n]) for i in range(len(w) - n + 1))
dups = sorted([(c, g) for g, c in grams.items() if c > 1], reverse=True)
if dups:
    problems += len(dups)
    for c, g in dups:
        print('  ' + str(c) + '회  ' + ' '.join(g))
else:
    print('  없음')

# 2. 사동, 명사형, 번역투
head('2. 사동 / 명사형 / 번역투')
bad = ['하게 만', '가능하게', '되어지', '에 대한', '에 있어서', '를 진행',
       '을 진행', '를 가지고 있', '중 하나입니다', '했었었', '를 탐색', '활용하']
found = [(i, p, L) for i, L in body for p in bad if p in L]
if found:
    problems += len(found)
    for i, p, L in found:
        print('  ' + str(i) + ': [' + p + '] ' + L.strip()[:70])
else:
    print('  없음')

# 3. 내부 참조와 목표
head('3. 내부 참조와 목표')
inner = ['목표는', '0줄', '완료 조건', '명세에 적', '기획서가', '앞에서 ', '위에서 ']
found = [(i, p, L) for i, L in body for p in inner if p in L]
found += [(i, 'N절', L) for i, L in body if re.search('[1-9]절', L)]
if found:
    problems += len(found)
    for i, p, L in found:
        print('  ' + str(i) + ': [' + p + '] ' + L.strip()[:70])
else:
    print('  없음')

# 4. 두 문장 불릿
head('4. 두 문장 불릿 (둘째가 새 정보인가)')
two = [(i, L) for i, L in body
       if L.lstrip().startswith('- ') and re.search('니다\\.\\s*\\S', L)]
if two:
    for i, L in two:
        print('  ' + str(i) + ': ' + L.strip()[:80])
else:
    print('  없음')

# 5. 기술 스택 항목과 면접 단골 (전체 글일 때만)
if whole:
    head('5. 0회인 항목')
    tech = ['상태 머신', '다형성', '피격', 'Input System', '이벤트', '풀링',
            'ScriptableObject', '모디파이어', 'JSON', '방 배치', 'BFS',
            '격자', '어셈블리', '테스트']
    interview = ['대시', '스탯', '세이브', '절차적']
    zero = [k for k in tech + interview if raw.count(k) == 0]
    if zero:
        problems += len(zero)
        for k in zero:
            print('  0회  ' + k)
    else:
        print('  없음')

# 6. 숫자
head('6. 숫자 (센 것인가 잰 것인가)')
num = [(i, L) for i, L in body
       if re.search('[0-9]', L) and 'github.com' not in L and 'mailto' not in L]
for i, L in num:
    print('  ' + str(i) + ': ' + L.strip()[:80])

# 7. 볼드 줄
head('7. 볼드 줄만 이어 읽기')
for i, L in body:
    s = L.strip()
    if s.startswith('<b>'):
        print('  ' + re.sub('<[^>]+>', '', s)[:90])

# 8. 접속부사. 개조식에서는 불릿 자체가 관계를 보이므로 군더더기다
head('8. 접속부사')
adv = ['그런데', '그리고', '그래서', '또한', '하지만', '따라서', '즉',
       '다만', '그다음', '그러므로', '게다가', '그러나', '그래도']
found = []
for i, L in body:
    whole = L.strip()
    head_ = re.sub('^<b>', '', re.sub('^-\s*', '', whole))
    for a in adv:
        if head_.startswith(a) or re.search('(니다[.,]|\. )\s*' + a + '\s', whole):
            found.append((i, a, whole))
            break
if found:
    problems += len(found)
    for i, a, L in found:
        print('  ' + str(i) + ': [' + a + '] ' + L[:70])
else:
    print('  없음')

print('')
print('=== 걸린 것 ' + str(problems) + ' 건 (4, 6, 7 은 눈으로 본다) ===')
````

**바깥 펜스가 백틱 넷인 이유.** 1번의 정규식에 백틱 셋이 들어 있다. 셋으로 감싸면 블록이 거기서 끊긴다.

### 두 번째 스크립트 (blocks.py)

**블록 안에서 제목과 불릿이 같은 말을 하는지 본다.** `check.py` 의 n-gram 이 못 잡는
자리다. 주제어의 되풀이가 섞여 나오므로 **뽑아만 주고 사람이 가른다.**

```python
# 블록 안에서 제목과 불릿이 같은 말을 하는지 본다.
# 어절의 앞 두 글자만 남겨 거칠게 어간을 잡고, 겹치는 수를 센다.
import re, sys
sys.stdout.reconfigure(encoding='utf-8')

def strip_tags(s):
    s = re.sub(r'\[[^\]]*\]\([^)]*\)', ' ', s)
    s = re.sub(r'<[^>]+>', ' ', s)
    return s.strip()

def stems(s):
    out = set()
    for w in re.findall(r'[가-힣]{2,}', s):
        out.add(w[:2])
    return out

raw = open(sys.argv[1], encoding='utf-8').read()
raw = re.sub(r'```[^`]*```', '', raw)
lines = raw.split('\n')

cur = None
block = []
def flush():
    if not cur or not block:
        return
    h = stems(cur)
    if len(h) < 2:
        return
    for b in block:
        t = stems(b)
        if not t:
            continue
        both = h & t
        if len(both) >= 2:
            print('  제목  ' + cur[:70])
            print('  겹침  ' + ' '.join(sorted(both)))
            print('  줄    ' + b[:70])
            print('')

for L in lines:
    s = L.strip()
    if s.startswith('<b>') and not s.startswith('- '):
        flush(); cur = strip_tags(s); block = []
    elif s.startswith('- '):
        if cur: block.append(strip_tags(s[2:]))
    elif s == '---' or s.startswith('#'):
        flush(); cur = None; block = []
flush()
```

### 세 번째 스크립트 (topics.py)

**한 주제가 몇 절에 흩어졌는지 본다.** 절 번호와 토글 안팎을 함께 보여, 같은 사실이
색인(1절 표와 토글)과 본문과 다른 절에 몇 번 적혔는지 한눈에 든다.
**세 자리 이상에 걸친 주제만 뽑는다.** 주제어의 자연스러운 되풀이가 섞이므로 사람이 가른다.

```python
# 한 주제가 여러 절에 흩어져 있는지 본다. 토글 안과 밖, 절 번호를 함께 보인다.
import re, sys
sys.stdout.reconfigure(encoding='utf-8')

raw = open(sys.argv[1], encoding='utf-8').read()
raw = re.sub(r'```[^`]*```', '\n', raw)
lines = raw.split('\n')

sec = '머리'
intog = False
rows = []
for L in lines:
    s = L.strip()
    m = re.match(r'^# (\d)\.', s)
    if m:
        sec = m.group(1) + '절'
    if s.startswith('<toggle>'):
        intog = True
    if s.startswith('</toggle>'):
        intog = False
        continue
    if not s or s.startswith('<') and not s.startswith('<b>'):
        continue
    t = re.sub(r'\[[^\]]*\]\([^)]*\)', ' ', s)
    t = re.sub(r'<[^>]+>', ' ', t).strip()
    if t:
        rows.append((sec, '토글' if intog else '본문', t))

words = ['장애물', '끼', '테스트', '씬', '전수 조사', '어셈블리', '인터페이스',
         'IGridItem', 'IPathField', '풀', '합격선', '회전', '시너지', '상태 패턴',
         '흐름장', 'BFS', '거리표', '데이터', '결정 문서', '커밋']
for w in words:
    hits = [(a, b, t) for a, b, t in rows if w in t]
    where = sorted(set(a + '/' + b for a, b, t in hits))
    if len(where) >= 3:
        print('=== ' + w + '  (' + str(len(hits)) + '줄, ' + ', '.join(where) + ')')
        for a, b, t in hits:
            print('   %-6s %-4s %s' % (a, b, t[:62]))
        print('')
```

### 네 번째 스크립트 (leaveout.py)

**모든 줄을 블록 단위 번호로 펼친다.** 한 줄씩 빼서 **그 블록의 제목이 여전히 받쳐지는가**를
묻는 데 쓴다. 판단은 사람이 하고, 도구는 번호와 블록 경계만 준다.
**산출물은 뺀 목록이 아니라 남긴 이유다.** 남긴 이유가 안 나오면 뺀다.

```python
# 줄마다 빼 보는 시험지. 블록 제목 아래에 그 블록의 줄을 번호로 매겨 펼친다.
# 판단은 사람이 한다. '이 줄을 빼면 제목이 여전히 받쳐지는가' 를 묻는다.
import re, sys
sys.stdout.reconfigure(encoding='utf-8')

raw = open(sys.argv[1], encoding='utf-8').read()
raw = re.sub(r'```[^`]*```', '\n[그림/코드]\n', raw)

def clean(s):
    s = re.sub(r'\[([^\]]*)\]\([^)]*\)', r'\1', s)
    return re.sub(r'<[^>]+>', '', s).strip()

n = 0
sec = '머리'
for L in raw.split('\n'):
    s = L.strip()
    m = re.match(r'^# (\d)\.\s*(.*)', s)
    if m:
        sec = m.group(1)
        print('\n' + '=' * 70)
        print('%s절  %s' % (sec, m.group(2)))
        print('=' * 70)
        continue
    if s.startswith('<callout') or s.startswith('</callout') or s.startswith('<quote') or s.startswith('</quote'):
        continue
    if s.startswith('<table-of'):
        continue
    if s == '---':
        print('   ' + '-' * 60)
        continue
    if s.startswith('<toggle>'):
        print('   [토글 시작]')
        continue
    if s.startswith('</toggle>'):
        print('   [토글 끝]')
        continue
    t = clean(s)
    if not t:
        continue
    if t.startswith('|'):
        continue
    n += 1
    kind = '불릿' if s.startswith('- ') else ('제목' if s.startswith('<b>') else '산문')
    print('%3d %s  %s' % (n, kind, t[:88]))
print('\n줄 %d 개' % n)
```

### 다섯 번째 스크립트 (sync.py)

**기술 스택 항목이 README 표와 노션 토글에서 같은지 본다.** 한쪽만 고치면 걸린다.

```python
# 기술 스택 항목이 README 표와 노션 토글에서 같은지 본다.
# 항목의 원본은 README 다. 한쪽만 고치면 여기서 걸린다.
import re, sys
sys.stdout.reconfigure(encoding='utf-8')

readme, notion = sys.argv[1], sys.argv[2]

body = open(readme, encoding='utf-8').read()
table = re.search(r'## 기술 스택\n\n(\|.*?)\n\n', body, re.S)
tech = []
for row in table.group(1).split('\n'):
    cells = [c.strip() for c in row.strip('|').split('|')]
    if len(cells) != 2 or cells[0] in ('분류', '---'):
        continue
    tech += [x.strip() for x in cells[1].split(',')]

page = open(notion, encoding='utf-8').read()
tog = re.search(r'<b>표의 항목을 어디서 볼 수 있나</b>\n(.*?)</toggle>', page, re.S)
names = re.findall(r'^- <b>([^<]+)</b>', tog.group(1), re.M)

print('README 표 %d 항목 / 노션 토글 %d 줄' % (len(tech), len(names)))
gap = 0
for t in tech:
    if t not in names:
        print('  노션 토글에 없음   ' + t); gap += 1
for t in names:
    if t not in tech:
        print('  README 표에 없음   ' + t); gap += 1
if gap == 0:
    print('  순서까지 같음' if tech == names else '  항목은 같고 순서가 다름')
```

**도구 다섯을 쓰는 순서.**

```
절을 하나 쓸 때마다   check.py
절을 다 쓴 뒤        blocks.py    제목이 불릿을 요약하지 않는지
여섯 절을 다 쓴 뒤     check.py all + topics.py
통독을 닫기 전       절 제목 대조 + leaveout.py
노션이나 README 를 고친 뒤   sync.py
```


**두 가지를 조심한다.** 정규식에 역슬래시를 쓰지 않으려고 문자 클래스를 `[^가-힣...]` 로
짰고(4번의 `니다\.` 만 예외다), `sys.stdout.reconfigure` 를 코드 안에 두었다.
**셸에서 `PYTHONIOENCODING` 을 줘도 리디렉션에는 적용되지 않아 한글이 깨진다.**
실제로 한 번 깨져서 다시 돌렸다.

## 다시 쓰기로 정한 이유 (2026-11-01)

**부분 수정으로는 통일되지 않는다.** 통독에서 열 번 고쳤고, 고칠 때마다 다른 자리가
어긋났다. 중복이 두 번 생기고 절 번호가 한 번 꼬였다.

사용자가 **'규칙이 따로 없어서 통일도 안 되어 있고 쓸데없는 내용도 많다'** 고 했다.
**진단은 조금 다르다. 규칙은 있었고, 글을 쓴 뒤에 생겼다.** 1절은 기준 셋을 거쳐
쓰였고 3절은 열다섯을 거쳤다. 절마다 적용된 기준의 수가 달라 통일될 수 없었다.

**다시 쓸 때 지킬 것.**

```
내용은 다시 고르지 않는다     기술 셋, 구조, 저장소는 조사 근거로 정했다
문장과 배치만 다시 쓴다
위 체크리스트로 절마다 대조한다
쓴 뒤 내가 먼저 대조하고, 그 다음 사용자가 통독한다
```

- **GitHub Pages 나 별도 웹사이트.** 노션이 그 역할이다
- **`docs/` 73개를 다시 쓰는 것.** 입구만 만든다
- **README 를 두 벌(짧은 것과 긴 것)로 만드는 것.** 하나다

### 통독에서 나온 문장 기준 (2026-11-02)

**다시 쓴 여섯 절을 사용자가 통독하며 지적한 다섯이다.** 셋은 기계로 넘겼고 둘은 눈으로 남는다.

**하나. 흐름 불릿은 한 줄씩이다. 두 문장이 섞이면 길이가 튄다.**
1절의 흐름 다섯 중 하나만 두 문장이었고, 그 둘째 문장(`어디에 놓느냐로 스탯과 시너지가`)은
**맨 위 quote 의 되풀이였다.** 빼자 다섯 줄이 같은 길이로 읽혔다.
규모 줄의 `무기는 검과 창과 활 중에 고릅니다` 도 흐름 첫 줄로 올려 겹침을 없앴다.

**둘. 비유로 쓴 동사는 뜻을 함께 적는다.**

> 넷을 만든 근거는 모서리와 인접이 정면으로 부딪힌다는 예상이었습니다

`부딪힌다` 가 무슨 뜻인지 글 어디에도 없었다. 바로 위 표에 `인접=뭉친다`,
`모서리=흩는다` 가 있는데 **그 표와 이 문장을 잇는 한 마디가 없었다.**
`인접은 뭉치라 하고 모서리는 흩으라 한다 / 하나를 택하면 다른 하나를 버려야 한다고 봤다`
로 풀었다. **표가 있어도 표를 읽는 법은 글이 줘야 한다.**

**셋. 문제를 늘어놓은 토글에는 메운 것이 함께 있어야 한다.**
3절의 `보스 때문에 처음 드러난 것 셋` 은 셋 중 하나만 해결을 적었다.
**결함 목록으로 읽혀 마이너스가 된다.** `증상 / 메운 것` 두 칸 표로 바꿨다.
클래스와 인터페이스 이름이 곧 해결인데 그것이 증상 쪽에 붙어 있어 전달되지 않았다.

**넷. 접속부사는 check.py 8번으로 넘겼다.** 여섯 곳이 걸렸다.
`그런데`, `그래서`, `다만`, `그다음`. **개조식에서는 불릿 자체가 관계를 보인다.**
`그런데` 를 지우고 뜻이 흐려진 자리는 **그 불릿을 블록 맨 앞으로 올려** 두괄식으로 고쳤다
(2절의 `겹침을 검사하려면 격자가 아이템 크기를 알아야 합니다`).

**다섯. 같은 뉘앙스의 반복은 n-gram 으로 안 잡힌다.** 4어절 중복 검사는 전부 통과했는데
사용자가 반복을 느꼈다. 뜻이 같고 말이 다른 것은 **패턴으로 세어야 보인다.**

```
틀렸다 / 빗나갔다           다섯 곳 -> 셋. 절마다 하나로
막았다 / 막습니다            다섯 곳 -> 둘. '거절한다', '금지한다' 로 갈랐다
한 줄도 / 한 번도            다섯 곳 -> 셋. 3절은 결론에 양보했다
넣지 / 만들지 / 두지 않았다   다섯 곳 -> 넷. 한 토글 안에 둘이던 것을 갈랐다
'~보다 ~편이'               두 곳 -> 하나
```

**이것은 도구로 못 만들었다.** 패턴 목록이 글마다 달라서, 한 번 세어 보고 사람이 고른다.
세는 방법만 적어 둔다. 본문에서 코드와 링크와 태그를 지우고 **뜻이 같은 어미나 구문을
정규식 하나로 묶어 센다.** 한 패턴이 세 곳을 넘으면 그 자리들을 나란히 놓고 본다.

**여섯. 제목이 불릿의 요약이면 둘 중 하나가 군더더기다.** 1차 수정 뒤에도 반복이 남아
`blocks.py` 를 만들었다. 블록의 제목과 그 안의 불릿에서 **어절의 앞 두 글자만 남겨** 어간을
잡고, 둘이 두 개 넘게 겹치는 자리를 뽑는다. 주제어가 되풀이되는 것은 거짓 양성이라
사람이 가른다. 열여덟 곳이 걸렸고 그중 여섯이 진짜였다.

```
테스트를 통과하던 버그가 하나 있었습니다
  - 가로세로를 뒤바꿔 읽는 버그였는데 테스트가 전부 통과했습니다   <- 제목이 이 불릿의 요약
기준을 값보다 먼저 정했습니다
  - 값을 먼저 짜면 기준을 값에 맞춰 잡게 됩니다                 <- 같은 말로 설명했다
Logic 에는 ... 것만 둡니다
  - 공통에는 게임 용어가 없는 것만 둡니다                       <- '것만 둡니다' 가 그대로
```

**일곱. 쉬운 말을 쓴다.** `뭉친다`, `흩는다` 가 대중적이지 않다는 지적을 받았다.
`서로 붙여 둔다`, `네 모서리에 떼어 둔다` 로 바꿨다.
**짧은 말과 쉬운 말은 다르다.** 짧다고 고른 말이 흔한 말인지 따로 본다.

**여덟. 블록 제목은 앞 블록에서 이어져야 한다.**

> 모양은 갈리는데 선택은 한쪽으로 기웁니다

**왜 나온 건지 모르겠다는 지적을 받았다.** 앞 블록이 '합격선을 넘었다' 로 끝나는데
이 제목은 `모양` 과 `선택` 이라는 새 말을 꺼냈고, 첫 불릿의 `가장 먼 짝`, `일곱 중 다섯` 도
앞 표와 잇는 말이 없었다. `합격선을 넘어도 고를 이유가 없는 빌드가 있습니다` 로 바꾸고
**앞 블록의 말(합격선)을 제목에 넣었다.** 한계 블록은 특히 이 다리가 없으면 튄다.

**아홉. 절의 결론 첫 줄이 절 맨 위 문장과 같으면 안 된다.**
4절의 결론이 `적이 장애물을 돌아 쫓아옵니다` 였는데, **절 맨 위 문장의 뒷부분과 똑같았다.**
결론은 그 기능의 결과여야 하므로 `장애물을 넣고도 적이 끼지 않습니다` 로 바꿨다.
4어절 중복 검사가 못 잡은 것은 절 맨 위에서는 `적은 그 장애물을` 이라 어절이 하나 달랐기 때문이다.

**그 고친 결론도 다시 지적을 받았다.** `장애물` 과 `끼` 를 둘 다 그대로 가져왔기 때문이다.
**같은 절 안에서 한 주제가 두 번 결론으로 쓰이면 안 된다.** 결국 `늘 통과하는 검사 둘을 빼고,
끼임의 원인 다섯을 고쳤습니다` 로 바꿨다. 이 절이 **걷어낸 것**이 결과다.

### 통독 3차에서 나온 기준 (2026-11-02)

**열. 잰 주체를 흐리지 않는다.**

> 손으로 따진 답을 믿을 수 없어 모든 배치를 세어 봤습니다

사용자가 **'내 기억엔 일일이 세보진 않았다'** 고 했고 맞다. 센 것은 Python 이다.
`가능한 배치를 전부 프로그램으로 돌려 봤습니다` 로 바꾸고, 토글 제목도
`어떻게 세었나` 에서 `어떻게 돌려 봤나` 로 고쳤다. 4절의 `모든 갈래를 세어 보고서야` 도 같다.
**사람이 한 일과 도구가 한 일을 같은 동사로 쓰면 과장이 된다.**

앞 블록의 마지막 불릿 한 줄로 접자 사실로 읽혔다.

```
블록으로 둘 것     과정이 있는 것. 예상 -> 쟀다 -> 빗나갔다 -> 원인

```

**열셋. 결론이 토글 안의 내용을 가리키면 안 된다.**
4절 결론을 `검사 둘과 안전망 셋을 뺐습니다` 로 썼는데 **안전망 셋은 토글 안에만 있었다.**
토글을 열지 않은 독자에게는 튄다. 본문의 두 블록(검사 둘, 원인 다섯)으로 바꿨다.

**열넷. 표나 그림이 말한 것을 불릿이 되풀이하지 않는다.**
5절의 `의존 방향이 한쪽입니다` 는 바로 위 다이어그램의 화살표와 표의 참조 열이 이미 말한다.
뒷문장(`거꾸로 참조하고 싶어지면 코드가 잘못된 자리에 있다는 신호`)만 남겼다.
3절에서도 표의 세 행을 되풀이한 불릿 하나를 걷었다.

### 통독 4차 - 고치는 범위를 빠뜨렸다 (2026-11-02)

**사용자가 '4절에는 하나도 적용되지 않은 것 같다' 고 했고 맞다.**
확인해 보니 4절에 한 수정은 여덟 건 전부 **문장 수준**이었고, 2절과 3절에서 한
**블록 재편은 4절에 한 번도 하지 않았다.**

```
2절   블록 둘을 재편하고 한 블록을 통째로 접었다
3절   토글을 표로 바꾸고 블록 제목 둘을 다시 썼다
4절   접속부사, 어미, 중복 단어만 고쳤다. 블록 구조는 손대지 않았다
```

**원인은 도구가 아니라 적용 범위다.** `check.py` 와 `blocks.py` 는 4절에도 돌렸고 다 통과했다.
**이 도구들은 반복을 보고 쓸모를 보지 않는다.** 지적을 받은 절만 블록을 다시 보고
걸리지 않은 절은 문장만 다듬은 것이 실수였다.

**그래서 절마다 블록 질문을 따로 둔다.** 아래 넷은 2절과 3절에서는 물었고 4절에서는 묻지 않았다.

```
[ ] 제목이 판정이면, 불릿이 그 대상을 먼저 밝히는가
[ ] 그림이 있으면, 읽는 법이 그림 안이나 바로 앞에 있는가
[ ] 이득을 말하는 줄이 기계를 설명한 뒤에 오는가
[ ] 절 안에서 주제가 바뀌는 자리에 다리가 있는가
```

**열다섯. 제목이 판정이면 불릿이 대상을 먼저 밝힌다.**

> 넣으려던 검사 둘이 모두 '늘 통과하는 검사' 였습니다

**'넣으려는 검사가 뭔데' 라는 지적을 받았다.** 제목이 판정부터 하고 불릿이 뒤늦게 소개했다.
두괄식의 결론은 **독자가 이미 아는 말로** 써야 한다. 불릿을 `하나는 ~입니다`,
`다른 하나는 ~입니다` 로 고쳐 대상을 먼저 세웠다.

**열여섯. 그림에는 읽는 법을 그림 안에 붙인다.**

> 배치는 격자 위를 한 줄로 걷습니다

```
4 5 6
3 2 7
0 1 .
```

**그림이 한 줄이 아니라 뭉친 네모라 '뭐지?' 가 나왔다.** `한 줄` 은 모양이 아니라
갈림길이 없다는 뜻이었는데 글이 그 말을 안 했다. 제목을 `갈림길 없이 한 줄기로 잇습니다` 로
바꾸고, **숫자와 점이 무엇인지 그림 오른쪽에 적고**, `밟은 칸은 다시 밟지 않습니다.
그림처럼 뭉쳐 보여도 길은 하나입니다` 를 불릿으로 넣었다.
**그림은 글을 돕는 것이지 글을 대신하지 않는다.**

**열여섯하고 반. 세 번 지적받은 블록은 글을 고칠 자리가 아니라 뺄 자리다.**
`넣으려던 검사 둘` 블록을 제목부터 불릿까지 두 번 다시 썼는데도 '왜 들어갔는지 모르겠다' 가
세 번째로 나왔다. 그때 물어야 할 것은 문장이 아니라 **그 블록이 본문에 있을 자리인가**였다.

```
그 블록이 하던 일     '안 만든 것' 의 이야기. 배치가 어떻게 도는지 따라오던 독자가 샜다
또 하나              다음 블록(2,172가지)과 한 서사를 둘로 쪼갠 것이었다
```

본문 두 문단으로 접고, 가지형에만 필요했던 검증은 **그 가지형을 버린 토글로 보냈다.**
블록이 하나 사라지고 숫자와 판단은 남았다. **같은 블록을 세 번 고치게 되면 블록을 뺀다.**

**열일곱. 이득은 기계를 설명한 뒤에 놓는다.**

> 적이 몇 마리든 길찾기 계산은 한 번입니다. 흐름장(flow field)을 골랐습니다

**'계산이 한 번' 이 왜 좋은지 모른 채로 먼저 나와 뜬금없었다.** 비교 대상(적마다 길을 따로
찾는 것)은 아래 토글에 있었다. 제목을 `만들어진 방 안에서 적은 흐름장으로 길을 찾습니다` 로
바꾸고, `거리표 하나를 모든 적이 함께 봅니다. 적이 몇 마리로 늘어도 BFS 는 한 번입니다` 를
기계 설명 뒤의 셋째 불릿으로 내렸다. 그 제목이 **방에서 적으로 넘어가는 다리**도 함께 맡는다.

### 통독에서 나온 문장 기준 (2026-11-01)

**여섯 절을 다 쓴 뒤 사용자가 1절부터 통독하며 지적한 것들이다.**
전부 제가 못 본 자리였고, 같은 종류가 반복됐다.

**하나. 두 단락 넘게 떨어진 것은 대명사로 가리키지 않는다.**

> 그 한 줄을 게임이 실제로 하게 만든 것이 이 기능의 결과입니다

맨 위 한 줄을 가리킨 것인데 마지막 언급이 두 단락 전이라 **독자가 찾지 못한다.**
이름을 다시 부르거나 내용을 다시 적는다. `'맨 위에 적은 한 줄이 어디에 놓느냐로
빌드가 갈린다 인데'` 처럼 쓴 자리는 통했다. 가리키고 내용을 함께 적었기 때문이다.

**둘. 자명한 것은 적지 않는다. `'~니'`, `'그래서'`, `'그런데'` 가 신호다.**

```
"따로 짜면 그 다섯을 다시 짜야 하고"            상속 안 하면 다시 짜는 건 당연하다
"전부 다시 짜면 잘 돌고 있는 적 넷을 흔듭니다"    이것도 당연하다
```

**가방 절이 깔끔했던 이유가 여기 있다.** 사실을 늘어놓고 인과는 독자가 잇는다.
보스 절은 `'~니'`, `'그래서'` 로 내가 다 이어 주어 길어졌다.
**인과를 이어 주는 말이 있으면 그 자리에 자명한 것이 끼어 있을 가능성이 높다.**

**셋. 한 절에 다른 종류를 섞지 않는다.**

보스 절(제목이 '적 공통 부모와 보스' 이므로 **구조** 이야기)에 전투 디자인이 들어가
분량이 구조 이야기보다 커졌다. 사용자가 **'전부 따로 노는 느낌'** 이라고 했다.

```
구조        상속했다 / 상태를 열둘로 안 만들었다 / 분기를 안 만들었다 / 부모를 안 고쳤다
전투 디자인  휩쓸기가 왜 필요한가 / 무기마다 만나는 패턴이 다르다   <- 뺐다
```

패턴 표는 남겼다. **'패턴 넷에 단계 셋' 이 다음 단락의 전제**이기 때문이다.
절 안의 단락들이 서로 재료를 주고받는지 본다. 안 주고받으면 그 단락은 다른 절의 것이다.

**넷. 측정값은 그것이 무엇을 벌어 주었는지와 함께 쓴다.**

`'부모 클래스는 한 줄 바뀌었습니다'` 를 세 번 손댔다. 사용자가 **'무엇을 알려주고
싶은거야'** 라고 물었다. **숫자만 있고 그 숫자가 산 것이 없었다.**

```
전    부모 클래스는 한 줄 바뀌었습니다
후    보스를 올리면서 적 넷을 건드리지 않았습니다
      - 부모 클래스에서 바뀐 것은 읽기 전용 프로퍼티 한 줄입니다
      - 적 넷의 동작이 그대로라 **다시 확인할 필요가 없었습니다**
```

마지막 줄이 숫자에 뜻을 준다. 기존 기능을 건드리면 다시 확인해야 하고 안 건드리면 안 한다.
**원인은 숫자에 집착한 것이다.** 명세의 완료 조건이 '0줄이 목표' 였고 나는 그것을
자랑거리로 여겼다. 독자에게 숫자는 뜻이 없다.

**다섯. 표의 기준.**

```
표로 둘 것     셋 이상을 같은 축으로 비교할 때. 눈이 훑는다
문장으로 낼 것   항목이 둘일 때. 칸이 길어 표가 제 일을 못 한다
불릿으로 낼 것   열이 하나일 때. 1열 표는 표가 아니다
```

2행 표 셋을 문장으로 내리고 1열 표 하나를 불릿으로 바꿨다. 남긴 표는 넷이다
(시너지 네 종류, 보스 패턴 넷, 규모, 저장소 링크).

**여섯. 명세 문장을 어미만 바꿔 옮기지 않는다.**

보스 절의 네 문장을 `boss.md:74` 에서 `'~이다'` 를 `'~입니다'` 로만 바꿔 가져왔다.
사용자가 **'번역을 잘못 돌린 건지'** 물었다.

```
'벌하는'        게임 메커니즘 설명의 압축. 독자에겐 생소하다
'성립해'        논리 용어다
'무료가 된다'    비유인데 맥락이 없으면 안 통한다
'붙음 / 중간 / 멂'  품사가 서로 다르고 '멂' 은 거의 쓰지 않는 말이다
```

### 계단 3 - 본문을 쓰며

- **숫자를 틀렸다가 고쳤다.** '설계 결정 41건' 으로 여러 문서에 적어 왔는데 **실제로는 40건**이다.
  `git ls-files docs` 가 센 41 을 그대로 썼고, 그 41 에 `_TEMPLATE.md` 가 섞여 있었다.
  README 를 쓰고 링크를 대조하다 드러났다. 네 파일 일곱 자리를 고쳤다.
  **세는 명령이 무엇을 포함하는지 보지 않은 것**이고, 이미 적힌 규칙이다.
  명세 32건은 맞았다(템플릿 포함 33).
- **처음 쓴 것이 128줄이었고, 지적을 받아 100줄로 줄였다.** 사용자가 '생각보다 정보가 많다,
  무엇이 구현돼 있다는 것만 간단히 넣고 노션에서 제대로 설명할 생각이었다' 고 했다. **맞는 지적이다.**
  계단 1에서 내가 명세에 'README 는 30초 판단용' 이라고 적었는데 128줄은 30초에 읽히지 않는다.
  **내가 정한 역할 분담을 내가 어겼다.**
  원인은 조사 결과의 대상을 잘못 읽은 것이다. '의도와 장단점을 적는다' 가 세 출처에서 겹쳤는데,
  **그것을 둔 자리가 포트폴리오 문서였고 우리에게 그 자리는 노션이다.**
  (여기에 'arena5045 조차 README 에서는 요약만 하고 상세를 노션으로 보냈다' 고 적었는데
  **2026-11-01 에 그 노션을 열어 보니 반대였다.** 자리를 옮긴 결론은 그대로 유효하지만
  근거로 든 사례는 틀렸다.)
  게다가 '고민한 점' 셋은 노션의 '기술 셋 깊게' 와 정확히 겹쳐, **내가 경계한 두 벌을 내가 만들었다.**
  고친 방식은 지우는 것이 아니라 **자리를 옮기고 접는 것**이다.
- **목록 항목에 em-dash 를 썼다가 콜론으로 고쳤다.** `korean-style.md` 가 그 용법을 명시적으로
  금지한다. 세 줄이었고 전수로 찾아 고쳤다.
- **'직접 구현한 것' 이라는 절 제목을 뺐다.** 사용자가 '굳이 얘기할 필요가 있을지' 를 물었고,
  **1인 프로젝트에서 그 제목은 변명처럼 읽힌다.** '직접 구현한 것' 이 있으면 '직접 구현하지
  않은 것' 도 있다는 뜻이 된다.
  내가 넣은 근거는 조사에서 '본인이 만든 부분을 명시한다' 가 여럿 겹친 것이었는데,
  **영어권 가이드의 원문이 'which matters for team projects' 다.** 팀 프로젝트용 조언이라고
  적혀 있고, 넥슨의 '직접 작성한 코드를 반드시' 도 팀 작업물을 걸러내려는 말이다.
  **팀 프로젝트 조언을 1인 프로젝트에 가져왔다.** 계단 3에서 '고민한 점' 을 잘못 가져온 것과
  같은 실수다. 조사 결과를 쓸 때는 **그 조언이 어떤 상황을 겨냥한 것인지** 함께 봐야 한다.
- **면접관 눈으로 다시 보라는 요청에서 과한 것 셋이 나왔다**(위 '과해서 뺀 것 셋').
  셋 다 **실물보다 커 보이게 적은 것**이었다. 거짓은 아니었고 그래서 눈에 걸리지 않았다.
  규칙으로 만들면 이렇다. **분류 이름을 보고 그 폴더를 열었을 때 기대와 맞는가.**
- **'고민한 점' 셋을 결정 문서에서 그대로 끌어왔다.** 새로 쓰지 않았다.
  가방은 '5x5 정사각형이라 가로세로 뒤바뀜이 테스트를 통과했다',
  적은 '부모가 한 줄 바뀌었다', 방은 '검증 코드를 넣지 않고 전수 조사로 증명했다' 다.
  **문서가 있으니 쓸 거리를 찾는 일이 없었다.** 그 자리에 쓸 말이 없으면 기능이 약한 것이 아니라
  판단을 기록하지 않은 것이다.
