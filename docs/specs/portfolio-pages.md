# 포트폴리오 입구

## 왜 필요한가

**서류를 통과시키는 것은 영상과 README 와 이력서다.** 그런데 그 셋이 가리키는 곳이
흩어지면 읽는 사람이 길을 잃고, 같은 내용이 여러 곳에 적히면 고칠 때 한 곳만 고친다.
**입구마다 할 일을 먼저 가르는 것**이 이 작업이다.

## 동작 정의

### 세 겹으로 가른다

```
노션        이력서의 주 링크. 여기가 사람이 가장 많이 보는 곳이다
            영상, GIF, 기술 셋을 그림과 함께 놓고 설명한다
            긴 근거는 저장소로 링크한다

README      GitHub 에서 들어온다. 30초 판단용
            맨 위에 노션 링크를 둔다. 코드를 보러 온 사람이 읽는 문서다

docs/       더 파는 사람이 온다. 명세 32개, 결정 40개, 면접 문답은 비공개
            셋 중 사실의 출처는 여기 하나다
```

**이력서의 주 링크가 노션이므로 노션이 이력서보다 먼저 끝난다.**

### 어긋남을 막는 규칙 둘

- **`docs/` 를 노션에 복사하지 않는다.** 두 벌이 되면 한쪽만 고치는 날이 온다.
  노션은 읽히는 곳이고 `docs/` 는 근거다.
- **수치와 사실의 출처는 `docs/` 하나다.** 노션과 README 는 가리킨다.
  리소스 표를 한 곳에서만 관리하는 것과 같은 이유다 (CLAUDE.md 7번).
  같은 숫자가 네 곳에 적히면 넷이 다 달라진다.

### README 에 들어갈 것

- 한 줄 소개, **노션 링크**, 플레이 영상 링크, 실행 빌드 링크
- 조작 방법. 빌드를 받은 사람이 바로 움직일 수 있어야 한다
- 기술 세 항목. 각각 세 줄쯤이고 근거는 `docs/` 로 링크한다
- **코드 경계와 어셈블리 4분할.** 어디까지 본인 코드인지 밖에서 보여야 한다 (CLAUDE.md 7번)
- 사용 리소스 표. **맨 아래로 내린다**

### 어느 문서로 링크하는가

**지금 README 는 독자가 둘이다.** 면접관이 읽을 내용과 작업자에게 주는 운영 지시가
한 파일에 섞여 있다. 링크도 그렇다. 전수로 가렸다.

| 문서 | 판정 | 이유 |
|---|---|---|
| `design/GDD.md` | 남긴다 | 게임이 무엇인지가 여기 있다 |
| **`decisions/` 40개** | **새로 넣는다** | 가장 강한 자산인데 지금 링크가 없다 |
| **`specs/` 32개** | **새로 넣는다** | 같다 |
| `README.md` (문서 지도) | 뺀다 | '변경에 강하게 만드는 5가지 규칙', '폴더 사용법' 이다. 내부 운영 문서다 |
| `progress/STATUS.md` | 뺀다 | 아래 |
| `progress/ROADMAP.md` | **보류** | 지금은 미완 항목이 있어 '진행 중' 으로 보인다. Phase 6 이 닫히면 넣는다 |

**`STATUS.md` 를 빼는 이유.** '정리해야 할 것' 에 약점이 줄줄이 적혀 있다(페이드 겹침,
`RecordSign` 의 전제, 아무도 부르지 않는 `Restart`, 멈춘 적의 안전망).
정직한 기록이고 작업에 꼭 필요하므로 파일은 그대로 둔다. 다만 **면접관의 두 번째 클릭에
약점 목록이 오는 것**은 다른 이야기다. 서류 단계에서 공격 지점을 스스로 내주는 셈이다.
**반대 의견이 있을 수 있다.** 약점을 적어 둔 문서가 오히려 신뢰를 준다고 보는 쪽이다.
서류와 면접은 단계가 다르다고 보아 빼기로 했고, 면접에서는 이 문서가 무기가 된다.

### README 뼈대

```
제목과 한 줄 소개
가방 GIF 하나                  제목 바로 아래
링크 셋                        노션, 플레이 영상, 실행 빌드
프로젝트 정보                  엔진, 언어, 기간, 인원
기술 스택                      분류별 표. 스캔용
  그 아래 셋 각 한 줄           절을 따로 세우지 않는다. 설명은 노션으로
구조                           어셈블리 넷과 의존 방향. 한 문단
설계 기록                      링크 한 줄
조작                           접는다 (details)
사용 리소스                    접는다 (details). 맨 아래
```

**첫 화면에 보이는 것을 60줄 안쪽으로 둔다.** 전체는 100줄이고 접힌 둘이 40줄이다.

**가방 GIF 를 맨 위에 둔다.** 기준은 화려함이 아니라 **차별화**다. 보스 2페이즈 전환은
모든 액션게임에 있고 가방 격자 배치는 우리에게만 있다. 각 기능의 GIF 셋은 노션으로 보낸다.
**글만 있으면 링크를 누르지 않으므로** 맨 위 하나는 노션으로 미루지 않는다.

**'고민한 점' 은 노션에 둔다. README 에는 셋 각 한 줄이다.**
처음에는 README 에 무엇·어떻게·고민한 점 3단으로 넣었다가 뺐다(아래 계단 3 메모).
각 줄에는 **결과 하나씩만** 남긴다. '부모가 한 줄 바뀌었다', '계산이 한 번이다' 다.
설명이 아니라 **더 볼 이유**를 적는 자리다.

**조작과 사용 리소스는 `<details>` 로 접는다.** 지울 수 없는 것들이다. 조작은 빌드를 받은
사람에게 필요하고, 리소스 표는 한 곳에서만 관리하는 규칙이 있다 (CLAUDE.md 7번).
접으면 첫 화면에서 사라지고 필요한 사람만 펼친다.

**코드 스니펫을 넣지 않는다.**

### 기술 스택에 적을 것

저장소에서 확인한 것만 적는다. 없는 것(MVC, 네트워크, Addressables)은 적지 않는다.

```
게임플레이      상태 머신(FSM), 상속과 다형성, 인터페이스 기반 피격 판정,
                이벤트 기반 UI 갱신
최적화          투사체 오브젝트 풀링
데이터          ScriptableObject 데이터 주도, JSON 세이브 직렬화
알고리즘        절차적 방 배치, BFS 흐름장 길찾기, 격자 배치 유효성 검사
구조와 검증     어셈블리 분리, EditMode 유닛테스트
```

**기술 셋은 이 표 바로 아래에 세 줄로 붙인다.** 절을 따로 세우지 않는다.
두 자리가 모두 '무엇이 구현돼 있나' 이고 차이는 깊이뿐이어서 절이 둘이면 중복이 된다.

**오브젝트 풀링과 데이터 주도 설계가 여기 들어간다.** 셋으로 올리지 않아도 키워드로는
잡힌다. 현직자 조언이 가리킨 '메모리 관리, 최적화, 데이터 관리' 가 이 줄들이다.
프로파일링 수치가 나오면 그때 셋으로 올릴지 다시 본다.

**과해서 뺀 것 셋.** 면접관 눈으로 다시 보라는 요청에서 나왔다.

```
'툴' 분류          실물이 74줄 파일 하나다 (SaveFileMenu). 메뉴 5개뿐이고
                   커스텀 인스펙터도 EditorWindow 도 없다.
                   **기대를 올려놓고 실물이 작으면 그 항목만 깎이지 않는다.**
                   다른 항목까지 의심받는다
'Awake 캐싱'        기본기다. Update 에서 GetComponent 를 안 하는 것은
                   자랑거리가 아니라 안 하면 지적받는 것이다. 적으면 수준이 낮아 보인다
'GC Alloc 제거'     **'제거' 는 측정한 뒤에 쓰는 말이다.** 규칙으로 금지하고 코드에서
                   지켰지만 재지는 않았다. 프로파일링 뒤에 수치와 함께 넣는다
```

### 양을 세는 숫자는 README 에 적지 않는다

**기준은 하나다. 양을 세는 숫자는 빼고, 결과를 말하는 숫자는 남긴다.**

```
빼는 것    테스트 221개, 설계 결정 40건, 기능 명세 32건, 어셈블리 4분할,
           적 4종, 보스 1기
           '몇 개 했다' 는 양의 자랑이고, 링크를 누르거나 게임을 켜면 보이는 수다
           '적 4종' 은 넷이 같은 부모를 쓴다는 뜻이라 한 번 남겼다가 뺐다.
           '일반 적과 보스가 한 부모를 씁니다' 로 쓰면 숫자 없이 같은 말이 된다
남기는 것  '부모 클래스가 한 줄 바뀌었다'    적을수록 좋은 숫자. 결과다
           '길찾기 계산이 한 번이다'         같다
           '5x5 격자'                        게임 규칙이고 양이 아니다
           리소스 표의 '1점', '15점'         출처 기록이라 정확해야 한다. 접혀 있다
```

**숫자를 앞세우면 세는 방법을 설명해야 하는 자리가 된다.** 테스트가 그랬다. Runner 는 221 로
세고 메서드는 138개라서, 직접 세어 본 사람에게는 다르게 보인다. README 는 그 설명을 둘 자리가 아니다.

**셈법은 면접 문답 Q4 에 남겼다**(`interview/project-structure.md`).
노션과 면접에서는 숫자를 말할 수 있고, 면접관이 직접 셀 수도 있다.
**적지 않는 것과 답하지 못하는 것은 다르다.**

### 숫자를 말할 때는 세어서 말한다

README 에서는 양을 세는 숫자를 뺐지만(위), **노션과 면접에서 말할 숫자는 전부 파일에서 센 것이다.**
예측해 적지 않는다. 아래가 센 결과다.

```
테스트 221개      [Test] 138 더하기 [TestCase] 83
                  둘이 같은 메서드에 붙은 자리가 없고 다른 NUnit 속성도 없음을 확인했다
적 4종 더하기 보스 1기   SmallMeleeEnemy 는 분열로 나오는 것이라 종류에서 뺀다
아이템 15 / 무기 3 / 방 8
어셈블리          JM2D.Logic, JM2D.Runtime, JM2D.Editor, JM2D.Tests.EditMode
조작              무기 교체 1 2 3 은 #if UNITY_EDITOR 라 조작표에서 뺀다
```

### README 에서 걷을 것

줄 번호는 정비 전의 README 기준이다.

| 자리 | 지금 | 어떻게 |
|---|---|---|
| 24~25행 | `> 완성 후 채우는 항목. "무엇을 썼다"가 아니라...` | 뺀다. **작업자에게 주는 지시다** |

| 45~54행 | 아이콘 팩 라이선스 설명 네 문단 | 줄인다. 표의 라이선스 칸에서 각주 하나로 |
| 56~58행 | '스프라이트와 사운드는 Phase 5 에서 들여온다' | 뺀다. **끝난 일인데 미래형이다** |

**운영 지시는 CLAUDE.md 의 일이고 README 의 일이 아니다.** 저장소 문서에 적어 두면

채우는 규칙은 이미 CLAUDE.md 7번에 있다. **두 곳에 적힌 규칙은 한 곳이 낡는다.**

**표의 내용은 한 줄도 지우지 않는다.** 줄이는 것은 표 아래의 설명이다.

## 경계 - 이 기능이 하지 않는 것

- **영어 README.** 지원하는 곳이 국내다
- **GitHub Pages 나 별도 웹사이트.** 노션이 그 역할이다
- **`docs/` 73개를 다시 쓰는 것.** 입구만 만든다
- **README 를 두 벌(짧은 것과 긴 것)로 만드는 것.** 하나다

### 노션에 넣지 않을 것

들어가면 역효과인 것들이다.

```
명세 32개와 결정 40개의 전문        저장소에 있다. 링크로 보낸다
계단별 진행 기록                    과정을 그대로 옮기면 읽는 사람이 지친다
면접 문답                           비공개로 둔 것이다
코드 전문                           스니펫 몇 줄까지다
문서 운영 규칙                      README 에서도 빼는 것인데 노션에 둘 이유가 없다
커밋 수를 성과로 내세우는 것         수를 자랑하면 수를 센다
사용 리소스 표                      README 에서만 관리한다 (CLAUDE.md 7번). 노션은 링크
```

**실패한 시도는 한두 개만 깊게 쓴다.** 많이 늘어놓으면 성실함이 아니라 불안으로 읽힌다.

- **기술 문서를 저장소 안에 만들려던 계획을 노션으로 바꿨다.** 이력서에 넣는 링크로
  노션이 사실상 표준이고, 면접관 상당수가 GitHub 를 열지 않는다.
  그림과 영상을 놓기도 마크다운보다 쉽다. **다루는 경험 자체가 손해가 아니다.**
- **노션은 사용자가 직접 채운다.** Claude 는 마크다운으로 초안을 낸다.
  노션이 마크다운 붙여넣기를 받으므로 그림과 배치만 그쪽에서 손본다.
- **링크 넷과 본문을 전수로 가렸다.** 그러다 진단이 하나 나왔다.
  **README 가 독자를 둘 섞어 쓰고 있었다.** 면접관이 읽을 내용과 작업자에게 주는
  운영 지시가 한 파일에 있다. 뺄 것 다섯 중 둘이 후자다.
  **문서를 고치기 전에 '이 줄은 누가 읽는가' 를 묻는 것으로 판정이 거의 다 갈렸다.**
- **`docs/README.md` 가 비공개로 둔 폴더를 설명하고 있다.** 76행부터 `docs/interview/` 절이 있고
  그 파일은 공개 저장소에 올라가 있다. 폴더는 `.gitignore` 로 가렸는데 **'거기에 면접 문답을
  둔다' 는 설명은 공개된 상태**다. 가려 둔 것의 존재를 알려주는 셈이다.
  이 작업에서 고치지 않고 **Phase 6 맨 끝의 저장소 정리로 넘긴다**(STATUS 에 적었다).
  README 에서 그 문서로 가는 링크를 빼는 것은 여기서 한다.

### 계단 3 - 본문을 쓰며

- **숫자를 틀렸다가 고쳤다.** '설계 결정 41건' 으로 여러 문서에 적어 왔는데 **실제로는 40건**이다.
  `git ls-files docs` 가 센 41 을 그대로 썼고, 그 41 에 `_TEMPLATE.md` 가 섞여 있었다.
  README 를 쓰고 링크를 대조하다 드러났다. 네 파일 일곱 자리를 고쳤다.
  **세는 명령이 무엇을 포함하는지 보지 않은 것**이고, 이미 적힌 규칙이다.
  명세 32건은 맞았다(템플릿 포함 33).
- **처음 쓴 것이 128줄이었고, 지적을 받아 100줄로 줄였다.** 사용자가 '생각보다 정보가 많다,
  무엇이 구현돼 있다는 것만 간단히 넣고 노션에서 제대로 설명할 생각이었다' 고 했다. **맞는 지적이다.**
  계단 1에서 내가 명세에 'README 는 30초 판단용' 이라고 적었는데 128줄은 30초에 읽히지 않는다.
  **내가 정한 역할 분담을 내가 어겼다.**
  원인은 조사 결과의 대상을 잘못 읽은 것이다. '의도와 장단점을 적는다' 가 세 출처에서 겹쳤는데,
  **그것을 둔 자리가 포트폴리오 문서였고 우리에게 그 자리는 노션이다.** 참고한 arena5045 조차
  README 에서는 요약만 하고 상세를 노션으로 보냈다. 사례가 사용자 안과 같았는데 내가 README 로 끌어왔다.
  게다가 '고민한 점' 셋은 노션의 '기술 셋 깊게' 와 정확히 겹쳐, **내가 경계한 두 벌을 내가 만들었다.**

- **목록 항목에 em-dash 를 썼다가 콜론으로 고쳤다.** `korean-style.md` 가 그 용법을 명시적으로
  금지한다. 세 줄이었고 전수로 찾아 고쳤다.
- **'직접 구현한 것' 이라는 절 제목을 뺐다.** 사용자가 '굳이 얘기할 필요가 있을지' 를 물었고,
  **1인 프로젝트에서 그 제목은 변명처럼 읽힌다.** '직접 구현한 것' 이 있으면 '직접 구현하지
  않은 것' 도 있다는 뜻이 된다.
