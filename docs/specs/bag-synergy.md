# 가방 시너지

## 왜 필요한가

**가방을 만들었지만 아직 배치를 고민할 이유가 없다.**

지금은 어디에 놓든 효과가 같다. 아이템이 자리를 차지하니 공간 퍼즐은 되지만,
GDD 가 정체성으로 꼽은 것은 그게 아니다.

> 아이템을 '먹는' 게 아니라 **'어디에 놓을지 고민하는'** 것이 이 게임의 정체성이다.
> **같은 아이템도 배치에 따라 성능이 달라진다.**

두 번째 문장이 아직 거짓이다. **이 명세가 그것을 참으로 만든다.**

**아이템 명세에 남겨둔 숙제도 여기서 판가름난다.**

> 수치 아이템끼리 비슷해 보일 위험이 남아 있다. 시너지가 이 문제를 풀어야 하고,
> 못 풀면 고유 행동을 다시 봐야 한다.

'공격력 +2' 와 '공격력 +5' 는 크기만 다르다. **배치에 따라 값이 달라지면
같은 아이템도 어디 놓느냐에 따라 다른 아이템이 된다.**

## 무엇을 만드는가

| 어셈블리 | 무엇 |
|---|---|
| `JM2D.Logic` | **인접 세기.** 어느 아이템 옆에 몇 개가 있는가 |
| `JM2D.Runtime` | 조건 데이터(`ItemData`), 인접 수를 값으로 바꿔 스탯에 붙이기 |
| `JM2D.Tests.EditMode` | 인접 규칙 |

```
BagGrid (인접 세기)  →  인접 수  →  조건과 곱한다  →  Stat
                                        ↑
                                  ItemData 의 조건
```

**어려운 부분은 인접 세기이고 그것이 `Logic` 에 있다.**
대각선을 세지 않는 것, 두 칸에서 맞닿아도 하나로 세는 것,
자기 자신을 세지 않는 것이 전부 거기서 정해지고 테스트가 지킨다.

**남은 것은 인접 수와 조건 값을 곱해 스탯에 붙이는 조립이다.**
처음에는 이것까지 `Logic` 에 두려 했으나, 조건이 `ItemData` 에 있어
`Logic` 이 읽을 수 없다. 인터페이스를 하나 더 만들면 되지만
**그리드가 시너지를 알게 되고, 곱셈 하나를 테스트하려고 치르기에는 비싸다.**

## 동작 정의

### 시너지는 모디파이어를 더 붙인다

- 조건이 맞으면 **스탯에 모디파이어가 하나 더 붙는다.** 새 계산 규칙은 없다.
- 시너지로 붙은 모디파이어는 **아이템이 붙인 것과 구분된다.**
  배치가 바뀌면 시너지 것만 전부 지우고 다시 계산한다.

### 이번에 만드는 것은 인접 하나다

- **인접**: 상하좌우로 맞닿은 아이템을 센다. 대각선은 아니다.
- 아이템이 **몇 칸을 차지하든** 맞닿아 있으면 한 번만 센다.
  `2×2` 와 `1×1` 이 두 칸에서 맞닿아도 인접한 아이템은 하나다.
- **자기 자신은 세지 않는다.**

**같은 행, 같은 열, 모서리는 이번에 만들지 않는다.**
인접 하나로 배치를 고민하게 되는지 먼저 본다.

### 조건과 보상은 아이템이 갖는다

아이템은 **시너지 조건 하나**를 가질 수 있다. 없어도 된다.

```
검   : 인접한 아이템 1개당 공격력 +10%
부츠 : 인접한 아이템 1개당 이동속도 +5%
```

**에셋만 만들면 새 시너지가 생긴다.** 코드는 늘지 않는다.

### 배치가 바뀌면 전부 다시 계산한다

- 아이템을 놓거나 뺄 때마다 **시너지 모디파이어를 전부 지우고 다시 만든다.**
- 아이템 하나를 놓으면 **주변 아이템의 시너지도 함께 바뀐다.**
  검 옆에 부츠를 놓으면 검의 공격력도 오른다.

**증분 갱신하지 않는다.** 연쇄를 추적해야 하고 25칸 규모에서는 이득이 없다.
화면을 다시 그리는 방식과 같다.

## 경계: 이 기능이 하지 않는 것

- **같은 행 · 같은 열 · 모서리 시너지** → 인접이 재미를 만드는지 본 뒤에 판단한다.
  안 나오면 셋을 더 만들어도 안 나온다.
- **세트 시너지** (칼·부츠·갑옷이 모이면) → 하지 않는다. 계산을 분리해 두므로
  **나중에 규칙을 더하는 방식으로 들어온다.** 태그 체계가 필요해 지금은 이르다.
- **시너지로 새 효과 주기** (관통, 흡혈) → 하지 않는다. 수치가 아니라 규칙이라
  모디파이어로 표현되지 않는다. 아이템 명세의 한계에 있는 것과 같은 문제다.
- **시너지 표시 UI** → 하지 않는다. 어느 아이템이 왜 세졌는지 화면에 그리지 않는다.
  **Console 로그로 확인한다.** 보여주는 것은 Phase 5 다.
- **음수 시너지** (인접하면 약해지는 것) → 만들지 않는다. 값을 음수로 넣으면
  동작은 하지만 지금 필요하지 않다.
- **아이템 15종 채우기** → 이번에는 넷에 시너지를 붙여 본다.

## 검증

**EditMode 테스트**: 이번 기능의 주된 검증 수단이다.

시너지 계산은 배치와 조건만 보고 결과를 낸다. 씬도 스탯도 필요 없다.

- [x] 아이템이 하나뿐이면 인접 수가 0이다
- [x] 상하좌우로 맞닿으면 인접으로 센다
- [x] **대각선은 인접이 아니다**
- [x] **두 칸에서 맞닿아도 한 번만 센다** (`2×2` 와 `1×1`)
- [x] 자기 자신은 세지 않는다
- [x] 인접 수만큼 모디파이어 값이 커진다
- [x] 시너지 조건이 없는 아이템은 모디파이어를 만들지 않는다
- [x] **아이템을 빼면 주변 아이템의 인접 수가 줄어든다**

> 셋째와 넷째가 실수하기 쉬운 자리다. 대각선을 세면 인접의 의미가 흐려지고,
> 맞닿은 칸마다 세면 큰 아이템 옆이 유리해진다.

**플레이모드 체크리스트**

- [x] 검 하나만 놓으면 시너지가 없다
- [x] 검 옆에 아무거나 놓으면 **검의 공격력이 오른다**
- [x] **그 아이템을 빼면 원래대로 돌아온다**
- [x] 검을 가운데 두고 사방을 채우면 공격력이 네 배만큼 오른다
- [x] 대각선에만 놓으면 오르지 않는다
- [x] 같은 검을 두 자리에 놓으면 **각자의 인접 수로 따로 계산된다**
- [x] 재시작하면 시너지가 없는 상태로 시작한다

## 메모

**완료 조건 넷째가 이 명세의 진짜 목적이다.** 나머지는 그것을 판단할 재료다.

인접 하나로 '어디에 놓을지 고민하는' 상태가 되면 **같은 행·열·모서리를
더해 넷을 채운다.** 안 되면 **고유 행동 아이템을 다시 봐야 한다.**
아이템 명세에서 안 B 로 미뤄둔 것이다.

**시너지 모디파이어의 출처를 어떻게 둘지 정해야 한다.** 아이템이 붙인 것과
구분되어야 배치가 바뀔 때 시너지 것만 지울 수 있다. 공통 객체 하나로 둘지,
아이템마다 따로 둘지는 계단에서 정한다.

**인접을 세는 방법도 정해야 한다.** 아이템이 차지한 칸의 이웃을 훑는 방식이
자연스러운데, `BagGrid` 가 아이템의 위치를 알려주지 않는다는 점이 걸린다.
**계단 1에서 위치를 배열에만 두기로 한 결정과 만난다.**
그리드에 조회 메서드를 더할지, 계산기가 배열을 훑을지 정해야 한다.

**결과: 인접 하나로는 배치를 고민하게 만들지 못한다.**
완료 조건 넷째의 답이며, 근거는 [시너지 방향](../decisions/synergy-direction.md)에 있다.

**뭉치면 무조건 이득이라 최적해가 자명하다.** 인접은 한 방향으로만 작동하고
5×5 에 아이템 넷이 9칸을 쓰므로 공간 제약도 없다.

**나머지 3종을 만들기로 했다.** 새 개념을 발명하지 않는다.
GDD 가 요구한 넷이 이미 서로 충돌한다. 모서리는 귀퉁이로 흩어야 이득이라
인접과 정면으로 부딪히고, 같은 행과 같은 열도 서로 배타적이다.

**어디까지 할지 선을 그었다.** 선택이 존재하는 데까지만 만들고
밸런싱을 정교하게 다듬지 않는다. 신입 포트폴리오에서 재미의 깊이는
평가 항목이 아니지만, **문서가 주장하는 것이 게임에 없으면 그것은 다른 문제다.**

**계산기를 Logic 에 두려던 것을 되돌렸다.** 조건이 `ItemData` 에 있어
`Logic` 이 읽을 수 없었다. 어려운 부분인 인접 세기는 이미 `BagGrid` 에 있고
테스트가 지키므로, 남은 곱셈을 위해 인터페이스를 나누지 않았다.

**가방에 스탯 표시를 붙였다.** 명세에 없던 것인데, 배치를 바꿀 때마다
콘솔을 뒤지면 판단이 흐려진다. 디버그용이며 Phase 5 에서 정리한다.
