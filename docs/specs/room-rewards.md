# 보상과 가방 (4-D)

## 왜 필요한가

**GDD 코어 루프의 마지막 두 칸이 비어 있다.** 지금은 방을 깨도 아무 일이 없고, 아이템은 마우스 휠로 디버그 팔레트에서 골라 놓는다.

```
방 입장 → 적 웨이브 격파 → 아이템 획득 → 가방에 배치(빌드 결정) → 다음 방
  4-B        4-C           여기부터가 4-D
```

**차별화 지점이 네 번째 칸이라고 GDD 가 적어 두었다.** 아이템을 먹는 것이 아니라 어디에 놓을지 고민하는 것이 이 게임의 정체성이다.
그 고민이 실제로 게임 안에서 일어나는 것은 이 명세가 처음이다. 1-A 부터 1-E 까지 만든 아이템 15종과 시너지 4종이 여기서 판에 연결된다.

## 정해진 것

명세를 쓰기 전에 합의했다. 근거는 4-D 를 마칠 때 결정 문서로 옮긴다.

- **보상은 셋 중 하나 고르기다.** 방을 깨면 창이 뜨고 게임이 멈춘다. 하데스의 은혜 선택, 슬레이 더 스파이어의 카드 보상과 같은 모양이다.
  아이작처럼 방 안 받침대에 놓고 주워 가게 하면 '고르는 순간' 이 흐려진다.
- **후보 셋은 아이템 15종에서 서로 다른 셋을 뽑는다.** 판 시드로 만든 난수를 쓴다(4-C 의 조합 뽑기와 같은 방식).
  **보상끼리는 중복을 허용한다.** 한 판에 보상이 여섯이라 18장을 뽑는데 종류가 15종뿐이고, 같은 아이템 둘을 겹쳐 쓰는 것도 빌드다.
- **고른 아이템은 '손' 에 한 개 들어온다.** 가방을 열면 그것을 들고 있고, 빈칸에 놓으면 손이 빈다.
  여러 개를 쌓는 보관함은 두지 않는다. 한 방에 하나씩 주므로 손 하나면 된다.
- **놓지 않고 다음 방에 가도 손에 남는다.** 잃지 않는다. 전투 중에는 가방을 못 열어 그 방을 깰 때까지 놓지 못한다.
- **전투 중에는 가방을 열 수 없다.** 방을 깬 뒤와 시작 방에서는 언제든 연다.
  백팩 배틀스처럼 싸우는 시간과 정리하는 시간이 갈린다. 가방을 연 채 시간을 멈추는 장치가 필요 없어진다.
- **마우스 휠 팔레트를 지우고, 인스펙터 체크로 켜는 디버그 모드만 남긴다.** 난이도 튜닝에서 특정 배치를 만들어 볼 일이 있다.
- **가방이 꽉 차면 기존 것을 빼서 자리를 만든다. 뺀 아이템은 버려진다.** 뺀 것을 손에 되돌리면 두 개를 들게 되어 '손은 하나' 와 어긋난다.

## 동작 정의

### 보상

- **전투 방의 마지막 웨이브를 깨면 보상 창이 뜨고 게임이 멈춘다.** 문은 4-C 대로 함께 열린다.
- 창에는 **서로 다른 아이템 셋**이 이름, 크기, 색, 효과와 함께 보인다.
- 하나를 고르면 창이 닫히고 게임이 다시 흐른다. **고른 아이템은 손에 들어온다.**
- **보스 방을 깨면 보상 창 대신 클리어 화면이 뜬다.**
- 고정 시드를 켜면 방마다 **같은 후보 셋**이 나온다.

### 가방

- 손에 아이템이 있으면 **가방을 열었을 때 그것을 들고 있다.** 놓을 자리를 미리보기로 보여 주는 것은 지금과 같다.
- 빈칸에 놓으면 손이 빈다. 스탯과 시너지가 곧바로 반영된다(1-A ~ 1-D 그대로).
- **전투 중에는 가방이 열리지 않는다.** 열려 있는 상태에서 전투가 시작되면 닫힌다.
- 이미 놓은 아이템을 빼면 **그 아이템은 사라진다.**
- 손에 아이템이 있는 동안 화면에 그 사실이 보인다.

### 판의 흐름

- 시작 방에서는 보상 없이 가방을 열 수 있다(빈 가방).
- 한 판을 끝까지 돌면 보상을 여섯 번 받는다(전투 방 여섯).
- 게임 오버, 다시 시작, 타이틀로 가기가 전과 같다.

## 정할 것

**구조를 먼저 정하지 않는다.** 계단에서 대안을 견주고 정한 뒤 메모에 적는다.

### 1. '손' 을 누가 갖는가

`ItemInventory`(가방과 스탯을 잇는 것)에 둘지, 판 전체를 보는 새 컴포넌트에 둘지, `BagView` 가 들고 있을지 정한다.
손은 화면에 보여야 하고(UI), 판이 끝날 때까지 남아야 하며(게임 상태), 가방에 놓이면 사라진다.

### 2. 보상 후보를 뽑는 곳과 아이템 목록의 출처

아이템 15종의 목록을 인스펙터 배열로 둘지, 폴더에서 읽을지 정한다. 뽑기는 4-C 의 조합 뽑기와 같은 자리에 둘지 따로 둘지도 정한다.
**서로 다른 셋을 뽑는 방법**(뽑은 것을 빼면서 세 번 vs 섞어서 앞의 셋)도 함께 정한다. 순수 계산으로 떨어지면 EditMode 테스트를 붙인다.

### 3. 게임을 멈추는 방법

`ResultPanel` 은 `Time.timeScale = 0` 으로 멈추고 되돌리지 않는다(게임이 끝나는 화면이라서). 보상 창은 닫으면 다시 흘러야 한다.
`timeScale` 을 쓸지, 입력과 적 업데이트만 막을지 정한다. **멈춘 동안 마우스로 고르는 것이 되는지 확인한다.**

### 4. 가방 잠금을 UI 가 어떻게 아는가

`RoomCombat` 에 '지금 싸우는 중' 을 묻는 프로퍼티를 둘지, 전투 시작과 끝을 이벤트로 알릴지 정한다.
4-C 는 방 클리어만 알린다. 전투 시작 알림은 아직 없다.

### 5. 보상 창의 모양

프리팹 구조(버튼 셋, 아이템 하나에 보여 줄 것), 화면 어디에 뜨는지, 키보드로도 고를 수 있는지 정한다.
아이템의 효과 문구를 어떻게 만들지도 정한다(`ItemData` 의 모디파이어를 사람이 읽을 문장으로).

### 6. 디버그 팔레트를 남기는 모양

인스펙터 체크 하나로 켜고 끄되, 꺼져 있을 때 휠과 팔레트 코드가 어떻게 되는지 정한다.

## 경계: 이 기능이 하지 않는 것

- **무기 보상, 무기 교체** → Phase 5 메타 해금과 함께 정한다. 숫자 키 확인용 입력은 그대로 둔다.
- **상점, 재화, 되팔기** → GDD 에 없다.
- **보상 다시 뽑기(리롤), 보상 건너뛰기** → 넣지 않는다.
- **보스 방 보상** → 없다. 클리어 화면이 뜬다.
- **아이템을 얻는 다른 경로**(상자, 적 드랍) → 넣지 않는다.
- **아이템 등급과 희귀도** → 넣지 않는다. 15종이 평평하다. 난이도 튜닝에서 다시 본다.
- **가방 크기 변경** → 5×5 를 유지한다.
- **가방 UI 를 제대로 만들기** → Phase 5. 지금은 디버그 티를 벗는 정도까지만 한다.

떨어지지 않으면 해당 없음과 이유를 적는다.

## 메모

**계단 1 결과: `Logic/Common/RandomPick.Distinct(종류 수, 뽑을 수, 난수)` 를 만들었다(정할 것 2).**
`Logic` 은 `Runtime` 을 참조하지 않아 `ItemData` 를 볼 수 없다. 그래서 번호만 뽑고, 번호로 아이템을 꺼내는 일은 부르는 쪽이 한다.
뽑기는 부분 셔플(피셔 예이츠를 뽑을 수만큼)이라 중복이 구조적으로 불가능하다. 뽑을 수가 종류 수보다 많으면 예외를 낸다.
`RandomPickTests` 는 메서드 6개, `[TestCase]` 를 포함해 실행 11개이고 EditMode 테스트는 154 개가 됐다.
**채울 때 맞바꾼 뒤 엉뚱한 자리를 읽는 실수가 있었다**(`result[i] = pool[j]`). 결과가 늘 0, 1, 2 언저리였고, 시드 1000개를 도는 테스트가 잡았다.
분포가 치우치는 실수(`Next(0, count)`)는 테스트로 잡지 않기로 했다. 근거는 [번호 뽑기](../decisions/random-pick-indices.md)에 있다.

**계단 2 결과: 전투 중에는 가방이 잠긴다(정할 것 4).** `RoomCombat` 에 `OnCombatStarted(Room)` 를 더해 `OnRoomCleared(Room)` 와 짝을 맞췄다.
`BagView` 가 둘을 듣고 잠그고 푼다. 전투가 시작될 때 열려 있으면 닫는다. 프로퍼티를 두고 매 프레임 묻는 안은
'열려 있던 가방을 닫는' 일을 UI 가 알 수 없어 결국 폴링이 되므로 버렸다.

**계단 3 결과: '손' 은 `ItemInventory` 가 갖는다(정할 것 1).** `Hand`, `PutInHand`, `RotateHand`, `TryPlaceHand` 넷이다.
**놓기는 실패할 수 있어 성공한 뒤에 손을 비운다.** 먼저 비우면 놓을 수 없는 칸을 클릭했을 때 아이템이 사라진다.
`BagView` 의 `_preview` 필드가 사라지고 **놓는 경로가 하나가 됐다.** 휠 팔레트는 인스펙터 체크(`_debugPalette`)로 켜는 디버그 수단이 되어, 보상과 같은 자리(손)를 채운다.

**계단 4 결과: `RewardPanel` 이 카드 셋을 코드로 만든다(정할 것 5).** 창은 `Show(후보)` 와 `OnPicked(고른 것)` 만 안다.
번호 키 1, 2, 3 과 클릭 둘 다로 고른다. 인스펙터 우클릭 메뉴로 방을 깨지 않고 띄워 볼 수 있다.
효과 문구는 `ItemData` 의 모디파이어와 시너지에서 만든다(`공격력 +2`, `인접 하나당 공격력 +1`). 퍼센트의 가산과 승산은 구분해 적지 않는다.
**`RectTransform` 의 앵커와 피벗을 코드가 정하지 않아 자리가 엉켰고, 같은 실수를 두 번 했다.** 처음에는 카드와 글자, 두 번째는 패널 자신이었다.
패널이 100 × 100 인 채여서 가림막이 화면 대신 그만큼만 덮었다. 규칙에 이미 있는 항목이다.

**계단 5 결과: `RewardGiver` 하나가 넷을 잇는다.** 방 클리어를 듣고, 보스 방이면 아무것도 하지 않고, 후보를 뽑아 창을 띄우고 멈춘다(`Time.timeScale = 0f`).
고른 것을 손에 넣고 다시 흐르게 한다. `SceneLoader` 가 씬을 불러올 때 `timeScale` 을 1 로 되돌리고 있어 다시 시작 경로도 안전하다(확인함).
뽑기 난수는 `System.Random(이번 판 시드)` 이고 조합 뽑기 난수와 별개다. **가방을 열 때 표시 줄을 다시 쓰지 않아 '손 없음' 으로 보이는 버그가 있었다.**
손은 가방 밖에서 채워지므로 여는 순간에도 다시 쓰게 고쳤다.

**계단 6 결과: 관찰 넷 중 하나를 넣었다.**

| 관찰 | 결과 | 판단 |
|---|---|---|
| 선택이 고민이 되는가 | 괜찮았다 | 6번 난이도 튜닝에서 수치와 함께 다시 본다 |
| 가방 5×5 가 넉넉한가 | 괜찮았다 | 같음 |
| 보상 창이 흐름을 끊는가 | 끊지 않았다 | 연출은 Phase 5 |
| 고른 뒤 가방을 여는 흐름 | **번거롭다** | 고르면 가방이 자동으로 열리게 했다. 계단 5 에서 미뤄 둔 항목이다 |

자동 열기는 `RewardGiver` 가 **손에 넣은 뒤** `BagView.Open()` 을 부른다. `BagView` 가 `OnPicked` 를 따로 듣는 안은
구독 순서에 따라 손이 채워지기 전에 열릴 수 있어 버렸다. 잠겨 있거나 이미 열려 있으면 `Open()` 은 아무 일도 하지 않는다.
