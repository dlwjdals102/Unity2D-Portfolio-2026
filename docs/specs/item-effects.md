# 아이템 효과 시스템

## 왜 필요한가

**GDD 가 이 게임의 차별화 지점으로 꼽은 것이 가방 배치**인데, 놓을 아이템이 없다.
지금 이 프로젝트는 아이템이 빠진 평범한 탑다운 슈터다.

**스탯 시스템이 아이템을 기다리고 있다.** 출처 추적을 아이템보다 먼저 넣었고
지금은 디버그 키로 흉내만 내는 중이다. **아이템이 붙어야 그 설계가 실제로 검증된다.**

그리고 열린 질문 하나가 여기 걸려 있다.

> 아이템 20종이 데이터 추가만으로 되는지 → Phase 4 에서 서너 종을 만들어 보고 점검.
> 안 되면 12종으로 축소.

**서너 종을 일찍 만들어 봐야 20종이 가능한지 알 수 있고, 안 되면 줄일 시간이 남는다.**

## 왜 그리드와 나눴는가

Phase 4 의 아이템 항목은 원래 '아이템 20종 + 시너지 규칙 4종' 하나였다.
**둘로 나눈다.**

| | 이 명세 | 다음 명세 |
|---|---|---|
| 무엇 | 아이템이 스탯을 바꾼다 | 가방 그리드와 시너지 |
| 검증 | 먹으면 세지고 버리면 돌아온다 | 배치가 유효한가, 시너지가 잡히는가 |

**그리드는 '어떻게 장착하는가'의 UI 다.** 그리드에 아이템을 놓아도 효과가 없으면
의미가 없으므로 효과가 먼저다. 합치면 명세 하나가 Phase 3 전체만 해진다.

## 무엇을 만드는가

**아이템은 데이터다. 코드가 아니다.**

아이템 하나는 **'어느 스탯에 어떤 종류로 얼마'** 의 목록을 갖는다.
장착하면 그 모디파이어들이 붙고, 해제하면 떨어진다.

| 어셈블리 | 무엇 |
|---|---|
| `JM2D.Logic` | 스탯을 지목하는 수단 (이미 있는 `Stat` 을 그대로 쓴다) |
| `JM2D.Runtime` | `ItemData` (ScriptableObject), 장착과 해제 |

**새 계산 규칙을 만들지 않는다.** 스탯 시스템이 이미 다 갖고 있다.
이번에 만드는 것은 **데이터에서 스탯을 지목하는 길**뿐이다.

## 동작 정의

**아이템 하나가 여러 스탯을 건드린다**
- 아이템은 모디파이어를 **하나 이상** 갖는다. 어느 스탯에 어떤 종류로 얼마인지를 담는다.
- 아이템을 만드는 데 코드를 쓰지 않는다. **에셋을 하나 더 만들면 아이템이 하나 는다.**

**장착과 해제**
- 장착하면 그 아이템의 모디파이어가 전부 붙는다.
- 해제하면 **그 아이템 것만** 떨어진다. 같은 종류의 다른 아이템은 그대로 남는다.
- **같은 아이템을 둘 장착하면 효과가 두 번 적용된다.** 하나를 빼면 하나만 남는다.

**효과는 즉시 나타난다**
- 장착한 다음 프레임부터 이동 속도와 연사 속도가 달라진다.
- 최대 체력 아이템은 **HP 바가 즉시 갱신되고, 늘어난 만큼 현재 체력도 찬다.**

**만드는 아이템은 넷이다**

| 아이템 | 효과 | 종류 |
|---|---|---|
| 검 | 공격력 +2 | 가산 |
| 부츠 | 이동속도 +20% | 승산 가산 |
| 장갑 | 공격속도 +15% | 승산 가산 |
| 갑옷 | 최대체력 +2 | 가산 |

**네 스탯을 하나씩 건드리고 두 종류를 쓴다.** 스무 종을 만들기 전에
**구조가 실제로 데이터만으로 늘어나는지** 확인하는 것이 목적이다.

## 경계: 이 기능이 하지 않는 것

- **가방 그리드와 배치 UI** → 다음 명세다. 이번에는 **디버그 키로 장착하고 해제**한다.
- **시너지** → 그리드가 있어야 인접을 판단할 수 있다. 다음 명세다.
- **아이템 20종** → 넷만 만든다. 나머지는 구조가 검증된 뒤 데이터로 채운다.
- **아이템 획득과 드롭** → 하지 않는다. 적이 죽으면 아이템이 떨어지는 것은
  아이템이 있고 나서 붙일 일이다.
- **아이템 등급과 확률** → 하지 않는다. 뽑기가 없으므로 등급도 필요 없다.
- **적의 아이템** → 하지 않는다. 적 스탯 자체가 Phase 4 뒷부분이다.
- **아이템별 고유 행동** → 하지 않는다. '적을 처치하면 폭발' 같은 것은
  모디파이어로 표현되지 않는다. **스무 종이 전부 수치 변경으로 되는지 먼저 본다.**
  안 되면 그때가 판단 시점이다.
- **세이브** → Phase 5 다.

## 검증

**EditMode 테스트**

`ItemData` 는 ScriptableObject 라 Logic 이 아니다. 다만 **스탯을 지목하는 수단**은
Logic 에 들어가므로 그 부분만 테스트한다.

- [ ] 스탯 종류로 지목하면 해당 스탯이 나온다
- [ ] 없는 종류를 지목하면 알 수 있다 (조용히 null 을 돌려주지 않는다)

> 장착과 해제 자체는 `Stat.AddModifier` 와 `RemoveAllFrom` 을 부르는 것뿐이고,
> **그 둘은 이미 테스트 22개가 지키고 있다.** 같은 것을 두 번 테스트하지 않는다.

**플레이모드 체크리스트**

- [ ] 부츠를 장착하면 눈에 띄게 빨라지고, 해제하면 원래 속도로 돌아온다
- [ ] 검을 장착하면 적이 한 발에 죽는다
- [ ] 갑옷을 장착하면 HP 바가 즉시 다섯 칸이 되고, **한 대 맞은 상태였다면 4/5 가 된다**
- [ ] 장갑을 장착하면 연사가 빨라진다
- [ ] **검을 둘 장착하면 공격력이 +4 가 되고, 하나만 빼면 +2 로 돌아온다**
- [ ] 부츠와 장갑을 함께 장착해도 서로 간섭하지 않는다
- [ ] 재시작하면 아무것도 장착되지 않은 상태로 시작한다

> 다섯 번째가 이번 명세의 핵심이다. **출처 추적을 아이템보다 먼저 넣은 이유**가
> 여기서 증명된다. 값이 똑같은 모디파이어 둘 중 하나만 정확히 떨어져야 한다.

## 완료 조건

- [ ] EditMode 테스트 통과
- [ ] 플레이모드 체크리스트 통과
- [ ] **아이템 하나를 코드 수정 없이 추가할 수 있는지 실제로 해본다**

## 메모

**데이터가 스탯을 지목할 방법을 정해야 한다.** 지금 `PlayerStats` 는 스탯을
프로퍼티 넷으로 갖고 있어서, 에셋에 '이동속도에 +20%' 라고 적을 수단이 없다.
열거형으로 지목하는 것이 자연스러운데, **프로퍼티를 없앨지 함께 둘지**는
계단에서 정한다. 코드가 직접 쓸 때와 데이터가 지목할 때는 사용처가 다르다.

**장착 주체를 어디에 둘지도 정해야 한다.** 지금은 `PlayerStats` 가 스탯을 갖고
있는데, 장착 목록까지 갖게 하면 책임이 둘이 된다. 그리드가 들어오면
그쪽이 장착 목록의 주인이 될 수도 있다. **다음 명세를 염두에 두고 정한다.**

**디버그 키를 재사용한다.** 지금 `StatDebugKeys` 가 모디파이어를 직접 붙이는데,
이번에는 **아이템을 장착하는 방식으로 바꾼다.** 흉내가 실물로 바뀌는 것이고,
그리드가 생기면 이 컴포넌트는 지운다.

**아이템 20종이 전부 수치 변경일 수는 없다.** 재미있는 아이템은 대개 고유 행동을
갖는다. 이번에는 수치만으로 넷을 만들어 보고, **스무 종을 수치로만 채울 수 있는지**
판단한다. 못 한다면 그것도 답이고, 종류를 줄이거나 행동을 표현할 방법을 찾는다.
