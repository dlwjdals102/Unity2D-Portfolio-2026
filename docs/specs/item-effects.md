# 아이템 효과 시스템

## 왜 필요한가

**GDD 가 이 게임의 차별화 지점으로 꼽은 것이 가방 배치**인데, 놓을 아이템이 없다.
지금 이 프로젝트는 아이템이 빠진 평범한 탑다운 슈터다.

**스탯 시스템이 아이템을 기다리고 있다.** 출처 추적을 아이템보다 먼저 넣었고
지금은 디버그 키로 흉내만 내는 중이다. **아이템이 붙어야 그 설계가 실제로 검증된다.**

그리고 열린 질문 하나가 여기 걸려 있다.

> 아이템 20종이 데이터 추가만으로 되는지 → Phase 4 에서 서너 종을 만들어 보고 점검.
> 안 되면 12종으로 축소.

**서너 종을 일찍 만들어 봐야 20종이 가능한지 알 수 있고, 안 되면 줄일 시간이 남는다.**

## 왜 그리드와 나눴는가

Phase 4 의 아이템 항목은 원래 '아이템 20종 + 시너지 규칙 4종' 하나였다.
**둘로 나눈다.**

| | 이 명세 | 다음 명세 |
|---|---|---|
| 무엇 | 아이템이 스탯을 바꾼다 | 가방 그리드와 시너지 |
| 검증 | 먹으면 세지고 버리면 돌아온다 | 배치가 유효한가, 시너지가 잡히는가 |

**그리드는 '어떻게 장착하는가'의 UI 다.** 그리드에 아이템을 놓아도 효과가 없으면
의미가 없으므로 효과가 먼저다. 합치면 명세 하나가 Phase 3 전체만 해진다.

## 무엇을 만드는가

**아이템은 데이터다. 코드가 아니다.**

아이템 하나는 **'어느 스탯에 어떤 종류로 얼마'** 의 목록을 갖는다.
장착하면 그 모디파이어들이 붙고, 해제하면 떨어진다.

| 어셈블리 | 무엇 |
|---|---|
| `JM2D.Logic` | `StatType` 열거형. 이미 있는 `Stat` 은 그대로 쓴다 |
| `JM2D.Runtime` | `ItemData` (ScriptableObject), 스탯 조회, 장착과 해제 |

**새 계산 규칙을 만들지 않는다.** 스탯 시스템이 이미 다 갖고 있다.
이번에 만드는 것은 **데이터에서 스탯을 지목하는 길**뿐이다.

## 동작 정의

**아이템 하나가 여러 스탯을 건드린다**
- 아이템은 모디파이어를 **하나 이상** 갖는다. 어느 스탯에 어떤 종류로 얼마인지를 담는다.
- 아이템을 만드는 데 코드를 쓰지 않는다. **에셋을 하나 더 만들면 아이템이 하나 는다.**

**장착과 해제**
- 장착하면 그 아이템의 모디파이어가 전부 붙는다.
- 해제하면 **그 아이템 것만** 떨어진다. 같은 종류의 다른 아이템은 그대로 남는다.
- **같은 아이템을 둘 장착하면 효과가 두 번 적용된다.** 하나를 빼면 하나만 남는다.

**효과는 즉시 나타난다**
- 장착한 다음 프레임부터 이동 속도와 연사 속도가 달라진다.
- 최대 체력 아이템은 **HP 바가 즉시 갱신되고, 늘어난 만큼 현재 체력도 찬다.**

**만드는 아이템은 넷이다**

| 아이템 | 효과 | 종류 |
|---|---|---|
| 검 | 공격력 +2 | 가산 |
| 부츠 | 이동속도 +20% | 승산 가산 |
| 장갑 | 공격속도 +15% | 승산 가산 |
| 갑옷 | 최대체력 +2 | 가산 |

**네 스탯을 하나씩 건드리고 두 종류를 쓴다.** 스무 종을 만들기 전에
**구조가 실제로 데이터만으로 늘어나는지** 확인하는 것이 목적이다.

## 경계: 이 기능이 하지 않는 것

- **가방 그리드와 배치 UI** → 다음 명세다. 이번에는 **디버그 키로 장착하고 해제**한다.
- **시너지** → 그리드가 있어야 인접을 판단할 수 있다. 다음 명세다.
- **아이템 20종** → 넷만 만든다. 나머지는 구조가 검증된 뒤 데이터로 채운다.
- **아이템 획득과 드롭** → 하지 않는다. 적이 죽으면 아이템이 떨어지는 것은
  아이템이 있고 나서 붙일 일이다.
- **아이템 등급과 확률** → 하지 않는다. 뽑기가 없으므로 등급도 필요 없다.
- **적의 아이템** → 하지 않는다. 적 스탯 자체가 Phase 4 뒷부분이다.
- **아이템별 고유 행동** → 하지 않는다. '적을 처치하면 폭발' 같은 것은
  모디파이어로 표현되지 않는다. **스무 종이 전부 수치 변경으로 되는지 먼저 본다.**
  안 되면 그때가 판단 시점이다.
- **세이브** → Phase 5 다.

## 검증

**EditMode 테스트**: 해당 없음.

처음에는 스탯 조회를 Logic 의 별도 클래스로 빼서 테스트하려 했다.
**다시 보니 그 클래스가 하는 일은 `Dictionary` 조회 한 줄이라,
테스트하면 자기 코드가 아니라 표준 라이브러리를 시험하는 셈이 된다.**
클래스를 만들지 않고 `PlayerStats` 가 `Dictionary` 를 직접 갖는다.

장착과 해제도 `Stat.AddModifier` 와 `RemoveAllFrom` 을 부르는 것뿐이고,
**그 둘은 이미 테스트 22개가 지키고 있다.** 같은 것을 두 번 테스트하지 않는다.

`ItemData` 는 ScriptableObject 라 Logic 대상이 아니다.

**플레이모드 체크리스트**

- [x] 부츠를 장착하면 눈에 띄게 빨라지고, 해제하면 원래 속도로 돌아온다
- [x] 검을 장착하면 적이 한 발에 죽는다
- [x] 갑옷을 장착하면 HP 바가 즉시 다섯 칸이 되고, **한 대 맞은 상태였다면 4/5 가 된다**
- [x] 장갑을 장착하면 연사가 빨라진다
- [x] **검을 둘 장착하면 공격력이 +4 가 되고, 하나만 빼면 +2 로 돌아온다**
- [x] 부츠와 장갑을 함께 장착해도 서로 간섭하지 않는다
- [x] 재시작하면 아무것도 장착되지 않은 상태로 시작한다

> 다섯 번째가 이번 명세의 핵심이다. **출처 추적을 아이템보다 먼저 넣은 이유**가
> 여기서 증명된다. 값이 똑같은 모디파이어 둘 중 하나만 정확히 떨어져야 한다.

## 메모

**데이터가 스탯을 지목할 방법을 계단 1에서 정했다.** 프로퍼티는 코드에만 있는
이름이라 에셋에 담기지 않는다. `StatType` 열거형을 만들어 값으로 지목하고,
`PlayerStats` 가 `Dictionary<StatType, Stat>` 하나에 담는다.
프로퍼티는 그 위의 껍데기로 남겨 기존 호출부를 그대로 살린다.

**저장이 한 곳이라는 것이 핵심이다.** 프로퍼티와 조회를 각각 따로 관리하면
스탯을 추가할 때 한쪽을 빠뜨리게 되고, **코드는 잘 도는데 아이템만 안 먹히는**
조용한 어긋남이 생긴다.

**장착 주체를 어디에 둘지도 정해야 한다.** 지금은 `PlayerStats` 가 스탯을 갖고
있는데, 장착 목록까지 갖게 하면 책임이 둘이 된다. 그리드가 들어오면
그쪽이 장착 목록의 주인이 될 수도 있다. **다음 명세를 염두에 두고 정한다.**

**디버그 키를 재사용한다.** 지금 `StatDebugKeys` 가 모디파이어를 직접 붙이는데,
이번에는 **아이템을 장착하는 방식으로 바꾼다.** 흉내가 실물로 바뀌는 것이고,
그리드가 생기면 이 컴포넌트는 지운다.

**아이템 20종이 전부 수치 변경일 수는 없다.** 재미있는 아이템은 대개 고유 행동을
갖는다. 이번에는 수치만으로 넷을 만들어 보고, **스무 종을 수치로만 채울 수 있는지**
판단한다. 못 한다면 그것도 답이고, 종류를 줄이거나 행동을 표현할 방법을 찾는다.

**계단 1에서 검 둘을 구분할 수 없다는 것이 드러났다.** 장착할 때 출처로
`ItemData` 에셋을 넘기면, 같은 종류 아이템 둘이 **같은 파일을 가리키므로
출처가 같아진다.** 하나만 빼려 해도 둘 다 떨어진다.

**원본과 인스턴스를 나눠야 한다.** ScriptableObject 데이터 분리 때와 같은 구조다.

| | 무엇 | 예 |
|---|---|---|
| `ItemData` | 아이템 종류. 에셋 파일 | '검이란 공격력 +2다' |
| `ItemInstance` | 이 검 한 자루. 런타임 객체 | 가방에 있는 그 검 |

출처로 쓰는 것은 인스턴스다. 서로 다른 객체라 정확히 구분된다.

**가방 그리드가 이것을 요구하기도 한다.** 아이템은 어느 칸에 있는지를 알아야
하는데, 에셋은 위치를 가질 수 없다. 가지면 모든 검이 같은 칸에 있게 된다.
**그러므로 가방이 인스턴스 목록의 주인이 되는 것이 자연스럽다.**
위에 적어둔 '장착 주체를 어디에 둘지' 미결이 여기서 답을 얻는다.

**결과: 20종은 데이터만으로 되지 않는다. 15종까지다.** 완료 조건에 넣어둔
질문의 답이며, 근거와 목록은 [결정 문서](../decisions/item-effect-design.md)에 있다.

수치로 되는 15종은 에셋만 만들면 되고, 나머지 5종(흡혈·관통·폭발·삼중발사·가시)은
**수치가 아니라 규칙이라 모디파이어로 표현되지 않는다.**

**12종으로 줄이지 않는다.** 15종이 되므로 축소는 과잉 대응이다.
다양성은 시너지가 만들기로 했다. 못 만들면 그때 고유 행동을 다시 본다.

**Phase 3 에서 만든 것 중 새로 만든 계산이 하나도 없다.**
출처 추적, 세 종류 계산, 캐싱, 변경 이벤트가 전부 그대로 쓰였다.
특히 출처 추적은 아이템이 없던 시절에 '나중에 붙일 수 없는 종류' 라는 이유로
미리 넣었는데, `ItemInstance` 가 그 자리에 정확히 들어갔다.

**테스트가 버그를 잡은 게 아니라 결백을 증명한 사례가 나왔다.**
아이템을 반복 장착·해제하면 깨진다는 제보가 있었는데, 시나리오를 테스트로
재현하니 통과했다. 원인은 Console 의 Collapse 설정이었다.
**'내 코드가 문제인가, 내가 잘못 본 것인가' 를 가르는 데 테스트가 값을 했다.**
