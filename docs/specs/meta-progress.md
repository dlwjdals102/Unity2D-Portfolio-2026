# 메타 진행

## 왜 필요한가

**판과 판 사이에 아무것도 남지 않는다.** 보스를 잡아도, 죽어도 다음 판은 똑같이 시작한다.
GDD 는 '획득한 메타 재화만 유지하고 처음부터' 라고 적었는데 그것이 게임에 없다.

**무기를 고를 자리도 없다.** 지금 무기를 바꾸는 길은 숫자 키 1, 2, 3 뿐이고 확인용으로 둔 것이다.
`weapons.md` 가 남긴 미해결이고 '판을 시작하기 전에 고르는 쪽을 메타 해금과 함께 정한다' 고 적어 두었다.

포트폴리오에도 필요하다. **세이브와 로드 직렬화는 면접 단골이고 CLAUDE.md 1번이 직접 작성할 영역으로 지정한 자리다.**
지금 프로젝트에 `PlayerPrefs`, `JsonUtility`, `File` 을 쓰는 코드가 한 줄도 없다(검색으로 확인).

## 동작 정의

- 게임을 켜면 **타이틀**이 뜬다. 시작을 누르면 **마을**로 간다.
- 마을에서 **걸어서** 선택대와 던전 입구로 간다. 마을에는 적도 전투도 없다.
- **무기대 앞에서 E 를 누르면 그 무기를 든다.** 무기마다 자리가 하나씩 있다.
  잠긴 자리는 **멀리서도 어둡게 보이고**, 다가가면 조건이 보인다. 눌러도 아무 일이 없다.
- 고른 무기는 **마을에서 바로 휘둘러 볼 수 있다.**
- 다른 무기대에 갔다 와도 **'지금 들고 있다' 표시가 맞는 자리에만 뜬다.**
- **던전에 들어가면 고른 무기로 시작한다.** 매번 새 시드로 방 여덟 개가 배치된다.
- 보스를 잡거나 죽으면 결과가 뜨고, **마을로 돌아온다.**
- 그 판의 기록(보스를 잡았는지, 몇 번째 방까지 갔는지)이 **저장된다.**
- 기록이 조건을 넘으면 **선택대에 새 무기가 열려 있다.** 게임을 껐다 켜도 그대로다.
- 저장 파일이 없으면 **처음 켠 것처럼 시작한다.** 파일이 깨져 있어도 게임이 멈추지 않는다.

## 경계 — 이 기능이 하지 않는 것

- **런 중간 저장.** 판을 하다 끄면 그 판은 사라진다. GDD 5번과 ROADMAP 이 명시적으로 뺀 항목이다.
  씬을 넘어 살아남는 것은 **고른 무기와 기록 둘뿐**이다. 가방, 스탯, 체력은 던전에 들어갈 때마다 새로 시작한다.
- **던전 둘.** 입구는 하나다. 같은 방 프리팹에 시드만 다르면 플레이어 눈에는 2회차이고,
  다르게 보이려면 타일셋과 적과 보스가 또 필요하다. GDD 스코프 표를 넘는다.
- **무기를 고르는 창.** 카드가 늘어선 창을 만들었다가 지웠다. 무기대 셋이 그 일을 한다.
  창이 없으니 **창이 열린 동안 이동과 공격을 막는 장치도 필요 없다.**
- **마을을 키우는 것.** 화면 두 배까지다. **NPC, 상점, 대화, 퀘스트, 꾸미기용 건물을 넣지 않는다.**
  넓은 마을에 할 일이 둘뿐이면 그것이 미완성으로 읽힌다. 작은 마을은 의도된 크기로 읽힌다.
- **메타 재화.** 떨어뜨리고, 모으고, 보여주고, 값을 매기는 일이 전부 새 시스템이다.
  **기록으로 해금한다.** GDD 의 '메타 재화' 를 바꾸는 것이므로 GDD 도 함께 고친다.
- **시작 아이템 해금.** GDD 스코프 표의 해금 5 중 무기 둘만 한다. 가방에 처음부터 아이템을 놓는 것은
  시너지와 밸런스에 바로 영향이 가서 난이도 튜닝과 묶인다.
- **저장 슬롯 여러 개, 클라우드, 암호화, 변조 방지.** 파일 하나다.
- **저장 포맷 마이그레이션.** 버전 숫자는 넣되 옛 버전을 읽어 고치는 코드는 쓰지 않는다.
  버전이 다르면 기본값으로 시작한다.

## 설계

### 씬은 셋이 된다

```
Title  ──시작──>  Town  ──입구──>  Gameplay  ──결과 화면──>  Town
                   ^                                          |
                   +------------------------------------------+
```

`SceneLoader` 가 이미 있고 `SceneNames` 에 상수를 더하면 된다. **타이틀을 남기는 이유**는
게임을 켜자마자 조작이 시작되지 않게 하고 '그만두기' 를 둘 자리를 지키기 위해서다.

마을 씬에는 **`RoomCombat`, `RewardGiver`, `BagView`, `LevelBuilder` 를 놓지 않는다.**
한 씬에서 '여기는 마을인가' 를 묻는 분기를 만들지 않고, **씬이 다르면 구성이 다른 것**으로 둔다.
마을의 플레이어는 걷기만 하므로 공격도 가방도 필요 없다.

### 저장하는 값은 넷이다

```
version            포맷 번호. 다르면 기본값으로 시작한다
bossKills          보스를 잡은 횟수
bestRoomsReached   한 판에서 도달한 가장 깊은 방 번호
selectedWeapon     마을에서 고른 무기 번호
```

**해금 목록은 저장하지 않는다.** 기록에서 계산한다. 저장해 두면 '기록' 과 '해금' 두 개의 진실이 생기고
둘이 어긋나는 순간(값을 손으로 고치거나 조건을 바꿨을 때) 무엇이 맞는지 알 수 없다.
**조건을 바꾸면 이미 저장된 기록에 그 조건이 곧바로 적용되는 쪽이 낫다.**

### 해금 판정은 `Logic` 에 둔다

`JsonUtility` 와 `File` 은 `UnityEngine` 쪽이라 `Runtime` 에 있어야 하지만,
**'이 기록이면 무엇이 열리는가' 는 순수 계산이다.** 그래서 둘을 가른다.

```
Logic/Progress/ 저장되는 값과 해금 규칙      테스트가 붙는다
Runtime         파일을 읽고 쓰는 것           씬과 경로를 안다
```

이 경계가 이 기능의 **테스트 가능한 부분을 만든다.** 경계값(조건 직전과 직후)을 EditMode 로 검증한다.

### 저장과 로드가 도는 자리

```
마을에서 무기를 고를 때        selectedWeapon 을 쓰고 저장한다
던전이 시작될 때               selectedWeapon 을 읽어 그 무기를 든다
판이 끝날 때                   bossKills, bestRoomsReached 를 갱신하고 저장한다
마을에 들어올 때               기록을 읽어 선택대에 해금 상태를 보인다
```

**기록은 더 좋은 값만 남긴다.** 세 번째 방에서 죽은 판이 여덟 번째까지 갔던 기록을 덮으면 안 된다.

### 무기대 셋이 창을 대신한다

처음에는 선택대 하나와 카드가 늘어선 창을 만들었다. **창을 지우고 무기마다 자리를 하나씩 두었다.**
얻은 것이 셋이다. UI 230줄이 사라졌고, **창이 없으니 이동과 공격을 막을 이유도 사라졌고**,
걸어 다닐 이유가 생겨 마을이 비어 보이지 않는다.

잃은 것은 **무기 셋의 수치를 나란히 놓고 비교할 수 없다**는 것이다. 셋 중에 고르는 데
나란히 볼 필요까지는 없다고 보았다. 각 자리에서 그 무기의 이름과 수치를 보여 준다.

**무기대끼리 서로를 모른다.** 플레이어가 다가오는 순간 각자 저장 파일을 다시 읽는다
(`Interactable.OnPlayerNear`). 그래서 검을 들고 활 쪽으로 걸어가면 활 자리의 글이 맞게 바뀐다.
서로에게 '내가 바뀌었다' 고 알리는 길을 만들었다면 자리가 넷이 될 때 연결이 여섯이 된다.
**파일이 이미 하나뿐인 진실이라 그것을 다시 읽는 쪽이 싸다.**

해금 판정은 세 자리에서 **같은 함수**를 지나간다. 멀리서 어둡게 할 때, 글을 쓸 때, 누를 때다.

### 파일이 없거나 깨졌을 때

**둘 다 기본값으로 시작한다.** 없는 것은 처음 켠 것이고, 깨진 것은 복구할 방법이 없다.
예외를 밖으로 던지면 게임이 멈춘다. **에디터에서는 경고를 남겨 조용히 지나가지 않게 한다.**

## 메모

**착수 전에 코드와 문서에서 확인한 것.**

| 확인한 것 | 어디 |
|---|---|
| 저장 코드가 0곳 | `PlayerPrefs`, `JsonUtility`, `File.Write`, `persistentDataPath` 전체 검색 |
| 씬은 `Title` 과 `Gameplay` 둘 | `SceneNames.cs` |
| 판의 끝을 아는 자리가 있다 | `ResultPanel` 이 죽음과 보스 방 클리어를 둘 다 듣는다 |
| `Logic` 은 참조가 비어 있다 | `JM2D.Logic.asmdef` |
| 무기를 바꾸는 길이 확인용뿐 | `PlayerInputReader.ReadWeaponSlot` |

**범위를 두 번 바꿨다.** 처음에는 메타 저장만 하기로 했고, 마을을 넣자는 이야기가 나왔을 때
내가 던전 둘과 런 중간 저장을 묶어 2~4주로 값을 매겨 반대했다. **그 둘은 요청에 없던 것이었다.**
돌아오는 시점이 '판이 끝난 뒤' 라서 씬을 넘는 것이 고른 무기와 기록 둘뿐이고,
마을에 전투 관련 컴포넌트를 놓지 않으면 분기도 생기지 않는다. 그래서 찬성으로 바꿨다.

**'완성으로 읽히는가' 는 고리가 닫히는지로 갈린다.** 퀘스트가 없어서 미완성으로 보이는 것이 아니라
**빈 공간**이 그렇게 보인다. 그래서 마을을 작게 두는 것이 이 기능의 방어선이다.

**역할 분담.** 저장과 로드 직렬화는 CLAUDE.md 1번의 사용자 작성 영역이다.
Claude 는 설계안, 시그니처, 빈칸 골격, 의사코드, 리뷰까지 한다.
마을 씬 구성과 상호작용은 에디터 작업과 작은 코드라 함께 본다.

**창을 만들었다가 지웠다.** 선택대 하나와 카드가 늘어선 창을 다 쓴 뒤에,
'무기마다 상호작용 자리를 두면 되지 않나' 는 제안이 나왔고 그쪽이 분명히 나았다.
**UI 230줄과 이동 막기 장치가 함께 사라졌다.** 쓰기 전에 지워서 버린 비용은 그 코드를 쓴 시간뿐이다.
`PlayerInputReader` 에 넣었던 `SetMoveBlocked` 도 쓸 곳이 없어져 되돌렸다.

**숫자 키로 무기를 바꾸는 길은 `#if UNITY_EDITOR` 로 감쌌다.** 무기를 고르는 정식 경로가 생겼고,
그 길은 해금을 지나쳐 잠긴 무기도 들린다. 가방의 휠 팔레트를 지운 것과 같은 판단인데,
**던전에서 무기를 바꿔 보는 수단이 없어지면 개발이 불편해** 지우는 대신 에디터 전용으로 뒀다.

**무기 번호가 네 곳에 있다.** `UnlockRules.Rules` 의 순서, `PlayerAttack` 의 무기 배열,
무기대의 `Weapon Index`, 저장된 `SelectedWeapon` 이다. 인스펙터에서 어긋나면 조용히 틀린다.
무기가 셋이라 눈으로 확인할 수 있어 그대로 뒀다. **늘어나면 데이터 하나로 묶어야 한다.**

**`JsonUtility` 가 무엇을 거르고 무엇을 흘려보내는지 눌러 보고 확인했다.**

| 망가뜨린 것 | 결과 |
|---|---|
| 중괄호나 쉼표를 지운다 | 예외. `catch` 가 받아 기본값으로 시작한다 |
| 파일에 `null` 네 글자만 둔다 | `FromJson` 이 `null` 을 돌려준다. `null` 검사에서 걸린다 |
| `"Version"` 값을 2로 바꾼다 | 버전 검사에서 걸린다 |
| **키 이름을 바꾼다** | **안 걸린다.** 모르는 키는 버리고 그 필드는 기본값이 된다 |
| **숫자 자리에 글자를 넣는다** | **안 걸린다.** 예외 없이 0이 된다 |
| 값만 엉뚱한 숫자로 바꾼다 | 안 걸린다. 그대로 들어온다 |

**즉 구조가 깨진 것만 예외가 되고, 값의 고장은 전부 조용히 지나간다.**
엄격하게 읽으려면 다른 파서를 들여야 하는데 그건 패키지 추가이고 이 범위가 아니다.

**그대로 두기로 했다.** 값이 틀려서 실제로 문제가 되는 필드는 `SelectedWeapon` 하나이고,
그것은 쓰는 쪽에서 `UnlockRules.IsUnlocked` 로 거른다. 범위 밖 번호(99 같은 것)도 같은 자리에서 걸린다.
나머지 셋은 기록일 뿐이라 숫자가 커지든 작아지든 게임이 깨지지 않는다.
**저장 파일을 손으로 고치는 것은 변조이고, 변조 방지는 경계에서 뺐다.**

**이름을 두 번 바꿨다.** 처음에 `MetaRecord` 와 `Logic/Meta/` 로 적었는데
'메타' 는 로그라이트 장르의 기획 용어이지 코드에서 흔한 이름이 아니다.
`PlayerProgress` 로 바꿨다가 그것도 버렸다. **이 저장소에서 `Player~` 는 플레이어 오브젝트에
붙는 컴포넌트를 뜻하고**(`PlayerStats`, `PlayerAttack`, `PlayerMotor`, `PlayerInputReader`),
이 클래스는 컴포넌트가 아니다. `GameProgress` 도 후보였지만 **'지금 판이 어디까지 왔나' 로
읽힐 자리가 생길 수 있어** 뺐다. 그런 값을 보는 클래스가 나오는 날 두 '진행' 이 생긴다.

**`SaveData` 로 닫았다.** 가장 널리 통하는 이름이고 저장 파일에 들어가는 덩어리가 맞다.
이 저장소에서 `~Data` 가 ScriptableObject 에셋을 뜻하는 것과 겹치지만,
에셋은 전부 `Scripts/Data/` 에 있고 `CreateAssetMenu` 가 달려 있어 자리로 갈린다.
폴더 이름 `Progress` 는 주제 이름이라 그대로 뒀다. `Save` 는 `Logic` 이 파일을 모른다는
경계를 이름부터 흐리고, `Unlocks` 는 기록까지 담는 것에 비해 좁다.

**`JsonUtility` 와 `PlayerPrefs` 중 무엇을 쓸지는 계단에서 정한다.** 면접에서 바로 나올 질문이라
고른 이유를 적어 둔다. 지금 기운 쪽은 파일에 JSON 으로 쓰는 것이다.
`PlayerPrefs` 는 윈도우에서 레지스트리에 키와 값으로 들어가 **구조가 있는 데이터에 맞지 않고
사람이 열어 보기 어렵다.** 다만 경로와 권한을 신경 쓰지 않아도 되는 것은 장점이다.
