# 아이템 15종 채우기

## 왜 필요한가

**시너지 넷으로도 배치의 정답이 뻔했고, 원인은 가방에 든 아이템의 수였다.**
[시너지 판단](../decisions/synergy-needs-more-items.md)의 결론이다.

> 검 옆에 붙을 아이템이 셋뿐이라 귀퉁이에서도 셋이 다 붙을 수 있었다.

지금은 아이템이 넷뿐이라 가방에 그 이상을 넣어 볼 수 없다.
같은 아이템을 여러 번 넣는 것은 판단에서 뺐다. 아이템 개수와 배치의 효과가 섞이기 때문이다.

GDD 스코프 표의 목표도 15종이다. 어차피 해야 하는 일이며,
**이번에는 그 일이 시너지 판단의 재료가 된다.**

## 어디까지 만드는가

| | 하는가 |
|---|---|
| 15종의 데이터를 만들어 가방에 넣을 수 있게 한다 | **한다** |
| 넣는 수를 바꿔 가며 배치의 정답이 뻔한지 다시 판단한다 | **한다** |
| 밸런싱을 정교하게 다듬는다 | 하지 않는다 |
| 한 판에 아이템을 몇 개 얻는지 정한다 | 하지 않는다. 절차적 방 배치에서 정한다 |

## 무엇을 만드는가

**게임 로직 코드는 한 줄도 늘지 않는다.** 이것이 이 기능이 증명할 것이다.
바뀌는 코드는 디버그 가방 UI 와 `ItemData` 의 크기 제한뿐이다.
[아이템 효과 설계](../decisions/item-effect-design.md)가 '15종은 에셋만 만들면 된다' 고
적었고, 이번에 실제로 확인한다.

| 무엇 | 누가 |
|---|---|
| 값 표 (크기, 색, 효과, 시너지) | Claude 가 초안, 사용자가 결정 |
| `ItemData` 의 크기 제한을 네 칸 이하로 넓힌다 | Claude (ScriptableObject 필드 정의) |
| 아이템 에셋 11개 (`.asset`, `.meta`) | **Claude 가 파일로 만든다.** 사용자가 인스펙터에서 확인 |
| 디버그 가방에서 15종 고르기 | Claude (UI 보일러플레이트) |
| 팔레트에 15종 연결 | 사용자 (씬 인스펙터). Claude 가 씬 파일로 확인 |

에셋을 파일로 만드는 것은 에디터 입력과 파일이 어긋난 일을 네 번 겪었기 때문이다.
값 표를 먼저 합의하고, 기존 에셋의 YAML 을 본떠 만든다.

## 동작 정의

### 15종의 이름

[아이템 효과 설계](../decisions/item-effect-design.md)의 목록을 그대로 쓴다.
검, 부츠, 갑옷, 장갑은 이미 있다. **새로 만드는 것은 열하나다.**

> 대검, 단검, 날개, 방패, 반지, 목걸이, 부적, 룬, 심장, 깃털, 망치

### 값 표가 지켜야 할 것

- 효과는 **네 스탯 안에서** 정한다. 새 스탯을 만들지 않는다.
- 크기는 **네 칸을 넘지 않는 직사각형**이다. GDD 스코프 표의 '1~4칸' 그대로다.
  `1×1`, `1×2`, `2×1`, `2×2` 에 더해 **`1×3`, `3×1`, `1×4`, `4×1` 을 쓸 수 있다.**
  지금은 `[Range(1, 2)]` 가 변을 2로 막고 있어 이것을 푼다.
  네 칸을 넘는 크기(`2×3` 등)는 인스펙터에서 걸러낸다.
- **크기가 한쪽에 몰리지 않는다.** 크기가 공간 압박을 정한다.
- **긴 직사각형은 시너지와 맞물린다.** 눕힌 `1×4` 는 네 열에 걸쳐 같은 열에 강하고,
  세우면 네 행에 걸쳐 같은 행에 강하다. 대신 한 줄을 거의 다 막는다.
  5×5 에서는 한 변의 다섯 칸 중 넷만 덮으므로 귀퉁이는 하나만 닿는다.
  시너지와 맞물린다는 것은 확인한 것이 아니라 예상이다.
- **네 시너지 조건이 고루 쓰인다.** 한 조건만 많으면 인접 하나일 때와 같아진다.
- **크기, 효과, 시너지가 모두 같은 아이템이 둘 있으면 안 된다.**
  아이템 효과 설계가 한계로 적은 '수치 아이템끼리 비슷해 보일 위험' 을 막는 선이다.
- **아이템 안에 손해를 둘 수 있다.** 대검은 연사가, 망치는 이동이 줄어든다.
  좋은 것만 다 넣으면 된다는 답을 깨는 장치이며 데이터만으로 된다.
- **공격력과 체력은 정수로 더한다.** 기본 공격력이 1이라 퍼센트로 주면 반올림에 묻힌다.
  퍼센트는 이동과 연사에만 쓴다.

### 값 표

계단 2 에서 정했다. 에셋 파일은 이 표를 원본으로 만든다. 기존 넷은 효과와 시너지를 그대로 둔다.

| 이름 | 크기 | 효과 | 시너지 |
|---|---|---|---|
| 검 *(기존)* | 2×2 | 공격력 +2 | 인접 하나당 공격력 +1, 모서리 공격력 +3 |
| 부츠 *(기존)* | 1×2 | 이동 +20% | 같은 행 하나당 이동 +5% |
| 장갑 *(기존)* | 2×1 | 연사 +15% | 같은 열 하나당 연사 +5% |
| 갑옷 *(기존)* | 1×1 | 체력 +2 | 인접 하나당 체력 +1 |
| 대검 | 1×4 | 공격력 +3, 연사 −10% | 같은 열 하나당 공격력 +1 |
| 단검 | 1×2 | 공격력 +1, 연사 +10% | 인접 하나당 연사 +5% |
| 날개 | 2×2 | 이동 ×1.15 (승산 승산) | 모서리 이동 +15% |
| 방패 | 2×2 | 체력 +2 | 같은 행 하나당 체력 +1 |
| 반지 | 1×1 | 공격력 +1 | 모서리 공격력 +2 |
| 목걸이 | 1×2 | 체력 +1, 이동 +10% | 같은 열 하나당 이동 +5% |
| 부적 | 1×1 | 없음 | 인접 하나당 공격력 +1 |
| 룬 | 1×1 | 연사 +10% | 모서리 연사 +20% |
| 심장 | 2×2 | 체력 +3 | 같은 열 하나당 체력 +1 |
| 깃털 | 1×3 | 이동 +10% | 같은 행 하나당 연사 +5% |
| 망치 | 1×3 | 공격력 +2, 이동 −10% | 같은 행 하나당 공격력 +1 |

- 크기는 한 칸 넷, 두 칸 막대 넷, 세 칸 막대 둘, 네 칸 막대 하나, 2×2 넷이다.
  **칸 수의 합이 38 이라 25칸 가방에 전부 들어가지 않는다.**
- 시너지 조건은 인접, 같은 행, 같은 열, 모서리가 넷씩이다.
- **귀퉁이는 넷인데 모서리를 원하는 아이템도 넷이다.** 검, 날개, 반지, 룬.
- 긴 막대는 반대쪽 조건과 짝을 지었다. 대검은 같은 열, 망치와 깃털은 같은 행이다.
- 날개는 승산 승산을 쓰는 유일한 아이템이다. 스탯 시스템의 세 방식이 전부 게임에서 쓰인다.
- 부적은 효과 없이 시너지만 있다. 깃털은 이동 아이템인데 시너지가 연사에 붙는다.

**색은 주 스탯 계열로 맞춘다.** 공격력 빨강, 연사 노랑, 이동 파랑, 체력 초록, 부적 회색.
효과가 둘인 단검은 빨강과 노랑 사이, 목걸이는 초록과 파랑 사이다. 기존 넷도 이 규칙으로 바꾼다.

### 가방에서 고르기

- 15종을 전부 고를 수 있다. 지금의 숫자 키 넷으로는 모자라 고르는 방법을 바꾼다.
- **지금 무엇을 골랐는지 화면에 보인다.** 색만으로는 15종을 구분하기 어렵다.
- 가방에 놓인 아이템도 무엇인지 알 수 있다.

### 판단

- 앞선 판단과 같은 질문을 던진다. **배치의 정답이 뻔한가.**
- 기준은 앞선 판단이 남긴 것을 쓴다. **'좋은 배치들이 서로 다른 모양인가'** 다.
- 가방에 넣는 수를 **몇 가지로 바꿔 가며** 본다. 한 판의 아이템 수가 정해지지 않았으므로
  수에 따라 결과가 어떻게 달라지는지를 본다. 수와 아이템 조합은 계단 6 에서 정한다.

**기준을 이렇게 센다.** 계단 1 에서 정했다.

| | 정의 |
|---|---|
| 좋은 배치 | 한 스탯을 최대로 만들면서 나머지도 더는 올릴 수 없는 배치. 목표 스탯마다 하나씩 나온다 |
| 같은 모양 | **목표를 바꿀 때 옮겨야 하는 아이템의 수**로 센다. 자리나 방향이 바뀐 아이템을 센다 |
| 뒤집기 | 가방을 좌우나 상하로 뒤집은 배치는 같은 배치로 본다. 점수가 같기 때문이다. 90도 회전은 행과 열이 바뀌어 점수가 달라지므로 다른 배치다 |
| 최선이 여럿일 때 | 가장 적게 옮기는 짝으로 센다. 가장 너그럽게 세야 '갈린다' 가 부풀려지지 않는다 |
| **합격선** | **가장 멀리 떨어진 두 목표 사이에서 아이템의 절반 이상을 옮겨야 하면 '빌드가 갈린다'** |

앞선 4개짜리 전수 조사에 대 보면, 가장 먼 짝(공격 속도 ↔ 이동 속도)도
4개 중 1개만 옮기면 된다. 합격선에 못 미쳐 '뻔하다' 가 나오며 앞선 판단과 맞는다.

**찾는 방법은 저장소 밖의 스크립트다.** 아이템이 늘면 전수 조사가 불가능하므로
무작위 배치에서 시작해 아이템을 하나씩 옮겨 보며 나아지면 받아들이는 탐색을
여러 번 되풀이한다. 값은 에셋 파일에서 읽는다.

- 진짜 최선을 보장하지 않는다. **답을 아는 4개짜리에서 전수 조사와 같은 결과를 내는지**
  먼저 확인하고 쓴다.
- `BagGrid` 의 사본이므로 EditMode 테스트의 배치로 C# 과 같은 답을 내는지 대조한다.
- 찾은 최선 배치 중 하나는 게임에서 직접 놓아 보고 대조한다.

**넣는 수와 조합은 계단 6 에서 정했다.**

| | 정의 |
|---|---|
| 넣는 수 | 5, 7, 9. 넉넉한 경우, 방마다 하나를 얻는 경우, 빠듯한 경우 |
| 조합 | 수마다 무작위 20개. **전부 들어가는 조합만 쓴다.** '무엇을 뺄까' 가 섞이지 않게 한다 |
| 목표 | 조합이 건드리는 스탯만. 이동 아이템이 없으면 '이동 최선' 은 없다 |
| 합치기 | **그 수에서 조합의 절반 이상이 합격선을 넘으면 그 수에서는 '빌드가 갈린다'** |

## 경계: 이 기능이 하지 않는 것

- **고유 행동 아이템 5종** (흡혈, 관통, 폭발, 삼중 발사, 가시) → 하지 않는다.
  아이템 효과 설계에서 미뤄 둔 것이며, 이번 판단 결과를 보고 다시 본다.
- **새 스탯, 새 시너지 조건** → 만들지 않는다.
- **직사각형이 아닌 아이템 모양** (L, T, S 등) → 하지 않는다. 칸 목록과 회전을
  새로 만들어야 하는 크기이고, 지금 넣으면 판단이 좋아졌을 때 15종 덕인지
  모양 덕인지 가를 수 없다. 계단 6 의 판단 뒤에도 뻔하면 다음 수단으로 본다.
  [기능 후보 풀](../design/feature-pool.md)에 올려 두었다.
- **가방 크기** → 바꾸지 않는다. 키우면 공간이 더 넉넉해져 앞선 판단과 반대 방향이다.
  한 판의 아이템 수와 짝으로 정해야 하므로 그때 함께 본다.
- **아이템 획득** (드롭, 보상 선택) → 하지 않는다. 방 작업에서 한다.
- **한 판의 아이템 수** → 정하지 않는다. 판단할 때만 가정한다.
- **밸런싱과 수치 스케일** → 하지 않는다. 퍼센트가 묻히는 문제는 STATUS 정리 목록에 있다.
- **아이템 설명 UI** → 만들지 않는다. 디버그 가방에서 이름만 보인다.

## 검증

**EditMode 테스트**: 해당 없음.

코드가 늘지 않는 것이 목표다. 에셋은 `Runtime` 타입이라 테스트 어셈블리가 볼 수 없다.
값 표를 지키는지는 Claude 가 에셋 파일을 읽어 확인한다.

**플레이모드 체크리스트**

- [x] 15종을 전부 가방에서 고를 수 있다
- [x] 무엇을 골랐는지, 놓인 것이 무엇인지 화면에서 알 수 있다
- [x] 새 아이템을 놓으면 값 표에 적힌 스탯이 오르고, 빼면 원래대로 돌아온다
- [x] 새 아이템의 시너지가 조건대로 붙는다. 조건마다 하나씩 확인한다
- [x] 재시작하면 가방이 빈 상태로 시작한다

## 메모

**판단 기준을 먼저 구체화해야 한다.** '좋은 배치들이 서로 다른 모양인가' 는
말로는 분명하지만 셀 방법이 없다. 무엇을 같은 모양으로 볼지 정하지 않으면
이번에도 기준이 느슨해진다.

**결과: '목표를 바꿀 때 옮겨야 하는 아이템의 수' 로 세고 합격선은 절반이다.**
값 표보다 먼저 정했다. 값을 먼저 짜면 기준을 값에 맞춰 잡게 되기 쉽다.

**크기 분포가 결과를 정한다.** 15종의 칸 수를 합하면 25를 넘길 가능성이 크다.
그러면 전부 넣을 수 없어서 무엇을 넣을지부터 선택이 된다.
그 선택이 배치의 고민인지, 아이템 고르기의 고민인지는 구분해서 본다.

**수치 스케일 문제가 드러날 수 있다.** 공격력 1에 +10% 는 반올림해도 1이다.
값 표를 짤 때 퍼센트 아이템이 화면에서 아무 변화도 없어 보이면 그렇게 기록하고
밸런싱으로 넘긴다.

**에셋 파일을 만들 때 GUID 가 겹치면 안 된다.** `.meta` 의 guid 를 새로 만든다.
Unity 가 열려 있어도 새 파일은 창에 포커스가 돌아올 때 임포트된다.
만든 뒤 파일과 인스펙터를 둘 다 확인한다.

**결과: 15종이면 배치의 모양은 갈리지만 선택은 한쪽으로 기운다.** 완료 조건 넷째의 답이며,
근거는 [15종 판단](../decisions/item-roster-judgment.md)에 있다.
5·7·9개 모두 합격선을 넘었다. 하지만 찾은 배치를 게임에 놓아 보니 연사 최선이
체력 2만 지고 나머지 셋을 전부 이겨 고를 수밖에 없었다. 기준은 '다른 빌드가 있는가' 를
봤고 느낌은 '고를 이유가 있는가' 를 봤다. **수치 조정은 난이도 튜닝으로 넘겼다.**

**수치 스케일 문제가 실제로 드러났다.** 망치의 '같은 행 하나당 공격력 +1' 이 한 배치에서
+6 을 냈다. 기본 공격력 1의 여섯 배다.

**'무엇을 넣을까' 와 '어디에 놓을까' 는 구분했다.** 판단에는 전부 들어가는 조합만 썼다.
9개에서 칸이 모자라 버린 조합은 하나였다.

**파일을 쓸 때 셸이 역슬래시를 먹었다.** 파이썬 문자열의 `\u` 와 C# 문자열의 `\n` 이
셸을 거치며 하나씩 사라져 에셋, `BagView`, 이 메모에서 세 번 멈췄다. 모두 쓰기 전에 실패해 파일은 온전했다.
`chr(92)` 와 자리표시자로 피했다.

**Unity 가 다시 쓴 에셋이 만든 파일과 같았다.** 대검의 크기를 바꿨다 되돌리고 저장했더니
Unity 가 파일을 새로 썼는데, 내용이 한 글자도 다르지 않았다. 손으로 만든 YAML 형식이
Unity 의 직렬화 결과와 같다는 뜻이다.

**명세에 틀린 말이 있었다.** `1×4` 가 귀퉁이 둘에 닿는다고 적었는데, 5×5 에서는 한 변의
다섯 칸 중 넷만 덮어 하나만 닿는다. 계단 2 를 준비하다 발견해 고쳤다.
