# 가방 그리드와 배치

## 왜 필요한가

**GDD 가 이 게임의 정체성으로 꼽은 것이 배치다.**

> **차별화 지점은 4번째 칸이다.** 아이템을 '먹는' 게 아니라
> **'어디에 놓을지 고민하는'** 것이 이 게임의 정체성이다.

지금은 아이템을 먹으면 그냥 효과가 붙는다. **놓을 자리가 없으니 고민할 것도 없다.**
이 상태로는 평범한 로그라이트다.

**그리고 `feature-pool` 이 이 기능을 A급으로 꼽았다.**

> 배치 유효성 검증 + 인접 시너지 탐색.
> 순수 로직이라 **EditMode 테스트 가능.**
> 그리드 UI 는 사각형이 정상이라 **아트 부재가 약점이 아닌 구간.**

마지막 줄이 이 프로젝트에 특히 맞다. 도형 프로토타입으로 개발하는데,
가방 그리드는 **원래 사각형이라 못생겨 보이지 않는다.**

## 왜 시너지와 나눴는가

Phase 4 의 아이템 항목은 '아이템 15종 + 시너지 규칙 4종' 하나였다.
효과 시스템을 이미 떼어냈고, **배치와 시너지도 나눈다.**

| | 이 명세 | 다음 명세 |
|---|---|---|
| 무엇 | 아이템을 그리드에 놓는다 | 배치에 따라 성능이 갈린다 |
| 검증 | **눈으로 본다** | **테스트로 본다** |

**배치 없이 시너지는 만들 수 없다.** 인접을 판단하려면 아이템이 어디 있는지
알아야 한다. 반대로 시너지 없이 배치는 성립한다.

## 무엇을 만드는가

| 어셈블리 | 무엇 |
|---|---|
| `JM2D.Logic` | 그리드 자체. 어느 칸이 비었는지, 놓을 수 있는지 |
| `JM2D.Runtime` | 위치를 갖는 아이템, 그리드 UI, 스탯 연결 |
| `JM2D.Tests.EditMode` | 배치 규칙 |

**그리드는 아이템이 무엇인지 몰라도 된다.** 어느 칸이 찼는지와 크기만 알면
배치를 판단할 수 있다. **Logic 이 `ItemData` 를 참조하면 안 되므로**
이 성질을 지키는 것이 설계 제약이다.

## 동작 정의

### 그리드

- 5 × 5 다. 크기는 고정이며 런 중에 바뀌지 않는다.
- 각 칸은 비어 있거나 아이템 하나가 차지한다.

### 아이템 크기

- 아이템은 **직사각형**이다. 1×1, 1×2, 2×1, 2×2 넷이며 최대 4칸이다.
- 크기는 아이템 종류의 성질이므로 `ItemData` 에 있다.

**임의 모양(L자 등)은 만들지 않는다.** GDD 가 '1~4칸' 만 요구하고,
칸 목록을 들고 다니면 겹침 검사와 회전이 훨씬 복잡해진다.

### 배치

- 아이템을 고르고 칸을 누르면 **그 칸을 왼쪽 위로 삼아** 놓인다.
- **놓을 수 없으면 놓이지 않는다.** 이유는 둘뿐이다.
  - 그리드 밖으로 나간다
  - 이미 다른 아이템이 있다
- 놓이는 즉시 그 아이템의 모디파이어가 스탯에 붙는다.

### 회전

- 놓기 전에 회전할 수 있다. **너비와 높이가 서로 바뀐다.**
- 1×1 과 2×2 는 회전해도 같으므로 아무 일도 일어나지 않는다.
- **놓은 뒤에는 회전할 수 없다.** 빼서 다시 놓는다.

### 제거

- 놓인 아이템을 빼면 **그 아이템이 차지하던 칸이 전부 빈다.**
- 빼는 즉시 모디파이어가 떨어진다. **그 아이템 것만 떨어진다.**
- 뺀 자리에 다른 아이템을 놓을 수 있다.

### 아이템 효과와의 관계

**가방이 아이템 목록의 주인이 된다.** 지금은 `ItemInventory` 가 목록을 들고
있는데, 아이템 명세 메모에 적어둔 대로 그 역할이 그리드로 넘어온다.

`ItemInventory` 는 남는다. **그리드가 배치를 판단하고, `ItemInventory` 가
스탯을 붙이고 뗀다.** 그리드는 스탯을 모르고 `ItemInventory` 는 좌표를 모른다.

## 경계: 이 기능이 하지 않는 것

- **시너지** → 다음 명세다. 이번에는 **어디에 놓든 효과가 같다.**
- **드래그앤드롭** → 하지 않는다. 아이템을 고르고 칸을 누른다.
  도형 프로토타입이라 드래그의 손맛이 어차피 살지 않는다. **Phase 5 폴리싱**에서 본다.
- **임의 모양** → 위에 적은 이유로 직사각형만 만든다.
- **가방 크기 변경** → 하지 않는다. 5×5 고정이다.
  '가방 확장' 아이템은 만들지 않는다.
- **아이템 획득과 드롭** → 하지 않는다. 적이 죽으면 아이템이 떨어지는 것은
  Phase 4 뒷부분이다. 이번에는 **디버그 키로 아이템을 만들어** 배치를 시험한다.
- **자동 정렬** → 하지 않는다. 배치를 고민하는 것이 이 게임의 핵심인데
  자동으로 정리해 주면 그 고민이 사라진다.
- **가방 저장** → Phase 5 다.

## 검증

**EditMode 테스트**: 이번 기능의 주된 검증 수단이다.

그리드는 좌표와 크기만 다루므로 순수 로직이다. 씬도 UI 도 필요 없다.

- [x] 빈 그리드에 1×1 을 놓으면 성공한다
- [x] 같은 칸에 또 놓으면 실패한다
- [x] **겹치는 위치에 2×2 를 놓으면 실패한다** (한 칸만 겹쳐도)
- [x] 그리드 밖으로 나가면 실패한다
- [x] **2×2 를 (4, 4) 에 놓으면 실패한다** (오른쪽 아래 경계)
- [x] 회전하면 너비와 높이가 바뀐다
- [x] **세로로는 안 들어가는 자리에 회전해서 놓으면 성공한다**
- [x] 빼면 그 아이템이 차지하던 칸이 전부 빈다
- [x] 뺀 자리에 다른 아이템을 놓을 수 있다
- [x] 5×5 에 1×1 을 25개 놓을 수 있고 26번째는 실패한다

> 세 번째와 다섯 번째가 실수하기 쉬운 자리다. 겹침 검사는 **아이템이 차지하는
> 모든 칸**을 봐야 하고, 경계 검사는 **왼쪽 위가 아니라 오른쪽 아래**를 봐야 한다.
>
> 일곱 번째가 회전이 실제로 쓸모 있는지 확인한다.

**플레이모드 체크리스트**

- [x] 5 × 5 그리드가 보이고 빈 칸과 찬 칸이 구분된다
- [x] 아이템을 고르고 칸을 누르면 놓인다
- [x] 겹치는 자리를 누르면 놓이지 않는다
- [x] 경계를 넘는 자리를 누르면 놓이지 않는다
- [x] `R` 로 회전하면 놓기 전에 모양이 바뀐다
- [x] **놓으면 스탯이 즉시 오른다**
- [x] **빼면 스탯이 즉시 내린다. 다른 아이템 효과는 남는다**
- [x] 같은 아이템을 두 자리에 놓으면 효과가 두 번 적용된다
- [x] 재시작하면 빈 가방으로 시작한다

## 메모

**아이템 크기를 `ItemData` 에 넣어야 한다.** 지금은 효과만 있다.
너비와 높이 둘이면 되는데, **1~4칸이라는 제약을 코드로 막을지**는 계단에서 정한다.
3×2 같은 것을 인스펙터에서 넣을 수 있게 두면 나중에 6칸 아이템이 생긴다.

**`ItemInstance` 가 회전 상태를 갖게 된다.** 아이템 명세에서 '지금은
`ItemData` 참조 하나뿐' 이라고 적어둔 것이 여기서 채워진다.

**위치는 갖지 않는다.** 처음에는 위치도 넣으려 했는데, 그리드의 배열이 이미
위치를 담고 있어 **같은 정보가 두 곳에 생긴다.** 어긋나면 어느 쪽이 맞는지
알 수 없어진다. UI 가 아이템을 그릴 때도 시너지를 탐색할 때도 그리드에 물으면
되므로 필요하지도 않다.

**그리드가 아이템 타입을 모르게 하는 방법을 정해야 한다.**
`BagGrid` 는 Logic 이라 `ItemData` 를 참조할 수 없다. 제네릭으로 두거나
크기를 인자로 받는 방법이 있는데, `Pool<T>` 에서 쓴 방식과 비슷해질 것 같다.

**UI 를 uGUI 로 그릴지 직접 배치할지 정해야 한다.**
`Grid Layout Group` 을 쓰면 칸 배치가 공짜지만, 아이템이 여러 칸을 차지하는
표현이 어려워진다. 계단에서 판단한다.

**가방을 언제 여는지도 정해야 한다.** 항상 보이게 할지, 키를 눌러 열지,
방 클리어 후에만 열지. **게임 흐름과 얽히므로 UI 계단에서 다룬다.**

**결과: 새로 만든 계산은 배치 판단뿐이다.** 스탯도 모디파이어도 출처 추적도
Phase 3 에서 만든 것을 그대로 썼다. 근거와 대안은
[가방 그리드 설계](../decisions/bag-grid-design.md)에 있다.

**미리보기를 넣었다.** 명세에는 없던 것인데, `R` 을 눌러도 아무것도 안 보이면
회전했는지 알 수 없어 체크리스트를 만족할 수 없었다. 놓을 수 있는지도
색으로 알려주므로 클릭하기 전에 판단할 수 있다.

**회전을 두 상태로 뒀다.** 직사각형은 180도를 돌려도 차지하는 칸이 같아
네 방향이 의미가 없다. 임의 모양을 만들지 않기로 한 결정의 파급효과다.

**UI 좌표에서 한 번 크게 헤맸다.** 앵커와 피벗을 인스펙터에 맡겼다가
클릭 좌표가 격자 절반만큼 어긋났다. 그리기는 멀쩡한데 읽는 쪽만 틀려서
원인을 찾기 어려웠다. **계산에 쓰이는 값은 코드가 못 박아야 한다는 기준**을
여기서 얻었다.

**테스트에서도 하나 배웠다.** 준비 단계에 `Assert` 를 안 붙였더니,
경계 조건을 뒤집었을 때 **깨져야 할 테스트가 통과했다.** 준비가 조용히
실패하면 테스트가 엉뚱한 상황을 시험한다.
