# 스탯 · 모디파이어 시스템

## 왜 필요한가

GDD의 아이템 20종이 전부 이 시스템 위에 올라간다. '공격력 +10', '이동속도 +20%'가
아이템마다 하드코딩되면 20종을 만들 수 없다.

**포트폴리오 관점의 이유가 하나 더 있다.** `feature-pool` 이 이 기능을
**면접 대화가 가장 깊게 들어가는 주제**로 꼽았다. 계산 순서와 스택 규칙에는
정답이 없고 게임마다 다른 선택을 하므로, 왜 그렇게 정했는지를 물을 수 있다.

**그리고 이 프로젝트에서 EditMode 테스트가 처음 붙는 자리다.**
`JM2D.Logic` 어셈블리도 여기서 처음 쓰인다. asmdef 를 넷으로 나눈 이유가
지금까지는 설계 의도였는데, 여기서 실제로 증명된다.

## 무엇을 만드는가

**두 어셈블리에 나눠 만든다. 이 경계가 이번 기능의 핵심이다.**

| 어셈블리 | 무엇 | 왜 거기인가 |
|---|---|---|
| `JM2D.Logic` | 스탯 값 계산, 모디파이어 | MonoBehaviour·씬·시간에 의존하지 않는다 |
| `JM2D.Runtime` | 플레이어의 스탯 묶음, 각 컴포넌트에 값 공급 | 씬 오브젝트와 붙는다 |
| `JM2D.Tests.EditMode` | 계산 규칙 테스트 | Logic 만 참조한다 |

**Logic 이 순수해야 테스트가 씬 없이, 플레이 없이 돈다.** 이 성질을 지키는 것이
설계 제약이자 이번 기능의 검증 대상이다.

## 동작 정의

### 다루는 스탯

넷이다. **계산 구조를 증명하는 최소치**이며, 서로 다른 성격을 하나씩 갖는다.

| 스탯 | 성격 | 쓰는 곳 |
|---|---|---|
| 최대 체력 | 정수 | `Health` |
| 이동 속도 | 실수 | `PlayerMotor` |
| 공격력 | 정수 | `PlayerAttack` 이 `Launch` 로 넘긴다 |
| 공격 속도 | 실수, 배율 | `PlayerAttack` 의 연사 간격 |

**공격 속도가 오르면 연사 간격이 줄어든다.** 스탯은 올라가는 방향으로 두고,
간격은 그것에서 계산한다. '연사 간격 -20%'보다 '공격 속도 +20%'가 읽기 쉽다.

### 모디파이어 세 종류와 계산 순서

```
최종값 = (기본값 + 가산합) × (1 + 승산가산합) × ∏(1 + 승산승산ᵢ)
```

- **가산**: 그냥 더한다. 공격력 +5
- **승산 가산**: 같은 종류끼리 더한 뒤 한 번 곱한다. +20%가 둘이면 **+40%**
- **승산 승산**: 각각 따로 곱한다. ×1.2가 둘이면 **+44%**

**둘째와 셋째를 나누는 것이 밸런싱의 핵심이다.** 같은 계열 아이템을 쌓을수록
이득이 줄어야 빌드가 한쪽으로 무너지지 않는다. 희귀 아이템만 승산 승산으로 준다.

**추가한 순서가 결과를 바꾸지 않는다.** 어떤 순서로 넣어도 같은 값이 나와야 한다.

### 출처 추적

모디파이어는 **자기가 어디서 왔는지**를 갖는다.

- 출처를 지정해 **그 출처의 모디파이어만 한 번에 제거**할 수 있다.
- 값이 똑같은 모디파이어가 여럿 있어도 **출처가 다르면 서로 구분된다.**

**출처 없이는 제거를 만들 수 없다.** 공격력 +10짜리 아이템 둘을 넣었다가 하나를
빼면, 똑같이 생긴 모디파이어 둘 중 어느 것을 지울지 알 방법이 없다.

지금 아이템은 없다. **그럼에도 지금 넣는 이유는 나중에 붙일 수 있는 종류가
아니기 때문이다.** 모디파이어를 만들 때 함께 들어가야 하고,
나중에 넣으려면 모든 생성 지점을 고쳐야 한다.

### 값이 언제 계산되는가

- 스탯 값을 읽을 때마다 다시 계산하지 않는다. **모디파이어가 늘거나 줄었을 때만** 다시 센다.
- 읽는 쪽은 이벤트를 구독하지 않고 그냥 읽는다.

**컴포넌트가 스탯 값을 자기 필드로 복사하지 않는다.** 데이터 분리 때와 반대다.
데이터는 시작할 때 한 번 정해지지만, **스탯은 게임 도중에 바뀌는 것이 목적**이다.

## 경계: 이 기능이 하지 않는 것

- **지속시간 만료** → 넣지 않는다. 만료를 처리하려면 누군가 매 프레임 시간을
  흘려보내야 하고, 그러면 `JM2D.Logic` 이 시간에 묶인다. **Logic 을 순수하게
  유지하는 것이 asmdef 를 나눈 이유 전체다.** 아이템은 영구라 쓸 데도 없다.
  포션류가 실제로 생기면 만료 판단을 Logic 밖에 두면 된다.
- **적의 스탯** → 하지 않는다. 엘리트 적과 층별 강화는 Phase 4다.
  지금 적에 붙여도 검증할 아이템이 없다.
- **조건부 모디파이어** → 하지 않는다. '체력 50% 이하일 때 +20%' 같은 것은
  상태를 감시해야 해서 순수 계산이 아니게 된다.
- **스탯 사이의 파생** → 하지 않는다. '힘 1당 공격력 2' 같은 것은 계산 그래프가
  되고 순환 참조를 걱정해야 한다. 아이템 20종에 필요하지 않다.
- **스탯 표시 UI** → 하지 않는다. Phase 5다.
- **아이템** → Phase 4다. 이번에는 **디버그 키로 모디파이어를 직접 붙여** 검증한다.
- **세이브** → Phase 4 이후다.

## 검증

**EditMode 테스트**: 이번 기능의 주된 검증 수단이다.

`JM2D.Tests.EditMode` 는 `JM2D.Logic` 만 참조한다. 씬도 플레이 모드도 필요 없다.

- [x] 모디파이어가 없으면 기본값이 그대로 나온다
- [x] 가산만 있으면 더해진다
- [x] 승산 가산 +20% 가 둘이면 1.4배가 된다
- [x] 승산 승산 ×1.2 가 둘이면 1.44배가 된다
- [x] 세 종류가 섞이면 가산 → 승산 가산 → 승산 승산 순서로 적용된다
- [x] **추가한 순서를 바꿔도 결과가 같다**
- [x] 한 출처의 모디파이어만 제거되고 다른 출처는 남는다
- [x] **값이 똑같은 모디파이어가 여럿일 때 한 출처만 지워도 나머지는 남는다**
- [x] 전부 제거하면 기본값으로 돌아온다

> 여섯 번째와 여덟 번째가 눈으로는 확인할 수 없는 항목이다.
> **테스트가 아니면 검증할 방법이 없는 종류**이며, 그래서 여기에 테스트를 쓴다.

**플레이모드 체크리스트**

- [x] 디버그 키로 이동 속도 +50% 를 걸면 눈에 띄게 빨라진다
- [x] 같은 키를 한 번 더 눌러 제거하면 원래 속도로 돌아온다
- [x] 공격력 모디파이어를 걸면 적이 더 적은 발수에 죽는다
- [x] 공격 속도 모디파이어를 걸면 연사가 빨라진다
- [x] 최대 체력 모디파이어를 걸면 **HP 바가 즉시 갱신된다**
- [x] 재시작하면 모디파이어가 전부 사라진 상태로 시작한다

> 다섯 번째를 주의해서 본다. 최대 체력이 바뀌면 현재 체력을 어떻게 할지,
> UI 에 어떻게 알릴지가 함께 걸린다. 나머지 셋보다 까다롭다.

## 메모

**정수 스탯의 반올림을 정해야 한다.** 최대 체력 3에 +15% 면 3.45다.
내릴 것인가 반올림할 것인가. 어느 쪽이든 **테스트에 값을 박아 넣게 되므로
먼저 정하고 시작해야 한다.**

**최대 체력이 늘어날 때 현재 체력을 어떻게 할지도 정해야 한다.**
같이 늘릴 것인가, 비율을 유지할 것인가, 그대로 둘 것인가. 세 게임이 세 가지로
다르게 한다. 계단에서 다룬다.

`Health.SetMaxHealth` 의 이름과 동작을 여기서 다시 본다.
[정리 목록](../progress/STATUS.md)에 올려둔 항목이다. 지금은 초기화 전용인데
스탯이 최대 체력을 바꾸기 시작하면 그 전제가 깨진다.

**플레이어 수치가 아직 프리팹에 있다.** ScriptableObject 분리 때 일부러
남겨둔 것으로, 이 기능이 다루게 된다. 다만 **데이터로 뺄지 스탯의 기본값으로
둘지는 별개 판단**이라 계단에서 정한다.

**결과: 테스트가 22개가 됐다.** 명세에 적은 9개에서 늘었다. 늘어난 것들은
전부 **구현 중에 실제로 겪은 문제**에서 나왔다.

| 추가된 테스트 | 왜 생겼나 |
|---|---|
| 전부_제거하면_음수까지_사라진다 | `RemoveAll` 이 조건부 삭제라 음수만 남던 버그 |
| 캐시 갱신 셋 | 기존 테스트가 '설정 → 한 번 읽기' 라 무효화를 못 봤다 |
| 정수 반올림 셋 | 은행가 반올림 함정 |
| 변경 알림 넷 | 이벤트 추가 후 세 경로를 각각 확인 |

**버그를 찾으면 그것을 잡는 테스트를 남기는 방식**으로 늘었다.
처음부터 22개를 설계한 것이 아니다.

**`?.` 을 지우면 22개 중 19개가 깨진다.** 처음에는 하나만 깨질 것으로 예상했는데,
테스트 대부분이 구독자 없이 `AddModifier` 를 부르기 때문이었다.
**구독자가 있는 경우가 예외이고 없는 경우가 기본**이라는 사실이
실패 개수로 드러났다.

**정수 스케일 문제를 발견했지만 고치지 않았다.** 공격력 1에 +10% 는
어떤 반올림 방식으로도 1이다. 기본 수치를 키워야 풀리는데 밸런스 전체가
움직이므로 Phase 4로 미뤘다. 결정 문서의 한계 항목에 있다.
