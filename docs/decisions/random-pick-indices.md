# 후보 뽑기는 아이템을 모르고 번호만 다루며, 부분 셔플로 뽑는다

## 문제

보상 후보 셋은 **서로 달라야** 하고, 같은 시드면 **같은 셋**이 나와야 한다.

여기에 어셈블리 경계가 걸린다. `Logic` 은 `Runtime` 을 참조하지 않는데 `ItemData` 는 `Runtime` 에 있다.
**`Logic` 에 두면 아이템을 볼 수 없고, `Runtime` 에 두면 EditMode 테스트가 무거워진다.**

## 검토한 대안

### 어디에 두고 무엇을 다루나

| 안 | 판단 |
|---|---|
| `Runtime` 에서 `ItemData[]` 를 받아 셋을 고른다 | 쓰기 편하다. 테스트가 에셋을 만들어야 하고 `Logic` 의 테스트 습관에서 벗어난다 |
| **`Logic` 에서 번호만 다룬다** | `Distinct(15, 3, 난수)` 가 `[7, 2, 11]` 을 준다. 번호로 아이템을 꺼내는 일은 부르는 쪽이 한다. 씬도 에셋도 없이 테스트된다 |

게임 용어가 하나도 없어 `Logic/Common/` 에 뒀다. 규칙이 `Common` 의 조건으로 정확히 그것을 적고 있다.

### 어떻게 뽑나

| 안 | 판단 |
|---|---|
| 거부 샘플링 (뽑고 중복이면 다시) | 짧다. 뽑을 수가 종류 수에 가까우면 헛도는 횟수가 늘고 최악에는 끝나지 않는다 |
| 전체를 섞고 앞의 셋 | 이해하기 쉽다. 셋만 필요한데 열다섯 번 일한다 |
| **부분 셔플 (피셔 예이츠를 뽑을 수만큼)** | 뽑는 수만큼만 일하고 **중복이 구조적으로 불가능하다.** 배열이 늘 순열이고, 뽑힌 값은 앞으로 옮겨져 고르는 범위에서 빠진다 |

### 뽑을 수가 종류 수보다 많으면

**예외를 낸다.** 조용히 둘만 돌려주면 창에 둘만 뜨고 왜 그런지 알 수 없다. 아이템 15종은 고정이라 지금은 닿지 않는 경계다.

## 선택과 이유

**`RandomPick.Distinct(count, pick, System.Random)` 이 번호 배열을 돌려준다. 난수는 매개변수로 받는다.**

- 난수를 밖에서 받아야 테스트가 시드를 넣어 '같은 시드면 같은 셋' 을 시험할 수 있다. 4-A 의 배치 생성, 4-C 의 조합 뽑기와 같은 방식이다.
- 고르는 범위가 `random.Next(i, count)` 인 것이 핵심이다. **`Next(0, pick)` 으로 쓰면 앞자리 안에서만 섞여 결과가 늘 `0, 1, 2` 가 된다.**
  눈으로는 그럴듯해 보여서, 테스트가 시드 1000개를 돌려 15개 번호가 모두 한 번씩은 나오는지까지 본다.

## 결과

- `RandomPickTests` 는 메서드 6개, `[TestCase]` 를 포함해 실행 11개다. EditMode 테스트는 154 개가 됐다.
- 채울 때 **맞바꾼 뒤 엉뚱한 자리를 읽는 실수**가 한 번 있었다(`result[i] = pool[j]`). 결과가 늘 `0, 1, 2` 언저리로 나오고 중복까지 생겼다.
  시드 1000개 테스트가 그것을 잡았다.
- `Logic` 이 아이템을 모른다는 것이 asmdef 4분할이 실제로 무엇을 막는지 보여주는 예가 됐다.

## 한계 / 남은 문제

- **분포가 치우치는 실수(`Next(0, count)`)는 테스트로 잡지 않는다.** 잡으려면 수십만 번 돌려 분포를 재야 하고, 보상 후보에서 그 정도 치우침은 눈에 띄지 않는다.
  중복과 범위는 잡히고, 앞자리만 섞는 실수도 잡힌다.
- 뽑을 때마다 크기 `count` 의 배열을 새로 만든다. 방을 깰 때 한 번이라 문제가 되지 않는다.
