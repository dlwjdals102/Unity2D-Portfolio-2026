# 방 안 장애물은 구역마다 하나씩 놓고, 적은 BFS 거리표를 따라 돈다

## 문제

**방이 넓고 비어 있었다.** 4-C 에서 웨이브가 방을 채운 뒤에도 그랬고, 관찰 항목으로 미리 적어 둔 기준에 걸렸다.

장애물만 넣으면 적 AI 가 망가진다. 적은 플레이어 쪽으로 곧장 움직여(`DirectionToTarget`) 기둥 뒤의 플레이어를 쫓다 기둥에 붙은 채 멈춘다.
**그래서 장애물과 길찾기는 한 몸이다.**

## 검토한 대안

### 길찾기를 무엇으로 하나

| 안 | 판단 |
|---|---|
| Unity 의 NavMesh (`com.unity.ai.navigation`) | **패키지 소스와 문서 파일을 읽어 확인했다.** 런타임 API 에 `Collider2D` 와 `Tilemap` 이 한 번도 나오지 않고, `NavMeshSurface` 는 재료를 렌더링 메시나 3D 콜라이더에서 모은다. 2D 타일맵을 쓰려면 외부 프로젝트를 얹거나 가짜 메시를 만드는 다리를 직접 놓아야 한다 |
| 적마다 A* | 적이 늘수록 탐색이 늘고, 우선순위 큐와 휴리스틱이 붙어 코드가 길어진다 |
| **흐름장(BFS 거리표)** | 플레이어 칸에서 한 번 BFS 를 돌려 칸마다 거리를 적어 두고, 적은 이웃 중 작은 쪽으로 걷는다. **적이 몇 마리든 계산이 한 번이다** |

사용자가 '버그가 많으니 다른 방안을 봐야 하지 않나' 고 물어 한 번 더 따졌다. 그때까지 나온 버그가 전부 **조종과 물리**에서 나왔고 격자와 거리표는 한 번도 틀리지 않아, 길찾기를 바꿔도 같은 버그가 남는다고 판단했다.
NavMesh 의 진짜 차이는 알고리즘이 아니라 `NavMeshAgent` 가 물리 대신 위치를 직접 옮긴다는 점이다. 근거는 [조종에서 겪은 끼임](enemy-steering-jams.md)에 있다.

### 이웃을 넷으로 보나 여덟으로 보나

처음에는 넷(상하좌우)으로 만들었다. **기둥을 사이에 두고 적과 플레이어가 일직선이면 좌우 이웃의 거리가 같아져 적이 제자리에서 꿈틀거렸다.**
0.4 초마다 다시 고를 때 반대쪽이 뽑히면 되돌아가기 때문이다. 이웃을 여덟으로 늘리자 대각선 이웃이 한 걸음 가까워 동점이 깨졌다.
**실험으로 확정했다.** 다른 조건을 그대로 두고 이웃만 넷으로 되돌리자 증상이 재현됐고, 여덟으로 되돌리자 사라졌다.

대각선은 **양옆 두 칸이 모두 비어 있을 때만** 허용한다. 모서리를 스치며 지나가면 몸이 낀다. 이 규칙을 `FlowField.CanStep` 한 곳에 두고,
거리표를 만들 때와 적이 다음 칸을 고를 때가 같은 함수를 부른다. 둘이 어긋나면 갈 수 없는 칸을 고른다.

### 장애물을 어떻게 놓나

| 안 | 판단 |
|---|---|
| 순전히 난수 | 한쪽 구석에 몰린다. 200판을 시뮬레이션해 보니 가장 가까운 두 덩어리가 2칸까지 붙었다 |
| **구역을 나눠 구역마다 하나** | 방 안쪽을 가로 3, 세로 2 로 나누고 `RandomPick.Distinct` 로 서로 다른 구역을 고른다. 보상 후보를 뽑는 계산을 그대로 쓴다 |

구역만으로는 경계에 붙는 경우가 남아 **덩어리 사이 최소 거리(체스판 거리 4)** 와 **구역 테두리 여백(1)** 을 더했다.
사용자가 '구역을 조금 축소하면 낫지 않겠나' 고 제안했고, 200판 시뮬레이션에서 여백 1 이 '자리를 못 찾는 덩어리' 를 7/987 에서 0 으로 줄이면서 거리는 그대로 지켰다.

## 선택과 이유

**장애물은 시드로 정해 방 프리팹의 `Obstacles` 타일맵에 칠하고, 적은 `RoomFlowField` 가 주는 다음 칸으로 걷는다.**

- **격자는 벽 타일에서 읽는다.** '가장자리 한 줄이 벽' 이라고 적지 않았다. 문 구멍도 '가장자리인데 타일이 없는 칸' 으로 찾아, 프리팹에서 문을 넓히면 따라온다.
- **놓은 뒤 BFS 로 길을 검사하고 막히면 다시 놓는다.** 4-A 가 '한 줄 걷기라 검증이 늘 통과한다' 며 뺀 검증이 여기서 살아났다.
  다만 지금 값(덩어리 4~6, 여백 넉넉)에서는 **200판 중 한 번도 실패하지 않았다.** 값을 조이면 바로 일하는 안전망이라는 점을 적어 둔다.
- **적은 `IPathField` 하나만 안다.** '다음에 갈 자리' 를 묻는 메서드 하나다. 적이 방과 격자와 BFS 를 모르고, `Rooms` 와 `Enemy` 사이에 반대 방향 참조가 생기지 않는다.
- **적은 그 자리를 붙잡고 간다.** 도착하거나 0.4 초가 지나야 다시 묻는다. 매 프레임 고르면 칸 경계에서 자기 칸이 뒤집혀 선택이 흔들린다.
  0.4 초는 한 칸을 걷는 시간(속도 3 기준 0.33 초)보다 조금 길게 잡았다.
- **거리표는 플레이어가 칸을 옮길 때만 다시 쓴다.** 576칸이라 비용이 작지만 같은 값을 다시 만들 이유가 없다.

## 결과

- EditMode 테스트가 154 개에서 **186 개**가 됐다(`RoomGrid` 10, `FlowField` 11, `ObstaclePlacer` 11).
  '기둥을 돌아가는 거리가 직선보다 크다', '대각선으로 모서리를 뚫지 않는다', '시드 100개에서 길이 막히지 않는다' 가 이 기능의 증거물이다.
- 방마다 평균 13칸이 막히고, 덩어리는 서로 네 칸 이상 떨어진다. 고정 시드면 같은 배치가 나온다.
- 장애물이 투사체를 막아 엄폐가 생겼다. 벽과 같은 취급이라 따로 코드를 넣지 않았다.
- **GDD 의 '방 프리팹 8' 을 이 판단으로 닫는다.** 모양이 다른 방 여덟 개 대신 장애물이 그 역할을 한다.

## 한계 / 남은 문제

- **대각선을 한 걸음으로 세어 거리가 실제보다 짧다.** 쫓아가는 데는 문제가 없지만 '몇 걸음' 이 실제 거리와 다르다. 거리 자체를 쓰는 곳이 생기면 다시 본다.
- **목표를 다시 고르는 0.4 초가 상수다.** 적 이동 속도가 느려지면 한 칸을 걷기 전에 다시 고르게 된다. 속도에서 계산하도록 바꿀 수 있다.
- **길 검증이 지금 값에서는 실패하지 않는다.** 4-A 가 검증을 뺀 이유와 같은 상태다. 값을 조일 때 다시 확인한다.
- **출현 지점은 모든 방이 같고 장애물만 다르다.** 방 프리팹이 하나라서다.
- 방이 비어 보이는 문제는 줄었지만, 사용자가 **'맵 자체가 넓게 느껴진다'** 고 적었다. 방 크기(32 × 18)와 카메라 크기(5)의 관계이고 6번 난이도 튜닝에서 함께 본다.
