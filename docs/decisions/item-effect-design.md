# 아이템은 수치 데이터로 만들고, 개체는 인스턴스로 구분한다

## 문제

GDD 가 아이템 20종을 **데이터만 추가하면 되도록** 설계하라고 요구한다.
스탯 시스템은 Phase 3 에서 만들어 뒀으니 그 위에 아이템을 얹으면 되는데,
세 가지를 정해야 했다.

1. 에셋이 '어느 스탯' 을 어떻게 가리킬 것인가
2. 같은 종류 아이템 둘을 어떻게 구분할 것인가
3. **정말 20종이 데이터만으로 되는가**

## 1. 스탯을 값으로 지목한다

프로퍼티는 코드에만 있는 이름이라 에셋에 담기지 않는다.
`.asset` 파일에는 숫자와 문자열, 다른 에셋 참조만 저장된다.

**`StatType` 열거형을 만들었다.** 열거형은 정수라 파일에 담기고,
인스펙터에서는 드롭다운으로 보인다. 실제 저장된 모습은 이렇다.

```yaml
_modifiers:
- Target: 2      # StatType.AttackDamage
  Type: 0        # ModifierType.Flat
  Value: 2
```

### 검토한 대안

**안 A: 프로퍼티는 두고 `Get(StatType)` 스위치를 따로 만든다**
- 단점: **정보가 두 벌이 된다.** 프로퍼티가 객체를 들고, 스위치가 그것을 가리킨다.
  스탯을 추가할 때 스위치를 빠뜨리면 **코드는 잘 도는데 아이템만 안 먹힌다.**

**안 B: 프로퍼티를 없애고 전부 `Get(StatType)` 으로**
- 단점: `PlayerMotor` 등 기존 호출부가 전부 장황해진다.

**안 C: `Dictionary` 하나에 담고 프로퍼티는 그 위의 껍데기**
- 장점: 저장이 한 곳이다. 프로퍼티를 빠뜨려도 데이터 경로는 그대로 동작한다.
- 장점: 기존 호출부가 한 글자도 안 바뀐다.

### 선택과 이유

**C를 골랐다.** 같은 정보를 두 곳에서 관리하지 않는다는 원칙을 따랐다.

**`Dictionary` 가 하는 일은 `if` 사슬과 같다.** 아이템 코드는 자기가 어느 스탯을
건드릴지 모르므로(에셋마다 다르다) 프로퍼티 이름을 코드에 박을 수 없고,
결국 '정수 → 객체' 를 잇는 무언가가 반드시 필요하다.
**없앨 수 있는 중간 단계가 아니라 유일한 연결이다.**

`StatSet` 이라는 별도 클래스로 빼려다 되돌렸다. 하는 일이 `Dictionary` 조회
한 줄이라 **테스트하면 자기 코드가 아니라 표준 라이브러리를 시험하는 셈**이었다.

## 2. 원본과 인스턴스를 나눈다

### 문제

장착할 때 출처로 `ItemData` 에셋을 넘기면 **검 두 자루가 같은 파일을 가리키므로
출처가 같아진다.** 하나만 빼려 해도 둘 다 떨어진다.

명세의 핵심 검증 항목이 '검을 둘 장착하고 하나만 빼면 +2 가 남는다' 였으므로
그대로는 만족할 수 없었다.

### 선택

**`ItemInstance` 를 만들었다.** ScriptableObject 데이터 분리 때와 같은 구조다.

| | 무엇 | 예 |
|---|---|---|
| `ItemData` | 아이템 종류. 에셋 파일 | '검이란 공격력 +2다' |
| `ItemInstance` | 이 검 한 자루. 런타임 객체 | 가방에 있는 그 검 |

**지금 `ItemInstance` 는 `ItemData` 참조 하나만 갖는다.** 아무 데이터도 더 없다.
**서로 다른 객체라는 사실 자체가 구분의 근거**이기 때문이다.

가방 그리드가 이것을 요구하기도 한다. 아이템은 어느 칸에 있는지를 알아야 하는데
에셋은 위치를 가질 수 없다. 가지면 모든 검이 같은 칸에 있게 된다.

### 파급효과: `object` 출처의 대가

계단 3에서 `RemoveAllFrom(m.Value)` 라고 쓴 실수가 **컴파일을 통과했다.**
`object` 매개변수라 `float` 도 받기 때문이다. 아무것도 지워지지 않는데
오류도 나지 않는 조용한 실패였다.

**출처 타입을 `object` 로 둔 것은 여전히 옳다.** Logic 이 게임의 개념을 알면 안 된다.
다만 **잘못된 것을 넘겨도 컴파일 시점에 못 잡는다는 비용**이 따라온다는 것을
알고 쓰는 것과 모르고 쓰는 것은 다르다.

## 3. 20종은 데이터만으로 되지 않는다. 15종까지다

**실제로 20종을 뽑아 보고 판단했다.**

### 수치 변경만으로 되는 것 (15종)

검, 대검, 단검, 부츠, 날개, 갑옷, 방패, 장갑, 반지, 목걸이,
부적, 룬, 심장, 깃털, 망치.

전부 '어느 스탯에 어떤 종류로 얼마' 로 표현된다. 에셋만 만들면 되고
**코드는 한 줄도 늘지 않는다.**

### 고유 행동이 필요한 것 (5종)

| 아이템 | 왜 안 되나 |
|---|---|
| 흡혈 | 적을 죽였을 때 회복. 이벤트를 들어야 한다 |
| 관통 | 투사체가 적을 뚫는다. `Projectile` 로직 |
| 폭발 | 적이 죽을 때 주변 피해. 새 판정 |
| 삼중 발사 | 투사체 셋. `PlayerAttack` 로직 |
| 가시 | 맞으면 반사 피해. `Health` 이벤트 |

**수치가 아니라 규칙이라 모디파이어로 표현되지 않는다.**

### 검토한 대안

**안 A: 수치 15종으로 가고 다양성은 시너지가 만든다**
- 장점: 지금 구조 그대로다. 추가 설계가 없다.
- 단점: 아이템끼리 비슷해 보일 수 있다. '공격력 +2' 와 '+5' 는 크기만 다르다.

**안 B: 15종 + 고유 행동 5종**
- 단점: 아이템이 이벤트를 구독하거나 로직에 끼어들 수 있어야 한다.
  **지금 만든 것과 다른 종류의 설계**이고 Phase 4 가 커진다.

**안 C: 12종으로 축소** (STATUS 에 적어둔 원래 대비책)
- 단점: **줄일 이유가 없어졌다.** 15종이 되므로 축소는 과잉 대응이다.

### 선택과 이유

**A를 골랐다.** 근거는 GDD 에 있다.

> 아이템을 '먹는' 게 아니라 **'어디에 놓을지 고민하는'** 것이 이 게임의 정체성이다.

**재미의 원천이 아이템 종류가 아니라 배치라면, 아이템 하나하나는 단순한 편이
오히려 맞다.** 조합의 수가 재미를 만든다. 수치 15종에 시너지 4종이 곱해지면
경우의 수는 충분하고, 시너지를 승산 승산으로 주면 배치에 따라 성능이 크게 갈린다.

**B는 미룬다.** 시너지를 먼저 만들어 보고 그것만으로 부족하면 그때 판단해도 늦지 않다.

## 결과

- 아이템 넷을 만들었고 **코드 수정 없이 에셋만으로 추가된다는 것을 확인**했다.
- 검 둘을 끼고 하나만 뺐을 때 나머지가 정확히 남는다.
- 갑옷을 끼면 HP 바가 즉시 갱신되고, 늘어난 만큼만 현재 체력이 찬다.
- **EditMode 테스트가 24개가 됐다.** 반복 장착·해제 시나리오 둘을 추가했다.
- Phase 3 에서 만든 것 중 **새로 만든 계산이 하나도 없다.** 출처 추적, 세 종류
  계산, 캐싱, 변경 이벤트가 전부 그대로 쓰였다.

## 한계 / 남은 문제

- **고유 행동 아이템 5종을 만들 방법이 없다.** 시너지를 만들어 본 뒤 다시 본다.
- **수치 아이템끼리 비슷해 보일 위험이 남아 있다.** 시너지가 이 문제를 풀어야
  하고, 못 풀면 안 B 로 가야 한다.
- **`object` 출처는 컴파일러가 지켜주지 않는다.** 위 2번에 적은 대로다.
- **수치 스케일이 작아 퍼센트 아이템이 묻힌다.** 공격력 1에 +10% 는 반올림해도
  1이다. 검의 Value 를 실수로 `0.2` 로 넣었을 때 아무 일도 안 일어나는 것으로
  이 문제를 직접 확인했다. Phase 4 밸런싱에서 다룬다.
- **`ItemInventory` 는 임시 주인이다.** 가방 그리드가 생기면 인스턴스 목록의
  주인이 그쪽으로 넘어간다.
