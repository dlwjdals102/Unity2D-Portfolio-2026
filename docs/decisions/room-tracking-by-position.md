# 지금 어느 방인지는 트리거가 아니라 플레이어 위치를 칸으로 바꿔 안다

## 문제

카메라는 지금 방의 경계를 알아야 하고, 4-C 는 방에 들어가면 웨이브를 시작해야 한다. 임시 클리어도 보스 방 입장을 들어야 했다.
**'플레이어가 방에 들어갔다' 를 알릴 방법**이 필요했다.

## 검토한 대안

### 안 A: 방마다 트리거 콜라이더
- 장점: Unity 에서 가장 흔하다. 아이작은 문을 지날 때 방을 바꾼다.
- 단점: **우리 투사체는 트리거에 무엇이든 닿으면 사라진다**(`Projectile.OnTriggerEnter2D`). 방을 덮는 트리거를 두면 화살이 쏘자마자 사라진다.
  막으려면 트리거 전용 레이어를 만들고 충돌 매트릭스를 바꿔야 한다. 프로젝트 설정 변경이다.

### 안 B: 플레이어 위치를 방 크기로 나눠 칸으로 바꾼다
- 장점: 콜라이더와 레이어가 없다. 4-A 의 `RoomLayout` 과 방을 놓을 때 쓴 변환을 거꾸로 돌린다. 순수 계산이라 EditMode 테스트가 된다.
  엔터 더 건전은 칸마다 어느 방인지 적어 두고 위치로 찾는다.
- 단점: 매 프레임 나눗셈 두 번을 한다.

## 선택과 이유

**안 B. `RoomTracker` 가 매 프레임 플레이어 칸을 구하고, 지난 칸과 다르면 `OnRoomEntered(Room)` 을 알린다.**
칸과 월드 사이의 변환은 `Logic/Rooms/RoomSpace` 한 곳에 모았다(`ToWorld`, `ToCell`). 방을 놓을 때 `LevelBuilder` 안에 있던 곱셈도 여기로 옮겼다.

**경계는 `Math.Floor(x / 폭 + 0.5)` 로 늘 양의 방향 방에 붙인다.** 방은 가운데에서 반씩 퍼져 있어 0.5 를 더해 내리면 가장 가까운 칸이 된다.

| 계산 | x = 16 (0번과 1번 경계) | x = 48 (1번과 2번 경계) | x = -16.1 |
|---|---|---|---|
| **`Floor(x/32 + 0.5)`** | 1 | 2 | -1 |
| `Mathf.RoundToInt(x/32)` (은행가 반올림) | 0 | 2 | -1 |
| `(int)(x/32 + 0.5)` (0 쪽으로 자름) | 1 | 2 | **0** |

은행가 반올림은 경계마다 붙는 쪽이 다르고, 형변환은 음수에서 틀린다. 스탯의 정수 반올림에서 은행가 반올림을 이미 한 번 겪었다.

**판이 시작될 때 시작 방 입장도 알린다(`Start`).** 구독은 `OnEnable` 에서 하고, 씬이 열릴 때 모든 `OnEnable` 은 어떤 `Start` 보다 먼저라
첫 알림을 놓치지 않는다. `Awake` 가 아닌 이유는 `LevelBuilder.Awake` 가 방을 놓은 뒤라야 배치를 읽을 수 있어서다.

## 결과

- 투사체와 충돌 설정을 건드리지 않았다.
- `RoomSpaceTests` 20 개가 경계, 음수 칸, 가로와 세로가 바뀌는 실수, 되돌리기를 겨냥한다. 방 크기를 가로세로가 다른 32 × 18 로 둬 바뀐 실수가 드러난다.
  EditMode 테스트는 131 개다.
- 카메라(`RoomCameraSwitcher`)와 임시 클리어(`ResultPanel`)가 같은 알림을 듣는다. 4-C 의 웨이브도 여기에 붙는다.
- 채울 때 `Math.Floor` 가 `double` 을 돌려줘 `(int)` 가 필요하다는 것이 한 번 빠졌다.

## 한계 / 남은 문제

- **경계가 문 통로 한가운데라 앞뒤로 오가면 알림이 여러 번 온다.** 실제로 선을 넘은 것이라 틀린 알림은 아니다. 카메라에서 떨림이 보이지 않아
  `Hysteresis` 는 넣지 않았다. 4-C 에서 방 입장이 웨이브를 시작하게 되면, 문턱을 오가는 것만으로 웨이브가 다시 시작되지 않는지 본다.
  전투 중에는 문이 닫혀 이 경우가 줄어든다.
- **플레이어만 추적한다.** 적이 어느 방에 있는지는 모른다. 4-C 에서 적이 방 밖으로 나가는 일이 생기면 다시 본다.
- 방이 없는 칸에 플레이어가 서는 경우를 처리하지 않는다. 벽과 닫힌 문이 막아 일어나지 않고, 일어나면 `GetRoom` 이 예외를 내 바로 드러난다.
