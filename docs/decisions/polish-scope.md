# 폴리싱에서 프로그래머가 가져갈 것만 가져간다

## 문제

Phase 5 폴리싱에 착수하기 전에 '클라이언트 개발자로서 필요한 폴리싱과 아닌 것' 을 갈라야 했다.
ROADMAP 은 이 구간을 **투자 대비 인상 개선이 가장 큰 구간**으로 적어 두었고 그 말은 맞다.
Phase 6 에서 영상을 찍는데 지금 화면에는 도형만 움직인다.

그런데 바로 앞에서 난이도 밸런싱을 **수치는 기획의 몫**이라는 이유로 범위에서 뺐다
([no-difficulty-tuning.md](no-difficulty-tuning.md)). 같은 기준을 폴리싱에 대면
'진폭 0.2 인가 0.4 인가' 도 같은 성격이다. 그러면 폴리싱도 빼야 하는가.

## 알게 된 것

**폴리싱은 항목 단위로 갈리지 않는다. 항목 하나하나 안에서 갈린다.**
항목마다 셋이 섞여 있다.

```
(A) 구조        반응을 어디에 걸고, 무엇을 멈추고, 무엇을 풀에서 꺼내는가
(B) 수치        정지 0.06초인가 0.1초인가, 진폭 0.2인가 0.4인가
(C) 에셋 제작   그리기, 작곡, 프레임 찍기
```

난이도 튜닝은 **항목 전체가 (B)** 였기 때문에 통째로 뺄 수 있었다.
폴리싱은 그렇지 않다. 히트스톱에는 (A) 와 (B) 가 같이 있고, 사운드에는 셋이 다 있다.

## 검토한 대안

| 안 | 판단 |
|---|---|
| 폴리싱도 통째로 뺀다 | 영상에 도형만 남는다. 서류 심사에서 앞 15초가 승부인데 그 15초를 버린다 |
| 계획대로 전부 한다 | (C)에 끝이 없다. 아트 작업으로 번지고, 끝까지 가도 아트 포트폴리오에는 못 미친다 |
| **항목마다 (A)만 가져간다** | (B)는 데이터로 빼고 한 번 정하고 덮는다. (C)는 CC0 로 조달한다 |

## 선택과 이유

**항목은 그대로 두고 각 항목에서 (A)만 가져간다.**

**(B)는 데이터로 뺀 뒤 한 번 정하고 덮는다.** ScriptableObject 로 빼 두면 그 값은
**면접에서 말할 거리가 아니라 구조의 증거**가 된다. 값 자체는 영상을 찍을 때 눈에 걸리면 한 번 만진다.
난이도 튜닝에서 쓴 것과 같은 처방이다.

**(C)는 만들지 않고 CC0 로 조달한다.** 경계는 `ThirdParty/` 고 출처는 루트 README 표 한 곳이다
(CLAUDE.md 7번). 고르는 시간에도 선을 둔다.

## 항목별로 좁힌 것

| 항목 | 가져갈 것 (A) | 데이터로 빼고 덮을 것 (B·C) |
|---|---|---|
| 히트스톱 | 타격 한 번에 반응 셋을 어떻게 거는가. `timeScale` 을 멈췄을 때 **무엇이 같이 멈추는가**(입력, 카메라, 사운드 피치, UI 애니메이션) | 정지 시간 |
| 카메라 셰이크 | **직접 만들지 않는다.** Cinemachine Impulse 를 쓰면서 `IgnoreTimeScale` 을 켜는 이유 | 진폭, 감쇠 곡선 |
| 피격 플래시 | **풀에서 나온 적의 색 복원.** 죽으면서 반환된 적의 코루틴이 다음 적의 색을 덮을 수 있다 | 색, 깜빡임 횟수 |
| 사운드 | `AudioSource` 풀링과 **동시 재생 제한.** 같은 타격음이 한 프레임에 여럿 겹칠 때 | 음원 고르기, 작곡, 믹싱 |
| 메타 저장 / 로드 | **전부 (A)다.** 직렬화 형식, 버전 필드, 저장 위치, 깨진 파일을 만났을 때 | 없음 |
| CC0 에셋 | 경계와 출처 기록 | 고르기, 자르기, 색 맞추기 |
| UI 정리 | 코드가 정하는 사각형의 기준점. 같은 실수를 두 번 한 자리다 | 여백, 색 |
| 프로파일러 점검 | **전부 (A)다.** 전후 수치가 증거물이다 | 없음 |

**셰이크는 패키지 소스를 읽고 정했다.** `Library/PackageCache/com.unity.cinemachine@f3f96bcb59af/Runtime/Impulse/CinemachineImpulseManager.cs:452`
에 `IgnoreTimeScale` 이 있고, 458줄이 `CurrentTime => IgnoreTimeScale ? Time.realtimeSinceStartup : CinemachineCore.CurrentTime` 이다.
**히트스톱으로 `timeScale` 을 0 으로 만들어도 셰이크가 멈추지 않는다.**
카메라에서 Cinemachine 을 고른 판단이 여기서 한 번 더 값을 한다 ([room-camera-per-room.md](room-camera-per-room.md)).

나머지 사례(격투 게임에서 온 히트 스톱, 2D 액션의 셰이크, 하데스나 데드 셀의 피격 플래시)는
**소스로 확인한 것이 아니라 알려진 이야기**다. 근거로 쓰지 않는다.

## 시간을 쓰지 않을 것

가장 큰 위험은 폴리싱이 **아트 작업으로 번지는 것**이다.

- 셰이더를 직접 쓰기 (피격 플래시를 셰이더로). 스프라이트 색 교체로 끝낸다
- 파티클 시스템 세부 조정. 이펙트는 풀에서 꺼내 재생만 한다
- 스프라이트 애니메이션 프레임 찍기, 리깅
- 음원 제작, 믹싱
- 느낌 수치를 며칠 만지기. 한 번 정하고 데이터에 넣고 덮는다
- UI 전환 애니메이션 공들이기

## 빌드에서 깨지지 않는지는 Phase 6 으로

UI 를 코드로 만들고 있어 **해상도가 바뀌면 틀어질 위험**이 남아 있다.
앵커와 피벗을 코드가 정하지 않아 같은 실수를 두 번 했고, 에디터 창 비율과 빌드 전체화면은 다르다.

이것은 기획도 아트도 아니고 **클라이언트 개발자가 아니면 아무도 보지 않는 일**이다.
그래서 빼지 않는다. 다만 Phase 5 의 새 항목으로 올리지 않고 **Phase 6 의 '실행 빌드' 항목에 묶는다.**
빌드를 실제로 내는 자리에서 확인하는 것이 맞고, 항목을 늘리지 않는 쪽이기도 하다.

**일시정지는 새 항목으로 보지 않는다.** 히트스톱이 `timeScale` 을 쓰면 일시정지와 같은 축을 나눠 쓰므로
히트스톱 안에서 함께 다룬다.

## 면접에서 이 판단을 어떻게 말하나

> 폴리싱에서는 구조만 제가 가져가고 수치와 에셋은 밖으로 뺐습니다.
> 히트스톱을 예로 들면, 정지 시간이 몇 초인지는 데이터에 있고 제가 설명할 것은
> 타격 한 번에 반응 셋을 어디에 걸었는지, `timeScale` 을 멈출 때 무엇이 같이 멈추는지입니다.
> 카메라 셰이크는 직접 만들지 않고 Cinemachine Impulse 를 썼습니다.
> 패키지 소스를 보니 `IgnoreTimeScale` 이 있어서 히트스톱과 같이 쓸 수 있었습니다.
> 에셋은 전부 CC0 이고 `ThirdParty/` 아래에 있습니다. 출처는 README 표 한 곳에서 관리합니다.

## 결과

- Phase 5 의 여섯 항목을 그대로 두고 **각 항목에서 (A)만 가져간다.**
- 셰이크는 Cinemachine Impulse 로 한다. 직접 만들지 않는다.
- '빌드에서 깨지지 않는지' 는 **Phase 6 의 실행 빌드 항목에 묶는다.**
- 다음은 폴리싱 첫 기능인 히트스톱, 셰이크, 피격 플래시다.

## 한계 / 남은 문제

- **(B)를 한 번에 정한다는 것이 지켜질지는 이 문서가 보장하지 못한다.** 느낌 수치는 만지면 계속 만져진다.
  명세 체크리스트를 **관찰 가능한 동작**으로 쓰고 수치를 기준에 넣지 않는 것으로 막는다.
- **사운드의 (A)가 얇다.** `AudioSource` 풀링과 동시 재생 제한뿐이라 면접에서 말할 거리가 적다.
  그래도 **무음 영상은 치명적**이어서 한다. 인상 쪽으로 하는 항목임을 인정한다.
- **CC0 에셋을 못 찾으면 도형으로 제출한다.** ROADMAP 이 이미 '실패해도 제출 가능한 상태 유지' 로 적어 두었다.
