# 오브젝트 풀을 직접 만들고, 투사체가 자기 풀을 필드로 갖는다

## 문제

투사체를 매번 `Instantiate` 로 만들고 `Destroy` 로 지우고 있었다.
측정으로 비용을 확인했고, 풀링으로 바꾸기로 했다.

여기서 세 가지를 정해야 했다.

1. Unity 에 이미 있는 `ObjectPool<T>` 를 쓸 것인가
2. 풀을 어디에 둘 것인가
3. 투사체가 자기 풀을 어떻게 알 것인가

## 1. Unity 내장 `ObjectPool<T>` 를 쓰지 않는다

### 검토한 대안

**안 A: `UnityEngine.Pool.ObjectPool<T>` 를 쓴다**
- 장점: 검증된 구현이다. 만들 것이 없다.
- 단점: **면접에서 "풀링을 어떻게 구현하셨나요"에 답이 없다.**

**안 B: 직접 만든다**
- 장점: 구현을 설명할 수 있다. 50줄 안팎이라 비용도 작다.
- 단점: 검증되지 않은 코드가 하나 는다.

### 선택

**안 B.** CLAUDE.md 1번이 오브젝트 풀링을 사용자 직접 작성 목록에 두었고,
7번이 그 목록을 외부 사용 금지 목록으로 규정한다.

**이 프로젝트의 목적이 취업이기 때문에** 내린 결정이다.
실무라면 검증된 것을 쓰는 편이 맞다.

**중요한 것은 내장이 있다는 사실을 알고 있다는 점이다.**
모르고 만든 것과 알고 만든 것은 면접에서 완전히 다르게 들린다.

## 2. 전역 풀 관리자를 만들지 않는다

### 검토한 대안

**안 A: 전역 관리자 (`PoolManager.Get<T>()`)**
- 장점: 어디서든 꺼낼 수 있다. 같은 프리팹의 풀이 하나로 유지된다.
- 단점: **싱글톤이 하나 생긴다.** 코딩 규칙이 static 남용을 경계한다.
  씬을 다시 로드할 때 초기화 시점이 애매해진다.

**안 B: 쓰는 쪽이 자기 풀을 소유한다**
- 장점: 싱글톤이 없다. 씬과 함께 사라지므로 재시작 처리가 공짜다.
- 단점: 적도 투사체를 쏘면 **풀이 둘로 늘어난다.**

### 선택

**안 B.** 풀이 둘로 늘어나는 것이 **실제로 문제가 될 때** 다시 본다.

지금은 발사하는 쪽이 하나뿐이다. 없는 문제를 위해 싱글톤을 만들 이유가 없다.

## 3. 투사체가 자기 풀을 필드로 갖는다

### 검토한 대안

**안 A: 콜백을 람다로 넘긴다**

```csharp
p.Launch(dir, () => _pool.Release(p));
```

- 장점: 투사체가 풀 타입을 몰라도 된다. 읽기에 깔끔하다.
- 단점: **발사할 때마다 클로저 객체가 새로 할당된다.**
  초당 600발이면 초당 600개다. **풀링으로 없애려던 할당을 다른 곳에서 만드는 셈이다.**

**안 B: 투사체가 `Pool<Projectile>` 을 필드로 갖는다**

```csharp
p.Bind(_pool);
p.Launch(dir);
```

- 장점: 할당이 없다. 같은 값을 다시 넣을 뿐이므로 매번 불러도 무해하다.
- 단점: 투사체가 풀 타입을 알게 된다.

**안 C: 소유자가 활성 목록을 들고 매 프레임 회수 대상을 찾는다**
- 단점: 폴링이다. 코딩 규칙이 금지하는 방향이다. → 탈락

### 선택

**안 B.** 안 A 의 단점이 이 기능의 목적과 정면으로 충돌한다.
**깔끔해 보이는 코드가 성능 목적을 무너뜨리는 경우다.**

안 B 의 단점은 크지 않다. 투사체가 아는 것은 **자기가 나온 서랍**뿐이고,
**누가 쐈는지는 여전히 모른다.** 적이 쏘면 적의 풀을 넣어 주면 되고
투사체 코드는 바뀌지 않는다.

## 결과

측정 결과는 [측정 기록](../measurements/pooling-baseline.md)에 있다.

| 항목 | 전 | 후 |
|---|---|---|
| `PlayerLoop` | 3.05ms | 2.65ms (-13%) |
| 물리 | 1.71ms | 1.35ms (-21%) |
| 스크립트 | 0.39ms | 0.50ms (+28%) |
| GC Alloc | 1.2 KB | **0 B** |
| Object Count | 7.78k | 9.22k (+18%) |

**개선폭은 크지 않다.** 물리 연산이 여전히 지배적이고 그 부분은 풀링과 무관하다.

**늘어난 항목도 있다.** 수명 타이머가 수백 개 돌기 시작했고 오브젝트 수가 늘었다.
**메모리와 생성·파괴 비용을 맞바꾼 것이지 공짜가 아니다.**

## 한계 / 남은 문제

- **풀 크기에 상한이 없다.** 한 번에 만 개가 만들어지면 그 만 개가 계속 남는다.
  지금은 그만큼 만들 일이 없고 줄일 시점을 판단할 근거도 없어 넣지 않았다.
- **`Bind` 를 부르지 않고 `Launch` 만 하면 반환할 때 예외가 난다.**
  부르는 곳이 한 군데뿐이라 방어하지 않았다. 적이 투사체를 쏘게 될 때 주의해야 한다.
- **중복 반환은 비활성 여부로 판단한다.** 풀 바깥에서 오브젝트를 직접
  비활성화하면 이 판단이 어긋난다. 지금은 그런 코드가 없다.
- **측정은 에디터에서 했다.** `EditorLoop` 이 85% 를 차지해 절대값을 신뢰할 수 없다.
  Phase 6 빌드 때 다시 잰다.
