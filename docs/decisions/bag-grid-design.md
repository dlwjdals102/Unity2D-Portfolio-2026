# 그리드는 아이템을 모르고, 위치는 그리드만 안다

## 문제

GDD 가 이 게임의 정체성으로 배치를 꼽았다. 5×5 가방에 1~4칸짜리 아이템을
놓는 구조를 만들어야 했고, 정할 것이 다섯이었다.

1. 그리드가 아이템을 어떻게 다룰 것인가
2. 아이템의 위치를 어디에 둘 것인가
3. 아이템 모양을 어디까지 허용할 것인가
4. 회전을 몇 방향까지 만들 것인가
5. UI 를 어떻게 그리고 어떻게 조작할 것인가

## 1. 그리드는 크기만 안다

### 문제

`BagGrid` 는 `JM2D.Logic` 이고 `ItemData` 는 `JM2D.Runtime` 이다.
**Logic 이 Runtime 을 참조하면 컴파일 에러**라 그리드가 아이템을 직접 다룰 수 없다.

### 검토한 대안

**안 A: `BagGrid<T>` 제네릭. 크기를 인자로 받는다**
- 장점: `Pool<T>` 와 같은 패턴이다. 인터페이스가 늘지 않는다.
- 단점: **크기를 잘못 넘길 수 있다.** `2×2` 아이템에 `TryPlace(item, x, y, 1, 1)` 이라고
  부르면 한 칸만 차지한 것으로 기록되고, **오류 없이 겹침 검사만 틀린다.**

**안 B: `IGridItem` 인터페이스. 아이템이 크기를 알려준다**
- 장점: 크기가 어긋날 방법이 없다. 호출부도 짧다.
- 장점: 테스트에서 가짜 아이템을 만들 수 있어 **테스트가 Runtime 을 전혀 안 본다.**
- 단점: 구현이 하나뿐인 인터페이스가 생긴다.

### 선택과 이유

**B를 골랐다.**

B의 단점은 겉모습이다. **이 인터페이스는 다형성이 아니라 의존 방향을 뒤집기 위한 것**이다.
Logic 이 약속을 정의하고 Runtime 이 구현한다. **이 방법 말고는 그리드가 아이템을
다룰 길이 없다.**

`Pool<T>` 가 제네릭으로 푼 문제를 여기서는 인터페이스로 풀었다. 차이는
**크기를 누가 아느냐**에 있다. 풀은 담기는 것의 성질을 알 필요가 없지만
그리드는 알아야 한다.

**회전도 이 결정에 얹혔다.** 아이템이 회전이 반영된 크기를 돌려주므로
**그리드는 회전을 아예 모른다.** 크기가 다른 아이템으로 보일 뿐이다.

## 2. 위치는 그리드의 배열에만 있다

### 검토한 대안

**안 A: `ItemInstance` 가 좌표를 갖는다**
- 장점: 아이템에게 어디 있냐고 바로 물을 수 있다.
- 단점: **같은 정보가 두 곳에 생긴다.** 배열과 좌표가 어긋나면 어느 쪽이 맞는지
  알 수 없다.

**안 B: 배열만 갖는다. 제거할 때는 25칸을 훑는다**
- 장점: 진실이 한 곳이다. 어긋날 방법이 없다.
- 단점: `Remove` 가 전체를 순회한다.

### 선택과 이유

**B를 골랐다.** 5×5 는 25번이라 순회 비용이 없다시피 하다.

**명세에는 처음에 '`ItemInstance` 가 위치와 회전을 갖게 된다' 고 적었다가
계단 2에서 되돌렸다.** 계단 1에서 위치를 배열에만 두기로 해놓고 명세가
그것과 어긋난 채 남아 있었다.

**위치가 필요한 곳도 없었다.** UI 가 아이템을 그릴 때는 배열을 훑고,
시너지 탐색도 그리드에 물으면 된다.

## 3. 직사각형만 만든다

`1×1`, `1×2`, `2×1`, `2×2` 넷이다. 각 변을 `[Range(1, 2)]` 로 제한했다.

**임의 모양(L자 등)을 만들지 않는다.** GDD 가 '1~4칸' 만 요구하고,
칸 목록을 들고 다니면 겹침 검사와 회전이 훨씬 복잡해진다.

**제한을 어트리뷰트로 건 것은 인스펙터 실수를 막기 위해서다.**
`3×2` 를 넣을 수 있게 두면 언젠가 여섯 칸 아이템이 생기고,
그때는 명세와 코드 중 무엇이 맞는지 알 수 없어진다.

## 4. 회전은 두 상태다

`Rotate()` 는 눕혔는지 여부를 뒤집는다. 90도와 270도가 같고 0도와 180도가 같다.

### 왜 네 방향이 아닌가

**직사각형은 180도를 돌려도 차지하는 칸이 같다.**

| 회전 | `2×1` 의 크기 |
|---|---|
| 0도 | 2 × 1 |
| 90도 | 1 × 2 |
| 180도 | **2 × 1** |
| 270도 | **1 × 2** |

**배치에 아무 영향이 없다.** 도형 프로토타입이라 보기에도 똑같아서,
`R` 을 네 번 눌러야 제자리로 오는데 눈에는 두 번마다 같은 것이 나온다.
**오히려 헷갈린다.**

**임의 모양이었다면 네 방향이 전부 달랐을 것이다.** 3번 결정의 파급효과다.

**Phase 5 에서 스프라이트가 들어오면 다시 본다.** 칼끝이 위를 향하느냐 아래를
향하느냐는 그때 보이기 시작한다. 다만 그것은 시각 문제라 배치 계산과 분리할 수 있다.

### 상태는 하나만 저장한다

`Width` 와 `Height` 를 직접 뒤집지 않고 **눕혔는지 여부만 저장하고 크기는 매번 계산한다.**

값을 직접 바꾸면 원본을 잃어 **'지금 눕혀져 있는가' 를 물을 수 없다.**
`Stat` 이 기본값을 보존하고 `Value` 를 계산하는 것과 같은 구조다.

## 5. 칸 위치를 코드로 계산하고, 클릭으로 놓는다

### 그리기

**안 A: `Grid Layout Group`**
- 단점: 여러 칸을 덮는 아이템과 싸워야 한다. 모든 자식을 같은 크기로 만들려 든다.

**안 B: 코드로 위치 계산**
- 장점: 아이템을 자기 크기만큼 얹을 수 있다. 격자가 정사각형이라 계산도 단순하다.

**B를 골랐다.** `칸 크기 × 좌표` 한 줄이면 끝난다.

### 조작

**드래그앤드롭 대신 클릭 후 클릭**으로 했다. 도형 프로토타입이라 드래그의
손맛이 살지 않는다. **Phase 5 폴리싱에서 바꾸는 것이 순서에 맞다.**

미리보기는 넣었다. `R` 을 눌러도 아무것도 안 보이면 회전했는지 알 수 없기 때문이다.
**계단 1에서 `CanPlace` 와 `TryPlace` 를 나눠둔 것이 여기서 쓰였다.**
실제로 놓지 않고 물어보기만 해야 한다.

### 파급효과: 앵커와 피벗을 코드가 못 박는다

**인스펙터에 맡겼다가 클릭 좌표가 격자 절반만큼 어긋났다.**

`RectTransformUtility.ScreenPointToLocalPointInRectangle` 이 돌려주는 좌표는
**피벗이 원점**인데, `CellRoot` 의 피벗이 가운데였다. 격자 중앙을 클릭하면
`(0,0)` 이 나와 왼쪽 위 칸으로 계산됐다.

**그리기는 멀쩡했다.** 칸의 앵커가 부모 rect 의 왼쪽 위 모서리를 가리키는데,
그 모서리는 피벗과 무관하게 같은 자리이기 때문이다. **읽는 쪽만 다른 원점을 쓰고 있었다.**

앵커도 함께 못 박았다. `sizeDelta` 를 크기로 쓰는 코드는 **점 앵커를 전제로 한다.**
범위 앵커에서는 같은 숫자가 '여백' 으로 해석된다.

**기준이 하나 생겼다. 계산에 쓰이는 값은 코드가 정하고, 보기에만 관여하는 것은
인스펙터에 둔다.** 피벗은 좌표 계산의 전제였고, 색과 위치는 보기의 문제였다.

## 결과

- **EditMode 테스트가 36개가 됐다.** 그리드 12개가 스탯 24개에 더해졌다.
  가짜 아이템으로 시험하므로 `Runtime` 을 전혀 참조하지 않는다.
- 테스트 준비 단계에도 `Assert` 를 붙였다. **준비가 조용히 실패하면 테스트가
  엉뚱한 상황을 시험한다는 것**을 경계 조건을 뒤집어 보다가 발견했다.
- 아이템 목록의 주인이 `ItemInventory` 에서 `BagGrid` 로 넘어갔다.
  `ItemInventory` 는 그리드와 스탯을 잇는 역할만 남았다.
- `StatDebugKeys` 를 지웠다. 가방이 아이템을 장착하는 수단이 되어 역할이 끝났다.

## 한계 / 남은 문제

- **시너지가 없다.** 어디에 놓든 효과가 같아서 아직 배치를 고민할 이유가 없다.
  다음 명세에서 다룬다. **이 기능의 값어치가 거기서 판가름난다.**
- **가방을 여는 시점이 임시다.** 지금은 `Tab` 인데, 방 사이에만 열게 하면
  배치가 더 무거운 선택이 된다. **방 개념이 생기는 Phase 4 뒷부분에서 다시 본다.**
- **아이템 획득이 없다.** 숫자 키로 만들어 낸다. 적이 아이템을 떨어뜨리는 것은
  아직 만들지 않았다.
- **`Redraw` 가 매번 전부 다시 그린다.** 25칸이라 문제없지만 가방이 커지면
  부분 갱신이 필요해진다. 다만 그때는 화면과 그리드가 어긋날 위험을 함께 떠안는다.
- **`IGridItem` 을 `ItemInstance` 로 되돌리는 캐스팅이 UI 에 있다.**
  경계를 지킨 대가이며, 넣는 것이 `ItemInstance` 뿐이라 지금은 안전하다.
