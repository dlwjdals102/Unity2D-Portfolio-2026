# 상태 전이의 진입 조건과 탈출 조건을 다른 값으로 둔다

## 문제

적의 상태 머신에서 `Chase`와 `Attack`은 거리를 **서로 반대 방향으로 민다.**

```
Chase   적이 다가온다  →  거리가 준다
Attack  적이 멈춘다    →  플레이어가 물러나면 거리가 는다
```

한 값으로 두 전이를 모두 판정하면 그 경계에서 두 상태가 서로를 뒤집는다.
플레이어가 적보다 느리게 물러날 때 상태가 매 물리 스텝마다 바뀌고 적이 떨린다.

### 지금 값에서는 재현되지 않는다

**이 사실이 이 결정의 핵심이다.**

현재 이동 속도는 플레이어 6, 적 3이다. 물러나기 시작하면 거리가 계속 벌어져
적은 `Chase`에 머문다. 게다가 키보드 입력은 속도가 0 아니면 6이라
**"적보다 조금 느리게 물러나기"를 할 방법이 없다.**

적 속도를 10으로 올려 플레이어보다 빠르게 만들면 곧바로 재현된다.
`Attack`(초록)과 `Chase`(파랑)가 번갈아 깜빡인다.

### 그런데 언젠가 반드시 도달한다

- GDD 스코프의 **돌진 적**은 순간적으로 플레이어보다 빠르다
- Phase 3 스탯 시스템에 이동 속도 버프가 들어온다
- 게임패드를 지원하면 스틱을 살짝 기울여 천천히 물러날 수 있다

## 검토한 대안

### 안 A: 여유를 두지 않고 문제가 보일 때 넣는다
- 장점: CLAUDE.md 3번에 가장 충실하다. 지금 없는 문제를 다루지 않는다.
- 단점: 위 셋 중 하나가 들어오는 순간 원인 모를 떨림으로 나타난다.
  그때는 적 종류가 늘어 있어 어느 값 때문인지 찾기 더 어렵다.

### 안 B: 배수로 여유를 준다 (`_attackRange * 1.2f`)
- 장점: 탈출 범위가 진입 범위보다 항상 크다는 것이 **구조적으로 보장**된다.
- 단점: 배수가 코드에 박힌다. 그리고 감지 쪽은 절대값(`_giveUpRange`)인데
  공격 쪽만 배수면 같은 개념을 두 가지 방식으로 쓰게 된다.

### 안 C: 절대값 필드를 하나 더 둔다 (`_attackExitRange`)
- 장점: `_detectRange` / `_giveUpRange` 쌍과 **같은 관용구**가 된다.
  읽는 사람이 한 번만 이해하면 된다. 인스펙터에서 바로 조절된다.
- 단점: 탈출 값을 진입 값보다 작게 넣는 실수를 코드가 막지 못한다.

## 선택과 이유

**안 C를 택했다.**

안 A를 버린 이유는 비용이 거의 0이기 때문이다. 필드 하나다.
그리고 이것은 "일어날 수 없는 상황"이 아니라 **"지금 값에서 안 일어나는 상황"** 이다.
CLAUDE.md 3번이 금지하는 대상과 성격이 다르다.

안 B를 버린 이유는 일관성이다. 감지 쪽이 이미 절대값 쌍으로 돼 있는데
공격 쪽만 배수로 두면, 코드를 읽는 사람이 "왜 다르지"를 묻게 된다.
안전성에서 안 B가 낫지만, 같은 위험이 감지 쪽에도 이미 있으므로
**두 쌍이 같은 위험을 지는 편이 예측 가능하다.**

```
Idle   → Chase   : distance <= _detectRange     (6)
Chase  → Idle    : distance >  _giveUpRange     (8)
Chase  → Attack  : distance <= _attackRange     (1.2)
Attack → Chase   : distance >  _attackExitRange (1.6)
```

## 결과

- 적 속도를 10으로 올려 재현되던 떨림이 사라진다.
- 기본 값(적 3)에서는 원래 재현되지 않았으므로 눈에 보이는 변화가 없다.
  **이것을 기록해 두지 않으면 나중에 "이 여유가 왜 있지"가 된다.**

### 배운 것

히스테리시스가 필요한 조건은 "조건식이 같다"가 아니다.
**두 상태가 값을 서로 반대 방향으로 밀 때**다.

`Idle`과 `Chase` 사이에는 이 문제가 없다. `Chase`는 거리를 줄이고
`Idle`은 그대로 두므로 양쪽 다 스스로 안정된다.
그쪽의 `_giveUpRange`는 떨림 방지가 아니라 **추적이 즉시 끊기지 않게 하는
게임 느낌**을 위한 것이다. 같은 모양이지만 이유가 다르다.

## 한계 / 남은 문제

- **두 값의 대소 관계를 코드가 강제하지 않는다.** 탈출 값을 진입 값보다
  작게 넣으면 오히려 떨림이 생긴다. 지금은 값을 만지는 사람이 한 명이고
  잘못 넣으면 색이 깜빡여 바로 보이므로 검증을 넣지 않았다.
  Phase 3에서 적 데이터를 ScriptableObject로 빼고 적이 4종이 되면
  `OnValidate` 로 막는 것을 다시 검토한다.
- 여유 값 `0.4`(1.2 대 1.6)는 근거 없이 정한 값이다. 적이 4종이 되면
  종류마다 적절한 폭이 다를 수 있다.
