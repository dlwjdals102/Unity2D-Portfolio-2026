# ScriptableObject 는 원본이고 컴포넌트는 사본을 갖는다

## 문제

적과 투사체의 수치가 프리팹에 박혀 있었다. Phase 4에서 적이 4종, 무기가 3종으로
늘면 프리팹을 복제해 값을 하나씩 고치는 방식이 무너진다.

ScriptableObject 로 빼기로 하면서 세 가지를 정해야 했다.

1. 컴포넌트가 데이터를 언제 읽을 것인가
2. 투사체의 피해량을 누가 가질 것인가
3. `Health` 는 플레이어와 공유하는데 적 체력을 어떻게 데이터에서 받을 것인가

## 1. 데이터는 `Awake` 에서 자기 필드로 복사한다

### 검토한 대안

**안 A: 쓸 때마다 `_data.MoveSpeed` 로 읽는다**
- 장점: 필드가 줄고 코드가 짧다. `Awake` 에 복사 코드가 없다.
- 단점: **런타임에 값이 바뀔 자리가 없다.** 다음 단계인 스탯 · 모디파이어에서
  '이동속도 +20%' 를 얹을 곳이 사라진다.
- 단점: 데이터를 직접 고치고 싶은 유혹이 생긴다. ScriptableObject 는 디스크의
  에셋 파일이라 **에디터에서 고치면 파일이 실제로 바뀌고 플레이를 멈춰도 남는다.**

**안 B: `Awake` 에서 자기 필드로 복사한다**
- 장점: 인스턴스마다 값이 독립이다. 한 마리에 건 버프가 다른 마리에 새지 않는다.
- 장점: 복사한 필드가 곧 **버프를 곱할 자리**가 된다.
- 단점: 필드가 늘고 `Awake` 가 길어진다. 적은 복사가 일곱 줄이다.
- 단점: 플레이 중에 에셋을 고쳐도 이미 존재하는 인스턴스에는 반영되지 않는다.

### 선택과 이유

**B를 골랐다.**

A의 단점이 결정적이다. 스탯 시스템이 바로 다음 항목으로 확정되어 있어
'언젠가 필요할지 모른다'가 아니라 **다음 주에 필요하다.**

성능은 근거가 아니다. 프로퍼티 접근 한 번은 필드 읽기와 사실상 같은 비용이다.
캐싱의 값어치는 속도가 아니라 **값이 바뀔 자리를 만드는 것**에 있다.

B의 두 번째 단점은 실제로 관찰됐다. 플레이 중에 에셋의 속도를 올려도 이미
날아가는 투사체는 그대로다. **이것은 버그가 아니라 이 결정의 정의 그 자체다.**
개발 중 값 조정은 플레이를 멈추고 하면 된다.

## 2. 투사체는 자기 피해량을 모른다

### 검토한 대안

**안 A: `ProjectileData` 에 피해량을 두고 발사하는 쪽이 읽어서 넘긴다**
- 단점: 같은 데이터 에셋을 프리팹과 발사자가 **각각 참조**하게 된다.
  둘을 다르게 물려 놓아도 아무 경고가 없다.

**안 B: `ProjectileData` 에 두고 투사체가 스스로 쓴다**
- 단점: 공격력 스탯이 끼어들 자리가 없다. 원래 풀려던 문제가 안 풀린다.

**안 C: 데이터에 넣지 않는다. 발사할 때 인자로 받는다**
- 장점: 책임이 갈린다. 투사체는 '어떻게 날아가는가', 발사자는 '얼마나 아픈가'.
- 장점: 같은 투사체를 적이 쏘거나 무기 여러 종이 공유해도 각자의 공격력이 실린다.
- 단점: `ProjectileData` 에 값이 둘만 남아 빈약해 보인다.

### 선택과 이유

**C를 골랐다.** `Launch(Vector2 direction, int damage)` 가 됐다.

C의 단점은 겉모습일 뿐이다. Phase 4에서 관통 횟수나 폭발 반경이 붙으면 채워지고,
**빈약해 보인다는 이유로 엉뚱한 값을 넣는 쪽이 나쁘다.**

여기서 부수적으로 갈린 것이 하나 더 있다. 속도와 수명은 `Awake` 에서 정해지고
피해량만 `Launch` 에서 정해진다. **투사체는 풀에서 재사용되어 `Awake` 가 다시
돌지 않으므로, 발사할 때마다 달라져야 하는 값은 `Launch` 에 있어야 한다.**
풀링을 먼저 한 덕분에 생긴 구분이다.

## 3. `Health` 는 데이터를 모른 채 밖에서 최대 체력을 받는다

### 문제

적 체력은 `EnemyData` 에서 와야 하는데 `Health` 는 플레이어도 쓴다.
`Health` 가 `EnemyData` 를 참조하면 플레이어가 적 데이터를 들고 다니게 된다.

그리고 **`Awake` 실행 순서는 보장되지 않는다.** `Health.Awake` 가
`_current = _maxHealth` 를 하므로, 밖에서 넣은 값을 뒤늦게 덮어쓸 수 있다.

### 검토한 대안

**안 A: `Health.SetMaxHealth(int)` 를 두고 `EnemyController.Awake` 에서 부른다**
- 장점: 순서에 영향받지 않는 모양으로 만들 수 있다. 아래 참조.
- 단점: 적 프리팹에 최대 체력이 두 군데 생긴다. 인스펙터 값은 무시된다.

**안 B: `Health` 의 초기화를 `Start` 로 옮긴다**
- 장점: 모든 `Awake` 가 끝난 뒤 도므로 순서가 정리된다.
- 단점: **`HealthBar` 가 첫 값을 `Start` 에서 읽는다. `Start` 끼리도 순서는
  보장되지 않는다.** 전에 겪은 'HP 바가 비어 있는' 버그가 그대로 돌아온다.

**안 C: 자동 초기화를 없애고 모두가 명시적으로 초기화한다**
- 장점: 가장 정직하다. 초기화 시점이 코드에 드러난다.
- 단점: 플레이어 쪽에도 초기화 코드를 새로 만들어야 한다.
  **적 하나 때문에 플레이어까지 손대게 된다.**

### 선택과 이유

**A를 골랐다.** 핵심은 `_current` 만이 아니라 `_maxHealth` 도 함께 바꾸는 것이다.

| 먼저 깨는 쪽 | 벌어지는 일 | 결과 |
|---|---|---|
| `Health` | `_current` 가 인스펙터 값으로 찼다가 데이터 값으로 덮인다 | 데이터 값 |
| `EnemyController` | 데이터 값이 들어가고, `Health.Awake` 가 `_current = _maxHealth` 를 하는데 그 `_maxHealth` 가 이미 데이터 값이다 | 데이터 값 |

**순서를 맞추려 하지 않고 순서가 상관없는 모양으로 만들었다.**

B는 이미 한 번 겪은 버그를 부른다. C는 이번 문제에 비해 파급이 크다.

## 결과

- 적 프리팹에서 수치 일곱 개가 사라지고 `_data` 참조 하나만 남았다.
- `EnemyController` 의 diff 가 20줄 추가, 14줄 삭제인데
  **`FixedUpdate` 와 `ChangeState` 는 한 줄도 바뀌지 않았다.**
  값의 출처만 바꾸고 행동은 건드리지 않았다는 것이 커밋에 그대로 남는다.
- 값이 다른 데이터를 물린 적과 원래 적이 같은 씬에서 다르게 움직이는 것을 확인했다.
- 적 셋이 같은 데이터를 공유하면서도 체력은 서로 독립인 것을 확인했다.
- 적을 죽인 뒤에도 에셋 파일의 값이 그대로인 것을 확인했다.

## 한계 / 남은 문제

- **적을 풀링하면 `SetMaxHealth` 호출이 깨진다.** `Awake` 에서 부르고 있어
  재사용될 때 다시 돌지 않는다. 투사체에서 `_damage` 를 `Launch` 로 옮긴 것과
  같은 문제다. 적 풀링은 Phase 4 이므로 그때 함께 본다.
- **`SetMaxHealth` 라는 이름이 실제보다 넓게 들린다.** 초기화 전용인데
  게임 도중에 불러도 되는 것처럼 읽힌다. 부르면 체력이 가득 차고
  `OnHealthChanged` 도 발생하지 않는다. 지금은 주석으로 막아뒀다.
  최대 체력 변경을 정면으로 다루는 스탯 시스템에서 다시 본다.
- **데이터 값에 검증이 없다.** 감지범위를 포기범위보다 크게 넣으면
  적이 영원히 쫓아온다. 데이터가 둘뿐이라 눈으로 확인되지만,
  종류가 늘면 `OnValidate` 나 에디터 툴이 필요해진다.
- **플레이어 수치는 아직 프리팹에 있다.** 하나뿐인 것을 데이터로 빼는 것은
  확장성 증명이 되지 않아 남겨뒀다. 스탯 시스템이 다루게 된다.
