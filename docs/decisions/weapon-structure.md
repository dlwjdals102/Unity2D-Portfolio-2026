# 무기는 '한 번 공격하기' 만 자식이 갖고, 값은 스탯 기본값 0 위에 무기 출처로 얹는다

## 문제

GDD 스코프의 무기 셋을 넣어야 했다. 지금까지는 `PlayerAttack` 하나가 입력, 공격 간격, 대시 금지, 풀, 발사를 모두 했고
공격력과 공격 속도는 `PlayerStats` 인스펙터의 기본값이었다.

풀어야 할 것은 셋이었다.

- 무기마다 다른 것과 같은 것의 경계를 어디에 긋나
- 무기 데이터를 어떤 모양으로 두나
- 무기를 바꿀 때 공격력과 공격 속도를 어떻게 바꾸고, 가방의 아이템 효과는 어떻게 지키나

무기 셋은 처음에 GDD 대로 근접, 원거리, 광역이었다. 명세를 쓰며 **활, 검, 창**으로 바꿨다. 역할 이름은 쓰는 법이 떠오르지 않고,
광역을 날아가다 터지는 투사체로 만들면 새 구조가 하나 더 필요했다. '여럿을 한 번에' 는 넓게 휘두르는 검이 맡는다.

## 1. 구조

지금 `PlayerAttack` 이 하는 일을 무기 셋에 대 보니 입력, 공격 간격, 대시 금지, 조준과 공격력은 모두 같았고
**다른 것은 '한 번 공격할 때 하는 일' 하나였다.**

### 검토한 대안

| 안 | 판단 |
|---|---|
| `PlayerAttack` 하나에 `switch` | 지금은 가장 짧다. 하지만 데이터에 투사체용 칸과 범위용 칸이 섞여 무기마다 절반이 빈다. 적 데이터에서 피한 모양이다 |
| **공통 부모 컴포넌트 + 무기별 자식** | `Weapon` 이 `Attack(origin, direction, damage)` 하나만 정한다. 입력, 간격, 대시, 스탯은 `PlayerAttack` 에 남는다 |
| 행동을 ScriptableObject 에 | 에셋은 여럿이 나눠 쓰는 파일이라 풀 같은 실행 중 상태를 담기 어렵다. '행동은 데이터에 없다' 는 원칙과 반대다 |
| 인터페이스 `IWeapon` | 인스펙터가 인터페이스 타입 필드를 받지 못해 결국 `MonoBehaviour` 부모가 필요하다 |

### 선택

**공통 부모 컴포넌트.** 다른 것이 정확히 하나라 부모의 추상 메서드도 하나다. 적 AI 의 `EnemyBase` 와 `MeleeEnemy`,
`EnemyData` 와 `MeleeEnemyData` 와 같은 모양이라 한 번 설명한 구조로 둘 다 설명된다.

데이터는 추상 `WeaponData`(공격력, 초당 공격 수) 아래 `BowWeaponData`(투사체 프리팹)와 `MeleeWeaponData`(길이, 폭, 보이는 시간)다.
처음에는 활만의 수치가 `ProjectileData` 에 이미 있어 활 전용 클래스가 빈 클래스가 된다고 보고 활이 부모를 그대로 쓰게 했다.
세 무기가 같은 모양이면 좋겠다는 의견을 받아 다시 보니 **어떤 투사체를 쏘는지가 활만의 값**이라 옮겨 담았다. 풀의 부모는 씬 오브젝트라 컴포넌트에 남는다.

## 2. 무기의 값과 스탯

### 검토한 대안

| 안 | 판단 |
|---|---|
| **기본값 0, 무기가 `Flat` 으로 전부 준다** | [스탯 설계 결정](stat-modifier-design.md)이 약속한 모양이다 |
| 기본값은 두고 무기는 차이만 준다 | 무기 데이터에 '검의 공격력' 이 아니라 '활보다 얼마나 센가' 가 적혀 에셋만 보고 무기를 알 수 없다 |
| 무기를 들 때 기본값을 갈아 끼운다 | 기본값은 `readonly` 이고, 스탯을 새로 만들면 `OnChanged` 구독이 끊긴다 |

### 선택

**기본값 0 위에 출처가 무기 컴포넌트인 `Flat` 모디파이어로 얹는다.** `PlayerAttack.Equip` 이 옛 무기의 것을 `RemoveAllFrom(옛 무기)` 로 떼고
새 무기의 것을 얹는다. `RemoveAll` 은 아이템 효과까지 지워 쓰지 않는다. 출처로 데이터 에셋이 아니라 컴포넌트를 쓴 이유는
에셋이 여러 곳에서 나눠 쓰일 수 있어서다. 아이템도 에셋이 아니라 가방에 놓인 인스턴스를 출처로 쓴다.

`PlayerStats` 의 공격력과 공격 속도 인스펙터 칸은 지웠다. 늘 0 인 값을 칸으로 두면 누가 넣은 값이 무기 값에 조용히 더해진다.
`Equip` 은 `PlayerStats.Awake` 가 스탯을 만든 뒤라야 해서 `Start` 에서 부른다.

## 결과

- **스탯 설계 결정의 약속이 처음으로 확인됐다.** 공격력 퍼센트 아이템을 넣은 채 무기를 바꾸면 효과가 새 무기에 얹힌다.
  계산은 `(0 + 무기 Flat) × (1 + 퍼센트 합)` 이라 같은 10% 가 활(1)에서는 1.1, 검(3)에서는 3.3 이 된다.
- **창은 코드를 한 줄도 고치지 않고 들어갔다.** `MeleeWeapon` 과 `MeleeWeaponData` 를 그대로 쓰고 에셋 하나와 인스펙터 연결만 더했다.
  무기 코드가 커밋 전이라 `git diff` 대신 창을 넣기 전후로 `Scripts/` 의 C# 파일 49개 해시를 비교해 모두 같았다.
- `PlayerAttack` 에 있던 풀 만들기 한 줄과 발사 네 줄이 `BowWeapon` 으로 옮겨 갔고, 새로 생긴 것은 `Equip` 하나다.
- 무기마다 자식 오브젝트(`Bow`, `Sword`, `Spear`)에 컴포넌트를 둔다. `Player` 에 같은 `MeleeWeapon` 이 둘 붙어 인스펙터에서 구분되지 않았다.
  클래스를 나누면 같은 코드가 두 번 생기고, 이름만 다른 빈 자식 클래스는 하는 일 없는 파일이 된다. 무기는 `origin` 으로 플레이어 위치를 받아 어디 붙어도 같다.
- **투사체를 쓰는 무기가 활 하나라** [풀을 씬에 두기 결정](projectile-pool-in-scene.md)이 넘긴 'PlayerAttack 을 ProjectilePool 로 옮길지' 는 옮기지 않는다.
- **가방의 스탯 글자가 처음 열 때 0 으로 보이는 버그**가 나왔다. 가방은 정해진 순간에만 글자를 새로 썼는데, 무기가 `Start` 에서 값을 얹게 되면서
  `Awake` 에 쓴 0 이 남았다. `BagView` 가 스탯 넷의 `OnChanged` 를 구독하게 고쳤다. 규칙의 'UI 는 이벤트로 갱신한다' 로 돌아간 것이다.

## 한계 / 남은 문제

- **무기를 얻는 방법이 없다.** 숫자 키 1, 2, 3 으로 바꾸는 확인용 입력뿐이다. 방 보상이나 시작 전 고르기는 방 배치와 Phase 5 세이브에서 정한다.
- **숫자 키는 입력 에셋이 아니라 `Keyboard.current` 로 읽는다.** 게임패드로는 무기를 바꿀 수 없다. 얻는 방법이 정해지면 함께 본다.
- **데이터 네임스페이스(`JM2D.Data`)가 투사체(`JM2D.Combat`)를 알게 됐다.** `Projectile` 이 이미 `ProjectileData` 를 써서 두 네임스페이스가 서로를 안다.
  같은 어셈블리 안이라 컴파일은 문제없다.
- **무기를 바꿔도 공격 간격은 그대로다.** 검을 휘두른 직후 활로 바꾸면 검의 남은 간격을 기다린다. 바꿔서 간격을 없애는 꼼수는 막지만 답답할 수 있다.
- **밸런싱은 하지 않았다.** 값은 '세 무기가 다르게 쓰인다' 가 보이는 데까지만 맞췄고, 아이템 15종 판단과 함께 난이도 튜닝에서 본다.
