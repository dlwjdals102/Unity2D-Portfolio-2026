# 스탯 계산은 순수하게, 전파는 중개자를 거쳐서

## 문제

아이템 20종을 데이터만 추가해서 만들려면 '공격력 +10' 같은 것이 코드가 아니라
값이어야 한다. 그러려면 스탯이 기본값과 모디파이어를 분리해 들고 있어야 한다.

정할 것이 다섯이었다.

1. 모디파이어를 몇 종류로 나누고 어떤 순서로 적용할 것인가
2. 지속시간 만료를 넣을 것인가
3. 아이템이 없는데 출처 추적을 지금 넣을 것인가
4. 계산 결과를 캐싱할 것인가
5. 스탯이 바뀐 것을 `Health` 에 어떻게 알릴 것인가

## 1. 세 종류로 나누고 순서를 고정한다

```
최종값 = (기본값 + 가산합) × (1 + 승산가산합) × ∏(1 + 승산승산ᵢ)
```

### 검토한 대안

**안 A: 가산과 승산 두 종류**
- 장점: 코드가 짧다. 열거형에 값이 둘이면 되고 누적기도 둘이다.
- 단점: **쌓았을 때 늘어나는 방식을 조절할 수 없다.**

**안 B: 세 종류**
- 장점: 흔한 아이템은 선형으로, 희귀 아이템은 지수로 늘릴 수 있다.
- 단점: 열거형 값 하나와 누적기 하나가 는다.

### 선택과 이유

**B를 골랐다.** 비용이 거의 없고 밸런싱 수단이 하나 생긴다.

`+20%` 를 n개 모았을 때 차이가 이렇다.

| 개수 | 승산 가산 | 승산 승산 |
|---|---|---|
| 5개 | 2.0배 | 2.49배 |
| 10개 | 3.0배 | 6.19배 |
| 20개 | 5.0배 | 38.3배 |

**흔한 아이템을 승산 승산으로 주면 그것만 모으는 게 정답이 되어
다른 선택지가 의미를 잃는다.** 가방이 5×5 라 10~15개는 현실적으로 모인다.

**가산을 맨 앞에 두는 것도 의도적이다.** 무기를 좋은 것으로 바꾸면 갖고 있던
퍼센트 아이템이 함께 강해진다. 순서를 뒤집으면 무기와 아이템이 서로 무관해진다.
**빌드 게임에서는 요소들이 서로를 키워야 재미가 있다.**

### 정수 변환도 같은 자리에 뒀다

최대 체력과 공격력은 정수다. `Stat.IntValue` 를 Logic 에 두어
**반올림 규칙이 한 곳에만 있게** 했다. 읽는 쪽에서 캐스팅하면 규칙이 흩어지고
테스트로 검증할 수도 없다.

`MidpointRounding.AwayFromZero` 를 명시했다. C# 과 Unity 의 기본 반올림은
**은행가 반올림이라 2.5 를 2 로 만든다.** `.5` 가 걸리는 값에서만 어긋나므로
대부분의 테스트를 통과하고 나중에 이상한 수치로 나타난다.

## 2. 지속시간을 넣지 않는다

### 검토한 대안

**안 A: 모디파이어에 남은 시간을 두고 만료시킨다**
- 장점: 시간제 버프를 바로 만들 수 있다.
- 단점: **누군가 매 프레임 시간을 흘려보내야 한다.** `JM2D.Logic` 이 시간에 묶인다.

**안 B: 넣지 않는다**
- 장점: Logic 이 순수하게 남는다. 테스트가 씬도 플레이도 없이 돈다.
- 단점: 포션류를 만들 때 다시 손대야 한다.

### 선택과 이유

**B를 골랐다.** 아이템이 영구라 지금 쓸 데가 없고, **Logic 을 순수하게 두는 것이
asmdef 를 넷으로 나눈 이유 전체**다.

포션류가 실제로 생기면 **만료 판단을 Logic 밖에 두면 된다.** 시간을 재는 쪽이
만료된 모디파이어를 `RemoveAllFrom` 으로 떼면 Logic 은 여전히 순수하다.

변경 알림에 `System.Action` 을 쓴 것도 같은 기준이다. `System` 은 UnityEngine 이
아니므로 순수성을 깨지 않는다. `UnityEvent` 였다면 깼다.

## 3. 출처 추적을 아이템보다 먼저 넣었다

아이템이 아직 없다. 규칙대로면 빼야 한다.

### 그럼에도 넣은 이유

**출처 없이는 제거를 만들 수 없다.**

공격력 +10 짜리 아이템 둘을 넣었다가 하나를 빼는 상황을 생각해 보면,
리스트에 값이 똑같은 모디파이어가 둘 있다. 값으로 찾으면 어느 것이 지워질지
알 수 없고, **화면상으로는 공격력이 맞아 보여서 나중에야 드러난다.**

그리고 **출처는 나중에 붙일 수 있는 종류가 아니다.** 모디파이어를 만들 때
함께 들어가야 하므로, 나중에 넣으려면 모든 생성 지점을 고쳐야 한다.

타입은 `object` 로 뒀다. 아이템 타입을 쓰면 **Logic 이 게임의 개념을 알게 된다.**
식별만 하면 되고 내용을 읽을 일이 없어 가능한 선택이다.

**부수적으로 무기 교체 문제도 이 구조가 감당한다.** `_baseValue` 는 `readonly`
라 바꿀 수 없지만, 무기 성능을 출처가 무기인 `Flat` 모디파이어로 표현하면
무기를 바꿔도 아이템 모디파이어가 그대로 남는다.

## 4. 캐싱은 측정 없이 넣었다

**이 항목은 정직하게 적는다.** 풀링 때와 달리 프로파일러로 재지 않았다.

### 규모

| | 값 |
|---|---|
| 스탯 4종 × 초당 50프레임 | 초당 200회 읽기 |
| 모디파이어 10개를 순회 | 초당 2,000회 비교 |

**이 정도는 프로파일러에 잡히지 않는다.** 풀링에서 얻은 0.40ms 에 비하면
측정 오차 안에 묻힌다. CLAUDE.md 3번의 포트폴리오 예외는 최적화를 허용하지만
**전후 수치를 증거로 요구하는데, 그 조건을 채우지 못했다.**

### 그럼에도 남긴 이유

- **성능이 아니라 구조 때문이다.** '읽기가 계산을 유발한다'와 '읽기는 저장된
  값을 돌려준다'는 다른 구조이고, 스탯과 아이템이 늘어도 후자는 무너지지 않는다.
- 더티 플래그는 무효화 지점을 빠짐없이 찾는 것이 어려운 부분이다.
  **그것을 테스트로 막아둔 것까지가 한 세트**이며, 그 과정 자체가 보여줄 값어치가 있다.

**면접에서 측정 여부를 물으면 안 했다고 답하는 것이 맞다.** 왜 그럼에도 넣었고
대신 무엇으로 안전을 확보했는지가 답이 된다.

### 무효화 지점을 한 곳으로 모았다

리스트가 바뀌는 세 메서드가 각각 `_isDirty = true` 와 `OnChanged?.Invoke()` 를
두 줄로 갖고 있으면 **한 줄만 적는 사고가 난다.** `MarkChanged()` 하나로 묶어
빠뜨릴 방법을 없앴다.

두 줄의 순서도 정해져 있다. **캐시를 먼저 낡게 만들고 그다음 알린다.**
반대로 하면 알림을 받은 쪽이 `Value` 를 읽는 순간 낡은 값을 받는다.

## 5. 최대 체력만 다른 경로로 흐른다

이동 속도는 `PlayerMotor` 가 매 프레임 그냥 읽으면 끝난다. 상태가 없기 때문이다.
**`Health` 는 `_current` 를 들고 있어서 최대가 바뀌면 결정이 필요하다.**

### 검토한 대안

**안 A: 모디파이어를 붙이는 쪽이 `Health` 에도 알린다**
- 단점: 알리는 것을 잊으면 조용히 어긋난다.

**안 B: `Health` 가 `PlayerStats` 를 구독한다**
- 단점: **적도 `Health` 를 쓴다.** 적이 없는 컴포넌트를 참조하게 된다.
  데이터 분리 때 `Health` 가 `EnemyData` 를 몰라야 했던 것과 같은 문제다.

**안 C: `PlayerStats` 가 스탯 변화를 듣고 `Health` 에 알린다**
- 장점: `Health` 는 아무것도 몰라도 된다. 중개가 원래 `PlayerStats` 의 일이다.

### 선택과 이유

**C를 골랐다.** 사슬이 이렇게 흐른다.

```
모디파이어 추가 → Stat.OnChanged → PlayerStats → Health.ChangeMaxHealth
                → Health.OnHealthChanged → HealthBar
```

**중간의 누구도 양쪽 끝을 모른다.** `Stat` 은 Unity 를 모르고, `Health` 는 스탯을
모르고, `HealthBar` 는 아이템을 모른다. 적은 이 사슬의 위쪽 절반이 없고
`InitializeMaxHealth` 한 번으로 끝나는데, 그래도 아무 데도 걸리지 않는다.

### 최대가 늘면 늘어난 만큼 현재도 찬다

| 안 | 2/3 에서 최대 +2 | 문제 |
|---|---|---|
| 완전 회복 | 5/5 | 최대 체력 아이템이 물약을 겸한다 |
| **차이만큼** | **4/5** | |
| 그대로 | 2/5 | 아이템을 먹었는데 상황이 나빠 보인다 |

**차이만큼 늘리는 방식을 골랐다.** 뗐을 때도 자연스럽다. 최대 -2 면 현재도 -2 라
먹기 전 상태로 정확히 돌아간다.

**하한을 1로 뒀다.** 아이템을 뗐다고 죽으면 안 된다. 0 이 아니라 1 인 이유는,
`OnDied` 가 `TakeDamage` 에서만 발생하므로 **체력 0 인데 죽지도 않은 유령 상태**가
생기기 때문이다. 그런 상태를 아예 못 만드는 편이 낫다.

### 이름을 둘로 나눴다

`SetMaxHealth` 하나로는 초기화와 런타임 변경을 구분할 수 없었다.
게임 도중에 부르면 체력이 가득 차고 UI 갱신도 되지 않는데, **이름이 그것을
알려주지 않아** 계단 3에서 정리 목록에 올려뒀던 항목이다.

| 메서드 | 언제 | 현재 체력 |
|---|---|---|
| `InitializeMaxHealth` | 시작할 때 한 번 | 최대로 채운다 |
| `ChangeMaxHealth` | 런 도중 | 늘어난 만큼만 더한다 |

**주석으로 막던 것을 이름이 막게 됐다.**

## 결과

- **EditMode 테스트 22개.** 이 프로젝트의 첫 자동 테스트이며 씬도 플레이도 없이
  1초 안에 끝난다. `JM2D.Logic` 이 `System` 과 `System.Collections.Generic` 만
  참조하기 때문이다.
- 테스트가 실제로 일했다. `RemoveAll` 이 조건부 삭제였을 때 **음수 모디파이어만
  살아남던 버그**를 회귀 테스트로 남겼고, `?.` 을 빼면 22개 중 19개가 깨진다는
  것으로 **구독자가 없는 경우가 기본이라는 사실**이 드러났다.
- 플레이어 수치가 세 컴포넌트에 흩어져 있던 것이 `PlayerStats` 한 곳으로 모였다.
- 디버그 키로 네 스탯 모두 런타임 변경과 원복을 확인했다.

## 한계 / 남은 문제

- **수치 스케일이 작아 퍼센트 증가가 묻힌다.** 공격력 1에 +10% 는 반올림해도
  1이다. 반올림 방식으로 풀 수 없고 기본 수치를 키워야 하는데,
  적 체력 3과 투사체 피해량 1을 바꾸면 밸런스 전체가 움직인다.
  **Phase 4 밸런싱에서 다룬다.**
- **캐싱이 측정으로 정당화되지 않았다.** 위 4번에 적은 그대로다.
- **조건부 모디파이어와 스탯 간 파생이 없다.** '체력 50% 이하일 때 +20%' 는 상태
  감시가 필요하고, '힘 1당 공격력 2' 는 계산 그래프와 순환 참조를 끌고 온다.
- **상한과 하한이 없다.** 공격 속도에 -100% 가 붙으면 0이 되고
  연사 간격이 무한대가 되어 조용히 발사가 멈춘다.
- **적에게는 스탯이 없다.** 엘리트 적과 층별 강화는 Phase 4다.
- **디버그 키를 Phase 4에서 지워야 한다.** 아이템이 생기면 역할이 끝난다.
