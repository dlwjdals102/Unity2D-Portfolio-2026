# 보스를 적 넷의 FSM 위에 얹고, `EnemyBase` 는 한 줄만 열었다

## 문제

GDD 의 승리 조건이 '8번째 방의 보스 처치' 인데 보스가 없었다. 보스 방은 조금 강한 웨이브 하나였고,
한 판의 끝이 앞의 여섯 방과 같은 모양이었다.

그리고 [FSM 구조](enemy-fsm-structure.md)에서 **'상태 패턴은 적 넷 규모에서 이르다'** 고 판단했는데,
그 판단이 **더 복잡한 적 하나를 감당하는지** 확인된 적이 없었다. 보스가 그 시험대다.

## 검토한 대안

### 뼈대를 무엇으로 하나

| 안 | 판단 |
|---|---|
| **`Boss : EnemyBase`** | 체력 연결, 죽음, 길찾기, 밀어내기, 타격 판정, `Spawned` 알림이 그대로 온다. `EnemyBase` 의 계약이 '교전 중에 할 일은 자식이 정한다' 라 패턴 머신을 `TickEngaged` 에 넣으면 된다 |
| `MonoBehaviour` 로 따로 | 자유롭지만 위 여섯을 다시 짜야 하고, 보스만 4-E 의 길찾기를 못 받는다 |
| 이참에 상태 패턴으로 다시 | 적 넷이 함께 바뀐다. 보스 하나 때문에 도는 코드를 흔든다 |

**'교전에서 나오지 않는다' 를 값으로 만들었다.** 감지 범위와 교전 범위를 방보다 크게(50) 주고
`EngageRange` 를 `DetectRange` 로 그대로 쓰면, 입장하자마자 교전으로 들어가 `ReturnToChase` 를 부르지 않는 한 나오지 않는다.
코드에 특수 분기가 없고 **값 하나가 그 성질을 만든다.**

### 단계를 어떻게 나누나

패턴 넷(휩쓸기, 돌진, 사격, 소환)을 나란히 놓으니 **전부 예고 → 발동 → 회복의 같은 3단**이었다.

| 안 | 상태 수 |
|---|---|
| 패턴마다 자기 단계를 갖는다 | 4 곱하기 3 = 12 |
| **단계를 셋으로 공통화한다** | 단계 3 + 패턴 4 |

발동이 여러 스텝에 걸치는 패턴은 **돌진 하나뿐**이고 나머지 셋은 들어가는 순간 끝난다.
그래서 '단계에 들어갈 때 한 번' 하는 자리(`BeginWindup`, `BeginAct`)와 '발동 중 매 스텝'(`TickAct`)을 나눴다.

### 2페이즈 값을 어떻게 다루나

| 안 | 판단 |
|---|---|
| 바뀌는 값만 덮어쓴다 | 값을 읽는 곳마다 페이즈 분기가 생긴다 |
| **패턴 묶음을 페이즈마다 통째로 둔다** | 보스가 `_current` 하나만 들고 전환 때 갈아 끼운다. **분기가 0개** |
| ScriptableObject 값을 런타임에 고친다 | 플레이 중에 고친 값이 디스크에 남는다. 규칙에 적힌 함정이다 |

둘째는 에셋에 값이 두 벌 생기는 것이 비용이다. 대신 2페이즈에서 **무엇이든** 바꿀 수 있고,
'2페이즈는 회복도 짧게' 같은 생각이 나중에 나도 코드를 안 고친다.

## 선택과 이유

**보스는 `EnemyBase` 를 상속하고, 페이즈는 값 묶음을 갈아 끼우는 것으로 표현한다.**

- **단계 셋은 공통이고 패턴은 '발동에서 무엇을 하는가' 만 다르다.** 패턴이 정해질 때 그 패턴의 단계 시간과 색(`PatternSteps`)을
  한 번 꺼내 두므로, 단계가 바뀔 때마다 '지금 무슨 패턴인가' 를 다시 묻지 않는다.
  **패턴을 더할 때 고치는 자리가 `StartPattern` 의 `switch` 한 군데다.**
- **페이즈 전환은 단계 흐름 밖에서 가로챈다.** `Step` 에 하나를 더하지 않았다. 단계는 패턴의 것이고 전환은 패턴이 아니다.
  하던 패턴이 무엇이든 그 자리에서 끊긴다. 원거리 적의 후퇴를 `switch` 밖 규칙으로 둔 것과 같은 모양이다.
- **전환 무적은 `Health` 에 이미 있던 문을 쓴다.** `IsExternallyInvulnerable` 은 대시가 쓰던 것이고
  `Health` 는 그 이유를 모른다. 이유까지 알게 만들었다면 지금 `IsChangingPhase` 를 더하고 있었을 것이다.
- **어느 페이즈에 어떤 패턴이 있는지도 데이터가 정한다.** 소환은 `Prefab` 칸이 비어 있으면 쓰지 않는다.
  `if (_isPhase2)` 를 넣었다면 분기 0개가 무너졌다.

## `EnemyBase` 는 몇 줄 바뀌었나: 한 줄

명세의 완료 조건이 '0줄이 목표이고, 아니면 왜인지 남긴다' 였다. 계단 4까지 0줄이었고 **한 줄이 됐다.**

```csharp
protected Health Health => _health;
```

계단 4에서 보스가 체력 변화를 들으려고 자기 `_health` 필드를 따로 잡았더니
**Unity 가 '같은 이름이 상속 관계에서 두 번 직렬화된다' 고 경고**했다. 이름을 `_ownHealth` 로 바꿔 경고를 피할 수도 있었지만,
그러면 같은 컴포넌트를 가리키는 필드가 둘로 남는다. **숫자를 지키는 것보다 중복을 없애는 편이 낫다고 보고 한 줄 열었다.**

`EnemyBase` 는 이미 `Target` 과 `PathField` 를 열어 두었고, `Stop`, `Move`, `HitAround`, `SetColor` 가 `protected` 다.
읽기 전용 프로퍼티 하나를 더하는 것이라 적 넷의 동작은 바뀌지 않는다.

## 딸려 온 것 셋

작업 중에 **다른 곳이 막아서** 생긴 변경이다. 셋 다 보스 때문에 처음 드러났다.

| 무엇 | 왜 필요했나 |
|---|---|
| `Health.Kill()` | 보스가 죽을 때 소환물을 `Destroy` 로 치우면 `OnDied` 가 울리지 않아 **`EnemyCounter` 의 적 수가 줄지 않고 방이 영영 안 열린다** |
| `IProjectileShooter` | 보스와 원거리 적이 둘 다 씬의 투사체 풀을 받는다. `RoomCombat` 에 같은 일을 하는 가지가 둘 생기는 것을 하나로 묶었다 |
| `IPathField.CanStand` | 보스가 벽에 붙어 소환하면 잡몹이 벽 안에서 태어났다. 보스가 격자를 모르는 채로 '여기 설 수 있나' 를 묻는 문이다 |

셋째가 특히 그렇다. 4-E 에서 `IPathField` 에 **'어디로 갈까' 만** 두었는데, 무언가를 놓는 쪽은 **'여기 설 수 있나'** 를 묻는다.
인터페이스가 한 가지 쓰임만 보고 만들어졌던 셈이다.

## 결과

- **`EnemyBase` 1줄.** `Boss` 는 351줄, `BossData` 143줄, `BossHealthBar` 168줄, `FanSpread` 29줄이다.
- 적 넷(근접, 돌진, 원거리, 분열)은 한 줄도 바뀌지 않았다. `RangedEnemy` 는 인터페이스 이름표만 붙었다.
- 페이즈를 묻는 분기가 코드에 **0개**다. `_current` 를 한 번 바꾸는 것이 전환의 전부다.
- EditMode 테스트는 **203개**다(부채꼴 각도 17개가 늘었다).
- GDD 스코프의 '보스 1, 2페이즈' 를 이 판단으로 닫는다.

## 한계 / 남은 문제

- **보스는 풀링하지 않는다.** 한 판에 한 번 태어나므로 문제가 없지만, `Health.OnHealthChanged` 구독을
  `Awake` 에서 걸고 `OnDestroy` 에서 푼다. 적을 풀링하는 날 이 짝이 깨진다.
  `EnemyBase` 의 `OnEnable` 이 `private` 이라 같은 이름을 자식이 선언하면 부모 것이 가려질 수 있어 피한 자리다.
  **Unity 가 실제로 부모 것을 부르는지는 확인하지 않았다.** 그 답에 기대지 않는 자리를 골랐다.
- **소환한 잡몹의 명단이 한 판 내내 자란다.** 죽은 것을 그때그때 빼지 않고 셀 때 `== null` 로 거른다.
  한 판에 열몇 마리라 문제가 없지만, 소환을 크게 늘리면 다시 본다.
- **보스 체력 바와 플레이어 체력 바가 서로 다른 방식으로 줄어든다.** 플레이어는 스프라이트와 `fillAmount`,
  보스는 스프라이트 없이 앵커다. 폴리싱에서 UI 에 에셋을 입힐 때 맞춘다.
- **등장 연출이 없다.** 보스가 한 프레임에 나타난다. 붙일 자리는 명세 메모에 적어 두었다.
