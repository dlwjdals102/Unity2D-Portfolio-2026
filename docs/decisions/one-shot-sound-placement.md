# 한 번 나는 소리를 어디서 내는가

## 문제

타격음을 붙일 자리를 골라야 했다. 번쩍임과 셰이크는 맞은 대상에 붙어 있어
([hit-feedback.md](../specs/hit-feedback.md)) 소리도 같은 자리가 자연스러워 보였다.

**그 자리는 가장 중요한 소리를 잘라먹는다.** 적은 죽는 순간 파괴된다
([EnemyBase.cs:275](../../Assets/_Project/Scripts/Enemy/EnemyBase.cs:275)).
죽이는 타격은 `PlayOneShot` 을 부른 그 프레임에 오브젝트가 사라지므로
`AudioSource` 도 함께 사라진다. 투사체도 같다. 맞으면 풀로 돌아가 비활성이 된다.

두 번째 문제가 뒤따랐다. 씬에 하나인 것을 **판 도중에 태어나는 적이 가리킬 수 없다.**
`RoomCombat`, `Boss`, `SplitOnDeath` 셋이 적을 만들고, 만드는 쪽이 넣어 주는
주입 통로가 이미 하나 있다(`SetHitStop`). 소리를 위해 같은 모양을 하나 더 깔면
**배선 두 벌이 나란히 간다.**

세 번째는 휘두르는 소리를 넣을 때 왔다. **소리 내는 자리가 둘이 됐다.**

## 검토한 대안

### 안 A — 맞은 대상에 `AudioSource` 를 붙인다
- 장점: 번쩍임과 같은 모양이다. 주입이 필요 없다. 거리 감쇠를 쓸 길이 열린다.
- 단점: **죽이는 타격의 소리가 들리지 않는다.** 투사체도 같다.

### 안 B — `HitSound` 를 새로 만들어 씬에 두고 주입한다
- 장점: 책임이 또렷하다. 소리가 자기 클래스를 갖는다.
- 단점: `EnemyBase`, `HitReaction`, 주입 자리 셋이 전부 늘어난다. 클립 하나에 그만한 값을 하지 않는다.

### 안 C — 이미 모든 타격이 지나가는 자리에서 낸다
- 장점: **새 배선이 0 이다.** `HitReaction.OnDamaged` 는 모든 타격에서 `_hitStop.Stop()` 을 부른다.
- 단점: `HitStop` 이라는 이름이 하는 일보다 좁아진다.

### 안 D — 소리 내는 코드를 한 자리로 모은다 (휘두르는 소리가 생긴 뒤)
- 장점: 같은 네 줄이 두 번 복사되지 않는다.
- 단점: 플레이어는 파괴되지 않아 씬에 있을 이유가 없는데 **제약 없는 쪽까지 씬에 묶인다.**

## 선택과 이유

**C 를 골랐고, 클래스 이름을 `HitStop` 에서 `HitFeedback` 으로 바꿨다.**
`Stop(duration)` 도 `Hit(stopTime)` 이 됐다. 부르는 쪽이 알리는 것은 '타격이 일어났다' 는
사실이고, 멈추는 시간은 그중 하나의 값일 뿐이다.

A 를 버린 것은 증상이 또렷했기 때문이다. **거리 감쇠를 쓰지 않기로 한 범위 결정이
A 의 유일한 장점을 지웠다.** 소리에 위치가 없으면 '누가 낸 소리인가' 를
오브젝트로 표현할 이유가 없어진다.

B 는 늘어나는 자리가 다섯인데 얻는 것이 이름뿐이었다. 클립이 여러 개로 갈려
'어느 소리를 낼지 고르는 일' 이 생기는 날 다시 본다.

**D 도 버렸다.** 지금 두 자리는 수명이 다르다. 복사된 네 줄의 값보다
파괴되지 않는 쪽을 씬에 묶는 값이 비싸다.

## 결과

**새로 깐 배선이 0 이다.** 소리를 넣는 데 `HitReaction`, `EnemyBase`, 주입 자리 셋이
한 줄도 바뀌지 않았다. 늘어난 것은 `HitFeedback` 안의 네 줄과 인스펙터 칸 하나다.

**죽이는 타격의 소리가 끝까지 난다.** 플레이로 확인했다.

**겹침은 프레임으로 막는다.** 창으로 셋을 꿰면 `Hit` 이 같은 프레임에 세 번 불린다.
멈춤은 `Mathf.Max` 가 막고 있었지만 소리는 세 번 겹쳐 세 배로 커진다.
`_lastSoundFrame` 과 `Time.frameCount` 를 견주어 한 번만 낸다.

시간으로 막는 안을 둘 버렸다. `_audio.isPlaying` 은 소리 길이만큼, `_stopLeft > 0f` 는
멈춤 시간만큼 **그 사이에 들어온 다음 공격까지 조용하게** 만든다.
막아야 하는 것은 '한 번의 공격이 여럿을 맞힌 것' 이고 그것은 같은 프레임이라는 뜻이다.

**휘두르는 소리에는 같은 가드를 두지 않았다.** `CanFire` 가 쿨다운을 보므로
한 프레임에 두 번 들어올 길이 없다. 연사가 초당 20이어도 간격이 세 프레임이다.
**같은 문제로 보이는 두 자리가 다른 제약 아래 있었고, 습관으로 복사하면 쓰이지 않는 상태가 하나 는다.**

## 한계 / 남은 문제

**겹침을 막는 자가 '공격' 이 아니라 '프레임' 이다.** 서로 다른 두 공격이 같은 프레임에
들어오면 소리가 하나로 합쳐진다. 적과 플레이어가 동시에 맞는 장면이 그것이다.
들려야 할 소리가 빠지는 쪽이라 받아들였다. 실제로는 1~2 프레임 차이로 들어와 두 번 들린다.

**같은 네 줄이 두 군데 있다.** 세 번째가 생기면 모을 값이 생기고,
그때 구조가 뒤집힌다. 클립이 다섯 개를 넘어가면 재생기가 클립을 소유할 수 없다.

```
지금    재생기가 클립을 소유한다        부르는 쪽은 '사건' 만 알린다
그때    소리의 주인이 클립을 소유한다   재생기는 받아서 틀기만 한다
```

적 종류마다 타격음을 다르게 하려면 `HitFeedback` 이 '누가 맞았는지' 를 알아야 하고,
적을 추가할 때마다 그 파일을 고쳐야 한다. 뒤집으면 클립이 `EnemyData` 로 내려가
고치는 자리가 그 적의 데이터 에셋이 된다. **데이터 주도 설계가 소리까지 덮는 모양이고,
적 수치를 ScriptableObject 로 뺀 Phase 3의 선택이 거기서 한 번 더 값을 한다.**
지금 하지 않은 것은 클립 다섯과 데이터 에셋 다섯을 손보는 일이 폴리싱 범위를 넘기 때문이다.

**볼륨을 한꺼번에 줄일 방법이 없다.** `AudioSource` 셋이 각자 값을 들고 있다.
소리 끄기나 볼륨 조절이 필요해지는 날 오디오 믹서를 넣는다. 지금은 설정 UI 자체가 없다.

**씬의 `m_EditorClassIdentifier` 에 옛 이름이 남아 있다.** 참조는 `m_Script` 의 GUID 로
돌고 그 값이 유지되어 동작에는 관여하지 않지만, `HitStop` 으로 저장소를 훑으면 그 줄이 걸린다.
