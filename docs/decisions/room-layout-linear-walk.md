# 방 배치는 격자 위 한 줄 걷기이고, BFS 검증과 재생성을 두지 않는다

## 문제

[맵 구조 결정](map-structure.md)이 '방 8개 + 절차적 배치' 를 골랐고, 이제 그 배치를 어떻게 만들지 정해야 했다.
기능 후보 풀 A급 6번은 **'방을 무작위로 잇고, BFS 로 도달 가능성을 검증해 실패하면 재생성한다'** 를 차별화 지점으로 적어 뒀다.

정할 것은 넷이었다.

- GDD 의 '방 프리팹 8' 과 '8번째 방의 보스' 가 같은 8 인가
- 방을 어떤 모양으로 잇는가
- 무엇을 검증하고, 실패하면 무엇을 하는가
- 결과를 어떤 모양으로 담고, 문을 어떻게 정하는가

전제가 둘 있었다. **방 하나가 화면 두세 장 크기**이고, **특수 방(보물 방, 상점, 비밀 방)은 만들지 않는다.**

## 검토한 대안

### 1. 방 수

GDD 의 두 8 이 같으면 한 판에 프리팹 여덟 개를 한 번씩 모두 써, 무작위로 바뀌는 것이 순서뿐이다.
**한 판을 방 8개(시작 1, 전투 6, 보스 1)로 정하고, 프리팹 수는 4-B 에서 만들어 보며 정한다.**

### 2. 배치 모양

| 안 | 사례 | 판단 |
|---|---|---|
| 일직선에 순서만 섞기 | 하데스 | 격자가 없어 절차적 생성이라 부를 것이 거의 없고 테스트할 것도 없다 |
| 가지형 (한 칸씩 붙여 퍼뜨리기) | 아이작 | **처음 설계한 안이다.** 시작 방 둘레로 퍼뜨리고, BFS 로 가장 먼 막다른 방을 골라 보스 방으로 둔다 |
| 정답 경로 먼저 긋기 | 스펠렁키 | 옆과 아래로 내려가는 플랫포머의 전제라 사방으로 다니는 탑다운에 그대로 옮기기 어렵다 |
| 흐름 그래프에 방 끼우기 | 엔터 더 건전, 데드 셀 | 사람이 흐름을 여러 장 그려야 무작위가 생긴다. 방 8개에 과하다 |
| **격자 위 한 줄 걷기** | 스펠렁키의 경로 긋기, 엔터 더 건전의 큰 줄기 | 시작 칸에서 빈 이웃으로 한 칸씩 일곱 번 걷는다. 걸은 순서가 곧 진행 순서다 |

### 3. 가지형을 버린 이유

가지형 명세를 쓴 뒤 **"근접 판정을 부채꼴에서 겹침 쿼리로 줄였듯 방 생성도 더 간단한 방법이 없는가"** 라는 질문을 받았다.
[근접 판정 결정](melee-hit-query.md)과 같은 기준, 즉 **그 코드가 만드는 차이가 우리 게임에서 보이는가** 로 다시 봤다.

- **가지 끝에 둘 것이 없다.** 아이작의 가지가 의미 있는 것은 막다른 곳의 특수 방 때문이다. 우리 가지 끝에는 전투 방이 하나 더 있을 뿐이다.
- **되짚어 걷는 비용이 크다.** 아이작의 방은 화면 한 장이라 깬 방을 몇 초면 지난다. 우리 방은 두세 장이라 가지에 들어갔다 나오면 적 없는 넓은 방을 걷는 빈 시간이 생긴다.

막다른 방 판단, BFS 거리, 보스 방 고르기, 그것을 위한 재생성이 모두 **반갑지 않은 결과를 위한 코드**였다.

포트폴리오로도 따졌다. BFS 를 잃는 것보다 **"가지 끝에는 뭐가 있죠?"** 에 답하지 못하는 쪽이 더 약하다고 봤다.
레퍼런스를 조건과 맞춰 보지 않고 가져온 것이 드러나기 때문이다. 반대로 단순화 이야기가 이미 여럿이라
**'어려운 것은 다 피했다' 로 읽힐 위험**도 있어, BFS 를 버리지 않고 실패할 수 있는 자리로 옮기기로 했다(한계 절).

### 4. 검증과 재생성

| 대상 | 판단 |
|---|---|
| 모든 방이 이어졌나 (BFS) | 한 칸씩 붙여 만드는 배치는 만드는 순간부터 이어져 있어 **늘 통과한다.** 가지형에서도 한 줄 걷기에서도 같다 |
| 걷다가 갇혔나 (재생성) | 한 줄 걷기로 줄이며 '스스로 갇히는 일이 실제로 생겨 재생성이 의미를 갖는다' 고 예측했다. **전수 조사로 틀렸다** (결과 절) |

'막히지 않는다' 를 지키는 방법도 셋을 봤다.

| 안 | 판단 |
|---|---|
| 시드 여러 개로 테스트 | 표본이라 증명이 아니다. 격자를 두어 가장자리가 생기는 실수는 잡는다 |
| 선택을 밖에서 넣고 모든 갈래를 테스트로 돌리기 | 증명이 된다. 게임이 쓰지 않는 입구가 생산 코드에 생긴다 |
| **시드 1,000개 테스트 + 전수 조사 결과를 이 문서에 남기기** | 코드는 단순하고 근거는 문서에 있다 |

### 5. 결과의 모양과 문

| 안 | 판단 |
|---|---|
| **걸은 순서대로 쌓인 좌표 목록 하나** | 순서가 곧 데이터다. 종류는 순번(0 시작, 마지막 보스)으로, 문은 '순번이 하나 차이' 로 계산한다. 기록이 하나라 어긋날 곳이 없다 |
| 2차원 배열 | 칸으로 묻기 쉽지만 좌표가 음수가 되지 않게 격자를 정해야 하고, 그러면 가장자리가 생긴다 |
| 둘 다 | 두 기록이 어긋날 수 있다 |

U자로 꺾이면 **순번은 멀지만 칸은 붙은 두 방**이 생긴다. 문을 '옆 칸에 방이 있다' 로 정하면 그 사이에 문이 생겨 붙음을 막는 규칙이 필요하다.
**문을 '순번이 하나 차이' 로 정하면 붙은 두 방 사이는 저절로 벽이다.** 방 프리팹은 저마다 벽을 가져 4-B 는 가장자리 변과 똑같이 막으면 된다.

### 6. 난수

| 안 | 판단 |
|---|---|
| **생성기 안에서 `new System.Random(seed)`** | 시드만 같으면 결과가 같다 |
| 밖에서 `System.Random` 을 넣기 | 넘기는 쪽이 시드를 모르면 재현이 흐려진다 |
| `UnityEngine.Random` | 게임 전체가 함께 쓰는 난수라 다른 코드가 먼저 뽑으면 같은 시드에서도 배치가 바뀐다 |

## 선택과 이유

**격자 위 한 줄 걷기. 빈 이웃 중 하나를 같은 확률로 골라 일곱 걸음 걷고, 결과는 좌표 목록 하나다.**
BFS 검증과 재생성은 두지 않는다. 둘 다 이 배치에서 실패할 수 없는 검사라서다.

- 걸은 순서가 곧 진행 순서라 **거리 계산이 필요 없다.** 보스 방은 마지막 칸이고 시작에서 늘 문 7개 거리다.
- 방을 건너뛸 수 없어 **한 판에 얻는 아이템이 6개로 고정된다.** [시너지 판단](synergy-needs-more-items.md)이 빌드가 갈린다고 본 5개와 7개 사이다.
- 한 줄은 가지형의 부분집합이다. 특수 방이 생기면 줄기 옆에 막다른 칸을 붙이면 되어 되돌리는 비용이 작다.
- 방 수 8 은 `RoomLayoutGenerator.RoomCount` 한 곳에만 있다. `RoomLayout` 은 마지막 방을 `Count - 1` 로 구해 테스트가 방 2개, 4개짜리 그림을 쓸 수 있다.

## 결과

### 전수 조사

시작 칸에서 7걸음을 걷는 모든 갈래를 파이썬으로 셌다.

| 붙은 두 방 | 격자 (시작 칸에서 한쪽 칸 수) | 끝까지 걸은 경우 | 막힌 갈래 |
|---|---|---|---|
| **허용 (선택)** | **제한 없음 (선택)** | **2,172** | **0** |
| 허용 | 2 (5×5) | 296 | 8 |
| 허용 | 3 (7×7) 이상 | 1,048 | 0 |
| 막음 | 제한 없음 | 940 | 0 |
| 막음 | 2 (5×5) | 24 | 16 |
| 막음 | 3 (7×7) | 176 | 48 |
| 막음 | 4 (9×9) 이상 | 632 | 0 |

**막힘은 격자 가장자리에서만 나온다.** 무한 격자에서 스스로 갇히는 가장 짧은 걷기는 7걸음을 걸은 뒤에 막히고,
방 8개는 7걸음에서 끝나 막힐 차례가 오지 않는다. 좌표 목록만 쓰면 격자가 없어 이 표의 '제한 없음' 줄이 된다.
무작위로 고를 때의 실패율도 표본 20,000 판으로 쟀다. 붙음을 막고 7×7 이면 한 번 걸을 때 27% 가 막히고, 9×9 부터 0 이다.
끝까지 걸은 경우의 수는 회전과 뒤집기를 따로 센 값이다.

### 코드와 테스트

| 파일 | 줄 (빈 줄과 주석 제외) | 작성 |
|---|---|---|
| `RoomLayout` | 30 | 골격은 Claude, 빈칸은 사용자가 한 줄(목록 복사)을 채우고 나머지는 요청을 받아 Claude 가 설명하며 채움 |
| `RoomLayoutGenerator` | 29 | 골격은 Claude, 빈칸은 사용자가 두 줄(난수, 시작 칸)을 채우고 나머지는 요청을 받아 Claude 가 설명하며 채움 |
| `RoomCell`, `RoomType`, `DoorSide` | 51 | Claude |

EditMode 테스트가 28개 늘어 111개다(`RoomCellTests` 6, `RoomLayoutTests` 13, `RoomLayoutGeneratorTests` 9).
**재생성 코드와 막혔을 때를 처리하는 줄이 없다.** 후보가 비면 빈 목록에서 꺼내다 예외가 나 바로 드러난다.

### 테스트가 겨냥한 틀린 답

- **`Next` 의 위쪽 경계를 좁히기.** `Next(0, Count - 1)` 은 마지막 후보를 한 번도 뽑지 않는데, 배치는 겹치지 않고 붙어 있어 다른 검사를 모두 통과한다.
  첫 걸음은 후보가 늘 네 방향이라 '첫 걸음은 네 방향이 모두 나온다' 가 잡는다.
- **지금 칸을 목록의 첫 원소로 잡기.** 시작 방 둘레에만 붙이다 다섯째 방에서 후보가 없어 멈춘다.
- **순번 차이만 보기.** 빈 칸의 순번 -1 과 시작 방 0 도 차이가 1 이라 빈 칸과 시작 방 사이에 문이 생긴다. `HasDoor` 는 양쪽에 방이 있는지 먼저 본다.
- **보스를 시작보다 먼저 보기.** 방이 하나면 0번이 곧 마지막이라 시작 방이 보스가 된다.

### 작은 판단들

- `RoomCell` 은 `List.IndexOf` 와 `Contains` 가 쓰는 같음 비교를 `IEquatable` 로 구현했다. 구조체의 기본 `Equals` 는 리플렉션과 박싱을 쓴다.
- 생성자는 `IEnumerable` 로 받게 썼다가 `IReadOnlyList` 로 바꿨다. 넘기는 쪽이 늘 `List` 라 넓게 받아 얻는 것이 없고, 프로젝트에 이미 있는 타입이다.
- 북쪽은 y+1 이다. 월드 좌표와 방향이 같아 4-B 에서 칸 좌표에 방 크기를 곱하면 위치가 된다. 가방 격자(UI)와는 반대다.
- 방 종류 열거형은 `None` 이 첫 값이다. C# 은 새 배열과 필드를 0 으로 채운다.

## 한계 / 남은 문제

- **판마다 달라지는 것이 방 순서와 꺾이는 방향뿐이다.** 미니맵이 없으면 격자 모양은 플레이어에게 거의 보이지 않는다.
  **BFS 는 방 안 장애물로 옮기는 것을 4-B 후보로 뒀다.** 넓은 방에 장애물을 무작위로 놓고 문에서 문까지 길이 막히지 않았는지 BFS 로 확인하는 것이다.
  이것은 실제로 실패할 수 있는 검증이고, [맵 구조 결정](map-structure.md)이 걱정한 '도형으로 채운 넓은 공간은 회색 벌판' 도 함께 푼다.
  명세에 없던 기능이라 4-B 에서 방을 놓아 보고 판단한다.
- **플레이어가 길을 고르지 않는다.** 방을 건너뛰거나 위험과 보상을 저울질하는 선택이 없다. 선택은 가방 배치가 맡는다.
- **'막히지 않는다' 의 증명은 파이썬에 있다.** C# 테스트는 시드 1,000개 표본이다. 두 코드가 같은 규칙인지는 사람이 맞춘다.
  방 수를 9 이상으로 늘리면 갇힐 수 있어(7걸음 뒤 갇힘) 이 결정을 다시 봐야 한다.
- **`System.Random` 의 수열이 시드마다 같다는 것은 같은 런타임 안에서만 보장된다.** 시드를 저장해 다른 버전에서 다시 쓰는 기능은 만들지 않는다.
- **칸 찾기가 목록을 처음부터 훑는다.** 방 8개라 비용이 없다. 방이 수백 개가 되면 좌표에서 순번을 찾는 사전을 둔다.
- **방은 한 크기다.** 2×2 나 L자 방은 좌표 하나가 방 하나라는 전제를 깬다.
- **명세를 쓰는 중에 예측이 두 번 틀렸다.** 가지형의 BFS 검증이 의미 있다고 봤고, 한 줄 걷기의 재생성이 의미 있다고 봤다.
  둘 다 '늘 통과하는 검사' 였고, 둘째는 모든 갈래를 세어 보고서야 알았다.
